## Context

智谱 GLM-4.6V-Flash 是一个 9B 参数的多模态模型，免费使用，原生支持中文，OpenAI-compatible API 格式。用户将 JD 截图上传后，通过该模型提取结构化字段，经用户确认后存入 JD 库。

API 配置：
- Endpoint: `https://open.bigmodel.cn/api/paas/v4/chat/completions`
- Model ID: `glm-4.6v-flash`
- 调用方式: base64 图片 + system prompt 指示提取字段

## Goals / Non-Goals

**Goals:**
- 支持拖拽、粘贴、点击三种上传方式
- 批量上传（1-10张），并行处理，独立状态跟踪
- 结构化提取：公司名、职位名、地点、薪资范围、技能要求、JD 正文
- 逐张确认：可编辑提取字段，标记缺失项
- 确认后写入 JD 库（`jds` 表）
- 非 JD 图片检测

**Non-Goals:**
- 不实现流式输出（OCR JSON 提取不适合 streaming UI）
- 不支持 PDF 上传（仅图片格式：PNG、JPG、WebP）
- 不在 OCR 阶段做 JD 评分（评估是独立流程）
- 不保存原始图片（仅保存 OCR 提取文本，减少存储压力）

## Decisions

### D1: 图片上传方式

三种上传方式并存：
1. **拖拽**: 拖入图片到上传区域
2. **粘贴**: Ctrl+V 粘贴剪贴板中的截图
3. **点击**: 点击上传区域打开文件选择器

**理由**: 覆盖用户的三种主要截图场景——App 截图后文件传输、桌面截图直接粘贴、传统文件选择。

### D2: 批量处理架构

```
用户选择图片 → 预览队列（可拖拽排序、删除）
           → 点击"开始识别"
           → 并行调用 OCR API（每张独立请求）
           → 每张完成时更新状态（✅/❌）
           → 全部完成后进入逐张确认流程
```

- 并行度无限制（智谱免费 API 无并发限制）
- 每张图片最多重试 1 次（失败 → 重试 → 标记❌）
- 总超时: 单张 30s

**理由**: 并行处理最大化吞吐，独立请求隔离故障（一张失败不影响其他）。

### D3: OCR Prompt 设计

System prompt 要求模型返回结构化 JSON：

```json
{
  "company": "公司名",
  "role": "职位名",
  "location": "工作地点",
  "salary": "薪资范围",
  "skills": ["技能1", "技能2"],
  "body": "JD 正文全文"
}
```

- 无法识别的字段填 `"【缺失】"`（中文占位符，前端据此显示警告）
- 非 JD 图片（无公司和职位信息）→ 返回 `{ "isJD": false, "reason": "..." }`

**理由**: 使用 JSON mode（`response_format: { type: "json_object" }`）确保结构化输出，`【缺失】` 作为前端判断缺失字段的信号。

### D4: 逐张确认流程

```
┌──────────────────────────────────────────────┐
│  队列概览                                     │
│  ┌─────┐ ┌─────┐ ┌─────┐                    │
│  │ ✅  │ │ ✅  │ │ ❌  │   ← 状态图标         │
│  │Img1 │ │Img2 │ │Img3 │                    │
│  └─────┘ └─────┘ └─────┘                    │
│                                              │
│  ⬆ 当前确认：Img1                             │
│  ┌──────────────────────────────┐            │
│  │ 公司: [___阿里巴巴___]        │  ← 可编辑   │
│  │ 职位: [___前端工程师___]      │            │
│  │ 地点: [___杭州___]            │            │
│  │ 薪资: [___30-50K___]         │            │
│  │ 技能: [React, TypeScript...] │            │
│  │ ⚠️ 以下字段缺失，请补充：     │  ← 黄色警告  │
│  │ 正文: [___请补充 JD 正文___]  │            │
│  └──────────────────────────────┘            │
│  [跳过]  [保存到 JD 库]                       │
└──────────────────────────────────────────────┘
```

- 成功识别的图片可逐张编辑确认
- 失败的图片显示错误原因，可单独重试
- 用户可跳过某张（不入库）
- 确认保存后写入 `jds` 表（`sourceType: "ocr"`）

**理由**: 人工确认是 OCR 质量的关键保障，尤其是国内 JD 排版差异大，OCR 可能误识别。

### D5: 评估页 Tab 结构

评估页（`/evaluate`）改为三个输入模式 Tab：

| Tab | 图标 | 用途 |
|-----|------|------|
| 粘贴文本 | `FileText` | 手动粘贴 JD 文本 |
| 截图识别 | `Image` | OCR 图片上传 |
| 链接（可选） | `Link` | URL 来源记录 |

**理由**: 保持评估页作为统一入口，三种输入模式切换自然。

### D6: API 安全

- 图片 base64 大小限制：10MB（`MAX_IMAGE_SIZE`）
- 仅接受 image/png、image/jpeg、image/webp
- 服务端验证 `ZHIPU_API_KEY` 环境变量

**理由**: 防止恶意大文件攻击，确保 API Key 在服务端不泄露。

## Risks / Trade-offs

- **OCR 识别质量依赖模型能力**：GLM-4.6V-Flash 对中文 JD 截图效果待实测验证
- **批量上传 10 张图片，base64 体积可能较大**：单张 5MB → 总 50MB 内存占用，浏览器端可能卡顿；建议限制单张 5MB
- **免费 API 可能有速率限制**：智谱免费模型可能限频，并行 10 张可能触发限流，需加错误处理
- **非 JD 图片检测不完美**：模型可能误判（如把招聘海报当 JD）；人工确认环节承担最终判断
