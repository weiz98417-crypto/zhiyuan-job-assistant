## Context

V1.5 是四版迭代蓝图的第一轮升级，目标是让每个现有页面都有 AI 能力。当前 AI 只存在于 explore 页面的聊天 + summarize，其余页面全手动。升级版前端在 `E:\求职项目\求职助手升级版\frontend\`，基于 Next.js 16 + Tailwind CSS 4 + Framer Motion + Dexie.js（IndexedDB），后端 API 使用 Next.js Route Handlers，LLM 为 DeepSeek。

现有 API 路由 12 个，其中 5 个已使用 AI（chat/stream, chat/summarize, cv/analyze, evaluate, interview/questions）。V1.5 新增/改造约 10 个路由，全部使用 DeepSeek + streaming。

## Goals / Non-Goals

**Goals:**
- 四个核心工作流（看JD→改简历→备面试→看数据）全部接入 AI
- 用户感知到 AI 在"帮他做事"而非只能"问 AI 问题"
- 流式输出用于所有生成长内容场景（评估报告、简历优化）
- 复用现有组件体系（HandwritingTitle, WarmButton, PaperCard, ScoreBadge）

**Non-Goals:**
- 不做 Agent 自主运作（那是 V2.0）
- 不做语音面试（那是 V2.5）
- 不做浏览器插件/微信集成（那是 V3.0）
- 不改动数据存储层（继续用 IndexedDB + localStorage）
- 不做外部数据爬取（所有 JD 由用户主动喂入）

## Decisions

### Decision 1: 流式输出统一架构

所有生成长内容的 API 统一使用 SSE streaming，复用现有 `chat/stream` 的 pattern：

```
POST /api/evaluate/jd → SSE stream → 分段 JSON { type: "section", key: "summary", content: "..." }
```

**Why**: 用户不想等 15 秒看完整体报告。流式输出首字节 < 2 秒，体验更好。前端用已有的 streaming 处理逻辑。

### Decision 2: 雷达图实现

五维雷达图使用 SVG 手绘实现，不引入 chart 库。

```
技能匹配 ─── 经验匹配
     \         /
       \     /
        中心点
       /     \
     /         \
风险指数 ─── 成长空间
     薪资匹配
```

**Why**: 零依赖（不用 chart.js / recharts），体积小，风格可控（手帐温暖风格 ≠ 冰冷的图表库默认样式），约 80 行 SVG path 代码。

**Alternatives considered**: recharts（引入 400KB+ 依赖，样式与手帐风格冲突），canvas（可访问性差）

### Decision 3: 回答教练的六种模式

面试回答教练提供六种模式，覆盖国内全场景。用户输入经历 + 选择面试模式 → AI 按对应结构输出。非流式，一次生成。

```
模式1 项目复盘 —— 互联网大厂/科技公司
  背景→角色→难点→思考→方案→结果→反思→数据

模式2 行为问答 —— 外企/咨询
  Situation→Task→Action→Result→Reflection

模式3 情景应对 —— 大厂交叉面/群面/管培
  理解→拆解→方案→风险→反问

模式4 结构化面试 —— 中小企业(50-500人)
  为什么来→做过什么→怎么做的→结果→能带来什么

模式5 创始人对话 —— 初创/微型(<50人)
  理解业务→能立刻上手什么→薪资期望→接受创业节奏

模式6 稳重应答 —— 国企/央企/银行
  学历背景→政治觉悟→服从意识→长期规划→家庭情况
```

**Why**: 国内面试不是一套 STAR 通吃的。大厂看重项目复盘和数据思维，外企遵循标准 STAR，国企完全不看框架看"味道"，中小企业 HR 懂业务会追细节，初创老板关注即战力。单一 STAR 模板只覆盖 15% 场景。

交互方式：左侧输入经历 + 顶部模式选择器（六选一）+ 右侧 AI 输出。追问列表帮助用户提前准备。

### Decision 4: AI 周报的触发方式

手动的"生成周报"按钮 + 每周自动提醒（基于 localStorage 记录上次生成时间）。

**Why**: V1.5 不做后台任务/定时触发（无服务端），完全在客户端触发。后续 V2.0 可升级为 Agent 自动推送。

### Decision 5: 首页改造的范围

首页"今日手帳"增加一个 AI 摘要卡片，聚合：投递统计、最近评估、跟进行动项、Pipeline 健康灯。点击卡片跳转到对应详情页。

**Why**: 首页是用户每天早上打开看到的第一个东西。AI 摘要让它从"空壳"变成"仪表盘"。改动控制在 1 个组件，不破坏现有首页结构。

### Decision 6: 面试出题的架构

三层出题策略：
1. **JD 解析层**：从目标 JD 提取关键要求 → 生成技术/专业类题目
2. **Profile 匹配层**：对比用户简历与 JD 差距 → 生成弱项针对性题目
3. **通用层**：行为面试和文化匹配题（复用 + AI 增强现有 hardcode 题库）

**Why**: 前两层确保个性化，第三层做兜底。每个 JD 生成 8-12 道题，分四类标签。

### Decision 7: JD 行话解读的实现

用 LLM prompt engineering，在评估报告中增加 "⚠️ 注意信号" 段落：

```
System prompt: 你是资深 HR，能识别 JD 中的隐含信息。
识别以下表述的真实含义：
- "快速迭代" / "敏捷开发" → 可能加班频繁
- "扁平化管理" → 晋升路径不清晰
- "抗压能力强" → 工作强度大
- "独角兽潜力" → 公司风险较高，期权不确定
- "薪资open" / "面议" → 预算不透明
- "要有创业精神" → 可能需要身兼多职
- "结果导向" → KPI 压力大
```

**Why**: 这是中国求职市场的刚需——JD 行话已经形成了一套"密码体系"，求职者需要翻译。

### Decision 8: 模块实施顺序

按 VISION.md 优先级：**JD 评估 → 简历优化 → 面试教练 → AI 洞察**。

**Why**: 
1. JD 评估是入口（用户每天看 JD）
2. 简历紧跟其后（看完 JD 就改简历）
3. 面试备在投递之后
4. 数据分析是长期积累后才有的价值

## Risks / Trade-offs

| 风险 | 缓解 |
|------|------|
| LLM 评估质量不稳定（同一 JD 两次评估结果差异大） | 结构化 prompt + JSON schema 约束输出格式；结果可手动标记"不准确" |
| 流式 API 超时（长 JD 评估超过 60s） | 前端 60s 超时 + 重试按钮；优化 prompt 减少 token |
| 简历数据隐私（用户简历发到 DeepSeek API） | 已有隐私提示；后续 V2.0 做 PII 脱敏 |
| 四个模块同时开发工作量大 | 严格按顺序推进，做完一个验收一个再开始下一个 |
| 首页改动影响其他页面 | 新增组件插在首页末尾，不修改现有首页结构 |
