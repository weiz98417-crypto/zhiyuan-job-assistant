# Agent 稳定性调查（2026-09-23）

## 已确认的事实

- 当前线上版本为 0.10.6，Web 与 Worker 进程在线。DeepSeek API 实测：`deepseek-v4.1-flash` 返回 HTTP 400，错误列出的可用模型为 `deepseek-flash` 与 `deepseek-v4-pro`；`deepseek-flash` 的文本和图片请求均返回 HTTP 200。线上 Agent 主循环、图片识别和简历分析入口实际使用 `deepseek-flash`；无效模型名只在未被引用的旧 `zhipu.ts` 中残留。本地工作区多个入口却使用无效模型名，说明不能用本地配置推断线上故障。此前将线上截图失败归因于 `deepseek-v4.1-flash` 是错误判断，不能作为本次线上故障的根因。
- Agent 对话中的简历截图使用图片识别入口。当前任务分类只有简历查询与简历修改，没有独立的简历评估任务。另一个简历分析 API 要求 JD 或关键词，不能单独评估一份简历。
- 最近 24 小时的线上 Agent Run 记录只有一项 JD 评估，没有新建简历评估 Run。因此用户这次简历评估的失败点仍需依据具体请求时序复现，不能仅凭 Run 表断定唯一原因。
- 一次线上 JD Run 的契约约 2.15 MB，其中 `routing.jdSource.images` 约 2.15 MB；其输入还重复保存完整契约。Nginx 记录到同一段时间多个创建请求，其响应体约 1.27–5.15 MB。这是请求确认延迟和重复提交的明确风险，但尚未通过端到端计时证明它就是某次“消息未确认送达”的唯一原因。
- 本地仓库与当前线上 release 的干净源码不同：`run-admission.ts`、`task-contract.ts`、`task-routing.ts`、`durable-agent-run.ts` 的 SHA-256 均不同，线上还存在本地没有的 `submit-conversation-turn.ts`。选择性上传本地文件无法保证构建的是同一套功能，必须先确定单一可复现的源码基线。
- 本地简历截图链路存在确定断点：浏览器完成图片识别，但创建持久 Run 时只提交原始文字和图片，没有提交识别结果；服务端执行循环又从模型请求中剥除图片。简历截图被路由为 `resume_query`，其提示词指向已保存的“我的简历”，无法保证分析当前截图；客户端回退则停在“预览并确认保存”。这些是本地代码事实，不等于已证实的线上单次失败原因。
- 本地拟发布 `0.10.7` 的版本号和模型配置仍未提交，Git HEAD 没有对应版本标签。发布脚本不校验 Git SHA 或源码清单，当前本地工作树不能直接当作线上基线。
- Worker 历史日志出现过同一 PostgreSQL client 并发查询警告；代码中存在相应调用位置。尚无请求级证据证明该警告直接造成了用户看到的连接错误。
- 本地的契约未满足路径会用“落库校验”技术文案替换用户答复、保存到对话，再抛出失败；Recovery Supervisor 对这类失败最多重规划两次。初次加两次恢复可重复呈现三次文案，但尚未拿到用户那次 Run 的事件序列，不能断言线上重复必然出自这条路径。
- 本地存在跨对话状态竞态：旧对话的创建请求晚返回时，可以不核对当前对话就写入全局任务提示；新对话渲染提示也未按所属对话过滤。前端按新对话查询活动 Run 的正确逻辑不能阻止这条迟到响应覆盖状态。
- 本地创建 Run 的客户端设有 15 秒确认超时、两次提交与按 request ID 查找；线上一次 JD 创建响应达到 1.27–5.15 MB。体积和超时共同提高“消息未确认送达”的风险，但需要请求级计时才能确认某次事故。

## 已确认的产品规则

- 切换到新对话不取消旧 Agent Run；新对话只展示自己的任务状态，返回旧对话时恢复旧任务进度。
- JD 默认匹配用户简历。用户要求不匹配时，该限制绑定这份 JD，覆盖重做分析和后续追问；新 JD 恢复默认匹配。
- Agent 对话中仅有简历截图、没有 JD 时，也要提供只读简历诊断：内容、结构、ATS 可读性、证据缺口和具体建议。有 JD 才增加岗位匹配；截图识别失败时允许粘贴文字继续，不自动修改简历。
- Agent 回答与图片识别统一使用有效的 `deepseek-flash`。契约校验和恢复原因属于内部诊断，不应原样或重复出现在对话里；可恢复失败要让用户在原对话继续。

## 待确认
