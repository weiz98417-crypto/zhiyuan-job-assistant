# Spec 09: Memory Admission And Candidate Lifecycle

**Target label:** `ready-for-agent`
**Depends on:** Spec 08, the explicit-intent decision of Spec 01, verified facts from Spec 03, ADR-0032, and ADR-0034

## Problem Statement

求职者在闲聊、面试回答或引用材料时常会提到个人经历和偏好。这些内容若直接进入活跃记忆，系统可能把叙述当成当前意愿，把模型推断当成用户确认，或让敏感内容进入长期存储。现有两段式事实决策已有基础实现，但它还不能独自证明候选准入、用户确认、候选期限及关闭发现开关的全链路行为。

## Solution

建立统一的记忆写入准入 seam。系统先判断来源、授权、敏感性和证据，再决定即时写入活跃事实、生成个人记忆候选、请求确认或拒绝。闲聊候选在用户确认前不参与个性化；明确的当前求职偏好和已读回的任务结果分别走受约束的即时路径。候选有期限，用户可关闭自动发现并清除尚未确认的闲聊候选。

## User Stories

1. 作为求职者，我希望闲聊里提到的个人事实先成为待确认候选，从而由我决定它是否长期影响建议。
2. 作为求职者，我希望说“请记住”时看到系统拟保存的确切内容，从而能当场确认或拒绝。
3. 作为求职者，我希望直接表达的当前求职偏好及时生效，从而下一次岗位发现按我现在的意愿执行。
4. 作为求职者，我希望过去说过的话、面试回答和被引用的岗位描述不被误认成当前偏好，从而避免错误筛选。
5. 作为求职者，我希望薪资底线、工作许可或健康限制只在我主动说明并确认用途后保存，从而控制敏感信息的使用。
6. 作为求职者，我希望密码、密钥和证件号码不会进入长期记忆，从而避免私人凭据被再次调用。
7. 作为求职者，我希望未处理的闲聊候选在 30 天后自动清除，从而不积累不想保存的个人信息。
8. 作为求职者，我希望关闭自动发现后，已有未确认的闲聊候选立即清除，而已经确认的事实保持可单独管理。
9. 作为求职者，我希望一次忽略岗位不会变成明确偏好或公司黑名单，从而继续看到其他合适机会。
10. 作为求职者，我希望纠正旧记忆后，旧事实停止生效且新事实注明来源，从而后续回答使用正确版本。
11. 作为评测人员，我希望每条写入或拒绝都能解释来源、证据与确认状态，从而识别误写和遗漏。
12. 作为实现 Agent，我希望对话、任务结果和会话观察经同一准入规则处理，从而不会出现绕过用户确认的旁路。

## Implementation Decisions

- 写入准入接收来源类型、用户归属、当前操作意图、证据引用、分区、敏感性和候选内容；由服务端决定活跃事实、个人记忆候选、待确认或拒绝。页面和模型均不能单独将候选提升为活跃事实。
- 仅用户当前明确表达的求职偏好可按 ADR-0032 即时成为活跃偏好，并记录其来源和时间。叙述、引语、假设、简历或 JD 原文、面试回答、旧偏好及引导问卷中的模型推断均不能借此生效；有歧义先澄清。
- 敏感的求职限制须由用户主动告知并确认用于求职，才可写入私人记忆分区。密码、API 密钥和证件号码不得进入长期记忆或个人记忆候选。
- 已读回验证的 Task Program 完成事实可携带 Artifact 与结果证据即时写入；仅有工具成功响应、模型结论或页面显示不满足该门禁。
- 普通闲聊和会话观察只产生个人记忆候选。直接“请记住”请求先呈现拟保存事实并要求当场确认；确认之前不得供检索、推荐、Run Context 或 Task Program 使用。
- 候选记录须区分个人闲聊候选、用户主动请求和团队共享审核材料，并保留来源、创建时间、到期时间与状态。个人闲聊候选 30 天未确认即自动清除；团队共享审核队列不套用该期限。
- “自动发现记忆候选”默认开启，并在首次使用时说明。关闭后停止从闲聊自动提取，并立即清除尚未确认的闲聊候选；不清除已生效事实，用户仍可单次请求“请记住”。
- 在准入通过后，写入管线执行“提取候选、与相似现存事实比较”两段式决策，记录 ADD、UPDATE、DELETE 或 NOOP 及理由。此处 DELETE 仅使旧事实失效，不是 ADR-0033 的记忆清除；记忆纠正以有来源的新事实使旧事实失效。
- 行为反馈只可作为低权重、短期排序信号；重复且一致时才能提出待确认偏好。一次忽略或点击不得自动建立公司黑名单，也不能覆盖当前明确偏好。
- 写入准入应尊重记忆清除的来源抑制记录，避免保留的原始材料在后续提取中重新生成已清除的记忆；解除抑制须有用户后续明确的重新记住请求。

## Testing Decisions

- 在统一记忆写入 seam 用同一组来源与确认状态 fixture 验证活跃事实、个人记忆候选、拒绝和澄清结果；断言后续可用性及来源，不绑定提取模型的逐字输出。
- 覆盖“我忘记了曾在某公司工作”、引语、假设、过往偏好、简历内容、JD 内容、面试回答和引导总结，断言均不能成为用户当前确认的偏好或删除授权。
- 验证明确偏好与已读回任务结果的即时写入，以及敏感限制的用途确认；密码、密钥和证件号码在候选及活跃层均不得出现。
- 验证闲聊候选在确认前不能出现在 Run Context、推荐和任务决策，确认后才可按分区权限读取。
- 使用时间推进验证 30 天候选清除、发现开关关闭后的立即清除、开关再次开启、单次“请记住”和团队共享队列不受影响。
- 覆盖重复请求、并发确认、矛盾事实、纠正、NOOP 和旧事实失效，断言一条开放事实及可追溯来源，不将管线 DELETE 误报为记忆清除。
- 复用现有记忆事实账本和记忆上下文测试形态，并在真实持久化边界验证候选状态与读回一致。

## Out of Scope

- 不在本 spec 中实现用户记忆管理页面或管理员审核界面。
- 不在本 spec 中实现跨存储定向记忆清除、备份重放或原始业务记录删除。
- 不在本 spec 中改变混合检索的召回、排序或结构化画像读取策略。
- 不把全部会话观察或所有业务事件自动写成长期事实。

## Further Notes

- 本 spec 消费 Spec 01 的操作意图与 Spec 03 的 verified facts；不重新定义 Run Admission 或 Program 成功条件。
- 用户对活跃事实的记忆纠正与针对内容的记忆清除是两种不同操作；前者在本 spec 提供事实变更语义，后者遵守 ADR-0033 的独立清除流程。
- 当前部分事实决策和候选控制已有基础实现，但完整准入、期限和用户授权行为仍须按本 spec 验收。
