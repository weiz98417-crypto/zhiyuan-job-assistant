# Spec 29: Outcome Feedback Loop

**Target label:** `ready-for-agent`  
**Depends on:** Spec 26 的可信复盘数据（硬前置）、Spec 08–09 的账本与准入管线、ADR-0034 治理框架；批次归属 0.18.0 · 飞轮车（k-outcome-feedback-loop）

## Problem Statement

投递追踪记录了状态（投递→笔试→面试→offer/拒），但结果不回流：失败复盘只是把用户转介给 interview agent（`application-workflow.ts:283`）；`team-insights.ts:326` 只有一句提示文案「建议沉淀为题库」；推荐偏好分 prefFit 恒 50（`recommend.ts:127-132`，注释自认「Cannot determine from report alone」）；拒信无人解析；复盘产物无沉淀管道；story-bank 是 26 行空模板。整个私有数据飞轮的最后一段断裂——参考库/模式晋升/记忆账本的管道都在空转，产品「用得越久越准」的留存逻辑不成立。

## Solution

投递状态变更作为确定性完成事件即时写记忆账本；拒信粘贴解析为封闭原因标签、用户确认后入账；Spec 26 复盘的有效证据沉淀为经历故事册；prefFit 用真实投递反馈替换写死的 50。

## User Stories

1. 作为求职者，我希望更新投递状态后，教练与推荐逐渐知道我的真实行情，从而越用越准。
2. 作为求职者，我希望粘贴拒信后得到结构化原因标签，且我确认之后才会记录。
3. 作为求职者，我希望复盘里的好故事沉淀进故事册，下次面试直接调用。
4. 作为用户，我希望未经我确认的解析结果绝不进入我的记忆——这一点被测试断言固定。
5. 作为实现 Agent，我希望投递状态变更是记忆账本的一个确定性写入方，与 JD 评估完成事件同款，从而不新增旁路。

## Implementation Decisions

- **事件即时写**：application-workflow 状态迁移作为确定性完成事件写记忆账本（复用 M5 管线，来源=application_event，置信权重沿 `profile-skill-quality.ts:41-51` 的来源分级）。写入触发点在状态迁移的服务端 API 层（沿 `jd-evaluation-persistence.ts:116-125` 的 verified_task 事件同款），不经前端。事件事实与候选事实分层：投递结局是客观事件，即事实、不需确认；由此推导的偏好属于推断，仍走候选确认。
- **拒信解析**：用户粘贴文本 → LLM 提取封闭标签集（简历不匹配/已招满/薪资不匹配/流程无回应/其他+自由文本）+ 引用原文片段；标签经用户确认才入账（ADR-0034 治理）；无引用沿 Spec 26 veto 纪律作废。不做邮箱集成（2026-10B Q13）。
- **经历故事册**：Spec 26 复盘的「有效证据」字段 → 故事册候选（经历故事×适用问题类型×强度），用户确认入库；story-bank 模板启用为 Spec 25 注册表条目；面试教练出题后可提示「故事册中 N 条相关故事」。
- **prefFit 真实化**：`recommend.ts` 的 prefFit 从恒 50 改为真实信号——用户「进入面试」及以后的岗位特征（城市/岗位族/薪资段）加权偏好匹配；样本 <5 时保持 50 且 UI 标注「数据不足」。
- **不新增旁路**：所有写入走既有记忆写入管线；无人值守 Run 与 Run Gate 语义不变。

## Testing Decisions

- 事件入账：状态迁移产生账本事实的断言；幂等（同状态重复迁移不重复写）。
- 拒信：封闭标签解析正反例；未确认不入账断言；无引用作废断言。
- 故事册：候选→确认→入库→面试教练可见的完整链路；未确认候选不出现在提示里。
- prefFit：样本 <5 恒 50 + 「数据不足」标注；≥5 样本时权重方向正确（进入面试的岗位特征加分）。
- 记忆治理：事件事实与趋势事实可纠正/清除（沿 Spec 11/12 既有测试形状）。

## Out of Scope

- 邮箱集成（IMAP 授权）；拒信自动抓取；team-insights 团队共享层聚合深化；投递自动化的任何形式。

## Further Notes

- 依赖 Spec 26 是硬前置：分数不可信时回流会放大污染（2026-10B 依赖链）。
- 「事件即事实、推断走确认」的分层沿记忆分区与 ADR-0034 词表，不发明新机制。
