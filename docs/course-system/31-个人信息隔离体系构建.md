# 31 个人信息隔离体系构建

Zhiyuan 的核心资产都和个人求职有关：简历、JD 报告、Offer 薪资、面试回答、职业画像、长期记忆、Agent run 证据。个人信息隔离体系的目标是让每个用户只看到自己的材料，Agent 也只能在当前用户范围内工作。

本阶段完成的是 owner 边界设计：所有核心业务对象都必须从当前登录态派生 userId，再进入 API、repository、PostgreSQL + pgvector 和 read-back。

## 隔离原则

| 原则 | 含义 |
|---|---|
| 服务端派生 userId | 业务 API 不信任请求体里的 userId |
| 业务 ID 不单独授权 | reportId、offerId、proposalId、sessionId 必须和当前 userId 一起校验 |
| 默认私有 | 简历、Offer、面试、画像、私有记忆不默认共享 |
| 共享需治理 | 团队知识、参考材料、eval 候选必须经过 Admin 审核和脱敏 |
| 写入后同范围读回 | 用同一个 userId read-back，证明没有写错对象 |

## 保护对象清单

| 对象 | 页面 | owner 规则 | 验收方式 |
|---|---|---|---|
| 简历 | CV | 每个用户拥有自己的 `cv_data` | memberA/memberB 内容不同且互不可读 |
| 简历提案 | CV | proposal 归属当前用户 | apply/discard/rollback 均需 owner 校验 |
| JD | Evaluate | 用户保存的 JD 属于当前用户 | 当前用户可读回 |
| JD 报告 | Reports | report 与 JD 同用户范围 | reportNum 不能跨用户读取 |
| Offer | Compare | Offer 和 offer report 默认私有 | offerId + userId 校验 |
| 面试 session | Interview | session 归属当前用户 | 继续面试只恢复自己的状态 |
| 职业画像 | Profile | profile/signals 归属当前用户 | 来源、可见性、撤回路径可见 |
| 私有记忆 | Profile / Agent | owner 为当前用户 | 检索时带 owner 和 visibility |
| 团队记忆 | Admin | 审核后进入 team 范围 | 不包含用户私密原文 |
| Agent run | Admin / Run 证据 | 关联 owner 或脱敏摘要 | Admin 看到必要证据而非完整隐私 |

## 隔离链路

```text
auth_token
  -> getCurrentUser()
  -> userId
  -> API route
  -> repository(userId, objectId)
  -> SQL WHERE user_id = ...
  -> write/read transaction
  -> read-back
  -> 页面或 Agent 只展示当前用户对象
```

这条链路是产品信任的基础。用户问“我的简历是什么”，系统必须只返回当前用户的简历；用户说“继续刚才的面试”，系统必须只恢复当前用户的面试 session。

## Agent 隔离

Agent 系统必须遵守同样的 owner 规则。

| 场景 | 隔离要求 |
|---|---|
| `resume` 查询简历 | 只读取当前用户 CV |
| `evaluate` 读取历史报告 | 只读取当前用户 report |
| `offer` 分析 Offer | 只绑定当前用户 offer |
| `interview` 继续面试 | 只恢复当前用户 interview state |
| `profile` 写画像 | 只写当前用户 profile signal |
| `general` 导航 | 不能用通用权限读取私有对象 |

用户在提示词里写“读取另一个用户的简历”不会改变权限。工具层必须拒绝或澄清，不能把用户文本当授权。

## Admin 展示边界

Admin 需要治理能力，但治理不等于无限查看。

| Admin 场景 | 展示方式 |
|---|---|
| 用户审批 | 展示账号、状态、角色、注册时间等必要信息 |
| 记忆审核 | 展示候选摘要、来源类型、可见性、敏感标记 |
| Agent run 复查 | summary-first，隐藏或脱敏高敏原文 |
| 团队知识候选 | 审核后才能进入 team 可见 |
| 参考简历 | 必须有脱敏和可见性标记 |

Admin 的设计目标是让产品可治理，不是让所有私密求职材料变成后台可随意浏览的数据。

## PostgreSQL 与 pgvector

当前运行事实源是 PostgreSQL + pgvector：

- PostgreSQL 承载用户、简历、JD、报告、Offer、面试、画像、记忆和运行证据。
- pgvector 承载记忆和参考材料的向量检索。
- SQLite 只保留 fallback/archive/migration 角色。

隔离验收必须基于当前 runtime，不把 SQLite 迁移源当成交付证据。

## 完成状态

个人信息隔离体系完成后，应满足：

1. 所有核心对象都有 owner 规则。
2. 所有核心读取都按当前 userId 限定。
3. 所有核心写入都按当前 userId 读回。
4. Agent 工具不能被用户提示词诱导跨 owner。
5. Admin 展示遵循最小必要和脱敏原则。
6. 团队知识和参考材料有审核链路。

这为 32 的登录安全体系提供数据边界基础。

## 跨用户隔离样例

| 对照项 | memberA 数据 | memberB 数据 | 验收点 |
|---|---|---|---|
| 简历个人概述 | “5 年海外社交产品经验” | “3 年 B2B SaaS 增长经验” | B 不能读到 A 的概述 |
| JD 报告 | AI 产品经理 reportNum=12 | 数据产品经理 reportNum=12 | reportNum 相同也要按 userId 区分 |
| Offer | 28K*14，AI 产品 | 22K*13，运营经理 | 薪资不串用户 |
| 面试 session | 当前题目：Agent 产品设计 | 当前题目：数据指标拆解 | “继续面试”恢复各自题目 |
| 私有记忆 | 偏海外社交 | 偏企业服务 | 召回只在 owner 范围内 |

这个样例很适合说明为什么业务 ID 不能单独授权：两个用户都可能有 reportNum=12，真正决定可读范围的是当前 userId。

## owner 校验流程

```text
用户请求 /api/reports/12
  -> 从 auth_token 读出 currentUserId
  -> 查询 reports where report_num = 12 and user_id = currentUserId
  -> 找不到则返回 not found 或无权限
  -> 找到后返回报告
  -> 页面展示 report
```

这个流程刻意不问客户端“你是谁”。即使请求体里带了 `userId=memberB`，服务端也只能使用 token 派生出的当前用户。

## 共享材料的治理路径

不是所有信息都永远私有。求职产品里确实会出现可复用材料，比如优秀简历结构、JD 风险判断框架、面试反馈模板。但它们要经过治理路径：

```text
private 原始材料
  -> 提取通用规则或脱敏摘要
  -> 进入 team_pending
  -> Admin 审核
  -> 状态读回
  -> team 可见
```

因此，“共享”不是把用户原文公开，而是把可复用知识从私有材料中安全提炼出来。
