# 数据体系与功能集中测试

本篇把 Agent runtime 推进到数据可验证阶段。Zhiyuan 的数据体系要支撑 Agent Chat、JD、简历、Offer、面试、自我定位、记忆和 Admin 的完整产品链路；集中测试要证明这些对象在同一个用户、同一个 runtime、同一个业务目标下被正确读写。

当前 runtime 事实：PostgreSQL + pgvector 是主运行数据源。SQLite 只作为 fallback、archive、migration，不作为当前运行成功的依据。

## 数据对象地图

| 对象 | 产品含义 | 关键关系 |
|---|---|---|
| `users` | 身份、状态、角色、token version | pending/member/admin |
| `sessions` | Agent Chat 会话和 active task | userId、agent state、interview state |
| `cv_data` / resume sections | 当前简历 | userId、section id、hash |
| `resume_edit_proposals` | 简历修改草稿 | proposal id、target section、status |
| `jds` | JD 对象 | jdId、source hash、userId |
| `reports` | JD 评估报告 | reportId/reportNum、jdId、userId |
| `offers` / `offer_reports` | Offer 与分析结果 | offerId、offerReportId、userId |
| `profiles` / signals | 自我定位和画像信号 | source、confidence、status |
| `memory_items` / chunks | 长期记忆和向量检索 | visibility、owner、pgvector |
| `agent_runs` / steps | Agent 执行证据 | taskType、tool、verifier |
| Admin 相关表 | 审批、状态和管理动作 | role、read-back |

每个对象都要明确 owner、可见性、读写入口和页面承接方式。

## Repository 原则

数据读写应通过 repository 或受控 API 完成：

- 服务端从当前 token 派生 userId。
- 客户端传入的 `user_id/ownerId/createdBy` 不作为授权依据。
- 查询必须带 userId scope，Admin 查询也要区分管理对象和私有内容。
- 写入后按同一 userId 读回。
- 向量检索要带 visibility 和 owner 条件。
- SQLite 路径只用于兼容、导入、归档或降级说明。

数据体系的目标是让产品对象可追踪，而不是让页面各自维护一份局部状态。

## 集中测试范围

集中测试覆盖五条主线：

1. runtime：PostgreSQL 连接、schema、pgvector、SQLite fallback 边界。
2. Agent：路由、task contract、工具范围、read-back/verifier。
3. 业务对象：JD、简历、Offer、面试、画像、记忆。
4. 页面：Agent、CV、Reports、Offer、Interview、Profile、Admin 的对象一致性。
5. 权限：pending/member/admin 和 userId 隔离。

集中测试不是一次性点页面，而是按产品生命周期确认“从 Agent 发起，到数据写入，再到页面可见”的完整链路。

## 功能链路断言

| 链路 | 必须证明 |
|---|---|
| Agent 评估 JD | `evaluate` agent、`jd_evaluation`、report/JD 读回、Reports 可见 |
| Agent 查询简历 | `resume_query` 不生成 proposal，不调用写入工具 |
| Agent 修改简历 | proposal -> 用户确认 -> apply -> section hash 读回 |
| Agent 评估 Offer | `offer` agent、Offer 报告读回、不进入 JD 报告链路 |
| Agent 继续面试 | sessionId、currentQuestion、材料绑定可恢复 |
| 自我定位写画像 | signal 有来源、置信度和状态 |
| 记忆写入和审批 | private/team、owner、status、pgvector 检索范围正确 |
| Admin 管理动作 | role 校验、状态读回、UI 反馈一致 |

任何写入链路只要缺 read-back/verifier，就只能标记为未验证。

## 数据一致性表

集中测试应产出一张对象一致性表：

| 对象 | Agent 侧证据 | 页面侧证据 | 数据侧证据 |
|---|---|---|---|
| JD report | 工具卡显示 reportId/reportNum | Reports 打开同一报告 | `reports` 与 `jds` 按 userId 关联 |
| CV proposal | Agent 显示 proposalId | CV 页面显示同一差异 | proposal status 与 section hash |
| Offer report | Agent 显示 offerReportId | Offer 页面读取同一结果 | `offers/offer_reports` 按 userId 关联 |
| Interview | Agent 继续当前题 | Interview 页面显示同一题 | `interview_state_json` |
| Profile | Agent 显示 signal 来源 | Profile 页面可见状态 | profile signal 可读 |
| Memory | Admin 显示审批状态 | 记忆页面状态一致 | owner、visibility、pgvector 可查 |

这张表能说明产品对象在 Agent 和页面之间没有被重新猜测。

## 测试数据准备

集中测试需要固定数据包：

- `adminA`：active/admin。
- `memberA`：active/member，拥有完整简历、JD、Offer、面试、画像和 private memory。
- `memberB`：active/member，拥有明显不同的数据。
- `pendingC`：pending/member。
- `rejectedD`：rejected/member。
- JD、Offer、简历、图片、面试材料和记忆样本。
- PostgreSQL + pgvector 环境变量。

memberA 和 memberB 的公司名、岗位、薪资、报告编号、session 标题要刻意不同，便于识别串用。

## 集中测试报告

报告要写：

- runtime 环境：PostgreSQL、pgvector、SQLite fallback。
- 覆盖的 agent、taskType、工具数量。
- 覆盖页面和 API。
- 通过、未通过、跳过、阻断数量。
- 缺少环境或数据的说明。
- read-back/verifier 证据。
- 新增 eval candidate。
- 下一阶段进入页面联动调优前的阻断项。

报告用来决定产品是否能进入页面联动阶段。未跑浏览器、未连 PostgreSQL、未准备多用户数据时，不应把结论写成通过。

## 数据对象对照表

数据体系测试要把页面、agent 和表对象对齐。

| 产品对象 | 页面 | agent | 关键数据 | 测试重点 |
|---|---|---|---|---|
| JD 报告 | Reports | `evaluate` | `jds`、`reports` | report/JD 同 userId |
| 简历提案 | CV | `resume` | `cv_data`、`resume_edit_proposals` | pending/apply/read-back |
| Offer 报告 | Compare | `offer` | `offers`、`offer_reports` | 高敏字段私有 |
| 面试状态 | Interview | `interview` | `sessions`、`interview_state_json` | 刷新后恢复 |
| 画像信号 | Profile | `profile` | `profiles`、`profile_signals` | 来源和可见性 |
| 记忆 | Profile/Admin | `profile`/Admin | `memory_items`、`memory_chunks` | private/team_pending/team |
| 运行证据 | Admin | all | `agent_runs`、steps、reviews | 摘要、verifier、owner |

集中测试时，每个对象都要回答：谁创建、存在哪里、谁能读、谁能写、如何读回。

## 集中测试报告样例

```markdown
测试批次：DATA-RUNTIME-001
runtime：PostgreSQL + pgvector
账号：adminA / memberA / memberB

通过项：
- memberA 创建 JD report 后可按 reportId 读回。
- memberB 不能读取 memberA report。
- resume_edit_proposal 创建后 status=pending。
- apply 后目标 section hash 一致。
- memory private 检索只返回当前 owner 范围。

待补证据：
- Offer 截图进入 Compare 后的 offerReportId 读回。
- Admin memory 晋升后的 team visibility 读回。

结论：
数据主链路可进入页面联动调优；缺证据项进入 27 的联动测试补证。
```

报告要把“通过”和“待补证据”分开，避免把未验证链路写成通过。
