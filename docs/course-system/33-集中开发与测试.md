# 33 集中开发与测试

29-32 定义了身份、权限、隔离和登录安全，本阶段把这些设计集中落到可运行产品中，并通过测试证明它们能支撑完整求职流程。这里的重点不是泛化工程清单，而是围绕 Zhiyuan 的真实产品边界完成开发与验收。

集中开发与测试的目标：让用户能安全进入自己的 AI 求职工作台，让 Agent 在权限范围内工作，让高价值写入有证据，让 Admin 治理有边界。

## 集中开发范围

| 范围 | 完成内容 |
|---|---|
| 登录注册 | 注册、登录、退出、当前用户读回 |
| 权限矩阵 | 未登录、pending、member、admin、rejected 的页面/API 行为 |
| 个人资产隔离 | 简历、JD、报告、Offer、面试、画像、记忆按 userId 隔离 |
| Agent 工具治理 | 48 个注册工具受 taskType、agentAllowlist、effect、确认和读回约束 |
| read-back/verifier | 保存、应用、审批、导出等动作有证据 |
| Admin 治理 | 用户审批、记忆审核、运行证据复查 |
| 隐私展示 | Admin 和 run/review 采用摘要优先、脱敏和最小展示 |
| 当前 runtime | PostgreSQL + pgvector 作为交付事实源 |

## 测试账号

| 账号 | 角色/状态 | 用途 |
|---|---|---|
| adminA | active/admin | 审批用户、查看治理页面、验证 Admin 边界 |
| memberA | active/member | 完整求职主流程 |
| memberB | active/member | 跨用户隔离对照 |
| pendingC | pending/member | 验证待审批阻断 |
| rejectedD | rejected/member | 验证不可用账号阻断 |

memberA 和 memberB 的简历、JD、Offer、面试 session、画像和记忆要刻意不同，便于判断是否串数据。

| 材料 | 用途 |
|---|---|
| JD 文本 | 验证 evaluate、Reports、后续 CV/Interview 接力 |

| Offer 文本/截图 | 验证 offer agent 和 Compare |

| 私有记忆和团队候选 | 验证 memory visibility 和 Admin 审核 |

## 验收矩阵

| 编号 | 链路 | 必须看到的证据 |
|---|---|---|
| AUTH | 注册、登录、退出、当前用户 | userId、role、status 可读回，退出后失效 |
| PERM | pending/member/admin | 页面和 API 权限一致 |
| ISO | memberA/memberB 隔离 | 简历、报告、Offer、session、memory 不串 |
| JD | Agent Chat -> evaluate -> Reports | reportId/reportNum 可读回 |
| CV | Reports -> resume proposal -> CV apply | proposal 可见，确认后 section read-back |
| OFFER | Agent Chat -> offer -> Compare | offerReportId 可读回 |
| INT | Agent Chat -> interview -> Interview | currentQuestion 和 transcript 可恢复 |
| PROF | Agent Chat -> profile -> Profile | 画像信号有来源、可见性和撤回路径 |
| TOOL | 工具治理 | taskType、agentAllowlist、effect、read-back 生效 |
| ADM | Admin 治理 | 审批、审核、状态变化后读回 |
| PRIV | 隐私展示 | 高敏正文不在治理视图中默认裸露 |

## 集中测试方法

```text
准备账号和材料
  -> 执行登录与权限测试
  -> 执行跨用户隔离测试
  -> 执行 Agent 主链路测试
  -> 执行高风险写入 read-back
  -> 执行 Admin 治理测试
  -> 执行隐私展示检查
  -> 记录阻断项和证据
```

测试记录要包含 caseId、账号、输入材料、动作、预期、实际、证据和结论。

## 阻断标准

| 等级 | 示例 | 阶段处理 |
|---|---|---|
| P0 | 跨用户读取、未确认写简历、保存无读回却显示完成 | 不进入全量测试 |
| P1 | 权限提示不清、Admin 状态刷新不及时、低置信图片提示不足 | 进入风险清单并补证 |
| P2 | 文案、布局、筛选效率、非核心空态 | 可进入后续体验增强 |

这里的“阻断”用于定义产品交付门槛。

## 完成状态

集中开发与测试完成后，Zhiyuan 已经具备进入全量测试的条件：

1. 多账号权限矩阵稳定。
2. 核心求职资产按 userId 隔离。
3. Agent 主链路可在权限范围内执行。
4. 关键写入有 read-back/verifier。
5. Admin 治理动作有状态读回。
6. PostgreSQL + pgvector 是测试事实源。

34 将在这个基础上进行完整产品全量测试。

## 集中测试记录样例

```markdown
caseId：SEC-CV-APPLY-001
账号：memberA
输入：基于 reportId=rpt_1024 修改 personal_summary
动作：
1. Agent Chat 创建 resume_edit proposal。
2. CV 页面展示 proposal。
3. 用户确认 apply。
4. 系统读回 personal_summary。
预期：
- 未确认前 cv_data 不变化。
- 确认后目标 section 与 proposal 内容一致。
- memberB 不能看到 proposal。
证据：
- proposalId
- section hash before/after
- read-back result
结论：pass / partial / fail
```

这种记录能让测试结果被复查，而不是停留在“我点过了，可以用”。

## 开发完成定义

集中开发阶段的完成定义要和产品交付绑定。

| 能力 | 完成定义 |
|---|---|
| 登录 | 注册、登录、退出、me 读回都可用 |
| 权限 | pending/member/admin 页面和 API 行为一致 |
| 隔离 | memberA/memberB 核心资产互不可见 |
| Agent | 6 个业务 agent 由 task contract 约束 |
| 工具 | 48 个工具有 effect、allowlist、confirmation、evidence |
| 写入 | CV、report、Offer、memory、Admin 动作有读回 |
| 隐私 | Admin/run 展示摘要，不裸露高敏原文 |

只有这些能力同时满足，才能进入 34 的全量测试。
