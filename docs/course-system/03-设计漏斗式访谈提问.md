# 03 设计漏斗式访谈提问

本篇记录 0-1 阶段如何设计访谈问题。目标是把用户对求职的模糊表达转成可判断的产品机会、首版需求和风险边界。

访谈问题必须围绕求职用户和业务相关方展开。所有问题都要服务于产品判断：谁会用、为什么用、现在怎么解决、愿意交给系统什么、希望得到什么、最怕什么、怎样才算成功。

## 1. 访谈结构

```text
开场动机
  -> 求职阶段
  -> 当前替代方案
  -> 材料与输入
  -> 期望输出
  -> 信任与隐私边界
  -> 首版价值判断
  -> 需求候选
```

| 层级 | 目标 | 产出 |
|---|---|---|
| 开场 | 确认用户为什么会需要求职助手 | 动机和频率 |
| 阶段 | 判断用户处在选岗、简历、面试、Offer、定位哪一段 | 主链路 |
| 替代方案 | 了解用户现在用什么解决 | 差异化机会 |
| 材料 | 确认用户愿意提供 JD、简历、Offer、截图、回答等 | 输入能力 |
| 输出 | 确认用户要结论、报告、草稿、追问还是确认动作 | 产品形态 |
| 边界 | 确认不能发生的错误 | 安全规则 |
| 验证 | 确认用户如何判断有用和可信 | POC 标准 |

## 2. 通用开场问题

| 问题 | 追问 | 产品判断 |
|---|---|---|
| 你最近一次认真找工作是什么阶段？ | 选岗、投递、改简历、面试、Offer、转型定位？ | 判断用户类型 |
| 你最希望 AI 求职助手先帮你解决哪一件事？ | 如果只能保留一个能力，会选哪个？ | 判断首版核心 |
| 你现在怎么解决这个问题？ | 用通用 AI、顾问、朋友、模板、招聘平台还是表格？ | 判断替代方案 |
| 现在做法最让你不满意的是什么？ | 慢、不准、无法保存、不可信、太贵、隐私担心？ | 判断痛点 |
| 你愿意把哪些材料交给系统？ | JD、简历、Offer、截图、面试回答、职业经历？ | 判断输入范围 |
| 哪些内容必须你确认后才能保存或改动？ | 简历、Offer、画像、记忆、共享材料？ | 判断写入边界 |
| 如果系统说完成了，你怎么确认？ | 页面、报告编号、草稿、读回、导出、状态变化？ | 判断验收证据 |

## 3. JD 评估访谈

| 问题 | 追问 | 需求线索 |
|---|---|---|
| 你看到一个 JD 时最先判断什么？ | 值不值得投、匹配度、风险、准备路径、薪资预期？ | 报告结构 |
| 你通常怎么保存或转发 JD？ | 文本、截图、链接、招聘软件收藏？ | 输入方式 |
| 通用 AI 给 JD 分析时哪里不够？ | 结论泛、不能结合简历、无法复查、上下文丢失？ | 差异化 |
| 你希望先看到短结论还是完整报告？ | 聊天摘要和报告页如何分工？ | 页面承接 |
| 什么情况下你会不相信评估结论？ | 没引用 JD 字段、没有结合经历、风险判断空泛？ | 可信标准 |

## 4. 简历访谈

| 问题 | 追问 | 需求线索 |
|---|---|---|
| 你让 AI 改简历时最担心什么？ | 编造、夸大、改错 section、覆盖原文、风格不像自己？ | 提案机制 |
| 你更希望按哪种粒度确认修改？ | 整份、个人概述、项目经历、技能、逐段？ | section 设计 |
| 你希望系统给出哪些信息？ | 原文、建议文案、改动理由、对 JD 的对应关系？ | diff 设计 |
| 哪些事实必须你补充后才能写入？ | 数据指标、公司名称、职责、成果、时间线？ | 事实边界 |
| 修改后你如何确认真的保存了？ | 页面刷新、版本记录、目标 section 读回？ | read-back |

## 5. Offer 访谈

| 问题 | 追问 | 需求线索 |
|---|---|---|
| 你拿到 Offer 后最想先看什么？ | 总包、试用期、社保、公积金、年终、期权、合同主体？ | 字段抽取 |
| 你最担心 Offer 哪些风险？ | 试用期、绩效、加班、地点、团队、薪资口径？ | 风险模型 |
| 你会如何谈判？ | 要更多薪资、明确福利、确认发展空间、争取入职时间？ | 谈判建议 |
| 哪些信息缺失时不能下结论？ | 社保基数、年终规则、试用期薪资、合同主体？ | 澄清清单 |
| Offer 信息能否保存？ | 哪些字段默认私有，哪些可以脱敏复用？ | 隐私分级 |

## 6. 面试访谈

| 问题 | 追问 | 需求线索 |
|---|---|---|
| 你准备面试时最需要什么？ | 题目、追问、反馈、表达结构、项目复盘？ | 面试功能 |
| 你希望一次回答几道题？ | 一题一答还是一组题？ | 交互节奏 |
| 反馈要包含什么？ | 评分、优点、问题、追问、参考表达？ | 输出结构 |
| 面试准备需要绑定哪些材料？ | JD、简历版本、目标岗位、历史回答？ | session 设计 |
| 历史回答能否被记住？ | 私有复盘还是团队知识？ | 记忆边界 |

## 7. 自我定位访谈

| 问题 | 追问 | 需求线索 |
|---|---|---|
| 你说“不知道适合什么方向”，具体卡在哪里？ | 不懂岗位、不懂自己优势、不懂表达、不确定薪资？ | 定位入口 |
| 你过去最能证明能力的经历是什么？ | 业务结果、产品设计、增长、AI 应用、协作？ | 画像信号 |
| 哪些偏好应该长期记住？ | 城市、行业、薪资、远程、岗位类型、公司阶段？ | 记忆内容 |
| 哪些内容不能被系统长期判断？ | 情绪化表达、未确认偏见、敏感经历？ | 写入质量门 |
| 你希望定位结果是什么形式？ | 方向列表、推荐岗位、表达主线、下一步任务？ | 输出形态 |

## 8. 管理与治理访谈

| 对象 | 问题 | 需求线索 |
|---|---|---|
| 求职顾问 | 哪些判断可以复用，哪些必须因人而异？ | 团队知识审核 |
| HR/面试官视角 | 什么样的简历或回答让你觉得可信？ | 真实性约束 |
| 运营/管理员 | 哪些用户需要审批，哪些内容需要审核？ | Admin 权限 |
| 运营/管理员 | 如何判断一条记忆可以共享？ | private/team_pending/team |
| 运营/管理员 | 出现错误时需要看到哪些证据？ | run/review |

## 9. 访谈记录格式

| 字段 | 说明 |
|---|---|
| 用户角色 | 求职者、Offer 候选人、面试准备用户等 |
| 求职阶段 | 选岗、简历、面试、Offer、定位、复盘 |
| 原始表达 | 保留用户原话 |
| 当前替代方案 | 用户现在怎么解决 |
| 当前痛点 | 为什么现有方式不够 |
| 输入材料 | 用户愿意提供什么 |
| 期望输出 | 结论、报告、提案、反馈、谈判建议 |
| 信任边界 | 编造、误写、越权、隐私、假成功 |
| 首版需求 | 可进入需求池的一句话 |
| 验证方式 | POC 样本、页面承接、read-back 或用户判断 |

结论：03 的价值是让调研从一开始就服务产品定义。04 将把这些访谈结果、市场观察和替代方案整理成 0-1 阶段的调研结论。

## 10. 追问树样例

漏斗式访谈要准备追问树，而不是只准备一组平铺问题。以下以“帮我看看这个岗位”为例。

```text
用户：帮我看看这个岗位。
  -> 你现在是在决定要不要投，还是已经准备投递？
    -> 如果还没决定：你最想判断匹配度、风险、差距还是投递优先级？
    -> 如果准备投递：你是否已经有当前简历？是否愿意让系统读取？
  -> 这个岗位材料来自哪里？
    -> 文本 JD：直接进入 JD 样本
    -> 截图 JD：先识别类型和清晰度
    -> 招聘链接：先确认能否读取，不能读取则要求粘贴核心内容
  -> 你希望输出停在哪里？
    -> 只要结论：生成摘要
    -> 需要复查：保存 Reports
    -> 要继续改简历：进入 resume proposal
    -> 要准备面试：进入 interview session
```

这棵树的重点是把一个入口拆成多个分流，而不是把所有用户都推进同一个功能。

## 11. 访谈记录字段

访谈结束后，每条记录要能进入产品需求池。建议记录成以下字段：

| 字段 | 示例 |
|---|---|
| 用户阶段 | 转型 AI 产品，正在筛选第一批 JD |
| 触发事件 | 看到 JD 但不确定是否值得投 |
| 当前替代方案 | 通用 AI + 朋友建议 + 自己改简历 |
| 输入材料 | JD 文本、当前简历、过往项目经历 |
| 期待输出 | 投递建议、差距、简历修改方向、面试准备路径 |
| 信任条件 | 能看到理由；不能编造经历；保存后能复查 |
| 隐私边界 | 简历和 Offer 默认私有，薪资不共享 |
| 成功证据 | 报告页可见、提案可确认、写入可读回 |
| 需求线索 | JD report、resume proposal、read-back、user scope |

没有这些字段，访谈就很难从“聊天记录”变成“产品证据”。
