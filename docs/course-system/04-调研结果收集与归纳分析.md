# 04 调研结果收集与归纳分析

本篇沉淀 Zhiyuan 在立项前后的调研结果。这里的“调研结果”来自市场观察、用户访谈、替代方案、求职材料样本和业务相关方视角，用于归纳产品机会。

调研的核心结论：用户并不缺一个会写几段文字的 AI，而是缺一个能围绕求职材料连续工作、结果可复查、写入可确认、隐私可控的 AI 求职助手。

## 1. 调研材料

| 材料来源 | 内容 | 作用 |
|---|---|---|
| 市场观察 | LinkedIn 2026 研究、Indeed Career Scout 等公开资料显示 AI 正在进入求职、简历、职业辅导和招聘工具 | 判断时机 |
| 用户访谈 | 选岗、简历、Offer、面试、定位中的真实表达 | 判断痛点 |
| 替代方案 | 通用 AI、求职顾问、模板网站、招聘平台、表格记录 | 找差异 |
| 求职材料样本 | JD、简历、Offer、面试问题、职业经历、截图 | 判断输入能力 |
| HR/面试官视角 | 真实、对岗、证据、表达质量 | 约束输出 |
| 顾问/运营视角 | 可复用标准、记忆审核、用户审批、质量复盘 | 设计治理 |

## 2. 外部趋势观察

| 趋势 | 对 Zhiyuan 的启发 |
|---|---|
| 求职者越来越多使用 AI 写简历、准备面试、理解岗位 | 产品机会成立，但必须比通用聊天更可信 |
| 招聘和职业平台开始提供 AI career coach | 单点功能会被平台吸收，Zhiyuan 需要做连续工作流 |
| 用户对 AI 生成内容的真实性仍有顾虑 | 简历和画像必须有确认、证据和边界 |
| 职业决策依赖大量私密材料 | 默认私有、按 userId 隔离、Admin 脱敏是首版底线 |

## 3. 核心发现

| ID | 发现 | 用户痛点 | 产品机会 | 优先级线索 |
|---|---|---|---|---|
| FIND-001 | JD 判断是高频入口 | 不知道岗位是否值得投，怕浪费时间 | Agent Chat 输入 JD，生成可复查报告 | P0 |
| FIND-002 | 简历修改风险高 | 用户怕 AI 编造、覆盖、改错重点 | proposal -> confirm -> apply -> read-back | P0 |
| FIND-003 | 转型用户方向不清 | 不知道经历如何匹配 AI 岗 | guided profile session | P0 |
| FIND-004 | Offer 决策涉及高敏信息 | 薪资、福利、试用期和谈判空间难判断 | Offer 抽取、风险、谈判建议，默认私有 | P0 |
| FIND-005 | 面试准备需要上下文 | 泛题无用，必须贴 JD 和简历 | 绑定材料，一题一答 | P1 |
| FIND-006 | 截图是自然输入方式 | 用户不想复制长 JD/Offer | 图片类型识别和低置信澄清 | P1 |
| FIND-007 | 用户希望长期记住背景 | 重复解释经历和偏好很累 | 私有记忆、审核后团队知识 | P1 |
| FIND-008 | 顾问需要复用判断标准 | 每次从零分析成本高 | 报告模板、记忆治理、Admin 审核 | P1 |
| FIND-009 | 用户不信只存在聊天里的结果 | 聊天结论找不到、无法比较 | 多页面承接求职资产 | P0 |
| FIND-010 | 写入成功必须可证明 | 简历、报告、Offer 都是高价值资产 | read-back/verifier 成功态 | P0 |

## 4. 按求职链路归纳

### 4.1 选岗与 JD

用户原话集中在：

- “这个岗位我能投吗？”
- “这个 JD 说的到底要什么？”
- “我和它差距在哪里？”
- “我应该怎么准备？”

归纳结果：JD 是首版最适合的入口。它材料明确、任务高频、价值直观，能带出报告页、简历提案、面试准备和长期记忆。

### 4.2 简历

用户原话集中在：

- “帮我看看现在简历是什么样。”
- “按这个岗位改一下个人概述。”
- “不要帮我编经历。”
- “先给草稿，我确认后再改。”

归纳结果：简历链路必须把“查询”和“修改”分开。查询是只读，修改是提案，写入必须确认和读回。

### 4.3 Offer

用户原话集中在：

- “这个 Offer 值得接吗？”
- “薪资结构怎么算？”
- “怎么和 HR 谈？”
- “哪些信息还要问清楚？”

归纳结果：Offer 首版不追求复杂财务模型，先做字段抽取、风险提示、缺失字段清单和谈判问题。

### 4.4 面试

用户原话集中在：

- “基于这个 JD 模拟面试。”
- “我回答完你追问。”
- “指出我的问题，不要只给标准答案。”

归纳结果：面试准备必须绑定 JD 和简历，一题一答比一次给大量问题更适合首版验证。

### 4.5 自我定位

用户原话集中在：

- “我适合 AI 产品还是 AI 运营？”
- “我过去经历怎么包装成 AI 岗能力？”
- “我不想系统乱给我贴标签。”

归纳结果：定位不能一次给空泛结论，需要通过 guided session 逐步收集经历、偏好、约束和证据。

### 4.6 记忆与 Admin

用户和业务方共同关注：

- 用户不想重复解释背景。
- 顾问希望复用好的表达和判断框架。
- 管理员需要审批用户、审核记忆、处理争议材料。

归纳结果：记忆必须有可见性、来源、审核状态；Admin 是首版治理能力，不是后期附属页面。

## 6. POC 样本线索

| 样本 | 验证的产品假设 |
|---|---|
| AI 产品经理 JD 文本 | 用户是否能从 Agent Chat 获得可复查 JD 报告 |
| 当前简历 + 目标 JD | 系统是否能生成不编造的简历提案 |
| Offer 截图 | 系统是否能抽取字段并提示缺失信息 |
| 面试准备请求 | 系统是否能绑定 JD 和简历做一题一答 |
| “我适合什么方向？” | 系统是否能进入定位会话而不是直接给空泛结论 |
| 低清或混合截图 | 系统是否会澄清，而不是猜测执行 |

## 7. 调研结论

1. Zhiyuan 的首版机会是“可信的 AI 求职工作台”，不是单点生成器。
2. Agent Chat 适合作为入口，但业务结果必须落到页面和数据对象。
3. 首版要优先证明 JD、简历、Offer、面试和定位这几条链路的可行性。
4. 简历、Offer、画像和记忆属于高敏资产，默认私有，写入必须确认。
5. 成功态必须被 read-back 或 verifier 支撑，这是产品信任基础。

05 将基于这些调研结论做需求优先级分类，筛出进入 POC/MVE 的首版主线。

## 9. 原始材料到发现的归纳样例

调研分析不能只写结论，要能追溯到原始材料。下面是一组归纳样例。

| 原始表达或材料 | 初步标签 | 归纳发现 | 产品影响 |
|---|---|---|---|
| “我问 AI 能不能投，但过两天找不到那次回答了。” | 结果不可复查 | 聊天结论需要沉淀为业务资产 | Reports 页面成为 P0 |
| “我不介意 AI 帮我润色，但不能替我编项目。” | 真实性焦虑 | 简历修改必须有证据和边界 | proposal 展示理由和原文 |
| “Offer 上写的补贴和试用期我看不懂。” | 高敏决策 | Offer 分析不能只给分，要拆字段 | Compare 需要字段抽取和缺失信息 |
| “面试题不要一下给我二十道，我答完你追问。” | 长任务状态 | 面试准备要一题一答 | interview_state_json |
| “我想转 AI 岗，但我不知道我的经历怎么说。” | 定位模糊 | 自我定位需要连续追问 | profile guided session |
| JD 截图中混有招聘广告和水印 | 图片噪声 | 图片输入要先分类和置信判断 | image-intake、低置信澄清 |

## 10. 需求聚类结果

将调研发现聚类后，Zhiyuan 的首版机会被收敛成五个产品簇。

| 产品簇 | 包含需求 | 为什么重要 | 首版承接 |
|---|---|---|---|
| 求职判断 | JD 评估、投递建议、差距和风险 | 用户最早遇到、频率最高 | Agent Chat + Reports |
| 求职资产 | 简历查询、提案、确认写入、撤回 | 用户最怕被 AI 改坏 | CV + proposal |
| 高敏决策 | Offer 字段、风险、谈判问题 | 薪资和选择成本高 | Compare |
| 长任务准备 | 面试一题一答、回答反馈、状态恢复 | 需要连续上下文 | Interview |
| 长期画像 | 目标、偏好、经历信号、记忆 | 降低重复解释成本 | Profile + Memory |

聚类后可以看出，Zhiyuan 的首版不是“AI 帮你找工作”的泛产品，而是围绕求职材料建立可信工作台。
