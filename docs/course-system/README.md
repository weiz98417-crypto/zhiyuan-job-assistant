# Zhiyuan 求职助手产品全生命周期教学项目

本目录不是普通项目说明书，也不是工具教程，而是用筝筝纸鸢（Zhiyuan）求职助手复刻一个产品从无到有、从 0 到 1、再到优化和交付的完整生命周期。学习者应当沿着这些文档理解：一个 AI 求职助手如何先发现市场机会和用户痛点，再通过需求访谈、产品定义、POC、MVE、多页面开发、Agent 化重构、数据与 eval 治理、登录权限、安全审核和最终交付，逐步成为一个可讲清、可复现、可验收的产品项目。

每篇文档都围绕 Zhiyuan 的项目事实展开：Agent Chat 是主入口；业务覆盖 JD 评估、简历、Offer、面试、自我定位、记忆和 Admin 治理；产品 runtime 有 6 个业务 agent：`general`、`evaluate`、`resume`、`interview`、`profile`、`offer`；Orchestrator 是内部编排；工具体系按 48 个注册工具治理；PostgreSQL + pgvector 是当前 LAN runtime；SQLite 只作为 fallback、archive、migration source；所有写入和成功态都要能 read-back 或被 verifier 证明。

## 生命周期主线

```text
发现真实求职问题
  -> 判断目标用户和替代方案
  -> 定义产品机会和首版边界
  -> 收集需求和访谈证据
  -> 归纳需求池和优先级
  -> 定义 POC / MVE
  -> 设计多页面产品形态
  -> 开发核心页面和业务链路
  -> 验证 Demo 和可行性
  -> 做 Agent 化重构
  -> 建立多 agent、工具、记忆和 eval 治理
  -> 调优 Agent 与页面联动
  -> 建立登录、权限、隐私和安全体系
  -> 全量测试并交付
```

## 文档使用口径

| 口径 | 要求 |
|---|---|
| 不是泛泛方法论 | 每个结论都要落回 Zhiyuan 的 JD、简历、Offer、面试、画像、记忆、页面或 Admin 场景 |
| 从 0-1 写起 | 01-09 必须从产品尚未存在时的用户痛点、替代方案、机会判断和首版假设写起 |
| 不是开发流水账 | 讲清产品阶段、阶段产物、验收方式和为什么这样设计 |
| 不是工具展示 | Codex、测试脚本、浏览器和 gstack 只是验证手段，不能喧宾夺主 |
| 不是工程师访谈 | 需求来源是求职者、Offer 候选人、面试准备用户、HR/面试官视角、顾问和运营/管理员 |
| 不夸大能力 | run review、eval candidate 是治理证据，不等于产品能力已经完成交付 |
| 安全不抽象 | 登录、权限、注入、隐私、图片文字审核都必须绑定简历、JD、Offer、画像、记忆和工具调用 |

## 阶段交付物

每个阶段都要能讲清四件事：输入是什么，做了什么产品判断，产出什么项目材料，用什么证据验收。

| 阶段 | 输入 | 核心判断 | 阶段产出 | 验收证据 |
|---|---|---|---|---|
| 需求发现 | 市场观察、求职场景、用户访谈、替代方案、PRD 初稿 | 哪些是真问题，哪些是首版机会，哪些不做 | 用户画像、访谈问题、需求池、优先级 | 原始表达、需求卡、P0/P1/P2 分类 |
| POC/MVE | 需求池、产品假设、样本材料 | 哪条链路最能证明产品从 0 到 1 成立 | MVE 主线、POC 测试集、验证记录 | JD 报告、简历提案、跨页恢复、read-back |
| 多页面开发 | MVE 结论、页面职责、数据对象 | 哪些页面承接哪些业务事实 | Agent、CV、Reports、Offer、Interview、Admin 页面方案 | 页面状态、API 读写、run 记录、截图 |
| Agent 化重构 | 页面链路、任务路由、工具体系 | 哪些任务交给哪个业务 agent | 6 个业务 agent、编排器、工具治理、记忆体系 | task contract、allowedTools、verifier、eval |
| 联动与测试 | 页面、Agent、数据、权限边界 | 哪些链路仍会串场或假成功 | 页面联动测试、集中测试、全量测试 | 浏览器验证、Vitest、PostgreSQL 读回、run review |
| 安全交付 | 登录、权限、隐私、注入、OCR 风险 | 哪些安全能力达到交付口径 | JWT、隔离、注入防范、图片文字审核、安全交付矩阵 | pending/member/admin、userId 隔离、read-back、Admin 复盘 |
