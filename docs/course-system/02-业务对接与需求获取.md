# 02 业务对接与需求获取

本篇把 01 的产品机会转成业务对象和需求入口。此时 Zhiyuan 仍处在 0-1 产品定义阶段，重点不是拆开发任务，而是把真实求职链路中的人、材料、动作、结果和边界梳理清楚。

业务对接的对象是求职服务链路里的真实角色：求职者、转型 AI 岗候选人、Offer 候选人、面试准备用户、HR/面试官视角、求职辅导顾问、运营/管理员。

## 1. 业务目标

Zhiyuan 的业务目标是帮助用户做高质量求职决策和材料迭代。

| 业务目标 | 用户获得的结果 | 产品承接 |
|---|---|---|
| 看懂 JD | 判断值不值得投、差距在哪里、怎么准备 | JD 评估报告 |
| 改好简历 | 得到可确认的修改提案，不编造、不误写 | 简历提案和 read-back |
| 判断 Offer | 看清收益、风险、成长和谈判空间 | Offer 报告和谈判建议 |
| 准备面试 | 基于 JD 和简历一题一答，并获得反馈 | 面试 session |
| 做职业定位 | 把经历、偏好、约束收敛成方向 | Profile 画像 |
| 沉淀记忆 | 不重复解释背景，复用历史判断 | 私有/团队记忆 |
| 管理治理 | 审批用户、审核记忆、复盘运行证据 | Admin |

## 2. 业务对象

| 业务对象 | 用户语言 | 关键字段 | 首版处理 |
|---|---|---|---|
| JD | “这个岗位能投吗？” | 公司、岗位、职责、要求、加分项、风险 | 评估、保存、报告复查 |
| 简历 | “我现在的简历是什么？”“按这个 JD 改一下” | section、原文、提案、版本、hash | 只读查询、提案、确认写入 |
| Offer | “这个 Offer 怎么样？”“怎么谈？” | 薪资、试用期、福利、地点、合同主体、缺失字段 | 字段抽取、风险、谈判 |
| 面试 | “基于这个 JD 模拟面试” | JD 快照、简历快照、题目、回答、反馈 | 一题一答、进度恢复 |
| 画像 | “我适合什么方向？” | 经历、能力信号、偏好、约束、置信度 | guided session、信号沉淀 |
| 记忆 | “以后别让我重复解释背景” | 可见性、来源、脱敏、审核状态 | private/team_pending/team |
| 用户与权限 | 注册、审批、Admin 管理 | status、role、userId、tokenVersion | pending/member/admin |
| 运行证据 | “这次处理是否可信？” | run、step、tool、verifier、review | 可复盘，不冒充完成 |

## 3. 需求获取对象

| 对接对象 | 要获取什么 | 不是问什么 |
|---|---|---|
| 求职者 | 选岗、投递、简历、面试、Offer 的真实卡点 | 不问“你想要几个页面” |
| 转型候选人 | 方向不清、经历表达不清、岗位理解不清 | 不问“你要哪个 Agent” |
| Offer 候选人 | 薪资结构、风险判断、谈判问题 | 不问“要不要一个 Offer 页面” |
| 面试准备用户 | 材料绑定、提问节奏、反馈结构 | 不问“要不要题库” |
| HR/面试官视角 | 真实、对岗、可证明的表达标准 | 不问内部流程工具 |
| 求职顾问 | 判断标准、复盘方式、可复用材料 | 不问开发排期 |
| 运营/管理员 | 用户审批、内容审核、记忆治理、证据复盘 | 不问日志字段偏好 |

## 4. 业务链路

```text
用户带来求职材料
  -> Agent Chat 发起任务
  -> 识别业务对象
  -> 进入 JD / 简历 / Offer / 面试 / 画像 / 记忆链路
  -> 生成结果
  -> 页面承接
  -> 数据读回
  -> 必要时进入 Admin 治理
```

首版并不要求每条链路都完整深入，但每条进入 POC/MVE 的链路都必须能回答：

| 问题 | 示例 |
|---|---|
| 用户是谁 | 正在投 AI 产品经理岗位的候选人 |
| 材料是什么 | JD 文本、当前简历、Offer 截图 |
| 想完成什么 | 判断是否投、生成简历提案、准备面试 |
| 结果落哪里 | Reports、CV、Compare、Interview、Profile |
| 成功怎么证明 | 页面可见、对象可读回、hash 或 verifier 通过 |
| 风险是什么 | 编造、误写、串用户、泄露隐私、假成功 |

## 5. 需求卡格式

0-1 阶段的需求卡要保留用户语言，同时能进入产品设计。

| 字段 | 说明 | 示例 |
|---|---|---|
| 用户角色 | 谁提出 | 转型 AI 岗候选人 |
| 求职阶段 | 正在做什么 | 选岗 + 改简历 |
| 原始表达 | 用户原话 | “这个 AI 产品经理岗位我能投吗？” |
| 当前做法 | 现在怎么解决 | 把 JD 发给朋友或通用 AI |
| 当前痛点 | 哪里卡住 | 不知道结论是否可信，也无法沉淀报告 |
| 输入材料 | 用户愿意给什么 | JD、简历、过往经历 |
| 期望结果 | 想拿到什么 | 投递建议、差距、简历提案 |
| 信任边界 | 不能发生什么 | 不能编造经历，不能未确认改简历 |
| 产品承接 | 落到哪个链路 | Agent Chat -> evaluate -> Reports -> resume proposal |
| 验证方式 | 怎么证明可行 | POC 样本、页面状态、read-back |

## 6. 首版业务范围

| 范围 | 首版处理 |
|---|---|
| Agent Chat | 作为统一入口，支持自然语言和图片材料进入任务 |
| JD | 支持文本/截图评估，输出摘要和完整报告 |
| 简历 | 支持当前简历查询、修改提案、确认写入 |
| Offer | 支持字段抽取、风险判断、谈判问题 |
| 面试 | 支持基于 JD 和简历的一题一答 |
| Profile | 支持引导式自我定位和稳定信号沉淀 |
| Memory | 支持私有记忆和审核后的团队知识 |
| Admin | 支持用户审批、记忆审核、运行复盘 |

## 7. 对接结论

业务对接后的核心判断是：Zhiyuan 的产品对象不是“聊天消息”，而是求职资产。JD、简历、Offer、面试进度、画像和记忆都需要有页面承接、数据归属和成功证据。

03 将基于这些业务对象设计漏斗式访谈问题，让调研能够从用户原话进入可排序的需求池。

## 8. 业务对接纪要样例

业务对接要把不同角色对求职链路的判断合并成产品事实。下面是一份对接纪要的结构样例。

| 角色 | 关键输入 | 对产品的要求 | 形成的业务对象 |
|---|---|---|---|
| 求职者 | JD、当前简历、投递犹豫点 | 快速判断能不能投，并知道下一步 | `jd`、`report`、`resume_edit_proposal` |
| 转型候选人 | 过往项目、目标方向、能力焦虑 | 梳理可证明能力，不给空泛鼓励 | `profile_session`、`profile_signal` |
| Offer 候选人 | Offer 文本、薪资结构、HR 沟通记录 | 找出风险、缺失字段和谈判问题 | `offer`、`offer_report` |
| 面试准备用户 | JD、简历版本、回答记录 | 一题一答、追问、反馈，不生成泛题堆 | `interview_session`、`interview_state_json` |
| 顾问/运营 | 优秀简历、常见判断框架、用户反馈 | 可复用但不能泄露个人隐私 | `reference_resume`、`memory_candidate` |
| Admin | 用户状态、记忆候选、运行证据 | 审批、审核、读回状态 | `user`、`memory_item`、`agent_run` |

## 9. 需求卡片样例

业务对接后的需求不能只写一句标题。每张需求卡至少要能回答“谁、在什么场景、拿什么材料、要什么结果、不能发生什么”。

```markdown
需求 ID：REQ-CV-EDIT-001
来源角色：正在按目标 JD 修改简历的求职者
触发场景：用户在 Reports 页面看完 JD 报告后，回到 Agent Chat 要求“按这个岗位改个人概述”
输入材料：当前用户 CV、目标 JD reportId、用户指定 section
期望结果：生成一条 pending resume_edit_proposal，包含原文、建议文案、修改理由、目标 section
风险边界：不能编造经历；不能直接覆盖 cv_data；不能显示“已保存”
成功证据：CV 页面可见 proposal；用户确认 apply 后，目标 section read-back 一致
优先级：P0
```

再看一个 Offer 需求：

```markdown
需求 ID：REQ-OFFER-001
来源角色：拿到 Offer 的候选人
触发场景：用户粘贴 Offer 文本或上传截图，询问“这个 Offer 怎么谈”
输入材料：公司、岗位、薪资、试用期、福利、地点、入职时间
期望结果：抽取字段，标注缺失信息，输出风险和 HR 追问清单
风险边界：不能伪造公司政策；不能默认公开薪资；不能给确定法律结论
成功证据：Compare 页面可读回 offerReportId
优先级：P1
```

这样的卡片才能进入后续 POC、MVE 和验收矩阵。
