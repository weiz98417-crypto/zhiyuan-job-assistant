# 11 多页面功能开发与实现

本篇关注“怎么把页面职责做成可运行的功能”。10 已经定义页面为什么存在，11 继续把每个页面拆成具体功能切片：用户目标、入口、业务 agent、工具、数据对象、页面状态和 read-back/verifier 证据。

功能开发的重点不是复述代码结构，而是保证每个功能都能服务真实求职任务，并能从 Agent Chat 延伸到页面工作流。

## 功能切片定义

每个功能切片都按同一组问题落地，但不同页面的实现重点不同。

| 问题 | 说明 |
|---|---|
| 用户目标是什么 | 例如评估 JD、查看简历、生成简历草稿、分析 Offer、准备面试 |
| 从哪里进入 | Agent Chat、业务页面按钮、报告详情、Admin 页面 |
| 由哪个 agent 承接 | `general`、`evaluate`、`resume`、`interview`、`profile`、`offer` |
| Orchestrator 做什么 | 只做内部分类、路由、任务约束和工具范围确定 |
| 读写哪些对象 | JD、report、CV、proposal、Offer、interview state、memory、Admin 记录 |
| 用哪些工具 | 48 个工具中符合 taskType 与 agent allowlist 的工具 |
| 如何证明完成 | 页面可见、对象可读回、verifier 通过、状态可继续 |

## Agent Chat 功能

Agent Chat 是所有业务的统一入口，首版必须具备以下能力：

| 功能 | 实现要求 | 验证方式 |
|---|---|---|
| 会话加载 | 恢复当前 session、messages、agent state | 刷新后上下文仍可继续 |
| 文本输入 | 自然语言进入 JD、简历、Offer、面试、自我定位任务 | 高频表达能路由到正确 agent |
| 图片输入 | 先识别 JD、Offer、简历等材料类型和质量 | 低置信材料进入澄清，不直接写入 |
| 工具卡片 | 展示中文名称、状态、摘要、目标对象和证据 | 用户能理解系统做了什么 |
| 待确认动作 | 简历 apply、画像写入、团队记忆公开等需用户或 Admin 确认 | 未确认不写入最终对象 |
| 跨页回到 Agent | 从报告、简历、Offer、面试页面回到同一任务上下文 | 稳定 ID 被带回 Agent Chat |

Agent Chat 不承担所有展示，它只负责把用户目标推进到正确的业务对象和页面。

## JD 与报告功能

| 功能 | 实现说明 |
|---|---|
| JD 输入 | 支持文本、链接、图片；图片先走材料识别 |
| JD 评估 | `evaluate` agent 负责生成结构化评估和投递建议 |
| 报告保存 | 保存 JD 与 report 后按 `reportId` 或 `reportNum` read-back |
| 报告详情 | `/evaluate/reports` 展示完整报告、追问入口和导出入口 |
| 报告追问 | 从报告详情回到 Agent Chat 时传递稳定 report 上下文 |
| 报告导出 | 导出前确认报告对象存在，导出后由文件 verifier 证明 |

JD 功能要避免把 Offer 或简历图片误当成 JD。任务类型必须由材料识别和上下文共同决定。

## 简历功能

简历是高价值资产，功能上必须把查询、草稿、确认、写入分开。

| 功能 | 实现说明 |
|---|---|
| 简历查询 | `resume_query` 只读当前用户简历，不创建 proposal |
| 简历草稿 | `resume_edit` 创建 `resume_edit_proposals`，包含目标 section、原文、建议文案和理由 |
| 差异展示 | `/cv` 展示草稿与当前简历差异，便于用户判断 |
| 确认应用 | 用户确认后才写入 `cv_data` |
| 写入读回 | apply 后读回目标 section，比较 hash 或等价证据 |
| 回滚与放弃 | 支持 discard、rollback，页面刷新后状态仍一致 |
| 参考简历 | 保存前确认 role category、visibility、来源和脱敏状态 |

实现底线：

```text
查询不写入。
草稿不覆盖。
未确认不 apply。
没有 read-back 不展示为已完成。
```

## Offer 功能

Offer 页面承接 offer 对象、offer report、谈判策略和多 Offer 对比。

| 功能 | 实现说明 |
|---|---|
| Offer 识别 | 文本或截图进入 `offer` agent，而不是 `evaluate` agent |
| Offer 首评 | 抽取公司、岗位、薪资、试用期、福利、风险和谈判点 |
| 报告保存 | 保存后按 `offerReportId` read-back |
| 谈判策略 | 基于已有 Offer report 生成策略和 HR 问题清单 |
| 多 Offer 对比 | 用户明确选择多个 `offerId` 后再对比 |
| 隐私边界 | Offer 默认个人可见，不跨用户读取 |

Offer 功能的重点是区分事实、假设和策略建议，不能伪造公司政策或法律结论。

## 面试功能

面试功能强调长任务状态。

| 功能 | 实现说明 |
|---|---|
| 材料绑定 | 绑定 JD、报告和简历快照 |
| 面试计划 | 生成当前准备目标和题目路径 |
| 一题一答 | 每轮只推进一个问题或一个追问 |
| 回答反馈 | 给出评分、优点、问题和改进建议 |
| 状态恢复 | `interview_state_json` 保存当前题目、材料快照和 transcript |
| 回到 Agent | 用户说“继续面试”时恢复当前题目，而不是重新开始 |

面试页面和 Agent Chat 要共享同一份 interview state。

## 自我定位、记忆与 Profile 功能

`profile` agent 负责自我定位和画像信号，记忆系统负责长期可复用信息。

| 功能 | 实现说明 |
|---|---|
| 自我定位 | 通过连续问题梳理目标、偏好、优势和约束 |
| 画像信号 | 区分用户事实、用户偏好、岗位要求、模型推测 |
| 记忆候选 | 只有稳定、可追溯、可撤回的信息才能进入长期记忆 |
| 可见性 | private、team_pending、team 必须明确 |
| Admin 管理 | 团队记忆、参考简历和敏感素材需要 Admin 页面管理 |

JD 要求不能直接写成用户长期画像。画像写入必须保留来源、置信度和撤回路径。

## Admin 功能

Admin 页面不是产品主入口，但它支撑权限和可管理性。

| 页面 | 功能 |
|---|---|
| `/admin/users` | pending/member/admin 状态管理，操作后读回状态 |
| `/admin/memory` | 记忆审批、拒绝、归档、重新索引，操作后读回可见性和索引状态 |
| `/admin/agent-runs` | 查看 Agent 运行、工具调用、verifier、目标对象 |
| `/admin/agent-reviews` | 查看需要人工判断的记录和评估候选状态 |

Admin 功能要服务产品可信度，不把内部记录包装成用户侧成果。

## 数据与权限实现规则

| 规则 | 要求 |
|---|---|
| 当前 runtime | PostgreSQL + pgvector |
| SQLite 角色 | 只作 fallback/archive/migration |
| user scope | 服务端从 token/session 判断当前用户 |
| 高价值写入 | 必须带 read-back 或 verifier |
| 工具调用 | 必须匹配 taskType、agentAllowlist、effect 和确认规则 |
| 页面状态 | 刷新、切页、回到 Agent 后仍能恢复关键上下文 |

## 完成标准

本阶段完成时，每个核心功能都要能回答：

1. 用户从哪里进入。
2. 哪个业务 agent 负责。
3. Orchestrator 内部如何选择 taskType。
4. 调用了哪些工具，是否在 48 个工具的允许范围内。
5. 读写了哪些 PostgreSQL 对象。
6. 写入如何 read-back 或由 verifier 证明。
7. 结果落在哪个页面，用户如何继续下一步。

## 功能切片展开

以“基于 JD 修改简历”为例，一个看似简单的功能实际拆成 8 个切片。

| 切片 | 输入 | 处理 | 输出 | 风险控制 |
|---|---|---|---|---|
| 识别意图 | “按这个岗位改个人概述” | 路由为 `resume_edit` | task contract | 不进入 `resume_query` |
| 绑定报告 | reportId/reportNum | 读取当前用户报告 | JD 摘要和差距 | 不跨用户读取 |
| 读取简历 | 当前 userId | 读取 `cv_data` | 当前 section 原文 | 只读，不写入 |
| 生成提案 | JD + CV section | 生成建议文案和理由 | pending proposal | 不覆盖原文 |
| 展示差异 | proposal | CV 页面 diff | 原文/新文案/理由 | 用户可拒绝 |
| 确认应用 | 用户点击确认 | apply proposal | 更新目标 section | 需要确认 |
| 读回校验 | 目标 section | read-back/hash | verified result | 不一致即失败 |
| 后续继续 | apply 结果 | 回到 Agent Chat | 可继续面试或导出 | 带稳定对象 ID |

这个拆分方式同样可以套到 Offer、Interview 和 Profile：先识别任务，再绑定对象，最后用页面和读回证据完成闭环。
