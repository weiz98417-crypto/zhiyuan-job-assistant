# 32 登录安全体系构建

登录安全体系处理的是会话生命周期：用户登录多久有效，退出是否真的失效，角色变化后旧 token 是否还能使用，失败态是否会暴露敏感信息，Agent 是否能借旧状态继续操作。

对 Zhiyuan 来说，登录安全不是通用账号模块，而是保护求职资产的前置条件。

## 安全目标

| 目标 | 产品含义 |
|---|---|
| token 可验证 | JWT 签名、过期时间和 tokenVersion 都能被校验 |
| cookie 安全 | 登录态保存在 HTTP-only cookie 中，降低脚本读取风险 |
| 退出有效 | 用户退出后核心页面和 API 不能继续使用旧会话 |
| 状态变化生效 | 被拒绝、改角色、重置密码后旧 token 不继续有效 |
| 失败态清楚 | 用户知道是未登录、待审批、无权限还是登录过期 |
| Agent 同步失效 | Agent run 和工具调用不能绕过登录安全 |

## token 生命周期

```text
登录成功
  -> 签发 JWT
  -> 写入 HTTP-only cookie
  -> 每次核心请求校验签名和过期
  -> 写操作校验 tokenVersion
  -> 退出或状态变化后旧 token 失效
```

JWT 中可以包含 userId、role、tokenVersion 等身份字段，但不能包含可被客户端当成授权依据的业务对象范围。

## cookie 规则

| 项 | 设计 |
|---|---|
| 存储 | HTTP-only cookie |
| 作用 | 浏览器自动携带登录态，脚本不能直接读取 |
| Secure | 生产或 HTTPS 环境启用 secure |
| SameSite | 降低跨站请求风险 |
| 退出 | 设置过期或 maxAge=0 |

登录安全要兼顾本地开发和交付环境。本地可允许非 HTTPS cookie，生产环境必须按安全策略启用 secure。

## 失败态设计

登录失败、权限失败和账号状态失败必须清楚区分。

| 场景 | 用户反馈 |
|---|---|
| 未登录 | 请先登录 |
| 密码错误 | 账号或密码错误 |
| pending | 账号待审批 |
| rejected | 账号不可用 |
| token 过期 | 登录已过期，请重新登录 |
| member 访问 Admin | 没有管理员权限 |
| 旧 token 写入 | 身份状态已变化，请重新登录 |

不能把所有失败都包装成“系统繁忙”。安全失败本身也是产品体验的一部分。

## 登录安全与 Agent

Agent Chat 和工具调用必须继承登录安全：

- Agent run 创建前校验当前用户。
- 工具执行前校验 task contract 和当前身份。
- 写入工具执行前校验 tokenVersion。
- 读回仍使用当前 userId。
- token 失效后，正在进行的高风险动作不能继续 apply。

例如，用户打开 CV 页面生成了一个简历提案，随后账号被 Admin 拒绝或 tokenVersion 变化。此时即使页面还显示旧提案，也不能继续应用到简历。

## 登录限流与枚举防范

登录入口要避免被暴力猜测和用户枚举利用。

| 风险 | 防范方式 |
|---|---|
| 高频试密码 | 登录限流、失败次数控制 |
| 用户名枚举 | 错误提示不过度暴露账号是否存在 |
| 重复提交 | 按账号和来源做基本节流 |
| 旧会话滥用 | tokenVersion 和退出失效 |

这些能力不需要喧宾夺主，但必须成为登录体系的一部分。

## 完成状态

登录安全体系完成后，应满足：

1. 登录态可验证、可过期、可退出。
2. 状态变化能让旧 token 失效。
3. pending/rejected/member/admin 的失败态明确。
4. Agent 和工具不绕过登录安全。
5. 高风险写入在 token 失效后无法继续。
6. 用户不会因为安全阻断而误以为数据已经保存。

这为 33 的集中开发与测试提供安全验收边界。

## 会话状态变化样例

| 事件 | 旧会话应该怎样 | 产品反馈 |
|---|---|---|
| 用户主动退出 | cookie 失效，核心 API 不能继续访问 | 回到登录状态 |
| Admin 将 member 改为 rejected | 旧 token 不能继续写入 | 提示账号不可用 |
| Admin 将 member 升为 admin | 旧 token 不直接获得新权限 | 重新登录后进入 Admin |
| 重置密码 | 旧凭证不能继续使用 | 要求重新登录 |
| token 过期 | Agent 不能继续高风险 apply | 提示登录过期，保留草稿状态 |

登录安全不是让用户频繁掉线，而是保证身份变化能真实生效，尤其是简历写入、Offer 保存、Admin 审批这类高价值动作。

## 高风险动作的登录安全门

| 动作 | 登录安全检查 | 失败时的产品处理 |
|---|---|---|
| 应用简历提案 | token 有效、status active、userId 为 owner、tokenVersion 最新 | 保留 proposal，提示重新登录 |
| 保存 Offer report | token 有效、member active、offer 属于当前用户 | 不保存，说明身份状态异常 |
| 导出报告 | token 有效、report 属于当前用户 | 不生成文件 |
| Admin 审批用户 | token 有效、role admin、tokenVersion 最新 | 不改变用户状态 |
| 写入团队记忆 | token 有效、role admin 或审核流程通过 | 保持 team_pending |

这里的关键是：登录安全不能只在“打开页面”时检查一次，高风险动作执行前也要检查。否则用户在页面停留期间角色变化，旧页面仍可能尝试写入。

## 安全失败的文案边界

| 失败类型 | 建议文案 | 避免文案 |
|---|---|---|
| 未登录 | “请先登录后继续。” | “系统繁忙” |
| 登录过期 | “登录已过期，请重新登录。当前草稿未应用。” | “保存成功” |
| 待审批 | “账号待审批，暂不能进入求职工作台。” | “无数据” |
| 无 Admin 权限 | “当前账号没有管理员权限。” | “页面不存在” |
| tokenVersion 变化 | “账号状态已变化，请重新登录后继续。” | “操作失败” |

安全提示要让用户知道发生了什么，同时不能泄露不必要的内部细节。

## 登录安全与草稿保护

登录过期时，用户最担心的是刚才生成的内容丢失。Zhiyuan 的处理方式是区分“草稿可保留”和“高风险写入不可继续”。

| 内容 | 登录过期后 |
|---|---|
| 聊天里的普通回答 | 可以保留在当前页面展示 |
| 简历 proposal | 可以保留为待确认状态 |
| apply 简历 | 必须重新登录后才能执行 |
| Offer report 保存 | 必须重新登录后才能执行 |
| Admin 审批 | 必须重新登录并确认仍是 admin |

这样既保护用户体验，也保护求职资产。
