# 05 需求管理与优先级分类

本篇把 01-04 收集到的 0-1 产品需求整理成首版需求池，并给出 P0/P1/P2/不做项。排序依据不是实现难度，而是用户痛点强度、求职资产风险、首版验证价值和产品信任。

需求管理的目标是筛出 POC/MVE 主线：用最少的产品链路证明 Zhiyuan 值得继续做。

## 1. 优先级规则

| 等级 | 判断标准 | Zhiyuan 示例 |
|---|---|---|
| P0 | 不做就无法证明产品成立，或影响用户核心资产与信任 | JD 评估、简历提案、写入确认、read-back、隐私隔离 |
| P1 | 增强产品连续性和治理能力，但不阻断首版验证 | Offer、面试、图片输入、记忆、Admin |
| P2 | 扩展体验、效率或数据分析 | 更多岗位源、趋势分析、报告筛选 |
| 不做 | 与定位冲突、风险过高或不适合首版 | 海投、绕平台风控、未确认改简历、默认共享隐私 |

首版排序逻辑：

```text
产品成立证据 > 用户资产安全 > 求职主链路连续性 > 治理可见性 > 体验增强
```

## 2. P0 需求池

| ID | 需求 | 用户场景 | 产品承接 | 验证方式 |
|---|---|---|---|---|
| P0-JD-001 | 输入 JD 后生成投递建议、匹配差距、风险和准备建议 | 用户问“这个岗位能投吗？” | Agent Chat -> evaluate -> Reports | JD 样本报告 |
| P0-JD-002 | JD 报告必须可复查 | 用户后续回看或继续追问 | Reports/JDs | reportId/reportNum 可读 |
| P0-CV-001 | 当前简历查询必须只读 | 用户问“我现在的简历是什么？” | Agent Chat -> resume_query -> CV | 不创建提案 |
| P0-CV-002 | 简历修改必须先生成提案 | 用户要求按 JD 改个人概述 | resume proposal | 展示原文、建议、理由 |
| P0-CV-003 | 确认后才写入简历 | 用户确认某个 section 改动 | CV apply | section read-back |
| P0-TRUST-001 | 高风险成功态必须有证据 | 保存报告、应用提案、审批记忆 | read-back/verifier | 缺证据不显示完成 |
| P0-PRIVACY-001 | 用户求职资产默认私有 | 简历、Offer、画像、面试回答 | userId scope | userA/userB 不串 |
| P0-PAGE-001 | 结果不能只留在聊天里 | 用户需要复查报告、提案、Offer | CV/Reports/Compare/Profile | 页面承接 |
| P0-PROFILE-001 | 自我定位要逐步追问 | 转型候选人不清楚方向 | profile guided session | 每轮只推进一个问题 |

## 3. P1 需求池

| ID | 需求 | 用户场景 | 产品承接 | 验证方式 |
|---|---|---|---|---|
| P1-OFFER-001 | Offer 字段抽取和风险判断 | 用户拿到 Offer | offer -> Compare | Offer 报告 |
| P1-OFFER-002 | Offer 谈判追问复用上下文 | 用户问“怎么谈？” | offer report | 不重复建立无关对象 |
| P1-INTERVIEW-001 | 面试准备绑定 JD 和简历 | 用户要模拟面试 | interview session | currentQuestion 可恢复 |
| P1-IMAGE-001 | 支持 JD/Offer/简历截图输入 | 用户发截图 | image intake | 类型和质量判断 |
| P1-MEMORY-001 | 支持私有记忆 | 用户不想重复解释背景 | memory private | owner 可读 |
| P1-ADMIN-001 | Admin 审核用户和团队记忆 | 运营管理用户与知识 | Admin users/memory | 状态读回 |
| P1-EVAL-001 | 关键链路沉淀 eval 样本 | 产品进入持续验证 | eval candidate | 样本可复跑 |

## 4. P2 需求池

| ID | 需求 | 说明 |
|---|---|---|
| P2-DISCOVER-001 | 扩展岗位发现来源 | 首版验证后再扩更多渠道 |
| P2-TRACKER-001 | 投递状态管理 | 可在多页面稳定后补强 |
| P2-ANALYTICS-001 | 求职趋势与复盘 | 依赖足够历史数据 |

## 5. 明确不做

| ID | 不做项 | 原因 |
|---|---|---|
| WONT-001 | 海投机器人 | 产品定位是高质量判断和材料迭代 |
| WONT-002 | 绕过招聘平台风控 | 合规和账号风险高 |
| WONT-003 | 未确认直接改简历 | 简历是用户核心资产 |
| WONT-004 | 默认共享简历、Offer 和薪资 | 涉及高敏隐私 |
| WONT-005 | 把不确定图片当成确定材料 | 会导致误判和误写 |
| WONT-006 | 把治理记录写成交付结果 | 治理证据不能替代产品验收 |
| WONT-007 | 把 SQLite 当成当前主运行口径 | 当前 runtime 是 PostgreSQL + pgvector |

## 6. Ready 条件

进入 POC/MVE 前，每条需求必须满足：

| 条件 | 要求 |
|---|---|
| 用户明确 | 写清谁在什么求职阶段使用 |
| 场景明确 | 写清输入材料和期望结果 |
| 边界明确 | 写清不能发生的风险 |
| 输出明确 | 写清是结论、报告、提案、反馈还是确认动作 |
| 证据明确 | 写清页面、对象、read-back、verifier 或用户判断 |

不合格示例：

- “做一个更智能的 JD 功能。”
- “简历优化体验更好。”
- “Offer 分析要准确。”

合格示例：

- “转型 AI 岗候选人输入目标 JD 后，系统输出投递建议、匹配差距、风险和准备路径，并在 Reports 页面生成可复查报告。”
- “用户要求按 JD 改个人概述时，系统先生成提案和理由，用户确认后才写入目标 section，并读回确认。”

## 7. MVE 主线选择

首版 MVE 选择下面的主线：

```text
Agent Chat 输入 JD
  -> 生成 JD 评估摘要和完整报告
  -> Reports 页面可复查
  -> 用户基于 JD 要求改简历
  -> 系统生成简历提案
  -> 用户确认写入
  -> CV 页面读回目标 section
```

选择理由：

| 理由 | 说明 |
|---|---|
| 高频 | JD 判断和简历修改是求职早期高频需求 |
| 连续 | 能证明 Agent Chat 不是孤立问答 |
| 高价值 | 直接影响投递决策和求职材料 |
| 高风险 | 能验证确认、读回、隐私边界 |
| 可扩展 | 后续自然延伸到面试、Offer、画像和记忆 |

## 8. 给 06-09 的输入

| 输入 | 用途 |
|---|---|
| P0 需求池 | 定义 POC 必须覆盖的能力 |
| P1 需求池 | 定义 POC 可选扩展样本 |
| MVE 主线 | 定义最小可验证体验 |
| 不做项 | 避免 POC 被海投、平台抓取、越权写入带偏 |
| Ready 条件 | 判断样本是否能进入验证 |

结论：05 把调研结果收敛成首版产品路线。06 将围绕 MVE 主线设计多页面 POC。

## 9. 优先级评审样例

需求排序不能只凭感觉。下面是一组简化评分，用来说明为什么 JD -> Reports -> CV proposal 被选为 MVE 主线。

| 需求 | 痛点强度 | 频率 | 风险 | 可验证性 | 首版价值 | 结论 |
|---|---:|---:|---:|---:|---:|---|
| JD 评估报告 | 5 | 5 | 3 | 5 | 5 | P0 |
| 简历提案确认 | 5 | 4 | 5 | 5 | 5 | P0 |
| Offer 分析 | 4 | 3 | 5 | 4 | 4 | P1 |
| 面试一题一答 | 4 | 3 | 3 | 4 | 4 | P1 |
| 自我定位 | 4 | 3 | 4 | 3 | 4 | P0/P1 |
| 投递趋势分析 | 2 | 2 | 2 | 2 | 2 | P2 |
| 海投自动化 | 3 | 4 | 5 | 2 | 1 | 不做 |

评分解释：

- 痛点强度：不解决是否会阻碍用户继续求职。
- 频率：是否在多数目标用户的早期链路中出现。
- 风险：错误执行是否会伤害用户资产或信任。
- 可验证性：是否能用 POC 样本快速证明。
- 首版价值：是否能支撑产品故事。

## 10. 需求冲突处理

首版需求经常互相冲突，必须记录取舍。

| 冲突 | 取舍 | 原因 |
|---|---|---|
| 用户想“一键改简历” vs 产品要求确认 | 保留提案确认 | 简历是核心资产，速度不能压过安全 |
| 用户想上传截图直接执行 vs 低置信需要澄清 | 保留低置信澄清 | 图片识别错误会导致任务串场 |
| 顾问希望沉淀优秀话术 vs 用户隐私默认私有 | 先进入 team_pending | 团队复用必须经过脱敏和审核 |
| Demo 想展示更多功能 vs MVE 只验证主线 | 先验证 JD-CV 主线 | 主线成立后再扩展 Offer/Interview/Profile |
| Admin 想看完整运行上下文 vs 用户隐私保护 | 展示摘要和必要证据 | 治理需要可复查，不需要裸露全部原文 |

这些取舍是产品判断的核心：产品经理不是把需求都收进来，而是决定哪些边界必须先立住。
