# 13 页面功能验证与可行性分析

本篇是多页面产品化阶段的收口：基于 10-12 的开发与测试结果，判断“Agent Chat + 多页面工作台”是否足以支撑首版 Demo，并为后续 Agent-first 设计提供依据。

可行性分析用于判断页面形态是否承接了产品价值：用户是否能从自然语言进入任务，结果是否能沉淀为业务资产，页面是否能让用户继续使用这些资产。

## 分析范围

| 范围 | 判断问题 |
|---|---|
| Agent Chat | 是否能作为统一主入口 |
| JD 与 Reports | JD 评估是否能生成可复查报告 |
| CV | 简历查询、草稿、确认、写入是否清晰 |
| Offer | Offer 是否有独立对象、报告和对比路径 |
| Interview | 面试准备是否能保持长任务状态 |
| Profile 与记忆 | 自我定位是否能形成可追溯的画像信号 |
| Admin | 用户、记忆和关键记录是否可管理 |

## 可行性证据

| 证据类型 | 说明 |
|---|---|
| 页面链路 | 用户从 Agent Chat 到业务页面再回到 Agent Chat 的路径 |
| 数据读回 | report、CV section、Offer report、interview state、memory item |
| 权限验证 | user scope、pending/member/admin 边界 |
| 工具证据 | 48 个工具调用的 effect、taskType、agentAllowlist、read-back/verifier |
| 页面状态 | 刷新、切页、继续任务后的状态一致性 |
| 用户理解 | 工具卡片、差异、确认、空态和错误态是否可理解 |

没有证据的判断只能作为待确认假设，不能写成阶段结论。

## 产品可行性

| 维度 | 可行表现 | 不成立表现 |
|---|---|---|
| 主入口 | 用户能在 Agent Chat 发起核心求职任务 | 用户必须记住每个页面和内部工具名 |
| 资产承接 | 结果进入 Reports、CV、Compare、Interview、Profile | 结果只停留在聊天里 |
| 用户控制 | 简历、画像、团队记忆等高价值动作有确认 | 系统绕过确认改动核心资产 |
| 可复查 | 报告、proposal、Offer、面试状态能按 ID 找回 | 页面无法定位刚才生成的结果 |
| 可继续 | 从页面回到 Agent Chat 仍围绕同一对象 | 系统重新开始或猜测“刚才那个” |

判断：多页面产品形态具备继续进入首版 Demo 的基础。它已经把 MVE 的单条价值链扩展为可复查、可确认、可继续的产品工作台。

## 技术可行性

| 支点 | 当前作用 |
|---|---|
| 6 个业务 agent | 覆盖 general/evaluate/resume/interview/profile/offer |
| Orchestrator | 内部分类、路由、任务约束，不对外作为业务 agent |
| 48 个工具 | 支撑读取、写入、导出、面试、记忆和 Admin 管理 |
| PostgreSQL + pgvector | 当前 runtime 和事实源 |
| SQLite | 只作 fallback/archive/migration |
| read-back/verifier | 证明写入结果，而不是依赖接口口头成功 |
| session state | 支撑跨页恢复和长任务 |

技术可行性的核心不是工具数量，而是工具是否能被任务边界和读回证据约束。

## 页面可行性判断

| 页面 | 判断 |
|---|---|
| `/agent` | 可作为主入口，但必须持续强化任务路由和工具卡片可读性 |
| `/evaluate/reports` | 可承接 JD 报告，并能作为后续简历优化和面试准备的上下文 |
| `/cv` | 可承接简历资产，前提是查询、草稿、确认、写入分离 |
| `/compare` | 可承接 Offer 分析，前提是 Offer 对象不与 JD 对象混淆 |
| `/interview` | 可承接长任务，前提是材料绑定和当前题目持久化 |
| `/profile` | 可承接自我定位，前提是画像信号有来源和撤回路径 |
| `/admin/*` | 可支撑管理需求，但不替代用户侧业务页面 |

## 进入 Demo 的条件

进入首版 Demo 前，需要固定以下条件：

1. 至少一条完整链路可以从 Agent Chat 进入 JD 评估，再进入 Reports。
2. 至少一条链路可以从报告上下文进入简历 proposal，并在 `/cv` 完成确认。
3. Offer、Interview、Profile 至少有明确的对象、页面和继续路径。
4. 写入动作都有 read-back/verifier。
5. PostgreSQL + pgvector 被明确写成当前 runtime。
6. SQLite 只保留 fallback/archive/migration 角色。
7. Orchestrator 只作为内部编排说明，不被宣传为业务 agent。

## 阶段结论

多页面产品化阶段的结论是：

```text
Agent Chat 负责理解和推进任务；
页面负责承接业务资产；
PostgreSQL + pgvector 负责保存当前事实；
read-back/verifier 负责证明写入；
Admin 负责管理用户、记忆和关键记录。
```

这个结论支撑 14-16 的首版 Demo 验证，也为 17-20 的 Agent-first 设计提供输入。

## 可行性评分样例

多页面阶段结束时，需要把“感觉可行”写成可比较的评分。

| 维度 | 分值 | 判断依据 | 下一阶段关注 |
|---|---:|---|---|
| 主入口自然度 | 4/5 | 用户能从 Agent Chat 发起 JD、简历、Offer、面试任务 | 降低低置信任务误路由 |
| 页面承接 | 4/5 | Reports、CV、Compare、Interview、Profile 都有明确资产 | 增强跨页返回 Agent 的上下文 |
| 写入可信 | 4/5 | 简历 apply、报告保存等有 read-back | 扩展到导出、Admin 和记忆晋升 |
| 长任务连续性 | 3/5 | 面试和定位能保存状态，但依赖稳定 session | 强化 interview state 和 guided state |
| 隐私边界 | 4/5 | userId scope 和默认私有口径明确 | 全量验证 memberA/memberB 对照 |
| 扩展空间 | 5/5 | Offer、Tracker、Analytics 可自然加入 | 避免首版过早扩张 |

结论示例：多页面形态具备进入 Agent-first 的基础，因为页面已经承接了核心业务资产；下一阶段要解决的是任务路由、工具约束、跨页状态和记忆治理。

这份输出让 13 不只是“评估页面”，而是明确把产品推进到 14-20 的依据。
