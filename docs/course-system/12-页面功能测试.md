# 12 页面功能测试

页面功能测试的目标是证明多页面产品形态可以承接 MVE 之后的真实工作流。测试不只看页面是否渲染，而是看用户从 Agent Chat 发起任务后，结果能否落到正确页面、正确对象、正确权限范围，并且写入有 read-back/verifier 证据。

## 测试目标

| 目标 | 说明 |
|---|---|
| 工作流成立 | Agent Chat 能发起 JD、简历、Offer、面试、自我定位任务 |
| 页面承接成立 | 业务资产能进入 CV、Reports、Compare、Interview、Profile、Admin |
| 数据可信 | PostgreSQL + pgvector 中的对象能按当前用户读回 |
| 权限可信 | pending/member/admin 和 userA/userB 边界由服务端控制 |
| 写入可信 | 保存、apply、导出、Admin 操作都有 read-back 或 verifier |
| 状态可信 | 刷新、切页、回到 Agent 后关键上下文不丢 |

## 测试分层

| 层级 | 关注点 | 示例 |
|---|---|---|
| 页面结构 | 入口、按钮、空态、加载态、错误态 | `/agent` 有输入区、工具卡片、待确认区 |
| 业务路由 | 用户表达是否进入正确 taskType 和 agent | Offer 截图进入 `offer`，不是 `evaluate` |
| API 与数据 | 服务端权限、数据读写、read-back | `resume_edit` apply 后读回目标 section |
| 页面联动 | Agent 与业务页面的上下文传递 | Reports -> Agent -> CV 保持同一 JD 上下文 |
| 长任务状态 | 面试、自我定位、待确认动作可恢复 | 刷新后 currentQuestion 仍存在 |
| Admin 管理 | 用户、记忆、运行证据可被管理 | Admin 操作后状态读回 |

## 主链路测试

| ID | 链路 | 必须看到的结果 |
|---|---|---|
| PAGE-01 | Agent Chat -> JD 评估 -> Reports | 生成 report/JD，Reports 页面可按 ID 展示 |
| PAGE-02 | Reports -> Agent Chat -> 简历 proposal -> CV | `resume` agent 创建 proposal，CV 页面展示差异 |
| PAGE-03 | CV apply -> read-back | 用户确认后目标 section 读回一致 |
| PAGE-04 | Agent Chat -> Offer 分析 -> Compare | Offer 对象和报告进入 Compare，不进入 JD 报告 |
| PAGE-05 | Agent Chat -> 面试准备 -> Interview | 绑定 JD 与简历快照，当前题目可继续 |
| PAGE-06 | Agent Chat -> 自我定位 -> Profile | 形成画像信号候选，来源和置信度可见 |
| PAGE-07 | Admin memory 操作 | 审批、拒绝、归档后状态读回 |
| PAGE-08 | userA/userB 隔离 | CV、report、Offer、memory 不串用户 |

## 页面测试地图

| 页面 | 测试重点 |
|---|---|
| `/agent` | 文本输入、图片输入、任务路由、工具卡片、待确认动作、跨页恢复 |

## 关键断言

| 场景 | 断言 |
|---|---|
| 简历查询 | 不创建 proposal，不触发 apply，不出现保存成功话术 |
| 简历修改 | 先有 proposal，用户确认后才写入 |
| JD 报告保存 | report/JD 在 PostgreSQL 当前路径下可读回 |
| Offer 识别 | Offer 不被当成 JD |
| 图片低置信 | 进入澄清或重传，不直接写入业务对象 |
| 面试继续 | “继续”恢复当前题目，不把“继续”当作答案 |
| 自我定位 | JD 要求不写成用户长期画像 |
| Admin 操作 | 操作后页面状态与数据库读回一致 |
| 权限隔离 | userA 不能读取 userB 的业务资产 |

## Read-back 与 Verifier 检查

写入动作不能只靠接口返回 `success: true`。

| 写入动作 | 证据 |
|---|---|
| 保存 JD 报告 | `reportId`、`jdId` 可按当前用户读回 |
| 应用简历 proposal | 目标 section hash 或等价内容一致 |
| 保存 Offer report | `offerReportId` 可读回，Compare 页面可见 |
| 更新面试状态 | `interview_state_json` 可恢复当前题目 |
| 写入画像信号 | 来源、类型、置信度、可撤回路径存在 |
| 导出文件 | 文件存在，size > 0，路径或 hash 可验证 |
| Admin 管理动作 | 状态、可见性或索引标记读回一致 |

## 通过标准

页面功能测试通过时，应满足：

1. Agent Chat 是可用主入口。
2. JD、简历、Offer、面试、自我定位、记忆、Admin 都有页面承接。
3. 6 个业务 agent 的任务边界在主链路中能被验证。
4. Orchestrator 保持内部编排角色。
5. 48 个工具调用受任务与 agent 边界约束。
6. PostgreSQL + pgvector 是当前 runtime；SQLite 只作 fallback/archive/migration。
7. 写入成功有 read-back/verifier 证据。
8. 用户切换页面后能继续同一业务对象。

## 关键测试步骤样例

页面测试要记录真实路径、对象 ID、页面状态和读回证据。

| caseId | 操作步骤 | 预期证据 |
|---|---|---|
| PAGE-JD-001 | 登录 memberA -> 打开 Agent Chat -> 粘贴 JD -> 生成报告 -> 打开 Reports | Reports 中出现当前用户报告，reportId 可读回 |
| PAGE-CV-001 | 从 Reports 点击“基于此报告改简历” -> 生成 proposal -> 打开 CV | CV 页面出现 pending proposal，包含目标 section、原文和建议 |
| PAGE-CV-002 | 点击确认应用 proposal -> 刷新 CV | 目标 section 内容保持一致，read-back 通过 |
| PAGE-OFFER-001 | 在 Agent Chat 粘贴 Offer -> 打开 Compare | Offer 字段和风险进入 Compare，不进入 Reports |
| PAGE-INT-001 | 基于 JD 开始面试 -> 回答一题 -> 刷新页面 | currentQuestion 和 transcript 可恢复 |
| PAGE-ISO-001 | memberA 生成报告后切换 memberB | memberB 看不到 memberA 报告 |

每个 case 都要保留“账号、输入、对象 ID、页面状态、读回证据”。没有对象 ID 的测试记录很难复查。

## 页面状态检查清单

页面测试除了主链路，还要看状态是否完整。

| 状态 | 要检查什么 | 示例 |
|---|---|---|
| 空状态 | 没有数据时是否告诉用户下一步 | Reports 无报告时引导输入 JD |
| 加载中 | 是否避免重复提交和误点 | CV proposal apply 时按钮进入处理中 |
| 成功态 | 是否有对象 ID 或读回证据 | “已应用”旁边能对应 proposalId |
| 待确认 | 用户是否能确认、取消、查看理由 | 简历 proposal 显示原文和建议 |
| 失败态 | 是否说明原因和下一步 | 图片低置信要求重传或粘贴文字 |
| 权限态 | 是否区分未登录、待审批、无权限 | pending 不进入业务页面 |
| 恢复态 | 刷新后能否恢复业务对象 | Interview 继续 currentQuestion |

这些状态决定页面能不能承接真实用户，而不是只在理想输入下成立。

## 测试数据准备

页面测试前要准备稳定数据，否则测试很容易变成随手点页面。

| 数据 | 准备要求 |
|---|---|
| memberA 简历 | 包含个人概述、项目经历、技能等 section |
| memberA JD | 至少一份 AI 产品经理 JD |
| memberA Offer | 包含薪资、试用期、福利、地点 |
| memberB 数据 | 与 memberA 明显不同，用于隔离对照 |
| pending 用户 | 用于验证待审批页面和 API 阻断 |
| admin 用户 | 用于验证 Admin 页面读回 |

这些数据让页面测试能覆盖主链路、权限和跨用户边界。
