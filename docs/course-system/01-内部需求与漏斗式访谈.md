# 01 内部需求与漏斗式访谈

本篇是 Zhiyuan 求职助手从 0 到 1 的起点。此时产品还没有被定义成页面、Agent 或工具，内部要先回答三个问题：为什么现在需要一个 AI 求职助手，第一批用户是谁，首版应该解决哪一段求职链路。

“内部需求”是产品团队在立项前形成的共同判断：用户的真实困境是什么，现有替代方案为什么不够，哪些材料用户愿意交给系统，哪些动作必须由用户确认，哪些能力首版坚决不做。

## 1. 产品机会

AI 求职工具已经成为求职者的新基础设施。LinkedIn 2026 研究显示，81% 的人已经或计划在求职中使用 AI，48% 认为 AI 工具能提升面试信心；Indeed 的 Career Scout 也把职业路径匹配、简历定制、面试准备和岗位探索放进 AI career coach。这里的市场机会不是“用户会不会用 AI”，而是“用户能不能得到可信、连续、不会伤害个人资产的 AI 求职协助”。

Zhiyuan 选择的切入点不是海投，也不是替用户绕过招聘平台，而是围绕高质量求职决策建立一个 Agent-first 工作台：

```text
用户带来真实求职材料
  -> Agent Chat 理解任务
  -> JD、简历、Offer、面试、定位、记忆链路分别承接
  -> 结果落到页面和数据对象
  -> 高风险写入必须确认、读回、可复查
```

首版产品假设：求职者愿意把 JD、简历、Offer、面试问题和职业经历交给系统，但前提是系统不编造、不越权、不把草稿当成保存、不把个人隐私变成公共知识。

## 2. 目标用户

| 用户 | 当前状态 | 核心困境 | 首版机会 |
|---|---|---|---|
| 正在投递的求职者 | 有简历，有目标岗位，投递选择多 | 不知道 JD 是否值得投，简历是否对岗 | JD 评估、差距分析、投递建议 |
| 转型 AI 岗候选人 | 有过往 C 端、运营、产品或项目经验 | 不知道如何把经历转成 AI 岗表达 | 自我定位、能力画像、简历表达主线 |
| 正在改简历的候选人 | 有目标 JD，需要修改个人概述或项目经历 | 害怕 AI 编造经历、改错位置、覆盖原文 | 简历提案、差异展示、确认写入 |
| Offer 候选人 | 拿到一个或多个 Offer | 不确定薪资结构、风险、谈判空间 | Offer 字段抽取、风险判断、谈判问题 |
| 面试准备用户 | 有 JD 和简历，即将面试 | 不知道会被追问什么，回答是否对岗 | 一题一答、反馈、材料绑定 |
| HR/面试官视角 | 关注真实匹配和表达可信 | 反感夸大、套话、AI 味过重 | 真实性约束、证据不足提示 |
| 求职辅导顾问 | 需要稳定判断标准和历史材料 | 重复做 JD 分析、简历建议和面试反馈 | 报告沉淀、记忆复用、参考材料治理 |
| 运营/管理员 | 管理用户、记忆、复盘材料 | 需要审批、审核、问题沉淀 | Admin 用户审批、记忆审核、run/review |

## 3. 用户现在怎么解决

| 现有方式 | 用户做法 | 问题 |
|---|---|---|
| 通用聊天机器人 | 把 JD、简历粘贴进去问“能投吗” | 结论难复查，容易上下文丢失，保存和写入没有证据 |
| 简历模板网站 | 套模板、改措辞 | 不能针对具体 JD 判断，也不能维护长期求职资产 |
| 求职顾问 | 人工看 JD、改简历、模拟面试 | 成本高、反馈周期长，历史材料难沉淀 |
| 招聘平台 | 查岗位、投递、看状态 | 只解决岗位入口，不解决是否值得投、如何准备 |
| 表格和本地文档 | 自己记录岗位、Offer、面试问题 | 材料分散，无法形成连续分析和记忆 |

因此 Zhiyuan 的核心机会不是“再做一个 AI 问答框”，而是把求职材料、AI 判断、页面资产、确认写入和长期记忆放在同一条产品链路里。

## 4. 漏斗式访谈目标

漏斗式访谈要从用户的一句模糊表达一路追到可进入需求池的事实。

```text
模糊表达
  -> 求职阶段
  -> 输入材料
  -> 当前替代方案
  -> 期望输出
  -> 信任边界
  -> 隐私边界
  -> 成功证据
  -> 首版需求
```

访谈不是问“你想要什么按钮”，而是问：

| 层级 | 要确认的问题 | 形成的产品判断 |
|---|---|---|
| 用户是谁 | 正在选岗、改简历、面试、谈 Offer，还是做职业定位 | 决定首版用户优先级 |
| 为什么现在需要 | 哪个环节卡住了，不解决会损失什么 | 判断痛点强度 |
| 现在怎么解决 | 用 ChatGPT、顾问、模板、招聘平台还是自己记录 | 找到替代方案缺口 |
| 愿意给什么材料 | JD、简历、Offer、截图、面试回答、经历描述 | 决定输入能力 |
| 希望看到什么 | 结论、报告、提案、问题清单、面试反馈 | 决定输出形态 |
| 最怕什么 | 编造、误写、隐私泄露、误判、假成功 | 决定安全和确认机制 |
| 如何确认成功 | 页面可见、报告编号、草稿可确认、保存可读回 | 决定验收证据 |

## 5. 首轮访谈问题

### 求职者

- 你最近一次犹豫要不要投某个岗位，是因为什么？
- 你判断一个 JD 是否适合自己时，最缺哪类信息：匹配度、风险、能力差距、准备路径，还是投递优先级？
- 你通常会把 JD 发给谁看？现在得到的反馈哪里不够？
- 如果 AI 给你一个“建议投/谨慎投/不建议投”的结论，你还需要看到哪些理由才会相信？
- 你希望报告保存在聊天里，还是进入一个可复查的报告页？

### 简历修改用户

- 你让别人改简历时，最担心什么：夸大、改错重点、表达不像自己，还是覆盖原文？
- 哪些内容可以让 AI 改写，哪些内容必须先问你？
- 你希望按整份简历确认，还是按个人概述、项目经历、技能等 section 确认？
- 你需要看到“为什么这样改”吗？
- 如果改完后发现不合适，你需要撤回到哪个版本？

### Offer 候选人

- 你拿到 Offer 后最想先判断什么：钱是否合理、风险、成长、团队、城市，还是谈判空间？
- Offer 里哪些字段你经常看不懂或拿不准？
- 你希望系统直接给结论，还是先告诉你还缺哪些信息要问 HR？
- 你愿意把薪资、公司、岗位信息保存到系统里吗？哪些字段必须私有？

### 面试准备用户

- 你准备面试时，最缺的是题目、反馈、追问，还是表达结构？
- 你希望系统一次给很多题，还是一题一答？
- 你的回答能否被保存成后续复盘材料？
- 你是否希望面试问题绑定某个 JD 和当前简历版本？

### 转型 AI 岗候选人

- 你说“不知道适合什么方向”时，具体是不懂岗位、不懂表达，还是不确定能力是否匹配？
- 你过去最能证明能力的经历是什么？
- 哪些偏好和约束需要长期记住：城市、薪资、行业、工作方式、岗位类型？
- 哪些自我判断不希望被系统长期保存？

## 6. 内部共识

| 共识 | 产品含义 |
|---|---|
| Agent Chat 是主入口 | 用户不必先理解页面结构，可以用自然语言进入任务 |
| 页面承接业务资产 | JD 报告、简历提案、Offer、面试进度、画像和记忆必须可复查 |
| 首版围绕高价值决策 | 先做 JD 判断、简历提案、Offer 判断、面试准备和定位，不做海投 |
| 写入必须确认 | 简历、画像、记忆、Offer 等高风险对象不能由模型直接改 |
| 成功必须有证据 | 保存、应用、审批、导出都需要 read-back 或 verifier |
| 隐私默认私有 | 简历、薪资、Offer、画像、面试记录默认归当前用户 |

## 7. 首版边界

| 做 | 不做 |
|---|---|
| JD 文本/截图分析 | 海投机器人 |
| 简历只读查询和修改提案 | 未确认直接改简历 |
| Offer 字段抽取和谈判建议 | 默认公开薪资和 Offer |
| 一题一答面试准备 | 一次生成大量泛题后不跟进 |
| 自我定位和画像信号 | 把单次情绪化表达写成长期画像 |
| 私有记忆和审核后的团队知识 | 未审核共享用户原文 |
| Admin 用户审批、记忆审核、run/review | 把治理记录当成问题已经解决 |

## 8. 阶段产物

本篇产出的是产品起盘共识：

| 产物 | 内容 |
|---|---|
| 产品机会 | AI 求职助手要解决“可信连续求职协助”，不是简单问答 |
| 目标用户 | 求职者、转型候选人、Offer 候选人、面试准备用户、顾问和管理员 |
| 替代方案分析 | 通用 AI、顾问、模板、招聘平台和表格的不足 |
| 访谈漏斗 | 从动机追到材料、输出、风险、隐私和成功证据 |
| 首版边界 | 明确做 JD、简历、Offer、面试、定位、记忆、Admin，不做海投和越权写入 |

结论：01 的作用是把 Zhiyuan 从“想做 AI 求职助手”推进到“知道为谁做、为什么做、首版做什么、不做什么”。02 将把这些用户需求进一步映射为业务对象和产品链路。

## 10. 一轮完整访谈样例

下面是一轮可放进产品立项材料的访谈记录。它不是问卷，而是从用户的一句含糊表达追到可进入需求池的产品事实。

| 访谈层级 | 访谈内容 | 产品侧记录 |
|---|---|---|
| 开场 | 用户：“我最近在看 AI 产品岗位，但不知道自己能不能投。” | 用户处于转型投递前期，动机强，材料可能包括 JD 和旧简历 |
| 现状 | 用户：“我会把 JD 丢给 ChatGPT 问适不适合，但问完就找不到了。” | 替代方案是通用 AI；缺口是可复查、可继续 |
| 决策压力 | 用户：“如果投错会浪费时间，也怕简历改得不像自己。” | 痛点不是生成文字，而是投递判断和材料风险 |
| 输入材料 | 用户愿意提供 JD、当前简历、项目经历，但不愿默认公开薪资和 Offer | 输入能力要支持文本、截图、私有材料 |
| 输出期待 | 用户想看到“能不能投、差距、怎么改简历、面试怎么准备” | JD 报告要能自然接到简历和面试 |
| 风险边界 | 用户强调“不要编经历，改简历前先给我看” | 简历链路必须 proposal -> confirm -> apply |
| 成功证据 | 用户希望报告有编号，简历改完能看到原文和改后差异 | Reports/CV 页面承接，写入后 read-back |

这轮访谈最终沉淀出三条 P0 判断：

1. JD 评估是最适合的首个入口，因为用户已经有明确材料和明确决策压力。
2. 简历修改不能直接写入，必须先生成提案和差异说明。
3. 结果必须落到页面，不能只存在对话历史里。

## 11. 从访谈到需求的转译

产品早期最容易犯的错，是把用户原话直接写成功能。Zhiyuan 的转译方式是先找“行为、材料、风险、证据”。

| 用户原话 | 不能直接写成 | 应转译为 |
|---|---|---|
| “帮我看看这个岗位能不能投” | 做一个岗位匹配按钮 | 输入 JD 后生成投递建议、匹配差距、风险和准备路径，并保存为报告 |
| “帮我改一下简历” | AI 一键改简历 | 生成目标 section 的修改提案，用户确认后写入，并读回目标 section |
| “我不知道自己适合什么方向” | 给用户推荐岗位 | 通过 guided session 梳理经历、目标、偏好和约束，形成画像信号候选 |
| “这个 Offer 靠谱吗” | Offer 评分 | 抽取薪资、福利、试用期、风险和缺失字段，输出谈判问题 |
| “帮我模拟面试” | 生成一组题 | 绑定 JD 和简历快照，一次推进一个问题并保存面试状态 |

这套转译方式让内部需求不再停留在“用户想要 AI 帮忙”这种空泛表达，而是进入可设计、可验证、可交付的产品对象。
