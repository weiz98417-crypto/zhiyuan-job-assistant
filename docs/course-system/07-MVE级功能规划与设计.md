# 07 MVE 级功能规划与设计

MVE 是 Minimum Viable Experience，最小可验证体验。它不是最少代码，也不是最少页面，而是用最短链路证明用户能完成一件有价值的求职任务，并愿意继续使用。

Zhiyuan 的 MVE 选择“JD 评估 -> 简历提案 -> 页面复查 -> 确认写入”作为主线，因为这条链路同时覆盖求职决策、材料迭代、页面承接和可信写入。

## 1. MVE 目标

| 目标 | 说明 |
|---|---|
| 证明入口成立 | 用户可以从 Agent Chat 发起求职任务 |
| 证明结果有价值 | JD 报告能帮助用户判断是否投递 |
| 证明产品不只是聊天 | 完整报告落到 Reports 页面 |
| 证明高风险写入可控 | 简历修改先提案，确认后写入 |
| 证明成功可验证 | 保存、应用、审批都有 read-back 或 verifier |

## 2. MVE 主线

```text
用户输入 JD
  -> Agent Chat 识别 JD 评估
  -> 生成投递建议、差距、风险、准备路径
  -> 保存为 JD 报告
  -> 用户基于报告要求改简历
  -> 系统生成简历提案
  -> 用户确认
  -> 写入目标 section
  -> 读回确认
```

## 3. 功能切片

| 切片 | 包含 | 不包含 |
|---|---|---|
| Agent Chat | 文本输入、图片入口、任务识别、工具状态、错误提示 | 替用户投递 |
| JD 评估 | 文本/截图识别、摘要、完整报告、报告保存 | 全网岗位抓取 |
| Reports | 报告列表、详情、继续追问入口 | 复杂 BI 分析 |
| CV | 当前简历查询、提案、确认写入、回滚 | 未确认改写 |
| Profile | 简单定位引导和信号记录 | 一次性生成终身职业规划 |
| Admin | 用户审批、记忆审核、运行复盘入口 | 复杂运营系统 |

## 4. 用户体验草图

### 4.1 JD 入口

用户可以直接说：

```text
帮我评估这个 AI 产品经理岗位是否值得投。
```

系统应先给短结论，再提供完整报告入口：

- 投递建议：建议投 / 谨慎投 / 不建议投。
- 匹配理由：结合 JD 要求和用户经历。
- 差距：缺少哪些经历或表达。
- 风险：硬性要求、行业、薪资、地点、经验不匹配。
- 下一步：是否改简历、准备哪些面试问题。

### 4.2 简历提案

用户继续说：

```text
基于这个 JD，帮我改个人概述，先给草稿。
```

系统只能生成 proposal：

- 目标 section。
- 原文。
- 建议文案。
- 改动理由。
- 是否包含新增事实。
- 确认 / 丢弃。

### 4.3 写入确认

用户确认后才能 apply。成功口径不是“模型说已保存”，而是：

- 写入目标 section。
- 读回目标 section。
- hash 或内容一致。
- CV 页面刷新后可见。

## 5. 数据设计口径

| 对象 | 说明 |
|---|---|
| `sessions` | 保存 Agent 对话和当前任务 |
| `reports` / `jds` | 保存 JD 报告和原始岗位材料 |
| `cv_data` | 保存当前用户简历 |
| `resume_edit_proposals` | 保存待确认简历提案 |
| `agent_runs` / `agent_run_steps` | 保存运行过程和工具调用证据 |
| `memory_items` | 保存私有或审核后的记忆 |

当前运行口径是 PostgreSQL + pgvector；SQLite 只作为 fallback、archive、migration source。

## 6. MVE 验收

| 验收项 | 通过标准 |
|---|---|
| JD 输入 | 用户输入文本或清晰截图后进入 JD 评估 |
| 报告生成 | 聊天里有摘要，Reports 页面有完整报告 |
| 简历查询 | 只读查询不创建 proposal |
| 简历提案 | 修改请求生成 proposal，不直接写入 |
| 用户确认 | 未确认不改简历 |
| 写入读回 | 确认后目标 section read-back |
| 隐私隔离 | 当前用户只能看自己的简历和报告 |
| 失败表达 | 缺材料、低清图片、写入无证据时不显示完成 |

## 7. 阶段产物

| 产物 | 内容 |
|---|---|
| MVE 主线 | JD 评估到简历提案的连续体验 |
| 功能切片 | Agent、Reports、CV、Admin 的首版范围 |
| 数据对象 | report、JD、CV、proposal、run、memory |
| 验收表 | 输入、输出、页面承接、读回和隐私 |

结论：07 确定了首版可验证体验。08 将把这些体验转换成可执行的 POC 测试集。

## 8. MVE 用户旅程细化

MVE 要讲清楚用户从开始到结束每一步为什么有价值。

| 步骤 | 用户心理 | 产品动作 | 可信证据 |
|---|---|---|---|
| 输入 JD | 我不知道这个岗位值不值得投 | Agent Chat 接收 JD，路由到 `evaluate` | taskType = JD 评估 |
| 查看摘要 | 我想先快速知道结论 | 输出投递建议、匹配点、差距、风险 | 摘要和报告结构一致 |
| 打开报告 | 我想之后还能找回来 | Reports 页面保存完整报告 | reportId/reportNum |
| 要求改简历 | 我想基于这个岗位更对岗 | `resume` 读取报告和当前简历 | 绑定 reportId 和 CV snapshot |
| 查看提案 | 我怕 AI 改坏或编造 | CV 页面展示 proposal 差异 | 原文、建议、理由 |
| 确认应用 | 我认可这次修改 | apply 目标 section | section read-back |

MVE 的价值不是覆盖所有功能，而是用这条链路证明“AI 判断 + 页面资产 + 用户确认 + 数据证据”可以成立。

## 9. MVE 不纳入项的原因

| 暂不纳入 | 原因 | 后续进入方式 |
|---|---|---|
| 多 Offer 对比 | 需要更多高敏字段和比较规则 | P1 扩展到 Compare |
| 完整面试题库 | 容易变成泛内容 | 先做一题一答和状态绑定 |
| 岗位发现平台 | 牵涉外部来源、去重和更新 | 多页面稳定后进入 Discover |
| 投递数据分析 | 需要历史数据规模 | Tracker/Analytics 阶段进入 |
| 团队知识库 | 涉及脱敏和审核 | Admin/Memory 阶段进入 |

这些不纳入项不是价值低，而是它们不能替代首版主线验证。
