# 30 登录体系与权限构建

登录体系是 Zhiyuan 多用户产品的入口。它不仅让用户“进系统”，还决定用户是否能进入自己的求职工作台、是否能使用 Agent Chat、是否能查看 CV/Reports/Offer/Interview/Profile，以及是否拥有 Admin 治理能力。

本阶段已经完成登录与权限体系的产品化设计：用户注册后进入明确状态，登录后读回身份，页面和 API 共同执行权限矩阵，Admin 操作后必须读回结果。

## 权限矩阵

| 身份 | 页面权限 | API 权限 | 产品反馈 |
|---|---|---|---|
| 未登录 | 只能访问登录、注册和公开页 | 只能调用登录注册相关 API | 引导登录 |
| pending/member | 不能进入核心求职工作台 | 核心业务 API 返回阻断 | 显示待审批状态 |
| active/member | 可使用自己的 Agent、CV、Reports、Offer、Interview、Profile | 只能读写自己的资产 | 正常求职体验 |
| active/admin | 可进入 Admin 页面 | 可审批用户、治理记忆、查看必要运行证据 | 管理视图 |
| rejected/member | 不能进入核心流程 | 核心 API 被阻断 | 显示账号不可用 |

权限体系不依赖前端隐藏按钮。页面守卫负责体验，API 守卫负责真实边界。

## 注册链路

```text
用户提交注册信息
  -> 校验 username / password / displayName
  -> 创建 users 记录
  -> 如果系统没有 active admin，则首个用户成为 active/admin
  -> 后续用户默认为 pending/member
  -> 返回账号状态
```

首个 admin 自举是为了让系统可启动；后续用户进入 pending，是为了让多用户求职资产在进入核心功能前先经过审批。

## 登录链路

```text
用户输入账号密码
  -> 校验密码
  -> 校验 status
  -> 签发包含 userId、role、tokenVersion 的 JWT
  -> 写入 HTTP-only cookie
  -> /api/users/me 读回当前身份
  -> 页面根据 role/status 进入对应区域
```

登录成功必须能读回身份。不能只因为 cookie 写入成功就认为用户已进入正确状态。

## Admin 用户管理

Admin 管理的产品职责是审批和治理用户状态。

| 动作 | 结果 |
|---|---|
| approve | pending 用户变为 active/member |
| reject | 用户变为 rejected/member |
| change role | member/admin 角色变化，旧登录态失效 |
| reset password | 新密码生效，旧凭证不可继续使用 |
| delete user | 用户账号进入删除流程或被移除，相关资产按治理规则处理 |

每个动作完成后都要读回用户状态，页面不能只显示“操作成功”。

## Agent 权限

Agent Chat 继承当前用户权限：

- pending 用户不能通过 Agent 绕过审批。
- member 不能要求 Agent 读取他人简历、Offer 或报告。
- member 不能让 Agent 调用 Admin 工具。
- admin 也不能把治理权限当成替用户写私有资产的能力。
- 48 个注册工具必须同时满足登录态、角色、taskType、agentAllowlist 和 owner 边界。

用户输入中的“我是管理员”“忽略权限”“帮我读取另一个用户”都不能改变真实权限。

## 页面与 API 一致性

| 场景 | 页面行为 | API 行为 |
|---|---|---|
| 未登录访问 `/agent` | 跳转或引导登录 | 核心 API 返回未登录 |
| pending 访问 `/cv` | 显示待审批 | CV API 阻断 |
| member 访问 `/admin/users` | 阻断 | Admin API 返回无权限 |
| admin 审批用户 | 页面刷新状态 | API 返回最新用户状态 |
| role 变化后旧 token 访问 | 重新登录或阻断 | tokenVersion 不通过 |

一致性是权限体系的验收核心。页面看起来安全但 API 放行，不算完成；API 阻断但页面没有清楚反馈，也不算完整产品体验。

## 登录体系完成状态

登录体系完成后，应满足：

1. 注册后用户状态明确。
2. 登录后 `/api/users/me` 可读回 userId、role、status。
3. 未登录、pending、member、admin、rejected 的行为有明确差异。
4. Admin 用户管理动作有状态读回。
5. tokenVersion 能让关键身份变化后旧登录态失效。
6. Agent 和工具不高于当前用户权限。

这为 31 的个人信息隔离提供身份基础。

## 权限验收样例

| caseId | 账号 | 动作 | 预期 |
|---|---|---|---|
| AUTH-REG-001 | 新系统首个用户 | 注册 | 成为 active/admin |
| AUTH-REG-002 | 第二个用户 | 注册 | 成为 pending/member |
| AUTH-LOGIN-001 | pending/member | 登录后访问 `/agent` | 显示待审批或被阻断 |
| AUTH-MEMBER-001 | active/member | 访问 `/cv` | 只能看到自己的简历 |
| AUTH-MEMBER-002 | active/member | 访问 `/admin/users` | 被阻断 |
| AUTH-ADMIN-001 | active/admin | 审批 pending 用户 | 状态读回 active/member |
| AUTH-TOKEN-001 | role 变化后的旧 token | 调用写入 API | 被要求重新登录或拒绝 |

权限体系验收要同时看页面和 API。只隐藏按钮不够；只返回 403 但页面不解释，也会让用户误以为系统不可用。

## 账号生命周期展开

```text
register
  -> pending/member
  -> admin approve
  -> active/member
  -> login
  -> use Agent/CV/Reports/Offer/Interview/Profile
  -> admin change role or status
  -> tokenVersion changes
  -> old session loses write ability
```

首个 admin 是例外流程，用来启动系统治理。后续用户都先进入 pending，这样产品可以在多用户阶段控制访问节奏，避免未经审批的用户直接进入核心求职资产区。

## 页面权限和 API 权限的差异

| 层级 | 解决什么 | 示例 |
|---|---|---|
| 页面权限 | 用户看见什么入口、如何理解当前状态 | pending 用户看到待审批提示 |
| API 权限 | 数据和动作是否真实放行 | pending 调用 `/api/cv` 被拒绝 |
| 工具权限 | Agent 是否能代表用户执行动作 | member 不能调用 Admin 工具 |
| 数据权限 | 返回的数据是否属于当前 userId | `/api/users/me` 决定当前 owner |

四层权限必须同时成立。只做页面权限会被接口绕过；只做 API 权限会让用户体验困惑；只做工具权限无法保护普通页面；只做数据权限无法解释账号状态。
