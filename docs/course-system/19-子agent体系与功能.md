# 19 子 agent 体系与功能

本篇定义 Zhiyuan 的 6 个业务子 agent。这里的“子 agent”不是组织架构，也不是越多越好，而是把求职全生命周期中不同类型的用户任务拆成稳定职责。

产品事实必须保持清楚：Zhiyuan 有 6 个业务 agent：`general`、`evaluate`、`resume`、`interview`、`profile`、`offer`。Orchestrator 是内部编排器，不是第 7 个业务 agent。

## 子 agent 设计原则

| 原则 | 说明 |
|---|---|
| 按用户任务拆分 | 不是按页面或代码模块拆分，而是按 JD、简历、Offer、面试、定位等任务拆分 |
| 一个任务一个主责 | 同一次请求只能有一个主责 agent，避免互相抢写 |
| 高风险动作可确认 | 简历、画像、记忆、Offer 等资产写入前必须确认 |
| 输出落到业务对象 | agent 不能只输出聊天文字，关键结果要进入页面和数据对象 |
| 证据优先 | 写入、审批、导出必须 read-back 或 verifier |

## `general`

`general` 是通用引导 agent，用于处理低风险说明、导航、澄清和无法分类的请求。

适合处理：

- 解释产品能做什么。
- 引导用户上传 JD、简历、Offer 或面试目标。
- 当任务意图不清时提出澄清问题。
- 将用户带到合适页面。

不适合处理：

- 直接修改简历。
- 判断 Offer 细节。
- 写入长期画像。
- 执行 Admin 高风险操作。

示例：

```text
用户：“我想开始准备找 AI 产品经理工作，不知道先做什么。”
general：先澄清用户当前材料，然后建议从 JD 评估或自我定位进入。
```

## `evaluate`

`evaluate` 负责 JD 评估，是首版最重要的业务入口之一。

核心能力：

- 识别 JD 的岗位职责、任职要求和隐性风险。
- 结合用户简历或画像判断匹配度。
- 输出投递建议、差距、准备路径和风险提示。
- 保存可复查报告。

页面承接：

- `/evaluate`
- `/evaluate/reports`
- 后续可进入 `/cv` 或 `/interview`

成功证据：

- 生成 report/JD 对象。
- `reportId` 或 `reportNum` 可读回。
- Reports 页面可复查。

边界：

- 不能把 Offer 当 JD。
- 不能替 `resume` 直接改简历。
- 不能把 JD 要求直接写成用户长期画像。

## `resume`

`resume` 负责简历查询和简历提案。它是高风险 agent，因为简历是用户核心资产。

任务类型分两类：

| 类型 | 行为 |
|---|---|
| `resume_query` | 只读当前简历，不创建 proposal，不出现保存成功话术 |
| `resume_edit` | 生成修改提案，展示差异，等待用户确认后应用 |

页面承接：

- `/cv`

成功证据：

- 查询类：读回当前简历。
- 提案类：proposal 可见。
- 应用类：目标 section read-back 一致。

边界：

- 不编造经历。
- 不绕过用户确认。
- 不把“草稿生成”说成“已保存”。

示例：

```text
用户：“我现在的简历是什么？”
resume：只返回当前简历内容。

用户：“基于这份 JD 改个人概述。”
resume：生成 proposal，并要求用户确认后才写入。
```

## `offer`

`offer` 负责 Offer 分析、比较和谈判建议。

核心能力：

- 抽取公司、岗位、薪资结构、试用期、福利、地点、入职时间。
- 标注缺失字段。
- 提示风险和需要问 HR 的问题。
- 多 Offer 对比。
- 生成谈判策略。

页面承接：

- `/compare`

成功证据：

- `offerId` 或 `offerReportId` 可读回。
- Compare 页面可见。

边界：

- 不伪造公司政策。
- 不给确定法律结论。
- 不默认公开薪资和 Offer。

## `interview`

`interview` 负责面试准备和一题一答。

核心能力：

- 绑定 JD、简历和报告快照。
- 制定当前面试准备目标。
- 一次推进一个问题。
- 根据用户回答给反馈、追问和改进建议。
- 保存当前问题、回答记录和状态。

页面承接：

- `/interview`

成功证据：

- `interview_state_json` 可恢复。
- 当前问题和 transcript 可见。

边界：

- 不生成脱离材料的泛题作为主流程。
- 不把用户临时回答默认写入长期记忆。
- 不在没有 JD 或简历上下文时假装个性化。

## `profile`

`profile` 负责自我定位和画像信号。

核心能力：

- 引导用户梳理职业目标、过往经历、偏好、约束和优势。
- 将稳定信息形成画像信号候选。
- 标注来源、类型、置信度和可见性。
- 支持撤回和更新。

页面承接：

- `/profile`

成功证据：

- 画像信号有来源。
- 可见性明确。
- 用户能查看和撤回。

边界：

- 不把 JD 需求写成用户画像。
- 不把一次情绪表达当长期事实。
- 不默认共享个人经历。

## agent 协作关系

6 个 agent 不是孤立功能，而是在求职链路中自然接力：

```text
evaluate 生成 JD 报告
  -> resume 基于报告生成简历提案
  -> interview 基于 JD 和简历准备面试
  -> offer 分析拿到的 Offer
  -> profile 沉淀长期方向和偏好
  -> general 在不确定处引导和澄清
```

协作依靠稳定对象 ID，而不是靠聊天里模糊的“刚才那个”。

## 子 agent 验收方式

| agent | 验收重点 |
|---|---|
| `general` | 能澄清意图并引导到正确任务 |
| `evaluate` | JD 报告可复查，不能串到 Offer |
| `resume` | 查询和修改分离，提案确认后才写入 |
| `offer` | Offer 私有、字段明确、风险和谈判问题可解释 |
| `interview` | 绑定材料，一题一答，状态可恢复 |
| `profile` | 画像信号有来源、置信度、可见性和撤回路径 |

结论：子 agent 体系的价值不是“多 agent”本身，而是让每类求职任务有清晰主责、边界和证据。

## 子 agent 边界对话样例

| 用户输入 | 应选择 | 不应选择 | 原因 |
|---|---|---|---|
| “我现在的简历是什么？” | `resume` + `resume_query` | `resume_edit` | 这是只读查询，不能生成提案 |
| “这份 JD 能投吗？” | `evaluate` | `general` | 需要结构化 JD 评估和报告 |
| “这份 Offer 怎么谈？” | `offer` | `evaluate` | Offer 是薪资和谈判对象，不是岗位匹配报告 |
| “继续刚才的面试” | `interview` | `general` | 需要恢复 interview state |
| “我适合 AI 产品还是运营？” | `profile` | `evaluate` | 这是定位问题，不是单个 JD 判断 |
| “这个页面在哪里看报告？” | `general` | `evaluate` | 这是导航和说明，不需要业务判断 |

这些样例能帮助建立一个核心认知：子 agent 是产品任务边界，不是模型人格。
