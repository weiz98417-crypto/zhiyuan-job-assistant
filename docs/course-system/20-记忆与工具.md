# 20 记忆与工具

本篇说明 Zhiyuan 为什么需要记忆系统和工具系统。进入 Agent 化后，用户不会只完成一次问答，而会反复带着 JD、简历、Offer、面试反馈和职业偏好回来。系统必须记住该记的，忘掉不该记的，并用工具把业务动作落到真实对象上。

记忆解决“连续性”，工具解决“可执行性”，read-back/verifier 解决“可信性”。

## 记忆的产品职责

记忆不是把对话全部存起来，而是把对后续求职有价值、用户可理解、来源清楚、可撤回的信息沉淀下来。

| 记忆类型 | 示例 | 默认可见性 | 写入条件 |
|---|---|---|---|
| 用户偏好 | 城市、行业、薪资下限、工作方式 | private | 用户明确表达或确认 |
| 职业目标 | 想转 AI 产品、偏海外社交、关注增长方向 | private | 来源清楚，允许更新 |
| 经历信号 | 做过 AI 接待、直播、C 端增长、项目管理 | private | 不能编造，最好来自简历或用户确认 |
| 求职约束 | 不接受加班、不能换城市、薪资不能低于某线 | private | 用户明确表达 |
| 团队知识候选 | 通用 JD 判断标准、简历表达规则 | team_pending | Admin 审核后才能进入 team |

不适合直接进入长期记忆：

- 单次情绪化表达。
- 模型推测。
- 未确认的 JD 要求。
- 面试中的临时回答。
- Offer 中的敏感薪资原文。

## 记忆生命周期

```text
用户表达或业务对象产生信号
  -> agent 判断是否有长期价值
  -> 形成 memory candidate
  -> 标注来源、类型、置信度、可见性
  -> 用户或 Admin 确认
  -> 写入 PostgreSQL + pgvector
  -> read-back
  -> 页面可查看、撤回或归档
```

Profile 页面让用户看到自己的画像信号；Admin 页面用于审核团队知识候选和管理记忆状态。

## 记忆边界

| 场景 | 正确处理 |
|---|---|
| 用户说“我想转 AI 产品” | 可形成职业目标候选，来源为当前对话 |
| JD 写“要求 AIGC 项目经验” | 不能直接写成用户有 AIGC 经验 |
| 用户上传 Offer | 默认只作为私有业务资产，不进入团队知识 |
| 用户回答面试题 | 用于当前 interview session，不默认长期保存 |
| 顾问整理通用建议 | 可作为 team_pending，需 Admin 审核 |

## 工具的产品职责

工具是 Agent 执行业务动作的方式。Zhiyuan 当前有 48 个注册工具，它们必须服务任务合同，而不是自由调用。

工具系统要回答：

- 这个工具能读还是能写？
- 哪个 agent 可以调用？
- 哪些 taskType 可以调用？
- 是否需要用户确认？
- 调用后如何证明成功？
- 结果落到哪个页面或对象？

## 工具分类

| 类型 | 作用 | 风险控制 |
|---|---|---|
| 读取工具 | 查询简历、报告、Offer、面试状态、记忆 | 必须按当前 userId 读 |
| 写入工具 | 保存报告、创建 proposal、应用简历、写入画像 | 需要确认和 read-back |
| 导出工具 | 导出报告或简历文件 | 文件 verifier |
| 记忆工具 | 创建候选、审批、归档、重建索引 | 可见性和状态读回 |
| Admin 工具 | 用户审批、角色管理、运行证据查看 | 只允许 admin，动作后读回 |
| 图片工具 | 识别 JD、Offer、简历等材料类型 | 低置信必须澄清 |

## 工具调用卡片

用户不需要看原始 JSON，但需要理解系统做了什么。

工具卡片应展示：

| 字段 | 说明 |
|---|---|
| 动作名称 | 例如“生成 JD 报告”“创建简历提案” |
| 目标对象 | report、proposal、offer、memory item 等 |
| 状态 | 待确认、执行中、已读回、需要补充信息、失败 |
| 摘要 | 关键结果或下一步 |
| 证据 | reportId、proposalId、section read-back、verifier |
| 用户动作 | 确认、取消、查看页面、继续追问 |

这让 Agent 的执行过程从黑箱变成可理解的产品体验。

## read-back 与 verifier

高价值动作必须用证据结束。

| 动作 | 证据 |
|---|---|
| 保存 JD 报告 | reportId/reportNum 可读回 |
| 创建简历提案 | proposal 可读回并展示差异 |
| 应用简历提案 | 目标 section 内容或 hash 一致 |
| 保存 Offer 分析 | offerReportId 可读回 |
| 更新面试状态 | currentQuestion 和 transcript 可恢复 |
| 写入记忆 | memory item 来源、可见性和状态可读回 |
| 导出文件 | 文件存在、大小有效、路径或 hash 可验证 |

没有 read-back/verifier 时，Agent 只能说明“已生成待确认结果”或“需要重新验证”，不能显示完成态。

## 记忆与工具如何协同

示例链路：

```text
用户输入 JD
  -> evaluate agent 调用 JD 评估工具
  -> 保存 report
  -> read-back reportId
  -> Reports 页面展示
  -> 用户要求改简历
  -> resume agent 读取 report 和 CV
  -> 创建 proposal
  -> 用户确认
  -> 应用 section
  -> section read-back
  -> 如果用户确认“以后我都偏 AI 产品方向”
  -> profile agent 创建私有记忆候选
```

在这条链路里，记忆不是替代工具，工具也不是替代判断。两者共同支撑连续求职。

## 完成状态

记忆与工具设计完成后，Zhiyuan 具备：

1. 用户长期背景可沉淀，但不越界保存隐私。
2. 工具调用可执行，但受 taskType 和 agentAllowlist 约束。
3. 高风险写入可确认。
4. 关键结果可读回。
5. 页面能展示结果、证据和下一步。
6. Admin 能管理团队记忆和关键治理动作。

这为 21-25 的多 agent 系统、编排器、evals 和数据集中测试提供基础。

## 工具卡片样例

用户侧看到的工具卡片要让执行过程可理解。

```text
动作：创建简历修改提案
目标：personal_summary
来源：reportId=rpt_1024 + 当前 CV
状态：待用户确认
证据：proposalId=rep_2048 已读回
下一步：查看差异 / 确认应用 / 放弃
```

Admin 或运行证据中看到的记录可以更完整：

```text
toolName: save_resume_section
agent: resume
taskType: resume_edit
effect: write_proposal
requiresConfirmation: true
targetObject: resume_edit_proposal
readBack: proposal_id_match
visibility: private
```

工具卡片的作用不是暴露技术细节，而是让用户知道系统没有偷偷改动高价值资产。

## 记忆写入样例

| 输入 | 是否进入记忆 | 写入方式 |
|---|---|---|
| “我长期想做 AI 产品，不考虑纯运营岗。” | 是 | private profile preference，来源为用户明确表达 |
| JD 中写“需要 RAG 经验” | 否 | 这是岗位要求，不是用户事实 |
| “这个 Offer 薪资是 28K*14” | 默认否 | 作为私有 Offer 资产，不进入通用记忆 |
| 顾问整理“JD 风险判断框架” | 可进入 | team_pending，Admin 审核后 team 可见 |
| 面试中用户回答失败 | 默认否 | 留在 interview session，不写成长记忆 |
