# 10 多页面整体开发

MVE 通过后，Zhiyuan 进入产品化阶段。这个阶段不是继续堆对话能力，而是把已经成立的主链路落成多页面产品形态：Agent Chat 负责发起和推进求职任务，业务页面负责承接可复查、可确认、可继续使用的业务资产。

多页面的意义在于让求职者不必记住系统内部结构，却能在需要时找到每一类结果：JD 评估报告在哪里、简历草稿在哪里、Offer 对比在哪里、面试进度在哪里、自我定位与记忆在哪里、Admin 管理入口在哪里。

## 阶段定位

| 项目 | 内容 |
|---|---|
| 生命周期位置 | MVE 成立后，进入首版产品化与多页面工作台建设 |
| 主入口 | Agent Chat |
| 业务覆盖 | JD、简历、Offer、面试、自我定位、记忆、Admin |
| Agent 事实 | 6 个业务 agent：`general`、`evaluate`、`resume`、`interview`、`profile`、`offer` |
| 编排事实 | Orchestrator 是内部编排，不作为第 7 个业务 agent |
| 工具事实 | 当前注册 48 个工具，工具调用必须受任务、agent、权限和 read-back/verifier 约束 |
| 数据事实 | PostgreSQL + pgvector 是当前 runtime；SQLite 只作 fallback/archive/migration |
| 成功门槛 | 写入成功必须有 read-back 或 verifier 证据 |

## 为什么需要多页面

MVE 证明的是核心价值可以成立，多页面证明的是这个价值可以被反复使用。Agent Chat 可以让用户用自然语言进入任务，但单靠聊天窗口无法承接所有业务资产。

| 只靠 Agent Chat 的局限 | 多页面承担的产品职责 |
|---|---|
| 结果混在对话历史里，难以复查 | 报告、简历、Offer、面试记录进入对应页面 |
| 高价值写入缺少确认面板 | 页面提供草稿、差异、确认、撤回和状态展示 |
| 长任务切换后容易丢上下文 | 页面和 session 共同保存稳定对象 ID |
| 管理动作不适合暴露在普通对话里 | Admin 页面承接用户、记忆和运行记录管理 |
| 用户需要比较和追踪 | Compare、Tracker、Analytics 承接结构化资产 |

多页面不是分散入口，而是把 Agent Chat 产出的业务对象放到正确位置。

## 页面与业务资产

| 页面 | 承接的业务资产 | 主要职责 |
|---|---|---|
| `/agent` | session、任务状态、工具卡片、待确认动作 | 主入口，理解用户意图，串联任务与页面 |
| `/evaluate` | JD 输入、评估任务 | 接收文本、链接、图片材料，发起 JD 评估 |
| `/evaluate/reports` | JD 报告、JD 记录、追问上下文 | 复查报告、继续追问、导出或进入简历优化 |
| `/cv` | 当前简历、修改 proposal、参考简历 | 展示简历资产，承接草稿、确认、应用、回滚 |
| `/compare` | Offer、Offer report、谈判策略 | 承接 Offer 分析、多 Offer 对比和 HR 问题清单 |
| `/interview` | 面试计划、当前题目、回答记录、反馈 | 绑定 JD 与简历快照，支持一题一答和继续准备 |
| `/profile` | 自我定位、画像信号、长期偏好候选 | 帮用户梳理方向，沉淀可追溯的画像信号 |
| `/discover` | 岗位发现、JD 候选 | 保存岗位，带稳定 ID 进入评估或 Agent Chat |
| `/tracker` | 投递记录、下一步动作 | 跟踪投递阶段、时间线和后续提醒 |
| `/analytics` | 报告、投递、阶段趋势 | 复查求职漏斗和策略效果 |
| `/admin/*` | 用户、记忆、运行记录、评估候选 | 管理权限、记忆可见性和关键证据 |

## 从 Agent Chat 到页面工作流

```text
用户在 Agent Chat 表达目标
  -> Orchestrator 内部判断任务类型
  -> 选择 6 个业务 agent 之一
  -> task contract 限定工具与成功条件
  -> 工具读取或写入业务对象
  -> read-back/verifier 证明结果
  -> 页面承接业务资产
  -> 用户在页面复查、确认或继续追问
```

示例链路：

1. 用户在 `/agent` 输入 JD。
2. `evaluate` agent 生成并保存 JD 评估报告。
3. `/evaluate/reports` 按 `reportId` 展示报告。
4. 用户追问“基于这份 JD 改我的简历”。
5. `resume` agent 创建简历修改 proposal。
6. `/cv` 展示差异，用户确认后写入。
7. 写入后按目标 section read-back，页面展示最终状态。

这条链路把聊天、业务对象、页面确认和数据证据连成一个产品工作流。

## 产品架构

```text
AppShell / AuthGate
  -> 页面路由
  -> 页面组件
  -> API route
  -> Agent task contract
  -> 48 tools
  -> repository-backed data access
  -> PostgreSQL + pgvector
  -> read-back / verifier
```

设计原则：

| 原则 | 说明 |
|---|---|
| Agent Chat 是主入口 | 用户用自然语言发起 JD、简历、Offer、面试、自我定位任务 |
| 页面是资产面板 | 页面展示可复查、可确认、可继续使用的业务对象 |
| 稳定 ID 串联页面 | JD、report、proposal、Offer、interview session 都要有稳定 ID |
| 写入不靠 toast | 保存、apply、导出、Admin 操作都必须能读回或被 verifier 证明 |
| 服务端判定权限 | 页面不能信任前端传入的 userId、role 或 owner |
| SQLite 不做当前主路径 | 当前 runtime 是 PostgreSQL + pgvector，SQLite 只保留 fallback/archive/migration |

## 从 0-1 的开发顺序

| 顺序 | 开发目标 | 验证重点 |
|---|---|---|
| 1 | AppShell、AuthGate、基础路由 | 用户身份、pending/member/admin 边界清晰 |
| 2 | `/agent` 与 JD 评估主链路 | Agent Chat 能触发 `evaluate` 并保存报告 |
| 3 | `/evaluate/reports` | 报告可按当前用户读回，可从报告继续追问 |
| 4 | `/cv` 与简历 proposal | 查询只读，修改先生成草稿，确认后写入 |
| 5 | `/compare` | Offer 进入独立对象，不与 JD 报告混淆 |
| 6 | `/interview` | 绑定 JD 与简历快照，支持继续同一场准备 |
| 7 | `/profile` 与记忆入口 | 自我定位和画像信号有来源、有可见性、有撤回路径 |
| 8 | `/admin/*` | 用户、记忆、运行记录可以被管理和复查 |
| 9 | `/discover`、`/tracker`、`/analytics` | 岗位发现、投递追踪、趋势复查形成完整工作台 |

首版不要求每个页面都做到最终形态，但每个页面必须明确承接什么资产、由谁写入、如何读回、用户在哪里继续操作。

## 完成标准

多页面整体开发完成时，应能说明并验证：

1. 用户可以从 Agent Chat 发起核心求职任务。
2. 每个核心结果都能落到对应页面。
3. 页面之间使用稳定 ID 或 session 状态传递上下文。
4. 高价值写入必须经过确认、read-back 或 verifier。
5. PostgreSQL + pgvector 是当前事实源，SQLite 只保留备用、归档和迁移角色。
6. Admin 可以看到用户、记忆和关键运行证据，但不替代业务页面。

## 页面蓝图展开

多页面整体开发需要先画出“用户从哪里来、资产落到哪里、下一步去哪里”。下面是首版页面蓝图。

| 页面 | 首屏必须让用户看到 | 主要动作 | 下一步入口 |
|---|---|---|---|
| `/agent` | 当前对话、输入框、工具卡片、待确认动作 | 输入 JD/简历/Offer/问题，继续任务 | Reports、CV、Compare、Interview、Profile |
| `/evaluate/reports` | 报告列表、报告详情、投递建议、差距 | 复查、导出、追问、生成简历提案 | Agent Chat、CV、Interview |
| `/cv` | 当前简历、目标 section、pending proposals | 查看、对比、确认、撤回 | Agent Chat、Reports |
| `/compare` | Offer 字段、风险、缺失信息、谈判问题 | 多 Offer 对比、生成问题清单 | Agent Chat、Tracker |
| `/interview` | 当前问题、绑定材料、回答记录、反馈 | 回答、追问、继续下一题 | Agent Chat、Profile |
| `/profile` | 职业目标、偏好、经历信号、记忆候选 | 查看来源、撤回、更新 | Agent Chat、CV |
| `/admin/*` | 用户状态、记忆候选、运行证据 | 审批、审核、读回状态 | Admin 子页面 |

这个蓝图能支撑开发拆分：每个页面都不是孤立视图，而是同一条求职任务链路里的资产面板。
