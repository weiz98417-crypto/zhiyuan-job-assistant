# 编排器开发

编排器是 Zhiyuan Agent runtime 的内部控制层。它把 Agent Chat 的自然语言、图片和页面上下文转成确定的业务任务，并把任务交给 6 个业务 agent。编排器不直接评估 JD、不改简历、不保存 Offer，也不对外展示成一个业务 agent。

## 输入模型

编排器每次接收的不只是 `content`：

| 输入 | 用途 |
|---|---|
| `content` | 用户本轮文本 |
| `sessionId` | 当前 Agent Chat 会话 |
| `activeTask` | 上一轮未完成任务 |
| `agentHint` | 页面或用户显式选择的 agent |
| `imageIntake` | 图片识别结果：JD、Offer、resume、unknown |
| `targetRefs` | 当前页面带入的 `jdId/reportId/offerId/proposalId/sessionId` |
| `currentUser` | 服务端身份和角色 |

这些输入共同决定 task contract。不能只凭最近一条消息猜测业务对象。

## 处理顺序

```text
读取 session 与 activeTask
  -> 处理图片 documentType 与置信度
  -> 判断是否继续、取消或切换 activeTask
  -> classifyIntent 选择业务 agent
  -> routeAgentTask 生成 taskType
  -> createTaskContract
  -> 计算 allowedTools
  -> 返回澄清、阻断或可执行计划
```

顺序很重要。图片冲突、active task 和权限状态都可能阻断工具执行。

## 意图分类

`classifyIntent(content)` 只负责选择业务 agent：

| 意图 | agent |
|---|---|
| 普通解释、导航、兜底 | `general` |
| JD 评估、岗位匹配 | `evaluate` |
| 简历查询、改写、proposal | `resume` |
| 面试准备、继续、评分 | `interview` |
| 自我定位、画像、长期偏好 | `profile` |
| Offer 解析、对比、谈判 | `offer` |

`offer` 的优先级要能覆盖“评估 Offer”“谈薪”“薪资福利”等表达，避免落入 JD 评估。`general` 是兜底，不是万能权限。

## Task Routing

`routeAgentTask` 负责从 agent 和上下文生成 `taskType`。

| 场景 | taskType |
|---|---|
| 查看当前简历 | `resume_query` |
| 生成简历修改草稿 | `resume_edit` |
| 应用或回滚简历 proposal | `resume_edit_apply` / `resume_edit_rollback` |
| 评估 JD | `jd_evaluation` |
| 查看 JD 报告 | `jd_report_query` |
| 评估 Offer | `offer_evaluation` |
| 面试开始或继续 | `interview_coaching` |
| 自我定位引导 | `career_positioning_guidance` |
| 写入画像信号 | `profile_update` |
| 导出文件 | `file_export` |
| Admin 审批或管理 | `admin_verified_action` |

只读和写入必须拆开。用户说“看看”时不应产生 proposal；用户说“保存”也要经过确认和 read-back/verifier。

## 图片路由

图片输入先进入 image-intake：

- `documentType=JD`：进入 JD 评估或 JD 追问。
- `documentType=Offer`：进入 Offer 评估或谈判建议。
- `documentType=resume`：进入简历解析、预览或 proposal，不直接覆盖当前简历。
- `documentType=unknown`：进入澄清。

当文本和图片冲突时，编排器只问一个明确问题：

```text
这张图更像 Offer 信息。你是要评估 Offer，还是把它作为 JD 相关材料？
```

澄清完成前，不开放高风险写入工具。

## Active Task

面试、自我定位和简历 proposal 都可能持续多轮。active task 的规则是：

- 用户模糊追问时保持当前任务。
- 用户明确切换时给出切换确认。
- 用户取消时关闭 active task 并写入状态。
- 新材料进入时重新计算目标引用。
- 高风险任务切换时保留原任务的可恢复信息。

这样用户从 Interview 回到 Agent，或从 CV 页面回到 Agent 时，系统仍知道“刚才那个问题”“刚才那个 proposal”指向什么。

## Contract 输出

编排器输出应包含：

```text
{
  agentId,
  taskType,
  contractPolicy,
  allowedTools,
  targetRefs,
  requiresClarification,
  clarificationQuestion,
  successCriteria,
  blockedReason,
  auditSummary
}
```

`contractPolicy` 可以分为：

| policy | 含义 |
|---|---|
| `read_only` | 查询、解释、导航 |
| `guidance` | 引导用户完成判断 |
| `verified_write` | 写入后需要 read-back/verifier |
| `high_risk_verified_write` | 写入前确认，写入后验证 |
| `export_verified` | 导出后验证文件 |
| `admin_verified` | Admin 动作并读回状态 |

## 与工具治理的连接

编排器生成 `allowedTools` 后，工具层仍要再次判断：

- 工具 effect 是否超过 contractPolicy。
- 工具是否允许当前 `taskType`。
- 工具是否允许当前 agent。
- 当前用户 role 是否满足要求。
- 写入是否具备 read-back/verifier。

编排器和工具治理是双层约束。任何一层不通过，工具都不能执行。

## 开发完成标准

编排器开发完成时，应有以下证据：

- 高频求职表达有稳定路由样本池。
- 6 个业务 agent 的优先级和兜底关系清楚。
- taskType 与 allowedTools 可追溯。
- 图片冲突和低置信度进入澄清。
- active task 在切页、刷新、继续时可恢复。
- Admin 动作只生成 `admin_verified` 类型合同。
- 写入合同都绑定 read-back/verifier。
- 新增路由规则同步进入 evals。

## 编排器决策表

编排器要把模糊输入转成明确任务。下面是核心决策表。

| 输入特征 | 上下文 | 判定 | 后续 |
|---|---|---|---|
| 包含岗位职责、任职要求 | 无 reportId | `evaluate_jd` | 进入 `evaluate` |
| “基于刚才报告” | 有 reportId | 延续 report 上下文 | 检查 report owner |
| “我现在的简历” | 无写入动词 | `resume_query` | 只读 CV |
| “改、优化、重写个人概述” | 有 CV section | `resume_edit` | 生成 proposal |
| 薪资、试用期、福利 | Offer 文本或截图 | `offer_analyze` | 进入 `offer` |
| “继续面试” | 有 interview state | `interview_continue` | 恢复 currentQuestion |
| “适合什么方向” | 无具体 JD | `profile_guided` | 进入 guided session |
| 文本和图片冲突 | 类型不一致 | `clarify` | 只问一个澄清问题 |

编排器的好坏直接影响用户信任：如果它把 Offer 当 JD，后面所有 agent 和页面都会沿着错误对象继续。
