# 09 POC 验证

本篇记录 Zhiyuan POC 如何判断产品假设是否成立。POC 验证要回答：用户是否能通过 Agent Chat 完成一条有价值、可信、可复查的求职任务。

验证结论会决定产品是否进入多页面开发和 Agent-first 重构。

## 1. 验证问题

| 问题 | 通过含义 |
|---|---|
| 用户是否愿意从 Agent Chat 发起任务 | 主入口成立 |
| JD 报告是否能帮助投递判断 | 核心价值成立 |
| 报告是否需要页面承接 | 多页面形态成立 |
| 简历修改是否必须提案确认 | 写入安全成立 |
| 结果是否能读回 | 成功态可信 |
| 用户资产是否能隔离 | 产品可交付基础成立 |

## 2. POC 验证链路

```text
准备样本
  -> 执行 POC 主线
  -> 记录输入和输出
  -> 检查页面承接
  -> 检查 read-back / verifier
  -> 记录用户价值和风险
  -> 判断进入 MVE / 多页面开发
```

## 3. 主线验证记录

| 样本 | 预期 | 通过标准 | 结论记录 |
|---|---|---|---|
| POC-01 JD 文本评估 | 生成投递建议和报告 | Reports 可读 | pass / partial / fail |
| POC-02 JD 截图评估 | 识别为 JD 并评估 | 类型和质量判断明确 | pass / partial / fail |
| POC-03 简历只读查询 | 返回当前简历 | 不创建 proposal | pass / partial / fail |
| POC-04 简历提案 | 生成 pending proposal | 未确认不写入 | pass / partial / fail |
| POC-05 确认写入 | 应用目标 section | read-back 一致 | pass / partial / fail |
| POC-06 跨页继续 | 围绕同一对象追问 | report/proposal 上下文不丢 | pass / partial / fail |

## 4. 扩展验证记录

| 样本 | 预期 | 是否进入首版 |
|---|---|---|
| Offer 首评 | 抽字段、识别缺失、给风险 | P1，可进入首版增强 |
| Offer 谈判 | 基于已有 Offer 给谈判问题 | P1 |
| 面试准备 | JD + 简历，一题一答 | P1 |
| 自我定位 | 逐步追问，不空泛定论 | P0/P1 之间 |
| 低清图片 | 澄清或重传，不猜测 | P1 |
| 跨用户读取 | 拒绝或空结果 | P0 |

## 5. 成功判定

POC 通过不是“模型回答得像样”，而是满足：

| 条件 | 说明 |
|---|---|
| 用户任务完整 | 能从输入走到结果 |
| 结果有页面承接 | 报告、提案、Offer、面试进度可复查 |
| 数据可读回 | 保存和写入不是口头承诺 |
| 风险被挡住 | 未确认不写入，低置信不猜测，跨用户不读取 |
| 用户价值清楚 | 用户知道下一步怎么投、怎么改、怎么问 |

## 6. 不通过判定

| 不通过表现 | 产品含义 |
|---|---|
| 只有聊天文字，没有报告或提案 | 多页面产品形态未成立 |
| 改简历不需要用户确认 | 资产安全不成立 |
| 报告保存后找不到 | 成功态不可信 |
| JD、Offer、简历截图串场 | 输入识别不成立 |
| 跨用户可读取资产 | 不能进入交付 |
| 用户看完不知道下一步 | 产品价值不成立 |

## 7. POC 结论模板

```markdown
## POC 验证记录

- 样本：POC-01
- 用户角色：正在投递的求职者
- 输入材料：AI 产品经理 JD 文本
- 预期结果：投递建议 + 完整报告
- 页面承接：Reports
- 数据证据：reportId / reportNum 可读回
- 用户价值：能判断是否投递并知道下一步准备
- 风险：如果报告不可读回，不能算成功
- 结论：pass / partial / fail
```

## 8. 进入下一阶段标准

| 标准 | 说明 |
|---|---|
| JD 主线通过 | 证明首个高频入口成立 |
| 简历提案通过 | 证明高风险写入可控 |
| 页面承接通过 | 证明多页面形态成立 |
| read-back 通过 | 证明成功态可信 |
| 权限隔离通过 | 证明用户资产边界成立 |
| 至少一个扩展链路可行 | Offer、面试或定位能自然接入 |

结论：09 的输出是 POC 是否成立的判断。成立后，10-13 进入多页面产品化开发和页面验证；不成立则回到 05 调整首版需求和 MVE 主线。

## 9. POC 结果判读样例

POC 记录不能只写 pass/fail，要说明为什么。下面是四种典型结果。

| 样本 | 现象 | 判读 | 后续动作 |
|---|---|---|---|
| POC-JD-001 | 生成报告，Reports 可按 reportId 打开 | 通过 | 进入多页面产品化 |
| POC-CV-002 | 生成简历建议，但没有 proposal 对象 | 部分通过 | 保留价值判断，补齐 CV proposal |
| POC-IMG-001 | JD 截图被识别成 Offer | 不通过 | 图片 intake 需要先做类型和置信判断 |
| POC-CV-APPLY | 显示“已保存”，但 section 读回不一致 | 不通过 | 成功态必须改为 read-back 后显示 |

判读的重点是产品假设：如果用户得到了文字但没有页面资产，不算完整通过；如果页面显示成功但没有数据证据，也不算通过。

## 10. POC 复盘输出

POC 结束后应形成一份复盘记录，供 10-13 使用。

```markdown
POC 复盘结论：
1. 主入口：Agent Chat 可以承接 JD 和简历相关表达。
2. 核心价值：JD 报告能帮助用户判断是否投递。
3. 页面必要性：Reports 和 CV 必须存在，否则结果难复查。
4. 高风险边界：简历修改必须使用 proposal 和确认写入。
5. 数据证据：report 保存和 CV apply 必须 read-back。
6. 扩展机会：Offer、Interview、Profile 可以作为 Demo 分支进入。
7. 暂不扩大：岗位发现、投递分析、团队知识库等进入后续阶段。
```

这份复盘把 POC 从“一次验证”转成后续产品化开发的依据。
