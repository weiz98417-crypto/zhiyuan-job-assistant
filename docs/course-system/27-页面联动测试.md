# 页面联动测试

页面联动测试用于证明用户能连续完成求职任务，而不是验证单个页面能单独打开。测试对象覆盖 Agent、CV、Reports、Offer、Interview、Profile、Admin，重点看对象 id、状态、权限和 read-back/verifier 是否跨页面保持一致。

## 测试准备

| 准备项 | 要求 |
|---|---|
| runtime | PostgreSQL + pgvector 可用；SQLite 仅标记为 fallback/archive/migration |
| 账号 | adminA、memberA、memberB、pendingC |
| 简历 | memberA/memberB 各有不同简历和 section hash |
| JD | 至少一份 JD 和一个可读报告 |
| Offer | 至少一份 Offer 和一个分析结果 |
| 面试 | 一个可继续的 interview session |
| Profile | 一组画像 signal 和定位状态 |
| Memory/Admin | 一个待处理 memory item 或 run 证据 |

测试数据要能区分用户，避免跨用户串用被误判。

## 页面对页面矩阵

| 起点 | 终点 | 验证点 |
|---|---|---|
| Agent | Reports | `reportId` 一致，报告可读 |
| Reports | Agent | 追问仍指向当前报告 |
| Agent | CV | `proposalId` 或 section id 一致 |
| CV | Agent | 继续优化同一 section |
| Agent | Offer | `offerReportId` 一致 |
| Offer | Agent | 谈判追问使用同一 Offer |
| Agent | Interview | `interviewSessionId` 与 currentQuestion 一致 |
| Interview | Agent | 评分解释回到同一题 |
| Agent | Profile | `profileId` 或 signal id 一致 |
| Profile | Agent | 自我定位继续同一阶段 |
| Admin | Memory | memory status 读回一致 |
| Admin | Agent | runId 或 evidence 可定位 |

## 核心测试链路

### JD 报告链路

```text
Agent 输入 JD
  -> evaluate agent
  -> report read-back
  -> 跳转 Reports
  -> Reports 打开同一 reportId
  -> Reports 发起追问
  -> Agent 保持 reportId
```

通过标准：Agent、Reports 和数据库中的 report/JD 关系一致。

### 简历修改链路

```text
Agent 生成 resume proposal
  -> 跳转 CV
  -> CV 展示同一 proposal diff
  -> 用户确认 apply
  -> section hash read-back
  -> 返回 Agent
```

通过标准：查询链路不写入；apply 后 hash 匹配；返回 Agent 后工具卡片显示验证结果。

### Offer 链路

```text
Agent 输入 Offer
  -> offer agent
  -> offer report read-back
  -> 跳转 Offer 页面
  -> 页面发起谈判追问
  -> Agent 使用同一 offerId
```

通过标准：Offer 不进入 JD 报告链路，薪资和福利字段不串到其他用户。

### 面试链路

```text
Agent 开始面试
  -> Interview 页面显示 currentQuestion
  -> 用户回答
  -> Agent 解释评分
  -> 刷新或返回后继续下一题
```

通过标准：currentQuestion、answer、planSnapshot 一致。

### Profile 与 Admin 链路

```text
Agent 完成自我定位
  -> 生成 profile signal
  -> Profile 页面显示来源和状态
  -> Admin 审阅记忆或 signal
  -> 状态 read-back
```

通过标准：private/team visibility、owner、status 不混淆。

## 权限联动测试

页面联动必须带权限验证：

- pending 用户不能进入 Agent、CV、Reports、Offer、Interview、Profile。
- member 不能进入 Admin。
- memberA 不能通过 URL id 打开 memberB 的报告、简历 proposal、Offer、面试、Profile 或 private memory。
- Admin 管理用户状态后，旧 token 的写入动作要被拒绝。
- Admin 页面不展示密码 hash、完整敏感 payload 或其他用户私有正文。

## 证据记录

每条页面联动测试要记录：

- caseId。
- 测试账号。
- 起点页面和终点页面。
- 传递的对象 id。
- 页面截图或状态摘要。
- API/数据库读回证据。
- read-back/verifier 结果。
- 结论：passed、needs-test、needs-fix、blocked、skipped。

没有对象 id 和读回证据的链路，不能标记为 passed。

## 通过标准

页面联动测试通过需要同时满足：

- Agent 与页面使用同一业务对象。
- 页面刷新后仍可恢复关键状态。
- 写入动作有确认和 read-back/verifier。
- 权限不因页面跳转被绕开。
- 用户能从结果页继续回 Agent 完成下一步。
- Admin 动作有状态反馈并可再次读取。

## 联动测试记录样例

```markdown
caseId：LINK-CV-REPORT-001
用户：memberA
起点：Reports 详情页
对象：reportId=rpt_1024
动作：点击“基于此报告修改简历”
预期：
1. Agent Chat 接收 reportId。
2. `resume` agent 创建 proposal。
3. CV 页面出现 proposalId。
4. 未确认前 cv_data 不变化。
5. 确认后 section read-back。
失败判定：
- proposal 没有目标 section。
- CV 页面看不到 proposal。
- apply 后读回不一致。
```

页面联动测试最重要的是“对象不断线”。只要 reportId、proposalId、offerId、interviewSessionId 丢失，用户就会觉得系统在重新猜。
