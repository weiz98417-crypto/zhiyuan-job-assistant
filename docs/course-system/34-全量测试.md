# 34 全量测试

全量测试用于证明 Zhiyuan 作为一个多用户 AI 求职助手可以完整交付。它不是只跑几个接口，也不是只验证页面能打开，而是把用户从注册、审批、Agent Chat、JD、简历、Offer、面试、画像、记忆到 Admin 治理的链路全部跑通。

全量测试必须以 PostgreSQL + pgvector 为当前 runtime。SQLite 只用于 fallback/archive/migration 相关验证，不能作为主交付证据。

## 全量测试目标

| 目标 | 产品意义 |
|---|---|
| 产品主链路成立 | 用户能从 Agent Chat 完成核心求职任务 |
| 身份权限成立 | 不同角色进入不同范围，页面和 API 一致 |
| 个人资产安全 | 简历、JD、Offer、面试、画像、记忆不串用户 |
| Agent 可控 | 6 个业务 agent 边界清楚，Orchestrator 只做内部编排 |
| 工具可信 | 48 个注册工具受任务合同约束 |
| 写入可证 | 高价值动作有 read-back 或 verifier |
| Admin 可治理 | 用户、记忆、运行证据能被管理且不越界 |
| 安全可交付 | 注入、隐私、图片文字审核进入下一阶段安全验收 |

## 全量测试数据

| 数据 | 要求 |
|---|---|
| adminA | active/admin，可审批用户和查看治理页面 |
| memberA | active/member，有完整简历、JD、Offer、面试、画像、记忆 |
| memberB | active/member，资产内容与 memberA 明显不同 |
| pendingC | pending/member，不能进入核心求职工作台 |
| rejectedD | rejected/member，被明确阻断 |
| JD 样本 | 文本 JD、截图 JD、风险 JD |
| Offer 样本 | 完整 Offer、缺字段 Offer、Offer 截图 |
| 简历样本 | 当前简历、目标 section、参考材料 |
| 面试样本 | JD + 简历快照 + 回答记录 |
| 画像样本 | 职业目标、偏好、约束、经历信号 |
| 记忆样本 | private、team_pending、team |

## 全量链路

```text
adminA 创建或审批 memberA
  -> memberA 登录
  -> Agent Chat 输入 JD
  -> evaluate 生成 Reports
  -> memberA 基于报告生成简历提案
  -> CV 页面确认并读回
  -> memberA 分析 Offer
  -> Compare 页面展示
  -> memberA 进入面试准备
  -> Interview 保存当前状态
  -> memberA 做自我定位
  -> Profile 展示画像信号
  -> Admin 审核团队记忆候选
  -> memberB 对照验证隔离
```

这条链路覆盖产品从用户进入到多 Agent 协作、页面承接、数据读回和 Admin 治理的主要闭环。

## 测试矩阵

| 类别 | case | 通过标准 |
|---|---|---|
| AUTH | 注册、登录、退出、me 读回 | 身份、角色、状态一致 |
| PERM | pending/member/admin/rejected | 页面和 API 同步阻断或放行 |
| ISO | memberA/memberB 资产对照 | 不串简历、报告、Offer、session、memory |
| JD | JD 文本和截图 | 正确进入 `evaluate`，Reports 可读回 |
| CV | 简历查询和提案 | 查询只读，提案确认后才写入 |
| OFFER | Offer 文本和截图 | 正确进入 `offer`，Compare 可读回 |
| INT | 面试准备 | 绑定 JD 与简历，状态可恢复 |
| PROF | 自我定位 | 画像信号有来源、置信度、可见性 |
| TOOL | 工具调用 | taskType、agentAllowlist、effect、read-back 生效 |
| ADM | 用户和记忆治理 | 状态变化、审核结果可读回 |
| PRIV | 隐私展示 | 治理视图不默认暴露高敏原文 |
| IMG | 图片文字材料 | 类型识别、低置信澄清、不得越权写入 |

## 全量通过标准

| 标准 | 说明 |
|---|---|
| P0 清零 | 不存在跨用户读取、越权写入、假成功、未确认改简历 |
| 主链路通过 | JD -> Reports -> CV proposal -> apply -> read-back |
| 扩展链路可用 | Offer、Interview、Profile 能独立完成关键任务 |
| 权限矩阵一致 | 页面和 API 行为一致 |
| runtime 明确 | PostgreSQL + pgvector 是当前事实源 |
| 证据完整 | 每个关键 case 有对象 ID、页面状态或 verifier |
| 安全下一阶段就绪 | 可以进入 35-39 的注入、隐私、图片文字审核交付 |

## 不通过判定

| 表现 | 结论 |
|---|---|
| memberA 能看到 memberB 的简历、Offer 或报告 | 不能交付 |
| 简历未确认就被写入 | 不能交付 |
| 保存失败却显示完成 | 不能交付 |
| pending 能使用核心 Agent | 不能交付 |
| Offer 被当成 JD 分析 | 需要重新验证材料路由 |
| Admin 默认暴露完整私密原文 | 需要调整治理展示 |
| SQLite 证据被当成主 runtime 证据 | 交付证据无效 |

## 阶段结论

全量测试通过后，Zhiyuan 已经具备完整产品交付基础：

1. 0-1 产品主链路成立。
2. 多页面工作台可以承接 Agent 产出。
3. 6 个业务 agent 的职责清楚。
4. 48 个工具在权限和任务边界内运行。
5. 用户资产隔离和登录安全成立。
6. 高价值写入有证据。
7. 可以进入最终安全体系：用户注入、用户隐私、图片文字审核和安全系统整体交付。

## 全量测试执行顺序

```text
1. 准备 PostgreSQL + pgvector runtime
2. 创建 adminA、memberA、memberB、pendingC、rejectedD
3. 为 memberA/memberB 准备不同简历、JD、Offer、面试、画像、记忆
4. 跑登录与权限矩阵
5. 跑 Agent 主链路：JD -> Reports -> CV proposal -> apply
6. 跑扩展链路：Offer、Interview、Profile
7. 跑跨用户隔离：A/B 数据互不可见
8. 跑 Admin 治理：审批、记忆审核、run 摘要
9. 跑图片文字和注入输入
10. 汇总 P0/P1/P2 与交付结论
```

全量测试不是把所有测试堆在一起，而是按产品交付顺序证明：身份成立、主链路成立、资产安全成立、安全体系成立。
