# 22 — 当前系统状态与治理闭环

本文说明项目真实运行能力，重点覆盖 Agent Loop、图片入口、运行台账、复盘治理和自动化边界。

---

## 1. 当前运行时地图

筝筝纸鸢现在是一个 Next.js 全栈应用，Agent Chat 是主要入口，运行时由以下几层组成：

```text
Agent Chat UI
  -> 图片/文件预处理
  -> image-intake 文档识别与路由
  -> orchestrator 选择子 Agent
  -> task-routing 生成任务契约
  -> tool-governance 执行前拦截
  -> client/server agent loop 执行工具
  -> read-back verification 校验写入结果
  -> Agent Run ledger 记录运行过程（Postgres 环境）
  -> Agent Run Review 复盘并生成 Eval 候选（Postgres 环境）
```

子 Agent 仍然是 6 个：`general`、`evaluate`、`resume`、`interview`、`profile`、`offer`。工具注册总数为 48 个，所有工具都必须补齐治理元数据：副作用类型、允许任务、允许 Agent、读回要求、成功契约和中文展示名。

## 2. 图片入口的当前逻辑

用户上传图片后，不再直接交给普通聊天模型发挥。Agent Chat 先调用 `/api/agent/image-intake`，把图片识别结果写成 `recognize_document_image` 工具消息，再由 `image-intake-router` 决定下一步。

| 场景 | 当前行为 |
|------|----------|
| 只丢图片 | 先识别图片类型，再询问用户要评估、保存还是只分析图片 |
| 文本说评估 JD + JD 图片 | 提取 JD 文本，路由到 `evaluate_jd_full` |
| 文本说评估 Offer + Offer 图片 | 提取 Offer 信息，路由到 `evaluate_offer` |
| 文本和图片冲突 | 不执行业务工具，先问用户确认 |
| 图片是简历 | 先预览/识别；如果用户要求保存优秀简历，还要确认岗位方向 |
| 图片无关求职 | 可以描述图片，但不进入 JD/Offer/简历业务流程 |
| OCR 超时或缩略图 | 返回 `retry_image`，说明是不稳定识别或原图问题，不把任务标记成功 |

大长图通过 `server-image-variants.ts` 生成候选版本和长截图切片，避免只把聊天窗口里的缩略图交给模型。当前边界是：如果上传文件本身就是缩略图或 OCR 服务超时，系统只能给出失败和重试建议，不能凭空恢复原图文本。

## 3. 任务契约

每个高风险业务任务都有 `AgentTaskContract`。它不是提示词建议，而是运行时成功条件。

| 任务 | 必须满足的成功条件示例 |
|------|------------------------|
| JD 评估 | 来源内容已提取、A-G 报告生成、报告已保存、保存报告读回验证通过 |
| Offer 评估 | Offer 内容已提取、模块生成、报告/Offer 已保存、读回验证通过 |
| 简历修改 | 草稿生成、用户确认、目标模块读回 hash 匹配、内容校验通过、版本快照创建 |
| 优秀简历保存 | 来源简历存在、岗位方向已确认、参考简历已保存、读回验证通过 |
| 自我定位/画像 | 引导框架加载、下一步问题生成、信号提取和写入校验通过 |

如果未满足条件，系统会返回安全消息，例如“这次 JD 评估没有完成可靠落库校验”，并阻止“已经完成”的误导性表述。

## 4. 工具治理

`src/lib/agent/tool-governance.ts` 是当前工具治理中心。它解决的是“Agent 聊得像对了，但调用错工具或写错东西”的问题。

治理维度包括：

- `effect`：只读、引导、写入、高风险写入、导出、管理员、内部工具。
- `allowedTaskTypes`：工具只能在允许的任务类型里运行。
- `agentAllowlist`：工具只能被允许的子 Agent 调用。
- `requiresUserConfirmation`：简历应用、丢弃、回滚等需要用户确认。
- `requiresReadBack`：写入、导出、管理员工具必须有读回证据。
- `successContract`：工具完成后必须满足的可验证结果。

典型拦截：

- 自我定位任务中，不能突然调用 Offer 评估工具。
- 简历修改不能直接写入未确认的 Markdown 片段。
- JD 截图评估不能绕过图片识别工具。
- 高风险写入没有读回证据时，不能进入成功态。

## 5. Agent Run 台账

Agent Run 台账只在 PostgreSQL 已配置时启用：

```text
DB_DRIVER=postgres
DATABASE_URL=postgresql://...
```

启用后会写入：

- `agent_runs`：一次业务任务的总体状态、任务类型、Agent、契约、结果和错误。
- `agent_run_steps`：每一步 phase、tool、输入摘要、输出摘要、verifier、error。

状态枚举：

```text
planned -> running -> waiting_user -> verifying -> repairing
terminal: recovered / needs_engineering / succeeded / failed / rolled_back / cancelled
```

前端可视化入口：

- Agent Chat 顶部活动 run 条：展示任务、状态、最近阶段和取消/查看入口。
- `/admin/agent-runs`：管理员运行台，展示 run、step、成功标准、校验器、路由治理、工具输出和错误。

SQLite fallback 环境不会沉淀完整运行台账，管理页会显示“未启用”；当前 LAN 运行态已切到 PostgreSQL。

## 6. 复盘治理与 Eval 候选

当 run 进入终态后，`run-review.ts` 会执行确定性复盘。复盘不是大模型自由判断，而是基于台账、步骤、工具结果和契约证据做规则检查。

当前会沉淀的失败类型包括：

- `image_intake_not_called`：上传图片但没有图片识别工具记录。
- `image_intake_failure`：OCR/文档识别失败或被跳过。
- `missing_readback`：写入类工具缺读回证据。
- `guided_task_drift`：活动引导任务漂移到其他 Agent。
- `tool_contract_mismatch`：工具和任务契约不匹配。
- `resume_write_pollution`：简历写入被 Markdown/占位符/不完整内容污染。
- `profile_signal_noise`：画像信号过短、泛化或无证据。
- `interview_policy_violation`：面试一次多题、忘记 JD/简历绑定等。

管理员入口：

- `/admin/agent-reviews`：复盘列表、复盘详情、Eval 候选队列。
- `接受`：表示这个候选应进入人工改进队列。
- `拒绝`：表示该候选不作为问题继续跟踪。
- `提升为回归草案`：生成 regression eval 草案信息。

重要边界：Eval 候选不会自动修改代码、不会自动提交测试、不会自动部署。它把失败抓出来并结构化，后续仍需要开发者显式把草案落成测试和修复。

## 7. 当前自检/自愈能力边界

已经具备的能力：

- 工具调用前做治理拦截。
- 高风险写入后做读回校验。
- 流式 JD 评估缺读回时阻止成功态。
- 图片识别失败、冲突或超时时进入可见失败/澄清路径。
- 部分可恢复工具错误进入 `repairing` 或重试路径。
- run 结束后可自动复盘并沉淀 eval 候选。

尚未自动化的能力：

- 不会自动改代码修 bug。
- 不会自动把 eval 候选写成 Vitest 测试。
- 不会自动迁移数据库或切换 runtime。
- 不会在 SQLite fallback 环境沉淀完整 run/review/eval 台账。
- 不会在无原图或 OCR 服务持续超时时保证图片文字识别成功。

---

## 8. 对用户可见的状态

Agent Chat 当前会展示以下状态：

- `extracting_ocr`：正在识别图片。
- `compressing_context`：正在压缩上下文/生成会话摘要。
- `executing`：正在执行工具。
- `verifying`：正在校验工具结果或写入结果。
- `responding`：正在生成最终回复。

管理员当前可查看：

- `/admin/agent-runs`：Agent Run Debug。
- `/admin/agent-reviews`：Agent 复盘治理和 Eval 候选。
- `/admin/memory`：优秀简历、向量索引、候选记忆模式和团队共享治理。
