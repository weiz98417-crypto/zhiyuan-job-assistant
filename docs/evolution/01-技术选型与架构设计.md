## 3. 关键技术决策

### 3.1 数据层：PostgreSQL 当前运行态 + SQLite fallback

项目早期选择 SQLite 是为了快速本地启动和零运维，但当前局域网部署已经切到 PostgreSQL/pgvector。现在的架构决策是：服务端业务代码优先通过 `getDataRepositories()` 访问数据层，运行时由 `DB_DRIVER` 决定底层驱动。

当前分工：

- **PostgreSQL/pgvector**：当前 LAN 权威事实源，承载多用户、管理员审批、报告/JD/Offer、简历草稿、Agent Run 台账、复盘治理、Eval 候选和长期向量记忆。
- **SQLite**：保留为本地 fallback、历史迁移源、归档读取和少量 legacy 脚本兼容路径。
- **切换校验**：`check:postgres`、`migrate:postgres`、`check:postgres-migration`、`check:postgres-cutover` 共同保证迁移和切换不靠猜。
- **运行时约束**：`server-db.ts` 在 `DB_DRIVER=postgres` 时会阻止直接 SQLite 写入，除非显式设置 `ALLOW_SQLITE_LEGACY=readonly` 做归档读取。

这个选择的收益是：保留 SQLite 的低成本恢复能力，同时让真正需要共享、审计、向量检索和长期治理的能力落在 Postgres 上。

### 3.2 Agent 系统：混合三级架构

**选择 TypeScript 子Agent + Server-Side 执行循环 + Claude Mode 文件。**

这是架构演进中最关键的决策。早期版本纯依赖 Claude Agent（通过 CLAUDE.md 路由和 Mode 文件驱动），所有智能都在对话边界内完成。随着系统复杂度增长，需要引入服务器端执行能力：

- **TypeScript 子Agent (6个)**: 意图分类（classifyIntent）+ 工具白名单（populateAgentTools）+ 系统提示词构建（buildSystemPrompt）。按优先级顺序匹配: Offer → Evaluate → Interview → Profile → Resume → General（兜底）。
- **Server-Side ReAct Loop (server-runner.ts)**: 替换客户端 fetch 代理循环。直接在服务器端调用 DeepSeek API，执行 native function calling，质量门控检查。5 阶段认知状态机: understanding → executing → verifying → reflecting → responding。CJK token 估算 + 流式降级 + 行缓冲 + 去重安全。
- **Claude Mode 文件 (modes/)**: 评分引擎、风险评估、Offer 对比、PDF 生成的领域知识库。由 `/api/agent/mode/[mode]` 动态路由加载。

代价（相比纯 Claude Agent 模型）:
- 系统提示词需要维护两份: TypeScript buildSystemPrompt + Mode Markdown 文件
- 子 Agent 的 intentPatterns 正则需要持续调优，避免路由误判
- 工具白名单矩阵需要审计，确保每个 Agent 不会越权调用

相比纯后端框架（LangChain 等）的收益:
- 零框架锁定 —— 工具定义就是 TypeScript 接口
- 正则路由可审计、可调试（不是黑盒 embedding）
- Claude Mode 文件保持极致灵活 —— 改 prompt 不需要重新部署

### 3.3 四层风险检测

**选择 正则匹配 + 字典黑名单 + 模式检测 + LLM补充，而非纯 LLM。**

理由：
- 前三层是确定性的（正则 + substring + 多信号组合），零 LLM 调用，零幻觉
- Layer 1 (Regex): `risk-intel-triggers.yml` 定义正则模式，覆盖常见伪装措辞
- Layer 2 (Dictionary): `modes/zh/risk-intel.md` 30+ 高危黑名单词条（试用期陷阱、外包/劳务派遣、竞业限制等）
- Layer 3 (Pattern): 骗术模式库 —— 2+ 信号同时命中才触发，降低误报
- Layer 4 (LLM): 通过评估管道运行，补充语义变体（正则无法覆盖的委婉措辞）
- 四层去重合并，保留最高严重度；Pattern 层优先级最高（多信号确认）

### 3.4 记忆系统：三层智能上下文

**选择 工作记忆 + 情节记忆 + 语义记忆，MemoryCoordinator 统一编排。**

这解决了纯对话摘要方法的三个固有问题:
- **上下文窗口溢出**: 工作记忆只保留最后10轮，超出的由情节记忆摘要接管
- **跨对话遗忘**: 语义记忆从多轮对话中抽取结构化事实（技能、薪资范围、行业偏好、底线），通过 repository 写入会话摘要、画像信号或长期记忆表；当前 LAN 持久化在 PostgreSQL
- **信息密度不足**: MemoryCoordinator 在 buildContext() 中合并三层输出: truncatedMessages + summaryInjection + semanticInjection

架构:
- **Working Memory** (`working.ts`): 滑动窗口，最后 N 轮对话原文
- **Episodic Memory** (`episodic.ts`): 对话超过 15 条用户消息时触发摘要，存储到 session_memory 表
- **Semantic Memory** (`semantic.ts`): 调用 LLM 从对话中提取结构化事实（SemanticFacts 接口），跨会话持久化

### 3.5 模型后备链：四级韧性

**选择 DeepSeek V4 Flash → DeepSeek V4 Pro → GLM-4.6V FlashX → Qwen-Long 四级降级链。**

不依赖单一 API 供应商。后备链在 `callLLM()` 函数中实现:
- 每层尝试最多 2 次（第1次失败后等1秒重试）
- 仅对 429 (Rate Limit) 和 503 (Service Unavailable) 触发重试
- 网络异常和超时 (AbortSignal.timeout 60s) 触发模型切换
- 其他错误直接尝试下一模型
- 全部失败时返回 `"All models failed"` 错误

### 3.6 Agent 互通：Repository 事实源 + API Route + Run Ledger

Agent 互通不再依赖“大家直接读同一个 SQLite 文件”。当前做法是：

- `/api/agent/claude-activity` 通过 `getDataRepositories()` 读取最近投递、报告和管道状态。
- `/api/agent/run` 在服务端执行 ReAct Loop，工具读写也通过 repository 或业务 API。
- PostgreSQL 启用后，`agent_runs` 和 `agent_run_steps` 记录每次任务的真实执行过程，管理员可在 `/admin/agent-runs` 调试。
- 终态 run 触发 `run-review.ts`，把缺图片识别、缺读回、任务漂移、工具契约不匹配等问题沉淀为 eval 候选。

API route 仍然是前端和服务端能力之间的边界，但事实源已经从“直接 SQLite 桥接”演进为“repository + Postgres governance”。
