## 2. 技术选型

### 2.1 前端框架

| 组件 | 选型 | 理由 |
|------|------|------|
| 框架 | **Next.js 16 (Turbopack) + React 19** | App Router, Server Components, 全栈一体化 |
| 样式 | **Tailwind CSS 4 + CSS 变量** | globals.css 定义设计令牌, 亮/暗双主题 |
| 动画 | **Framer Motion** | 页面过渡、卡片入场动画 |
| 图标 | **Lucide React** | 轻量、一致、Tree-shakable |
| 字体 | **LXGW WenKai (展示) + Noto Sans SC (正文)** | "手帐"设计美学 |

### 2.2 Agent 系统 (混合架构)

| 组件 | 选型 | 理由 |
|------|------|------|
| 子Agent框架 | **TypeScript 注册表 (5个Agent类)** | 意图分类、工具白名单、系统提示词构建 |
| 服务器端执行循环 | **ReAct Loop (server-runner.ts)** | SSE流式、native function calling、质量门控 |
| AI 模型主引擎 | **DeepSeek V4 Flash (API)** | 中文理解顶级, 低成本, 函数调用稳定 |
| 模型后备链 | **GLM-4.6V FlashX → Qwen-Long** | 自动降级, 每层1次重试, 429/503智能切换 |
| 评分系统 | **modes/scoring-dimensions.yml** | YAML 定义 A-G 7 维度, 中英文统一权重 |
| 语言路由 | **CLAUDE.md 内联路由表** | 根据 JD 语言自动选择 modes/ 或 modes/zh/ |
| Claude Mode 文件 | **Markdown 指令集 (modes/)** | 中文风险检测、评估、Offer对比、PDF生成 |

### 2.3 数据层

| 组件 | 选型 | 理由 |
|------|------|------|
| 数据库 | **SQLite (WAL模式, 14表)** | 单文件、零运维、事务隔离 |
| 数据库驱动 | **better-sqlite3** | 同步 API, 简化脚本/API逻辑 |
| 全文检索 | **FTS5 (reference_resumes_fts5)** | 简历参考库模糊搜索 |
| 客户端缓存 | **Dexie (IndexedDB封装)** | 离线状态缓存 |
| Schema 管理 | **server-schema.sql (120+行)** | 声明式建表, 可重建 |

### 2.4 后端工具链

| 组件 | 选型 | 理由 |
|------|------|------|
| 运行时 | **Node.js 22 (.mjs 模块)** | 项目统一运行时 |
| PDF 生成 | **Playwright + Puppeteer** | HTML → PDF, CSS 精确控制 |
| HTML 解析 | **Cheerio** | 轻量 DOM 查询, JD抓取 |
| YAML 解析 | **js-yaml** | 配置文件和知识库解析 |
| OCR | **pdf2json + pdf-parse + @napi-rs/canvas** | 截图JD文字提取 |
| MCP SDK | **@modelcontextprotocol/sdk** | Web搜索/百度地图/职位搜索代理 |

## 3. 关键技术决策

### 3.1 数据层：SQLite 单文件 + 全栈集成

**选择 SQLite 而非 PostgreSQL/MySQL。**

理由：
- 单人项目，零运维负担
- WAL 模式支持并发读写（API 层读 / 脚本写 不互斥）
- 单文件方便备份和迁移（`data/zhiyuan.db`）
- `better-sqlite3` 同步 API 简化脚本和 API route 逻辑
- `ON CONFLICT` 原生支持 upsert（投递记录自动去重）
- FTS5 全文引擎为简历参考库提供零配置搜索
- 14 表覆盖所有业务数据: 投递、评估、JD、画像、简历、Offer、故事、对话、偏好、记忆

### 3.2 Agent 系统：混合三级架构

**选择 TypeScript 子Agent + Server-Side 执行循环 + Claude Mode 文件。**

这是架构演进中最关键的决策。早期版本纯依赖 Claude Agent（通过 CLAUDE.md 路由和 Mode 文件驱动），所有智能都在对话边界内完成。随着系统复杂度增长，需要引入服务器端执行能力：

- **TypeScript 子Agent (5个)**: 意图分类（classifyIntent）+ 工具白名单（populateAgentTools）+ 系统提示词构建（buildSystemPrompt）。按优先级顺序匹配: Evaluate → Resume → Interview → Profile → General（兜底）。
- **Server-Side ReAct Loop (server-runner.ts)**: 替换客户端 fetch 代理循环。直接在服务器端调用 DeepSeek API，执行 native function calling，质量门控检查（检测空结果和不相关内容自动重试）。3 阶段流转: understanding → reflecting → responding。
- **Claude Mode 文件 (modes/)**: 评分引擎、风险评估、Offer 对比、PDF 生成的领域知识库。由 `/api/agent/mode/[mode]` 动态路由加载。

代价（相比纯 Claude Agent 模型）:
- 系统提示词需要维护两份: TypeScript buildSystemPrompt + Mode Markdown 文件
- 子 Agent 的 intentPatterns 正则需要持续调优，避免路由误判
- 工具白名单矩阵需要审计，确保每个 Agent 不会越权调用

相比纯后端框架（LangChain 等）的收益:
- 零框架锁定 —— 工具定义就是 TypeScript 接口
- 正则路由可审计、可调试（不是黑盒 embedding）
- Claude Mode 文件保持极致灵活 —— 改 prompt 不需要重新部署

### 3.3 四层风险检测

**选择 正则匹配 + 字典黑名单 + 模式检测 + LLM补充，而非纯 LLM。**

理由：
- 前三层是确定性的（正则 + substring + 多信号组合），零 LLM 调用，零幻觉
- Layer 1 (Regex): `risk-intel-triggers.yml` 定义正则模式，覆盖常见伪装措辞
- Layer 2 (Dictionary): `modes/zh/risk-intel.md` 30+ 高危黑名单词条（试用期陷阱、外包/劳务派遣、竞业限制等）
- Layer 3 (Pattern): 骗术模式库 —— 2+ 信号同时命中才触发，降低误报
- Layer 4 (LLM): 通过评估管道运行，补充语义变体（正则无法覆盖的委婉措辞）
- 四层去重合并，保留最高严重度；Pattern 层优先级最高（多信号确认）

### 3.4 记忆系统：三层智能上下文

**选择 工作记忆 + 情节记忆 + 语义记忆，MemoryCoordinator 统一编排。**

这解决了纯对话摘要方法的三个固有问题:
- **上下文窗口溢出**: 工作记忆只保留最后10轮，超出的由情节记忆摘要接管
- **跨对话遗忘**: 语义记忆从多轮对话中抽取结构化事实（技能/薪资范围/行业偏好/底线），持久化到 SQLite session_memory 表
- **信息密度不足**: MemoryCoordinator 在 buildContext() 中合并三层输出: truncatedMessages + summaryInjection + semanticInjection

架构:
- **Working Memory** (`working.ts`): 滑动窗口，最后 N 轮对话原文
- **Episodic Memory** (`episodic.ts`): 对话超过 15 条用户消息时触发摘要，存储到 session_memory 表
- **Semantic Memory** (`semantic.ts`): 调用 LLM 从对话中提取结构化事实（SemanticFacts 接口），跨会话持久化

### 3.5 模型后备链：韧性优先于性能

**选择 DeepSeek V4 Flash → GLM-4.6V FlashX → Qwen-Long 后备链。**

不依赖单一 API 供应商。后备链在 `callLLM()` 函数中实现:
- 每层尝试最多 2 次（第1次失败后等1秒重试）
- 仅对 429 (Rate Limit) 和 503 (Service Unavailable) 触发切换
- 其他错误直接尝试下一模型
- 全部失败时返回 `"All models failed"` 错误

### 3.6 Agent 互通：SQLite 桥接 + API Route

**选择 API route + fetch，而非共享内存或消息队列。**

理由：
- SQLite 已是所有组件共享的数据源
- `/api/agent/claude-activity` 服务端查询 SQLite 返回 Claude Agent 最近的评估活动
- TypeScript Agent 在 buildSystemPrompt 时通过 claudeAgentActivity 字段注入上下文
- 不需要新基础设施 —— 沿用现有的 API route + fetch 模式
- 总改动 < 50 行代码
