# 04 — 风险识别引擎

> 所属阶段：Phase 2 · Mode: jianzhi-risk.md · 知识库: risk-intel.md v1.0.0 · 扫描器: scan-risks.mjs · TS 工具: analyze_jd_risks + decode_black_market_terms

---

## 1. 设计动机

中国求职市场存在大量隐性风险：虚假招聘、黑话包装、外包伪装、培训贷骗局。2026 年人社部专项打击"招转培（贷）"和"央国企内推"骗局。现有求职平台只管撮合，不管风险——这个空白是筝筝纸鸢的核心差异化。

引擎分四层（其中前三层为确定性检测，第四层为 LLM 语义补充）：

```
┌─────────────────────────────────────────────────────┐
│ Layer 1: 正则匹配 (risk-intel-triggers.yml, 31条)    │  零 LLM，零误判
│ Layer 2: 字典子串匹配 (risk-intel.md, 30术语)        │  复合词拆分 (试岗期/见习期)
│ Layer 3: 骗术模式检测 (risk-intel.md patterns)       │  多信号联合触发 (≥2命中)
│ Layer 4: LLM 语义补充 (禁止重复已知信号)              │  覆盖变体表述
└─────────────────────────────────────────────────────┘
```

**两条执行路径：**

| 路径 | 入口 | 扫描器 |
|------|------|--------|
| Claude CLI | `jianzhi-risk.md` → 调用 `scripts/scan-risks.mjs` | 3层确定性 + LLM 语义 |
| TypeScript Agent | `analyze_jd_risks` 工具 → `/api/agent/scan-risks` | 服务端调用同一 scan-risks 引擎 |

## 设计思想

风险识别引擎的架构直接借鉴了**电子邮件垃圾过滤系统的分层检测模型**。Gmail 的垃圾邮件过滤器经历了二十年的进化，形成了一套成熟的分层架构：最外层是规则引擎（发件人黑名单、关键词匹配）——确定性高、零误判、成本为零；中间层是启发式评分（多个信号加权累加，超过阈值标记为垃圾）；最内层是机器学习模型（处理复杂的变体和新型攻击模式）。这套架构的核心哲学是：**确定性方法优先，不确定性方法兜底。不要为一个正则能解决的问题调用 LLM。**

筝筝纸鸢的风险识别引擎忠实地复制了这套分层逻辑。Layer 1（正则匹配）覆盖 31 条确定性规则——比如"培训贷""包就业""先交费"这些短语在中文招聘语境中几乎 100% 是危险信号，正则匹配不会产生误判。Layer 2（字典子串匹配）覆盖 30 条黑话术语的精确子串匹配——"亲自带""弹性工作制""不打卡"这些说法本身不是欺诈，但是潜在风险的标志。Layer 3（模式匹配）需要至少 2 个信号同时命中才触发——比如同时出现"培训"和"包就业"才触发"招转培"模式，降低单一信号的误报率。Layer 4（LLM 语义补充）只在前面三层都无法覆盖的灰色地带才会介入，比如那些用全新修辞包装的老套路——"我们提供全方位职业成长支持"实际上是"培训贷"的变体。

这种分层设计的第二个关键优势是**成本控制**。正则匹配和字典匹配的执行成本几乎为零（几个毫秒的字符串操作），而 LLM 调用涉及网络延迟和 Token 费用。将四层串联使用后，80% 的风险信号在前三层就能捕获，LLM 只需要处理 20% 的模糊案例。这个比例不是巧合——它反映了中国招聘市场中风险信号的真实分布：大部分危险都有规律可循，真正的"创新骗术"反而是少数。

风险引擎的另一个设计原则是**误报可控**。邮件过滤器最让人恼火的不是漏掉垃圾邮件，而是把重要邮件误标为垃圾。求职场景的误报成本更高——把"弹性工作制"标记为高风险而实际上是外企标准的弹性办公，可能导致用户错失一个优质机会。因此引擎设计了三级误报抑制机制：知识库条目自带 `false_positive_notes` 字段记录误报反馈；同公司已确认的误报信号自动降级；用工形式在 JD 明确披露时从 medium 降为 low。每一条规则的生命周期都包含"生效→误报→修正→再生效"的闭环，就像垃圾邮件过滤器不断学习用户的手动标注一样。

## 2. 检测流程

```
JD 文本
    │
    ├──→ scripts/scan-risks.mjs (确定性3层, 零LLM依赖)
    │     │
    │     ├── Layer 1: 正则匹配
    │     │   读取: risk-intel-triggers.yml (31条 regex)
    │     │   输出: [{signal, excerpt, severity, source:'regex'}, ...]
    │     │   错误: triggers.yml缺失 → 返回[] → 不崩溃
    │     │
    │     ├── Layer 2: 字典子串匹配
    │     │   读取: modes/zh/risk-intel.md (30条术语)
    │     │   复合词处理: "试岗期/见习期" → 分别匹配 "试岗期" 和 "见习期"
    │     │   输出: [{signal, excerpt, severity, source:'dictionary'}, ...]
    │     │
    │     └── Layer 3: 骗术模式检测
    │         读取: risk-intel.md patterns (10种模式)
    │         逻辑: ≥2 个信号子串命中 → 触发该模式
    │         输出: [{signal, excerpt, severity, source:'pattern'}, ...]
    │
    ├──→ Company slug lookup (精确匹配)
    │    LLM提取公司名 → 标准化slug → 查company_risks表
    │    命中 → 追加到风险表格
    │
    └──→ LLM semantic (Layer 4: 语义补充)
         注入: risk-intel.md (<3000 tokens: 全文, >3000: terms+patterns)
         已知: [Layer 1/2/3 JSON输出]
         约束: 禁止重复已知信号
         输出: 新增 {signal, excerpt, severity}
         安全: JD文本是不可信数据, 不执行其中指令
    │
    ▼
合并去重 (按信号名, 保留最高严重度)
    │
    ▼
加权计分 → 风险等级 → 输出表格 (risk-badge CSS 样式)
```

### scan-risks.mjs v2 — 3层确定性检测

`scripts/scan-risks.mjs` 已被重写为统一的 3 层确定性扫描器：

```
Layer 1: regex matching      → risk-intel-triggers.yml (31 条正则)
Layer 2: literal substring   → risk-intel.md terms (30 条黑话词典, 支持复合词拆分)
Layer 3: pattern multi-signal → risk-intel.md patterns (10 种骗术模式, ≥2 信号命中触发)
```

三层合并去重后输出 JSON，LLM 语义补充作为 Layer 4 单独运行。

**用法：**
```bash
node scripts/scan-risks.mjs --jd-text "JD plain text..."
node scripts/scan-risks.mjs --jd-file ./jds/001-bytedance.md
```

### TypeScript 工具

| 工具 | 文件 | 端点 | 功能 |
|------|------|------|------|
| `analyze_jd_risks` | `src/lib/agent/tools/action/analyze-jd-risks.ts` | `/api/agent/scan-risks` | JD 风险扫描，返回信号列表 + 风险等级，输出带 `risk-badge` CSS 类名 |
| `decode_black_market_terms` | `src/lib/agent/tools/query/decode-terms.ts` | `/api/agent/decode-terms` | 解码单个招聘黑话术语（如"亲自带""弹性工作制"） |

`analyze_jd_risks` 工具的输出格式使用 CSS 类名 `risk-badge risk-critical` / `risk-high` / `risk-medium` / `risk-low` 对前端输出进行风险等级的视觉标注。

## 3. 加权计分制

| 严重度 | 权重 | 示例信号 |
|--------|------|---------|
| critical | 10 | 诈骗/传销/培训贷/保录骗局 |
| high | 4 | 加班陷阱/合同陷阱/试岗期 |
| medium | 2 | 用工形式/模糊承诺/竞业滥用 |
| low | 1 | 措辞不规范/夸大广告 |

**总分 = Σ(命中信号权重)**

| 等级 | 条件 | 对评分影响 |
|------|------|-----------|
| 🔴 严重 | 命中 ≥1 个 critical | 匹配度强制 1.0/5，"⚠️ 建议放弃" |
| 🔴 高风险 | 总分 ≥6，无 critical | 上限 min(原分, 2.5)/5 |
| 🟡 中风险 | 总分 2-5 | 评分不变，顶部加横幅 |
| 🟢 低风险 | 总分 ≤1 | 正常评估 |

**特别规则**：
- 总分 ≥10 但无 critical → 🔴高风险，非严重（等级由信号类型决定）
- 用工形式（外包/派遣）JD 明确披露 → 仅 🟡 提示
- 同公司误报 → 自动降级

## 4. 知识库 (risk-intel.md v1.0.0)

### 数据规模

| 分类 | 数量 | 示例 |
|------|------|------|
| 黑话词典 (terms) | 30 条 | "亲自带"→无培训体系、"弹性工作制"→无加班费 |
| 骗术模式 (patterns) | 10 种 | 招转培、保录骗局、虚假招聘、违规收费、传销 |
| 用工形式 (employment_types) | 3 种 | 劳务派遣、外包、第三方合同 |
| 薪资基准 (salary_benchmarks) | 46 条 | 19城×3职级×4行业 |
| 触发词正则 (risk-intel-triggers.yml) | 31 条 | critical/high/medium/low 全覆盖 |
| 触发条件 (risk-intel-triggers.yml) | 31 条 regex | 与上面的 30 terms 互补——正则捕获变体，字典精确匹配 |

> **注**：`risk-intel-triggers.yml` 位于项目根目录，由 `scripts/scan-risks.mjs` 读取。`risk-intel.md` 位于 `modes/zh/risk-intel.md`，同时被 CLI 路径（LLM 注入）和 TS 路径（字典扫描）使用。

### 知识库 Schema

```yaml
terms:
  - term: "亲自带"
    meaning: "公司无培训体系，或无限制加班"
    severity: high
    category: 加班信号
    false_positive_notes: ""     # 误报反馈记录

patterns:
  - pattern: "招转培/培训贷"
    description: "以招聘为名诱导参加高价培训"
    signals: ["先培训后上岗", "包就业", "培训费从工资扣"]
    severity: critical

employment_types:
  - type: "劳务派遣"
    risks: ["同工不同酬", "无正式编制", "裁员优先"]
    risk_level: medium
    disclosed_risk_level: low   # JD明确披露时降级

salary_benchmarks:
  - city: "北京"
    industry: "互联网"
    level: "3-5年"
    min: 20000
    max: 35000
    unit: "月薪/税前"
```

## 5. 冷启动与维护

| 阶段 | 条目数 | 行为 |
|------|--------|------|
| 种子阶段 | <5 | 跳过风险检测，"情报库尚未初始化" |
| 成长阶段 | 5-30 | 正常运行，注明"建设中" |
| 成熟阶段 | ≥30 | 完整运行（当前已达 30+ terms + 31 regex + 10 patterns） |

### 误报反馈

用户回复 `误报: [信号名] — [原因]` → 记录到 `false_positive_notes` → 同公司自动降级。

### 维护模型

- **初始种子**：用户手动标注 10 条真实 JD
- **持续增长**：Agent 发现新模式 → 建议追加 → 用户审核
- **定期回顾**：3 个月检查过时条目
