# 19 — 分层记忆系统

## 概述

筝筝纸鸢的 Agent 系统使用三层记忆架构，模拟人脑的认知模型，在会话内上下文、跨会话经验、长期知识三个时间维度上组织信息。三层分别由 `working.ts`、`episodic.ts`、`semantic.ts` 实现，由 `coordinator.ts` 统一编排，被 `orchestrator/index.ts` 调用以构造 Agent 的 system prompt。

```
+------------------------------------------------------------------+
|                    Memory Coordinator (coordinator.ts)            |
|   buildContext(sessionId, messages) => MemoryContext              |
+------------------------------------------------------------------+
          |                  |                   |
          v                  v                   v
+------------------+ +-----------------+ +---------------------+
|  Working Memory  | | Episodic Memory | |  Semantic Memory    |
|  (working.ts)    | | (episodic.ts)   | | (semantic.ts)       |
|                  | |                 | |                     |
|  Lifetime: 当前会话| | Lifetime: 跨会话  | | Lifetime: 永久       |
|  Scope: 最近N条消息| | Scope: LLM摘要    | | Scope: 结构化事实    |
|  Storage: 内存     | | Storage: local   | | Storage: local     |
|                  | |   Storage         | |   Storage          |
+------------------+ +-----------------+ +---------------------+
          |                  |                   |
          v                  v                   v
+------------------------------------------------------------------+
|              Orchestrator (orchestrator/index.ts)                 |
|   orchestrate(content, ctx) => { systemPrompt, tools, ... }      |
+------------------------------------------------------------------+
          |
          v
+------------------------------------------------------------------+
|   Additional Context Sources (shared-memory.ts)                   |
|   - Career DNA (profile.yml + ZhiyuanProfile)                    |
|   - CV Summary (localStorage)                                     |
|   - Claude Agent Activity (SQLite applications table)             |
|   - Agent Knowledge (knowledge/index.ts)                          |
+------------------------------------------------------------------+
```

## 设计思想

分层记忆系统的架构不是凭空设计的——它直接模拟了**人类认知架构的三层模型**，这个模型在认知心理学中经过数十年的实验验证。工作记忆（Working Memory）对应人类的短时记忆：容量有限（Miller's Law: 7±2 个组块），保存的是你当前正在思考的内容，一旦注意力转移就会丢失。情景记忆（Episodic Memory）对应人类的个人经历记忆：你昨天和谁吃了饭，聊了什么，做了什么决定——这些不是"知识"，但构成了你理解上下文的背景。语义记忆（Semantic Memory）对应人类的长期知识：你知道自己的名字、技能、偏好、底线——这些是跨情境的、结构化的、相对稳定的。

这种类比不只是隐喻层面的巧合。三层记忆在工程实现上也反映了它们生物学对应物的关键特性。工作记忆是纯内存的、同步的、零延迟的——就像大脑的前额叶皮层，对当前信息做即时处理，没有"持久化到硬盘"的开销。情景记忆是异步的、有成本的——需要用 LLM 生成摘要，就像大脑在睡眠中通过海马体巩固记忆。语义记忆是持久的、结构化的——`localStorage` + JSON Schema，就像大脑皮层中的长期知识表征。三层有不同的生命周期、不同的存储后端、不同的检索策略，这些差异不是架构的缺陷，而是对认知现实的有意模仿。

系统的调度核心——**Memory Coordinator**——扮演的角色类似于大脑的**前额叶皮层**。它的职责不是在每层分别操作，而是根据当前任务统一决策：这个请求涉及面试准备，需要加载语义记忆中的用户技能列表；那个请求是日常闲聊，工作记忆就足够了，不需要触发昂贵的摘要生成。这种"按需加载"的策略避免了把所有上下文一股脑塞给 LLM 的粗暴做法——就像你不会在点一杯咖啡时回忆你二十年来所有的职业经历。

另一个隐性但关键的设计原则是**渐进增强**。新会话（sessionId 为 null）时，episodic 和 semantic 层在缓存为空时可以优雅降级为跳过，不会阻塞 Agent 启动。摘要生成的 LLM 调用是异步的、fire-and-forget 的——失败后静默返回空字符串，不会让用户看到"记忆系统故障"之类的错误。这种设计保证了记忆系统是一个**增强层**而非**阻塞层**：有记忆时 Agent 更聪明，没有记忆时 Agent 依然能正常工作。

系统还预留了明确的演进路径。当前实现中 episodic 摘要和 semantic 事实存储在 localStorage 中（换设备会丢失），但 SQLite 的 `session_memory` 表已经设计好了 schema。摘要的增量更新、动态窗口大小、跨会话语义合并、向量化检索——这些方向都已经在"演进方向"章节中规划好，每一个都对应着认知科学中的一个已知优化策略。分层架构的最大优势正是这种**独立演进**：改工作记忆的窗口大小不影响语义记忆的提取逻辑，替换 episodic 的存储后端不影响 working 的纯计算。

## 1. 三层模型总览

| 层次 | 文件 | 生命周期 | 存储 | 内容 | 触发条件 |
|------|------|---------|------|------|---------|
| Working | `memory/working.ts` | 单次会话 | 内存（React state） | 最近 10 轮对话 | 每次 orchestrate 调用 |
| Episodic | `memory/episodic.ts` | 跨会话 | `localStorage` | LLM 生成的会话摘要 | 用户消息 > 15 条 |
| Semantic | `memory/semantic.ts` | 永久 | `localStorage` | 结构化用户画像事实 | 会话结束 / 手动触发 |

**数据流向**：

```
用户消息 ──> orchestrator ──> buildContext()
                                 │
                    ┌────────────┼────────────┐
                    v            v            v
               working.ts   episodic.ts  semantic.ts
               (截取后10条)  (检查>15条?)  (读取localStorage)
                    │            │            │
                    v            v            v
               truncatedMsgs  summary    semanticInjection
                    │            │            │
                    └────────────┼────────────┘
                                 v
                          MemoryContext
                                 │
                                 v
                        agent.buildSystemPrompt()
```

## 2. 工作记忆 (Working Memory)

工作记忆保存**当前会话最近 N 轮对话**，是 Agent 最直接的上下文来源。它不持久化，会话结束后即消失。

### 2.1 核心逻辑

```typescript
// working.ts
export function buildWorkingContext(
  messages: { role: string; content: string }[],
  keepLast = 10,
): { role: string; content: string }[] {
  if (messages.length <= keepLast) return messages;
  return messages.slice(-keepLast);
}

export function countUserMessages(
  messages: { role: string; content: string }[],
): number {
  return messages.filter((m) => m.role === "user").length;
}
```

### 2.2 设计要点

- **保留窗口**：默认保留最近 10 条消息（5 轮用户+助手交替）。窗口大小硬编码在 `coordinator.ts` 调用处：`buildWorkingContext(messages, 10)`。
- **全量传递**：消息总数不足 10 条时，不做截断，全部传入 Agent。
- **统计用途**：`countUserMessages()` 不仅用于工作记忆本身，还被 episodic 层引用以判断是否需要触发摘要（阈值 15 条）。
- **不做内容过滤**：工作记忆不解析消息内容，不做去重或压缩。这些职责由 episodic 和 semantic 层承担。

### 2.3 在 orchestrator 中的位置

```typescript
// orchestrator/index.ts
const memCtx = await buildContext(ctx.sessionId, ctx.messages);
const promptCtx: AgentPromptContext = {
  ...
  currentMessages: memCtx.truncatedMessages,  // <-- 工作记忆注入
  ...
};
```

`truncatedMessages` 被注入到 `AgentPromptContext.currentMessages`，由各子 Agent 的 `buildSystemPrompt()` 拼接到 system prompt 中。

## 3. 情景记忆 (Episodic Memory)

情景记忆用 LLM 生成**当前会话的历史摘要**，替代超出工作记忆窗口的早期消息。核心思想：不丢掉历史，但也不占用 token 预算。

### 3.1 触发条件

```typescript
// episodic.ts
const SUMMARIZE_THRESHOLD = 15;

export function shouldSummarize(
  messages: { role: string; content: string }[],
): boolean {
  return countUserMessages(messages) > SUMMARIZE_THRESHOLD;
}
```

当用户累计发送超过 15 条消息时触发。`countUserMessages` 复用自 `working.ts`。

### 3.2 摘要生成流程

```
shouldSummarize(messages) === true
        │
        v
loadSummary(sessionId) 先查 localStorage 是否有缓存
        │
        ├── 有缓存 ──> 直接使用
        │
        └── 无缓存 ──> 取前 5 条消息 ──> fetch /api/agent/think
                             │
                             v
                     LLM 生成 ≤200 字摘要
                             │
                             v
                     saveSummary(sessionId, summary)
                     写入 localStorage: "zhiyuan_summary_{id}"
```

**摘要生成调用 `/api/agent/think`**，使用硬编码的 system prompt：

> "你是一个摘要助手。请用不超过200字总结以下对话的关键信息：用户讨论了什么话题、关注什么要点、做了什么决定。只输出摘要文本，不要加任何前缀。"

输入为前 5 条消息，截取前 3000 字符（`conversation.slice(0, 3000)`），降低 LLM 调用成本。

输出为 SSE 流式响应的聚合文本，最终截取前 200 字符。

### 3.3 存储机制

```typescript
const SUMMARY_PREFIX = "zhiyuan_summary_";

export async function saveSummary(sessionId: number, summary: string): Promise<void> {
  localStorage.setItem(`${SUMMARY_PREFIX}${sessionId}`, `[摘要] ${summary}`);
}

export async function loadSummary(sessionId: number): Promise<string> {
  return localStorage.getItem(`${SUMMARY_PREFIX}${sessionId}`) || "";
}
```

- **存储介质**：`localStorage`（浏览器端）
- **Key 格式**：`zhiyuan_summary_{sessionId}`
- **Value 格式**：`[摘要] {LLM 生成的摘要文本}`
- **生命周期**：与会话 ID 绑定，不会自动清理

注意：SQLite 中也有 `session_memory` 表（`summary_type = 'episodic'`），但当前 episodic.ts 的实现仍使用 `localStorage`。SQLite 路径是设计预留的后端持久化方案。

### 3.4 摘要注入

```typescript
// coordinator.ts
if (summaryInjection) {
  summaryInjection = `[摘要] ${summary}`;  // 已含前缀
}
// orchestrator/index.ts
const memoryDigest = ctx.memoryDigest || memCtx.summaryInjection || undefined;
```

摘要在 coordinator 中组装好 `[摘要]` 前缀，在 orchestrator 中作为 `memoryDigest` 传递给各子 Agent 的 system prompt。

## 4. 语义记忆 (Semantic Memory)

语义记忆从对话中**提取结构化用户画像事实**，跨会话持久化，形成对用户偏好和能力的长期理解。

### 4.1 数据结构

```typescript
export interface SemanticFacts {
  skills: string[];          // 技能列表，如 ["LLM应用", "数据分析", "产品设计"]
  salary: {                  // 薪资期望
    min?: number;
    max?: number;
    currency?: string;
  };
  industries: string[];      // 行业偏好，如 ["AI", "企业服务"]
  roles: string[];           // 岗位偏好，如 ["AI产品经理", "高级后端工程师"]
  dealbreakers: string[];    // 底线条件，如 ["不996", "不外包"]
  preferences: Record<string, string>;  // 其他偏好键值对
}
```

### 4.2 事实提取

```typescript
export async function extractFacts(
  messages: { role: string; content: string }[],
): Promise<SemanticFacts | null> {
```

调用 `/api/agent/think`，使用结构化提取 prompt：

> "你是信息提取助手。从对话中提取求职相关信息，只输出JSON。格式：{"skills":[],"salary":{},"industries":[],"roles":[],"dealbreakers":[],"preferences":{}}"

输入为全部消息的前 4000 字符。从 SSE 流中聚合文本后，用正则 `/\{[\s\S]*\}/` 提取 JSON 并解析。解析失败返回 `null`。

### 4.3 存储与读取

**存储**（`localStorage`）：

```typescript
const SEMANTIC_KEY = "zhiyuan_semantic_facts";
export async function saveSemanticFacts(facts: SemanticFacts): Promise<void> {
  localStorage.setItem(SEMANTIC_KEY, JSON.stringify(facts));
}
```

**读取**（渲染为紧凑文本）：

```typescript
export async function loadSemanticContext(): Promise<string> {
  // 读取 JSON → 转为中文描述
  // 岗位偏好: AI产品经理、高级后端工程师
  // 行业偏好: AI、企业服务
  // 薪资期望: 25K-35K
  // 底线条件: 不996、不外包
  // 技能: LLM应用、数据分析

}
```

### 4.4 在 orchestrator 中的注入

```typescript
// orchestrator/index.ts
if (memCtx.semanticInjection) {
  systemPrompt += `\n${memCtx.semanticInjection}`;
}
```

语义记忆以 `[已知用户偏好] ...` 格式**直接追加到 system prompt 末尾**，不与 careerDNA 或 memoryDigest 混合，确保 Agent 始终感知用户的长期画像。

### 4.5 与 Career DNA 的区别

| 维度 | Semantic Memory | Career DNA |
|------|----------------|------------|
| 来源 | LLM 从对话中自动提取 | `profile.yml` + IndexedDB ZhiyuanProfile |
| 内容 | 技能、薪资、行业、角色、底线 | 姓名、地点、目标岗位、archetype、成就、叙事 |
| 持久化 | `localStorage` JSON | 服务器端 YAML + IndexedDB |
| 更新方式 | `extractFacts()` 自动提取 | 用户手动编辑 / 系统学习 |
| 注入位置 | system prompt 末尾追加 | `AgentPromptContext.careerDNA`（前置） |

## 5. 记忆协调器 (Memory Coordinator)

`coordinator.ts` 是三层记忆的**唯一调度入口**。所有上下文组装逻辑集中在 `buildContext()` 中。

### 5.1 接口

```typescript
export interface MemoryContext {
  truncatedMessages: { role: string; content: string }[];  // Working
  summaryInjection: string;                                  // Episodic
  semanticInjection: string;                                 // Semantic
}

export async function buildContext(
  sessionId: number | null,
  messages: { role: string; content: string }[],
): Promise<MemoryContext>
```

### 5.2 组装流程

```
buildContext(sessionId, messages)
│
├── 1. Working Memory
│   truncatedMessages = buildWorkingContext(messages, 10)
│   （无状态，纯截取）
│
├── 2. Episodic Memory
│   if shouldSummarize(messages):          // > 15 条用户消息？
│     ├── summaryInjection = loadSummary(sessionId)  // 先读缓存
│     └── if !summaryInjection:
│           summary = generateSummary(messages[0:5])  // LLM 生成
│           if summary:
│             summaryInjection = "[摘要] " + summary
│             saveSummary(sessionId, summary).catch()  // 异步写缓存
│
├── 3. Semantic Memory
│   semanticInjection = loadSemanticContext()
│   （同步读 localStorage，无网络请求）
│
└── 返回 { truncatedMessages, summaryInjection, semanticInjection }
```

### 5.3 设计原则

1. **分层独立**：每层可以独立演进，不影响其他层。working 纯计算、episodic 异步 LLM、semantic 同步读。
2. **渐进增强**：`sessionId` 为 `null` 时（新会话），episodic 和 semantic 仍能工作（无缓存则跳过），不阻塞 Agent 运行。
3. **失败静默**：`generateSummary()` 和 `saveSummary()` 的异常被 `try/catch` 吞没，返回空字符串。不会因为摘要生成失败而阻断 Agent。
4. **缓存优先**：episodic 层先查 `localStorage` 缓存，命中则跳过 LLM 调用，节省 token 和延迟。

### 5.4 在 orchestrator 中的完整上下文装配

`orchestrator/index.ts` 的 `orchestrate()` 函数展示了**所有上下文来源的最终装配**：

```
systemPrompt =
  agent.buildSystemPrompt({
    careerDNA:         profile.yml + ZhiyuanProfile + CV localStorage
    memoryDigest:      episodic summary      ← 来自 coordinator
    currentMessages:   working messages       ← 来自 coordinator
    agentKnowledge:    knowledge injection    ← 来自 shared-memory
    claudeAgentActivity: SQLite 最近评估       ← 来自 shared-memory
  })
  + "\n" + semanticInjection                 ← 来自 coordinator (追加)
```

## 6. 会话管理

`sessions.ts` 管理 ChatSession 的完整生命周期，并生成 memory digest 供 Agent 使用。

### 6.1 ChatSession 数据结构

```typescript
export interface ChatSession {
  id?: number;
  title: string;               // 从首条用户消息截取前 6 字
  messages: AgentMessage[];    // 完整消息列表
  memoryDigest?: string;       // 服务端生成的摘要
  pinned: boolean;             // 置顶标记
  deletedAt?: string;          // 软删除时间
  createdAt: string;
  updatedAt: string;
}
```

### 6.2 会话 CRUD

| 操作 | 函数 | 存储策略 |
|------|------|---------|
| Create | `createSession(messages?)` | 先尝试 `POST /api/sessions`（SQLite），失败回退 Dexie IndexedDB |
| List | `listSessions()` | 从 Dexie 读取（`filter(!deletedAt).sortBy(updatedAt)`） |
| Get | `getSession(id)` | Dexie 单条查询 |
| Update | `updateSession(id, updates)` | Dexie 更新 + `PATCH /api/sessions/:id` 服务端同步（fire-and-forget） |
| Delete | `softDeleteSession(id)` | 设置 `deletedAt` + 5s 后物理删除 |
| Undo | `undoDeleteSession(id)` | 清除 `deletedAt` |
| Pin | `pinSession(id, pinned)` | 更新 pinned 字段 |
| Search | `searchSessions(query)` | 按 title + messages.content 模糊匹配 |

**双重存储策略**：
- **SQLite**（`data/zhiyuan.db` 的 `sessions` 表）是主存储源
- **Dexie IndexedDB** 是缓存层和离线回退
- 写操作：先 SQLite（`POST/PATCH`），成功后将返回 ID 写入 Dexie；SQLite 不可用时直接写 Dexie
- 读操作：当前从 Dexie 读（本地缓存），因为 `listSessions` 不走服务端 API

### 6.3 会话自动标题

```typescript
function makeTitle(messages: AgentMessage[]): string {
  const firstUser = messages.find((m) => m.role === "user");
  if (!firstUser) return "新对话";
  const text = firstUser.content.trim();
  if (text.length <= 6) return text;
  return text.slice(0, 6) + "...";
}
```

### 6.4 Memory Digest 生成

`generateMemoryDigest()` 是**规则引擎**，不依赖 LLM，从消息中提取结构化上下文：

```typescript
export function generateMemoryDigest(messages: AgentMessage[]): string | null {
  // 阈值: 至少 5 条用户消息
  // 提取:
  //   - 关注方向: 正则匹配 "岗位|职位|角色|方向|找|应聘|投递"
  //   - 关注公司: 正则匹配 "公司|企业|雇主"
  //   - 最近分析: 取最近 2 条助手回复 (>50字) 的前 100 字
  // 输出: "关注方向: ...; 关注公司: ...; 最近分析: ..."
}
```

**调用位置**：在 `agent/page.tsx` 中，每次用户发送消息后，若累计用户消息 >= 5 条，则生成 digest 并通过 `updateSession()` 持久化到 SQLite 的 `memory_digest` 字段。

### 6.5 默认会话机制

```typescript
export async function ensureDefaultSession(): Promise<number> {
  const sessions = await listSessions();
  if (sessions.length === 0) return createSession();
  return sessions[0].id!;
}
```

首次进入 Agent 页面时自动创建 `id=1` 的默认会话，确保消息有归属。

## 7. Claude Agent 活动桥接

`shared-memory.ts` 中的 `getClaudeAgentActivity()` 负责将 **Claude Agent（CLI 端）的评估历史** 桥接到 **Next.js Agent（Web 端）** 的上下文中。

### 7.1 数据来源

```typescript
export async function getClaudeAgentActivity(): Promise<string> {
  const res = await fetch("/api/agent/claude-activity");
  return data.activity || "";
}
```

API 路由 `/api/agent/claude-activity` 读取 `data/zhiyuan.db` 中的 `applications` 表：

```sql
SELECT company, role, score, status, date, notes
FROM applications
WHERE status NOT IN ('SKIP','Discarded')
ORDER BY num DESC LIMIT 5

SELECT status, COUNT(*) as cnt FROM applications GROUP BY status
```

### 7.2 生成文本格式

```
[Claude Agent 最近活动]
最近评估:
• 字节跳动 | AI产品经理 | 4.2/5 🟢 | 2026-05-10
• 美团 | 高级后端工程师 | 3.5/5 🟡 | 2026-05-09
管道状态: 3条待投递 | 5条进行中
```

风险等级图标映射：`notes` 包含 "高风险" → 🔴，"中风险" → 🟡，其他 → 🟢。

### 7.3 注入路径

```
SQLite applications 表
  → /api/agent/claude-activity
  → shared-memory.ts getClaudeAgentActivity()
  → orchestrator/index.ts orchestrate()
  → AgentPromptContext.claudeAgentActivity
  → 各子 Agent 的 buildSystemPrompt()
```

在每个 Agent 的 system prompt 模板中，`claudeAgentActivity` 以独立段落注入：

```
${ctx.claudeAgentActivity ? `## Claude Agent 活动\n${ctx.claudeAgentActivity}` : ""}
```

### 7.4 Career DNA 的并行获取

同一模块还提供 `getCareerDNASummary()`，聚合多个数据源：

```
优先级:
  1. /api/profile/dna  (profile.yml → 结构化摘要)
     ├── 姓名、地点
     ├── 目标岗位 (primary + archetypes)
     ├── 薪资期望
     ├── 底线条件
     └── 叙事 (superpower, passion, achievement)
  2. IndexedDB ZhiyuanProfile (goals, skills)
  3. "用户画像数据暂不可用" (fallback)
```

在 `orchestrate()` 中，Career DNA 和 Claude Activity 通过 `Promise.all` 并行获取，与三层记忆异步组装。

## 8. 存储架构

### 8.1 sessions 表 (SQLite)

```sql
CREATE TABLE IF NOT EXISTS sessions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL DEFAULT '新对话',
  messages_json TEXT NOT NULL DEFAULT '[]',
  memory_digest TEXT,                     -- generateMemoryDigest() 输出
  pinned INTEGER NOT NULL DEFAULT 0,
  deleted_at TEXT,                        -- 软删除标记
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_sessions_updated ON sessions(updated_at);
```

### 8.2 session_memory 表 (SQLite, 预留)

```sql
CREATE TABLE IF NOT EXISTS session_memory (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER DEFAULT 0,           -- 0 = 全局/跨会话
  summary_type TEXT NOT NULL,             -- 'episodic' | 'semantic' | 'digest'
  content TEXT NOT NULL,                  -- 摘要/事实/记忆的文本
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_session_memory_type ON session_memory(summary_type);
```

此表设计为统一存储 episodic 摘要和 semantic 事实，但当前实现仍使用 `localStorage`。`summary_type` 区分记录类型：

| summary_type | 对应层级 | 内容 |
|-------------|---------|------|
| `episodic` | Episodic Memory | 单次会话的 LLM 摘要 |
| `semantic` | Semantic Memory | 跨会话的结构化事实 |
| `digest` | Memory Digest | `generateMemoryDigest()` 的规则提取 |

### 8.3 localStorage 键空间

| Key | 格式 | 内容 | 来源 |
|-----|------|------|------|
| `zhiyuan_summary_{id}` | `"[摘要] {text}"` | 会话摘要 | episodic.ts |
| `zhiyuan_semantic_facts` | `JSON(SemanticFacts)` | 用户画像事实 | semantic.ts |
| `zhiyuan-cv` | `JSON(CVData)` | 简历数据 | cv-storage.ts |

### 8.4 Memory Digest JSON 格式 (messages_json)

`sessions.messages_json` 存储完整消息数组的 JSON 序列化：

```json
[
  {
    "role": "user",
    "content": "帮我看看字节 AI PM 这个岗位",
    "mode": "explore",
    "agent_id": "evaluate",
    "timestamp": "2026-05-11T10:00:00.000Z"
  },
  {
    "role": "assistant",
    "content": "好的，我来评估这个岗位...",
    "agent_id": "evaluate",
    "toolName": "evaluateJD",
    "toolResult": { "score": 4.2, "blocks": {...} },
    "timestamp": "2026-05-11T10:00:05.000Z"
  }
]
```

`sessions.memory_digest` 存储 `generateMemoryDigest()` 输出的紧凑文本：

```
关注方向: 岗位:AI产品经理、职位:高级后端; 关注公司: 公司:字节; 最近分析: 该岗位综合评分为4.2分... | 风险方面需注意...
```

## 9. 完整调用链路

以一次用户提问为例，展示三层记忆 + 共享上下文的完整协作：

```
用户输入: "字节 AI PM 这个岗位怎么样"

1. agent/page.tsx
   ├── 构建 messages 数组（含历史）
   ├── 读 session.memoryDigest（从 IndexedDB / SQLite）
   └── 调用 orchestrate(content, { sessionId, messages, memoryDigest })

2. orchestrator/index.ts orchestrate()
   ├── classifyIntent("字节 AI PM 这个岗位怎么样") → evaluate-agent
   ├── Promise.all 并行获取:
   │   ├── getCareerDNASummary()      → "目标岗位: AI产品经理\n薪资期望: 25K-35K..."
   │   ├── getCVSummary()             → localStorage 简历文本
   │   ├── getKnowledgeForAgent(...)  → 评估领域知识
   │   └── getClaudeAgentActivity()   → SQLite 最近5条评估
   ├── buildContext(sessionId, messages):
   │   ├── buildWorkingContext(msgs, 10)    → 最近10条消息
   │   ├── shouldSummarize(msgs) → false    → 跳过
   │   └── loadSemanticContext()            → "[已知用户偏好] 岗位偏好: AI产品经理 | 底线: 不996"
   ├── agent.buildSystemPrompt({
   │     careerDNA,
   │     memoryDigest,
   │     currentMessages: truncatedMessages,
   │     agentKnowledge,
   │     claudeAgentActivity
   │   })
   └── systemPrompt += "\n" + semanticInjection

3. Agent 收到最终 system prompt，包含:
   [用户画像] careerDNA + CV
   [Claude 活动] 最近评估记录
   [领域知识] 评估维度解释
   [会话记忆] 最近10条消息
   [已知用户偏好] 语义记忆提取的长期画像

4. agentLoopClient 发送 systemPrompt + messages → DeepSeek
```

## 10. 设计权衡与演进方向

### 10.1 当前权衡

| 决策 | 理由 | 代价 |
|------|------|------|
| episodic 摘要走 `localStorage` 而非 SQLite | 避免阻塞 UI 线程的网络延迟 | 换设备丢失摘要 |
| semantic 提取不自动触发 | LLM 调用有成本，仅按需提取 | 需要手动调用 `extractFacts()` |
| working 窗口固定 10 条 | 简单可预测，token 消耗可控 | 长对话可能丢失早期关键信息 |
| 摘要阈值为 15 条用户消息 | 摘要有 LLM 成本，短对话不值得 | 10-15 条之间的对话既无完整历史也无摘要 |
| sessions 读走 Dexie 不走 API | 即时响应，离线可用 | 多端数据可能不一致 |

### 10.2 演进方向

1. **自动触发语义提取**：在 `buildContext()` 中检测到新事实线索时自动调 `extractFacts()`，而非等待手动调用。
2. **SQLite 迁移**：episodic 摘要和 semantic 事实写入 `session_memory` 表，实现多端同步。
3. **动态工作记忆窗口**：根据消息复杂度（token 数）自适应调整保留条数，而非固定的 10 条。
4. **摘要增量更新**：当前每次重新生成摘要时只用前 5 条消息。应改为基于已有摘要做增量更新。
5. **跨会话语义合并**：多个会话的 semantic 事实应合并去重，而非各自覆盖。
6. **向量化检索**：session_memory 表增加 embedding 列，支持语义相似度检索历史记忆。
