# 19 -- 分层记忆系统

## 概述

筝筝纸鸢的记忆系统现在由两条线组成：

1. **会话记忆线**：working / episodic / semantic 三层上下文，负责让 Agent 在当前对话和近期会话里不丢上下文。
2. **长期向量记忆线**：PostgreSQL/pgvector 上的优秀简历、通用 memory items、证据、chunks 和反馈晋升，负责让系统沉淀可检索、可治理、可共享的长期知识。

当前局域网运行态已切到 PostgreSQL/pgvector。SQLite 只保留本地 fallback、迁移源和归档读取能力。

---

## 1. 总体架构

```text
用户消息
  -> AgentChat
  -> sessions.messages_json
  -> generateMemoryDigest / compressing_context
  -> memory coordinator
  -> orchestrator prompt context
  -> Agent Loop
```

```text
长期材料
  -> reference_resumes / memory_items
  -> evidence / chunk
  -> embedding
  -> pgvector 检索
  -> admin memory governance
  -> 反馈晋升 / 禁用 / 归档
```

---

## 2. 会话三层记忆

| 层 | 职责 | 典型来源 | 当前存储 |
|----|------|----------|----------|
| Working | 保留当前对话最近消息，给模型即时上下文 | 最近 N 条 messages | React state / runner context |
| Episodic | 对长会话生成摘要，减少上下文爆炸 | `generateMemoryDigest()`、LLM 摘要 | `sessions.memory_digest` / `session_memory` |
| Semantic | 注入稳定画像事实和任务相关事实 | profile、cv、最近 JD、历史报告、对话信号 | repository-backed tables；LAN 为 Postgres |

触发长会话压缩时，Agent Chat 会显示 `compressing_context`，先生成摘要再继续执行后续任务。这个状态必须可见，避免用户以为系统卡住。

---

## 3. 长期向量记忆

长期记忆依赖 PostgreSQL/pgvector，主要表包括：

| 表 | 用途 |
|----|------|
| `reference_resumes` | 优秀/参考简历主记录 |
| `reference_resume_chunks` | 优秀简历切片和 embedding |
| `reference_resume_usage` | 检索使用与反馈 |
| `memory_items` | 通用长期记忆条目 |
| `memory_evidence` | 记忆证据 |
| `memory_status_transitions` | 候选/激活/拒绝/归档状态流转 |
| `memory_chunks` | 通用长期记忆向量 chunk |

长期记忆状态：

```text
candidate -> active
candidate -> rejected
active/rejected -> archived
archived -> candidate
```

---

## 4. 优秀简历记忆

用户说“把这份简历保存成优秀简历”时，系统不能直接保存。必须先确认：

1. **岗位方向**：例如 AI 产品经理、AI 运营、AI 售前、数据产品经理。
2. **可见性**：默认私有；用户明确要求局域网/团队共享时才进入 team 路径。

流程：

```text
用户提供优秀简历
  -> 识别或读取简历正文
  -> 若岗位方向缺失，先询问
  -> save_reference_resume
  -> reference_resumes 写入
  -> 读回校验
  -> chunk + embedding best effort
  -> /admin/memory 治理
```

成功条件：

- 来源简历内容存在。
- 岗位方向已确认。
- 参考简历记录已保存。
- 读回校验通过。

读回失败时，Agent 不能告诉用户“已保存为长期记忆”。

---

## 5. 检索与使用边界

优秀简历和长期记忆的目标是帮助用户优化表达，不是复制别人的原文。

检索会考虑：

- 岗位方向。
- 语义相似度。
- 质量分。
- 使用反馈可信度。
- 私有/团队可见性。
- no-copy overlap guard。

Agent 使用方式：

- 可以参考结构、项目拆解方式、指标密度、关键词覆盖。
- 不应把参考简历原文直接写入用户简历。
- 团队共享材料需要管理员治理，不默认开放给所有用户。

---

## 6. 画像与信号记忆

求职画像不是简单把聊天中出现的短词都存进技能表。当前应遵循：

- 低质碎片、短词、上下文不完整片段应被拒绝。
- 技能信号需要证据、来源和类型。
- 写入 `profile_signals` 后必须读回。
- 可确认技能写入 profile 后也要验证 profile 中确实包含该技能。

相关路径：

```text
Agent 对话 / 行为
  -> profile signal extraction
  -> /api/data/signals
  -> profileSignalReadBackMatches
  -> profileContainsSkill
```

管理员和 eval 复盘会关注 `profile_signal_noise`，用于沉淀“无效底线/无效技能被提取”的回归样例。

---

## 7. 管理员记忆治理

入口：`/admin/memory`

当前治理对象：

- 全部优秀简历材料。
- 团队共享候选。
- 候选记忆模式。
- embedding 待处理/失败状态。
- 风险参考材料。

管理员动作：

- 接受或拒绝候选记忆。
- 禁用低质量参考材料。
- 审核团队共享材料。
- 查看 embedding 健康和索引状态。

普通用户不需要看到完整治理后台。对普通用户来说，记忆能力应该表现为“系统更懂我的简历、岗位方向和表达偏好”，而不是暴露复杂的候选队列。

---

## 8. 记忆与 Agent 自进化的边界

当前系统已经能沉淀数据，但还不是完全自动自修复系统。

已经具备：

- 长会话摘要和上下文压缩。
- 优秀简历向量化。
- 候选记忆模式。
- 反馈晋升。
- 记忆读回校验。
- 管理员治理。
- `eval:memory` 确定性回归。
- `smoke:embedding` 真实 embedding smoke test。

尚未自动化：

- 自动把 eval 候选写成测试。
- 自动改代码修复 Agent bug。
- 自动部署。
- 在 OCR 或 embedding 服务持续失败时保证任务成功。

因此，“长期记忆”提供的是事实沉淀和检索增强；“自我修复”仍需要 run review、eval 候选、开发者确认和代码修改共同完成。

---

## 9. 相关命令

| 命令 | 用途 |
|------|------|
| `npm run backfill:memory` | 为已有记忆/优秀简历补向量 |
| `npm run eval:memory` | 跑确定性记忆 eval |
| `npm run smoke:embedding` | 检查真实 embedding provider |
| `npm run check:postgres` | 检查 Postgres 与 pgvector |
| `npm run check:postgres-cutover` | 检查当前 runtime 是否干净切到 Postgres |
