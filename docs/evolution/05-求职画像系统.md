# 05 — 求职画像系统

> 所属阶段：Phase 1-3 · Profile + CV + Archetype 三层架构 + repository-backed profile_signals + Dexie/IndexedDB 缓存

---

## 1. 设计理念

求职画像系统是筝筝纸鸢的**"你是谁"引擎**。它不只是存一份简历——它构建了一个**自适应的求职身份**，同一份经历根据岗位类型自动切换叙事框架。

### 数据源全景

```
┌──────────────────────────────────────────────────────────┐
│                    求职画像 (Career DNA)                   │
│                                                          │
│  ┌─────────────────┐  ┌──────────────┐  ┌─────────────┐  │
│  │ 文件层 (4层)     │  │ Repository   │  │ IndexedDB   │  │
│  │                 │  │ profile_signals│  │ CareerDNA   │  │
│  │ cv.md           │  │ 信号表        │  │ 离线缓存     │  │
│  │ profile.yml     │  │ source/type  │  │ goals/prefs │  │
│  │ _profile.md     │  │ content_json │  │ skills      │  │
│  │ article-digest  │  │ session_id   │  │ dealBreakers│  │
│  └─────────────────┘  └──────────────┘  └─────────────┘  │
│                                                          │
│  Orchestrator 组装 AgentPromptContext { careerDNA, ... }  │
│  注入到所有子 Agent 的 system prompt                       │
└──────────────────────────────────────────────────────────┘
```

### 灵感来源

系统的 adaptive framing 设计受 **Andrej Karpathy 的 Personal Wiki** 理念启发：

| Karpathy's Wiki | 筝筝纸鸢 Profile |
|-----------------|-----------------|
| "Living document" — 持续更新 | Profile 是活的——每次评估后 Agent 学到新东西 |
| Multi-layered (notes, projects, talks) | 多源数据：文件 + repository + IndexedDB |
| Concrete metrics over adjectives | Proof points 必须有 hero_metric |
| Same person, different framing per audience | 同一个 proof point，不同 archetype 用不同叙事 |

> **注**：这是设计哲学层面的参考，不是代码层面的直接引用。

## 设计思想

求职画像系统的核心理念源自 **Andrej Karpathy 的个人 Wiki 方法论**——他曾在演讲中反复强调一个观点：使用 LLM 最有效的方式不是每次都从头写 prompt，而是维护一份不断演进的"个人上下文文档"，把你是谁、你关心什么、你的工作方式全部写进去，让 LLM 在每次对话时自动加载。筝筝纸鸢的求职画像正是这一理念在求职场景中的工程化实践。

传统求职工具要求用户手动填表——目标岗位、期望薪资、技能列表——这些静态字段很快就过时了，而且无法捕捉到一个人身上那些微妙的、不断变化的偏好。Karpathy 的洞察是：**AI 应该通过观察你的行为来学习你**，而不是让你填一份问卷。求职画像系统正是这样做的——它不问你"你的底线是什么"，而是观察你在评估时对哪些岗位说"这个不靠谱"，从拒绝中提炼你的 dealbreaker；它不问你"你的优势是什么"，而是观察你对哪些评价维度特别关注，从你的注意力分布中推断你的 superpower。

系统采用了**多层数据架构**来承载这种渐进式学习。最底层是 cv.md 和 profile.yml 的结构化身份——这些是用户主动提供的基础事实，不可被 Agent 自动覆盖。中间层是 repository-backed `profile_signals` 表——每一次对话、每一次评估都在这里留下信号痕迹，当前 LAN 写入 PostgreSQL。最高层是 IndexedDB 的 CareerDNA 缓存——将分散的信号提炼为可快速加载的上下文摘要。这三层不是简单的数据冗余，而是模拟了人类认知的三个层次：基础事实（我知道我是谁）、行为信号（我通过行动表达偏好）、提炼认知（我从行为中学习自己）。

最核心的设计决策是**自适应叙事引擎**。同一个人的同一份经历，面对 AI 产品经理岗位和 AI 运营岗位时，应该讲述不同的故事。这不是"美化简历"或者"造假"——而是像任何优秀的沟通者一样，根据听众切换表达重点。Karpathy 的 Wiki 中同一个项目可能出现在多个上下文中（技术演讲、博客文章、内部文档），每次都用不同的叙事框架。求职画像系统将这一原则系统化：6 个 AI 岗位 Archetype 各自有独立的证明点优先级、STAR 故事框架和职业叙事方向。Agent 不替你编造经历——它帮你选择哪些经历放在聚光灯下。

这种设计的另一个关键优势是**跨 Agent 认知一致性**。当用户从 JD 评估 Agent 切到面试教练 Agent 时，两个 Agent 的 system prompt 中都注入了同一份 Career DNA。你不是在和一群互不相识的 AI 对话——你是在和一个持续了解你的人工助手协作。这种一致性在传统求职工具中几乎不存在，却是 AI 原生体验的核心差异化。

## 2. 数据架构

### 2.1 文件层（4层，User Layer）

```
Layer 1: cv.md                    ← 原始简历（Markdown）
  └─ Layer 2: config/profile.yml   ← 结构化身份（YAML）
       └─ Layer 3: modes/_profile.md ← 自定义 archetype 映射 + 叙事框架
            └─ Layer 4: article-digest.md ← 详细证明点（可选）
```

#### Layer 1: cv.md — 标准简历

```markdown
# 张三 — 高级AI产品经理
## Summary
10年产品经验，主导3款AI产品从0到1...
## Experience
### 字节跳动 | AI产品负责人 | 2022-至今
...
## Projects
...
```

#### Layer 2: config/profile.yml — 结构化身份

```yaml
candidate:
  full_name: "张三"
  location: "北京市朝阳区"
  target_roles:
    primary: ["高级AI产品经理", "AI产品负责人"]
    archetypes:
      - name: "AI产品经理"
        level: "高级/负责人"
        fit: "primary"
      - name: "AI运营"
        fit: "secondary"
  narrative:
    headline: "10年产品人转型AI产品"
    superpowers:
      - "AI产品方案设计"
      - "用户需求挖掘与数据分析驱动决策"
      - "跨部门推动"
    proof_points:
      - name: "AI客服机器人"
        hero_metric: "将客服效率提升60%，日均处理5000+对话"
```

#### Layer 3: modes/_profile.md — 自定义 Archetype 映射

```markdown
## 你的自适应框架
| 如果岗位是…… | 强调你的…… | 证明来源 |
| AI产品经理 | 产品从0到1经验、AI功能设计 | article-digest.md + cv.md |
| AI运营 | 增长策略执行、AI工具在运营中的应用 | cv.md |
```

#### Layer 4: article-digest.md — 详细证明点（可选）

当 cv.md 不够时，提供更详细的量化指标和项目描述。

### 2.2 Repository：profile_signals 表

`profile_signals` 表是画像信号的**服务端持久化存储**。PostgreSQL schema 定义在 `src/lib/postgres-schema.sql`，SQLite fallback schema 定义在 `src/lib/server-schema.sql`：

```sql
CREATE TABLE IF NOT EXISTS profile_signals (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  source TEXT NOT NULL DEFAULT 'dingwei',   -- 信号来源 (dingwei/evaluate/interview/...)
  signal_type TEXT NOT NULL,                -- 信号类型 (skill_claim/role_pref/dealbreaker/superpower/...)
  content_json TEXT NOT NULL DEFAULT '{}',  -- 信号内容 (JSON)
  session_id TEXT,                          -- 关联会话
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_profile_signals_type ON profile_signals(signal_type);
CREATE INDEX IF NOT EXISTS idx_profile_signals_created ON profile_signals(created_at);
```

信号类型包括：
- `skill_claim` — 用户声明的技能
- `role_pref` — 岗位偏好
- `dealbreaker` — 硬底线
- `superpower` — 自述优势
- `limit_belief` — 限幅信念
- `direction` — 职业方向收敛结果

### 2.3 IndexedDB：CareerDNA 缓存

前端通过 Dexie.js 在 IndexedDB 中维护 `ZhiyuanProfile` 表，作为 CareerDNA 的离线缓存层：

```
IndexedDB: zhiyuan-profiles
  ├── goals          → { targetRoles[], salaryRange, dealBreakers[] }
  ├── skills         → [{ name, level }]
  ├── preferences    → { location, remote, industry }
  └── lastUpdated    → timestamp
```

`getCareerDNASummary()` (`src/lib/agent/shared-memory.ts`) 的读取优先级为：
1. `/api/profile/dna` 服务端 API（汇总 profile_signals + profile.yml）
2. IndexedDB `ZhiyuanProfile` 表（离线降级）
3. 降级字符串："用户画像数据暂不可用"

## 3. Orchestrator 的组装角色

`src/lib/agent/orchestrator/index.ts` 是画像数据的**中央装配器**。它在每次用户消息路由时运行：

```
用户消息
    │
    ▼
orchestrate(content, ctx)
    │
    ├── 1. classifyIntent(content) → 选择子 Agent
    │
    ├── 2. 并行加载:
    │     getCareerDNASummary()  → Career DNA 文本 (profile_signals + IndexedDB)
    │     getCVSummary()         → 简历摘要 (repository / cache)
    │     getKnowledgeForAgent() → 领域知识注入
    │     getClaudeAgentActivity() → 历史评估摘要
    │
    ├── 3. buildContext(sessionId, messages) → 分层记忆
    │
    └── 4. 组装 AgentPromptContext:
          {
            careerDNA,          ← 注入到所有 Agent 的 system prompt
            memoryDigest,        ← 会话摘要 (≥5条用户消息后激活)
            currentMessages,     ← 截断后的消息历史
            agentKnowledge,      ← 领域特定知识
            claudeAgentActivity  ← repository 历史评估记录
          }
          ↓
          agent.buildSystemPrompt(ctx) → 最终 system prompt
```

这意味着每个子 Agent（evaluate-agent、profile-agent、resume-agent、interview-agent、general-agent）的 system prompt 都包含同一份 Career DNA，保证了跨 Agent 的用户认知一致性。

### profile-agent.ts

`src/lib/agent/registry/agents/profile-agent.ts` 是求职画像子代理的定义文件。它负责：
- 自我定位 (dingwei) 对话引导
- 技能分析与职业方向收敛
- 限幅信念检测与矫正

其 `buildSystemPrompt` 注入 CareerDNA 上下文，并加载 dingwei SOP prompt（优先从 `/api/agent/context?scenario=dingwei` 获取，降级为内置 prompt）。

## 5. 6 个 AI 岗位 Archetype

系统内置 6 个中国 AI 市场核心岗位类型：

```
┌─────────────────────────────────────────────────────┐
│  AI产品经理    AI运营    AI解决方案                   │
│  (产品规划)    (增长)    (售前方案)                   │
│                                                     │
│  AI项目经理    AI咨询    AI增长/市场                  │
│  (交付管理)    (变革)    (获客增长)                   │
└─────────────────────────────────────────────────────┘
```

每个 Archetype 有独立的：
- 优先证明点（B 板块按 Archetype 调整）
- STAR 故事框架（F 板块按 Archetype 选择）
- 职业叙事方向（E 板块按 Archetype 生成求职信）

## 6. 自适应叙事引擎

### 工作流

```
求职画像 (profile.yml + _profile.md + profile_signals + IndexedDB)
    │
    ▼
JD Archetype 检测 (6选1或混合2个)
    │
    ▼
匹配画像中的对应 Archetype
    │
    ├──→ 选择该 Archetype 的 superpower 和 proof_point
    ├──→ 调整叙事框架 ("AI产品" vs "AI运营" vs "AI解决方案")
    └──→ 生成定制化简历摘要 + 求职信草稿
```

### 示例

同一份 CV 对不同岗位的输出：

**岗位 A: AI产品经理 (Primary)**
> "10年产品经验，主导3款AI产品从0到1。擅长PRD到上线的全流程，用数据驱动产品决策。"

**岗位 B: AI运营 (Secondary)**
> "10年互联网经验，专注增长策略和AI工具在运营中的落地。曾用A/B测试将社区用户从1万增长到10万。"

## 7. 数据闭环：评估后学习

```
每次评估后
    │
    ├── 用户说 "这个 archetype 不对" → 更新 _profile.md
    ├── 用户说 "你漏了我的X经验" → 更新 article-digest.md
    ├── Agent 学到新模式 → 建议更新 profile.yml
    └── profile_signals 表自动追加 (source=evaluate)
```

**关键规则**：Agent 绝不自动更新 User Layer 文件。用户始终掌控自己的画像。

### API 端点

| 端点 | 功能 | 数据源 |
|------|------|--------|
| `/api/profile/dna` | 返回 CareerDNA 摘要 | profile_signals + profile.yml |
| `/api/cv/dna` | 返回 CV 结构化数据 | repository-backed CV 数据 + 浏览器缓存 |
