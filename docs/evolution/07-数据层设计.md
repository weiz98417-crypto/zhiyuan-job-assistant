## 2. DATA_CONTRACT 分层

```
User Layer (NEVER auto-updated):
  用户数据、自定义、工作产出 — 更新永不修改
  ├── cv.md                      个人简历
  ├── config/profile.yml          身份、目标、薪资
  ├── modes/_profile.md           自定义 archetype 映射
  ├── article-digest.md           详细证明点
  ├── portals.yml                 搜索配置
  ├── data/applications.md        只读 legacy
  ├── data/pipeline.md            只读 legacy
  ├── reports/*.md                评估报告
  └── output/*.pdf                生成的简历

System Layer (safe to auto-update):
  系统逻辑、脚本、模板 — 随版本更新
  ├── modes/*.md                  模式文件
  ├── scripts/*.mjs               工具脚本
  ├── root *.mjs                  根级实用脚本
  ├── templates/*                 基础模板
  ├── CLAUDE.md                   Agent 指令

```

**硬规则**：Agent 自定义必须写入 User Layer（`modes/_profile.md` 或 `config/profile.yml`），绝不写入 System Layer。

## 3. 写入路径

### 主要路径 A：Next.js API → `server-db.ts` → SQLite

`src/lib/server-db.ts` 封装 `better-sqlite3`，供所有 API route 使用：

```typescript
import { getDb } from "@/lib/server-db";
// → 返回单例 better-sqlite3 Database 实例
// → 启动时自动执行 autoRunMigrations() 建表
```

API routes 直接写入对应表：
- `/api/sessions` → `sessions` 表（CRUD）
- `/api/offers` → `offers` 表
- `/api/stories` → `stories` 表
- `/api/cv/data` → `cv_data` 表
- `/api/data/reports` → `reports` 表读取
- `/api/data/reports/[reportNum]` → 单体报告读取/更新/删除
- `/api/data/jds` → `jds` 表读取/写入/删除
- `/api/agent/persist-eval` → `applications` + `reports` + `jds` 评估结果持久化
- `/api/report/save` → 人工确认后的报告/JD/追踪表持久化
- `/api/agent/prefs` → `agent_preferences` 表
- `/api/cv/record-preference` → `optimization_preferences` 表
- `/api/agent/coach/session` → `session_memory` 表（摘要写入）
- `/api/agent/context` → `session_memory` 表（跨会话语义读取）

### 评估产物写入路径：报告 + JD 同步入库

JD 评估完成后，服务端以 SQLite 作为事实源，同步写入三类记录：

1. `applications`：用于 Pipeline/首页/Analytics 的评估记录，按 `company + role` upsert。
2. `reports`：用于报告库、历史评估、PDF 导出，主键口径是公开编号 `report_num`。
3. `jds`：用于 JD 库和后续“这份 JD/刚才的 JD”上下文读取，`report_id` 存储对应报告的 `report_num`。

对应入口：
- `evaluate_jd_full` / client runner 完成后调用 `/api/agent/persist-eval`，该接口写入 `applications`、`reports`，并在 JD 正文长度足够时写入 `jds`。
- `/api/report/save` 用于人工确认保存场景，同样可写入 `reports`、`applications` 和 `jds`。
- `createJD()` 先调用 `/api/data/jds` 写入服务端；只有 API 不可用时才 fallback 到 Dexie。

`jds.report_id` 的外键口径是 `reports.report_num`，不是内部自增主键 `reports.id`。`server-db.ts` 启动时会检测旧外键并迁移：如果历史库中 `jds.report_id` 指向 `reports.id`，会转换为对应的 `report_num`。

### 评估读取与统计口径

评估页和报告/JD 子页面以服务端 API 为第一数据源：

- `/evaluate` 统计卡片并行读取 `/api/data/jds` 与 `/api/data/reports`，JD 数、报告数、平均分均来自服务端结果。
- `/evaluate/jds` 先读 `/api/data/jds`，失败后才回退 Dexie。
- `/evaluate/history` 与 `/evaluate/reports` 先读 `/api/data/reports`，失败后才回退 Dexie。
- Dexie 是离线/降级缓存，不是评估数量和报告库展示的主事实源。

### 主要路径 B：`db-write.mjs` → SQLite（Claude Agent 端）

```bash
# 应用记录
node scripts/db-write.mjs --action upsertApp --data '{
  "num": 42, "date": "2026-05-09", "company": "Acme",
  "role": "AI PM", "score": 4.2, "status": "Evaluated",
  "pdf_generated": 0, "report_path": "reports/042-acme-2026-05-09.md",
  "notes": ""
}'
# → INSERT ... ON CONFLICT(company, role) DO UPDATE

# 报告元数据
node scripts/db-write.mjs --action upsertReport --data '{...}'
# → INSERT ... ON CONFLICT(report_num) DO UPDATE
```

### Legacy Fallback：TSV（`db-write.mjs` 不可用时）

```bash
# 写入 batch/tracker-additions/042-acme.tsv
# 仅作为最低限度容错手段，不再推荐
042\t2026-05-09\tAcme\tAI PM\tEvaluated\t4.2/5\t❌\t[042](reports/...)\t备注
```

### 输入净化

`db-write.mjs` 和 `server-db.ts` 均对所有输入做净化：
- 控制字符过滤（`[\x00-\x08\x0b\x0c\x0e-\x1f]`）
- score 范围校验（1.0-5.0）
- date 格式校验（YYYY-MM-DD）
- company/role 不能为空
- SQLITE_BUSY 指数退避重试（3次, max 2s）

## 4. server-db.ts 自动迁移机制

`server-db.ts` 在首次导入时自动执行 `autoRunMigrations()`：

1. 读取 `src/lib/server-schema.sql`（所有 `CREATE TABLE IF NOT EXISTS` 语句）
2. 逐条执行建表语句（幂等，重复执行安全）
3. 新部署/新表自动创建，无需手动迁移脚本
4. 启动日志输出：`autoRunMigrations created N new tables`

**注意**：此机制仅负责建表（DDL），不负责数据迁移。数据迁移由 `migrateFromFiles()` 函数处理（解析 legacy 文件导入 SQLite）。

## 5. 关键子系统

### 三层记忆系统（session_memory 表）

`session_memory` 表是跨 Agent/跨会话记忆的底层存储：

| `summary_type` | 来源 | 用途 |
|---------------|------|------|
| `episodic` | `memory/episodic.ts` | 长会话自动摘要（15+ 轮触发） |
| `semantic` | `memory/semantic.ts` | 跨会话事实（如"用户偏好远程工作"） |
| `context` | `/api/agent/context` | 外部 Agent 注入的上下文片段 |

由 `memory/coordinator.ts` 统一编排读取，注入到 Agent 的 System Prompt 中。

### Judge Engine 学习循环（optimization_preferences 表）

简历优化工具的反馈循环：
1. 用户对某 section 优化结果点击"接受"或"拒绝"
2. `/api/cv/record-preference` 写入 `optimization_preferences`
3. `action` 字段记录 `accept` / `reject`
4. 积累的 accept/reject 模式用于后续优化时的风格偏好推断
5. 为未来的个性化优化模型提供训练数据

### Agent 偏好衰减（agent_preferences 表）

`agent_preferences` 实现了带衰减的偏好模型：
- `entity_type` + `entity_key` 唯一标识一个偏好项
- `weight` 表示偏好强度，随时间衰减
- `decay_rate` 控制衰减速度（默认 0.05/次）
- 每次匹配后更新权重并刷新 `last_updated`
- `/api/agent/prefs` 提供读写接口

## 6. 并发与完整性

| 机制 | 实现 |
|------|------|
| WAL 模式 | `pragma journal_mode=WAL` — 读写并发安全 |
| 繁忙超时 | `pragma busy_timeout=5000` — 等 5 秒 |
| 重试 | `runWithRetry()` — 指数退避 100ms→400ms→2s |
| 去重 | `ON CONFLICT(company, role)` — SQLite 原生 upsert |
| 错误日志 | `data/db-write-errors.log` — 失败写入自动记录 |

## 7. 迁移策略

### 初始导入

`server-db.ts` 的 `migrateFromFiles()` 函数：
- 解析 `data/applications.md` → 逐行导入 `applications` 表
- 解析 `reports/*.md` → 提取元数据 → 导入 `reports` 表
- 已存在记录（同 company+role 或同 report_num）自动跳过

### 回滚

- SQLite 文件删除 → 重新运行 `migrateFromFiles()` 恢复
- 所有改动是增量文件 → `git revert` 即可
