# 07 -- 数据层设计

所属阶段：Phase 0-3 持续演进  
当前状态：局域网运行态为 PostgreSQL/pgvector；SQLite 保留为 fallback、迁移源和归档读取路径。

---

## 1. 当前结论

项目的数据层已经从“SQLite 单文件主导”演进为“repository 抽象 + PostgreSQL 当前运行 + SQLite 兼容保留”。

当前分工：

| 层 | 当前角色 | 说明 |
|----|----------|------|
| `src/lib/data-repositories.ts` | 业务数据访问主入口 | 根据 `DB_DRIVER` 返回 Postgres 或 SQLite repository |
| PostgreSQL | 当前 LAN 权威事实源 | 多用户、报告、JD、Offer、简历、运行台账、复盘、向量记忆 |
| pgvector | 长期记忆检索基础 | 优秀简历 chunk、通用 memory chunks、语义检索 |
| SQLite | fallback / migration source / archive | 本地轻量运行、历史数据迁移、归档读取 |
| `server-db.ts` | SQLite legacy adapter | `DB_DRIVER=postgres` 时阻止直接写入，除非 `ALLOW_SQLITE_LEGACY=readonly` |

不能简单删除 SQLite，因为迁移、回滚、归档读取和部分 legacy 脚本仍依赖它；但当前局域网服务的主事实源不应再写成 SQLite。

---

## 2. 当前运行路径

```text
Next.js API / Agent Tools
  -> getDataRepositories()
  -> DB_DRIVER=postgres
  -> PostgreSQL + pgvector
  -> read-back verification
  -> Agent Run ledger / Memory governance
```

fallback/归档路径：

```text
DB_DRIVER=sqlite
  -> getDataRepositories()
  -> SQLite data/zhiyuan.db

DB_DRIVER=postgres + ALLOW_SQLITE_LEGACY=readonly
  -> server-db.ts readonly archive
  -> 只用于检查旧数据，不作为写入事实源
```

## 4. Repository 抽象

所有新服务端业务代码都应优先使用：

```typescript
import { getDataRepositories } from "@/lib/data-repositories";

const repos = getDataRepositories();
```

原因：

- 避免 API route 直接依赖 `better-sqlite3` 或 `pg`。
- 让同一业务代码在 Postgres 和 SQLite fallback 下都能运行。
- 让 Postgres cutover check 能发现仍然直连 SQLite 的运行时代码。
- 读回校验可以统一通过 repository 执行。

典型调用：

```typescript
const reports = await repos.reports.list(userId);
const report = await repos.reports.get(reportNum, userId);
const cv = await repos.cv.get(userId);
await repos.sessions.update(sessionId, userId, updates);
```

## 5. 写入路径

### 5.1 JD 评估持久化

```text
evaluate_jd_full
  -> /api/agent/persist-eval
  -> getDataRepositories()
  -> applications + reports + jds
  -> reportReadBackVerified / jdReadBackVerified
  -> success only when read-back passes
```

写入成功不只看 HTTP 200。`persist-eval` 会重新读取 `reports` 和 `jds`，比对 company、role、body、keywords、report_num 等关键字段。读回失败会返回失败，Agent Chat 不允许宣称评估完成。

### 5.2 Offer 评估持久化

```text
evaluate_offer
  -> offers
  -> offer_reports
  -> linked offer read-back
  -> report read-back
```

Offer 报告和 Offer 快照都需要读回；任一失败都进入失败路径。

### 5.3 简历修改

```text
create_resume_edit_proposal
  -> resume_edit_proposals pending
  -> proposal read-back
用户确认
  -> apply_resume_edit_proposal
  -> cv_data update
  -> section content/hash read-back
```

Agent 不能直接把聊天里的 Markdown 说明写进简历正文。必须先生成 proposal，再由用户确认应用。

### 5.4 优秀简历/长期记忆

```text
save_reference_resume
  -> 确认岗位方向和 visibility
  -> reference_resumes
  -> reference_resume_chunks embedding best effort
  -> read-back verification
```

通用长期记忆通过：

```text
/api/agent/memory-writeback
  -> memory_items
  -> memory_evidence
  -> candidate/active/rejected/archived 状态
  -> /admin/memory 治理
```

## 6. SQLite 的保留角色

SQLite 仍然存在，但它不是当前局域网的主事实源。

保留场景：

- 本地无 Postgres 时的轻量 fallback。
- `migrate:postgres` 的迁移源。
- `check:postgres-migration` 和 `check:postgres-cutover` 的对照源。
- `ALLOW_SQLITE_LEGACY=readonly` 下的归档读取。
- `scripts/db-write.mjs` 等 legacy 脚本兼容。

约束：

- `DB_DRIVER=postgres` 时，运行时代码直接调用 `getDb()` 会报错。
- 新 API route 不应 import `server-db.ts` 做写入。
- 需要读写业务数据时用 `getDataRepositories()`。

## 7. 迁移与切换

相关脚本：

| 命令 | 作用 |
|------|------|
| `npm run check:postgres` | 检查 `DATABASE_URL`、Postgres 连接和 pgvector |
| `npm run migrate:postgres -- --dry-run` | 生成迁移计划，不写入 |
| `npm run migrate:postgres -- --apply` | 从 SQLite 迁移到 Postgres |
| `npm run check:postgres-migration` | 严格迁移校验 |
| `npm run check:postgres-cutover` | 切换校验，允许 Postgres 是 SQLite 的 superset |
| `npm run backup:postgres` | 导出 Postgres JSON 备份 |
| `npm run restore:postgres` | 从 JSON 备份恢复 |
| `npm run backfill:memory` | 对已有记忆/优秀简历补向量 |
| `npm run eval:memory` | 记忆确定性回归 |
| `npm run smoke:embedding` | 真实 embedding provider smoke test |

当前 LAN 切换条件：

```text
DB_DRIVER=postgres
DATABASE_URL=<configured>
npm run check:postgres        # pass
npm run check:postgres-cutover # pass
```

`check:postgres-cutover` 的语义和 `check:postgres-migration` 不同：切换后 Postgres 可能已经产生新数据，因此 cutover 允许 Postgres 是 SQLite 的超集，但会继续阻止运行时代码绕过 repository 直连 SQLite。

## 8. DATA_CONTRACT 分层

User Layer 不应被更新脚本随意覆盖：

```text
cv.md
config/profile.yml
modes/_profile.md
article-digest.md
portals.yml
data/applications.md       legacy readable copy
data/pipeline.md           legacy readable copy
reports/*.md               report copy/export
output/*.pdf
```

System Layer 可以随版本更新：

```text
modes/*.md
scripts/*.mjs
templates/*
src/lib/postgres-schema.sql
src/lib/server-schema.sql
CLAUDE.md
VERSION
```

业务写入必须走数据层，不应直接改 System Layer 来保存用户状态。

## 9. 读回校验

当前高风险写入的共同规则：

```text
precheck
  -> mutation
  -> readBack
  -> verifier
  -> success/failure
```

读回证据可能来自：

- `verifiedAction.readBack.ok`
- `data.readBackVerified`
- `uiPayload.readBackVerified`
- `reportReadBackVerified`
- `jdReadBackVerified`
- `referenceReadBackVerified`
- `fileReadBackVerified`

`src/lib/agent/tools/readback-verification.ts` 会对需要读回的工具执行成功门控。没有证据时，即使工具 handler 返回了 `success: true`，也会被改为失败。
