# 云端简历文档是真源，聊天与浏览器只持有投影

我们决定把服务端的简历文档作为用户简历的唯一事实源。浏览器 `localStorage` 只保留可丢弃的缓存；CV 页面、Agent Chat、简历摄取和简历修改事务都必须通过同一份服务端文档读写，并在写入后读回验证。

每次上传或粘贴都会执行一次简历摄取并创建新的导入版本，而不是覆盖旧版本。摄取保留原始文件或完整原文、抽取诊断、分块内容、结构化 sections、内容哈希和完整性证据。长文本先分块解析，再确定性合并；任何固定长度截断都不能被视为成功导入。完整性不足的导入版本保持待确认状态，不自动替换活动版本。

Agent 通过简历读取投影按 section 或 chunk 分页读取完整内容，聊天消息只引用文档、草稿或修改事务的稳定标识，不承担大文本的唯一持久化。Agent 生成的多个修改方案保存为简历草稿工件；用户选定方案后，复用现有 `resume_edit_proposals` 的基础哈希、原子应用、读回验证和回滚能力，不建立第二套修改协议。

为兼容现有页面和接口，`cv_data` 暂时保留为活动简历的当前投影。新建的简历文档、原文工件、分块和草稿表负责历史与大内容持久化；任何对活动版本的成功写入都必须同步更新 `cv_data`，迁移期间旧入口不得绕过这一规则。

摄取接口必须在已认证用户范围内完成原子持久化和服务端读回，不提供“只解析不落库”的成功状态。文本材料只有在事实覆盖率至少 98% 且数字覆盖率 100% 时才可自动激活；图片识别由于没有独立 OCR 原文交叉验证，始终先保存为待确认导入版本，并保留 Agent Chat 原始图片与完整识别文本。

CV 页面手工写入同样携带基础版本和内容哈希，服务端在事务内检查并发冲突，拒绝旧页面覆盖 Agent 的新修改。摄取后的正文一旦改变，原完整性证据立即失效并回到待复核状态。一个简历草稿工件的全部 variants 必须在同一事务中创建，并逐项校验稳定 ID、正文和哈希的读回结果。
