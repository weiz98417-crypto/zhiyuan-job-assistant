# 投递追踪系统的产品构造

投递追踪系统是纸鸢求职助手里的求职进度账本。JD 评估告诉用户“这个机会值不值得投”，投递追踪记录用户“有没有投、投到哪一步、下一步要做什么”。没有这个系统，评分报告、简历优化、面试准备和 Offer 比较都会停留在单次动作，无法形成长期求职闭环。

这个系统不是一个简单的表格。它把岗位、评分、报告、状态、面试轮次、备注、导出和 Analytics 漏斗连接起来，让用户的每一次求职动作都能沉淀成可复盘的数据。

## 1. 产品定位

投递追踪系统解决的是求职过程中的状态丢失问题。

真实用户在求职时，经常会同时推进十几个甚至几十个机会。每个机会可能处在不同阶段：刚评估、已投递、HR 已回复、面试中、拿到 Offer、被拒绝、主动放弃、跳过。只靠聊天记录或脑子记，会很快混乱。

纸鸢把这个问题抽象成 `Application`：

```text
公司 + 岗位 + 分数 + 状态 + 日期 + 报告链接 + 备注 + 面试轮次
```

这条记录既是页面上的一张卡片，也是后续 Analytics、跟进提醒、Offer 预测、周报和复盘的基础数据。

完整位置如下：

```text
JD 评估 / 岗位发现 / 用户手动记录
  -> applications
  -> 投递追踪页
  -> 状态更新 / 面试轮次 / 备注 / 导出
  -> Analytics 漏斗、跟进提醒、周报、Offer 预测
```

## 2. 为什么不能只做“投递清单”

如果只做一个投递清单，用户只能看到“投过哪些公司”。这对真实求职帮助有限。

纸鸢需要记录的是求职漏斗，而不是单纯列表：

| 阶段 | 用户问题 | 系统需要记录 |
|---|---|---|
| 已评估 | 这个机会质量如何，是否值得投 | `score`、`reportPath`、`status=evaluated` |
| 已投递 | 什么时候投的，是否需要跟进 | `date`、`updatedAt`、`status=applied` |
| 已回复 | HR 是否回应，下一步是否要安排面试 | `status=responded` |
| 面试中 | 第几轮、何时面试、备注是什么 | `interviews[]` |
| 已获 Offer | 能否进入 Offer 对比 | `status=offer` |
| 已拒绝 | 哪些方向拒绝多，是否要调整 | `status=rejected` |
| 已放弃 | 用户主动放弃，不再跟进 | `status=discarded` |
| 跳过 | 不适合，不进入后续漏斗 | `status=skip` |

这套状态直接来自 `src/types/index.ts` 里的 `ApplicationStatus`。

## 3. 页面入口

投递追踪页面是 `src/app/tracker/page.tsx`。

页面主要能力包括：

| 能力 | 代码事实 | 产品含义 |
|---|---|---|
| 读取投递记录 | `db.applications.toArray()` | 当前页面以 Dexie IndexedDB 为主 |
| 搜索 | `search` 过滤公司和岗位 | 快速定位某个机会 |
| 状态筛选 | `statusFilter` | 只看某一阶段 |
| 排序 | `sortBy=date/score/company` | 按日期、分数或公司查看 |
| 批量选择 | `selected: Set<number>` | 支持选择部分记录导出 |
| 三种视图 | list、grouped、kanban | 同一批数据按不同工作方式呈现 |
| 状态更新 | `updateStatus()` | 用户推动机会进入下一阶段 |
| 面试轮次 | `interviews[]` | 记录第几轮、日期、总轮次、备注 |
| 导出 | `exportApplicationsMD()` | 导出为 `applications.md` |

页面当前是 local-first 形态，直接读写浏览器里的 Dexie 数据库 `zhiyuan`。服务端仓储层里也有 `applications` 表和 `getDataRepositories().applications`，但这个页面没有完全迁到服务端 repository。文档里必须区分这一点，不能把它写成纯服务端多用户看板。

## 4. 数据模型

投递记录类型是 `Application`。

核心字段如下：

| 字段 | 类型 | 产品含义 |
|---|---|---|
| `id` | number | IndexedDB 自增主键 |
| `num` | number | CLI/报告序号延续 |
| `date` | string | 投递或记录日期 |
| `company` | string | 公司名 |
| `role` | string | 岗位名 |
| `score` | number | JD 评估分 |
| `status` | ApplicationStatus | 当前求职阶段 |
| `pdfGenerated` | boolean | 是否生成过 PDF |
| `reportPath` | string | 关联评估报告 |
| `notes` | string | 备注 |
| `url` | string | 原始 JD 链接 |
| `interviews` | InterviewRound[] | 面试轮次记录 |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 最近更新时间 |

`InterviewRound` 包含：

| 字段 | 含义 |
|---|---|
| `round` | 第几轮 |
| `totalRounds` | 总轮次，可选 |
| `date` | 面试日期 |
| `notes` | 面试方式、面试官、补充信息 |

这说明投递追踪不是只存“公司/岗位/状态”。它已经把面试推进所需的最小信息纳入了同一条记录。

## 5. IndexedDB 存储结构

本地数据库定义在 `src/lib/db.ts`。

`ZhiyuanDB` 中 `applications` 表的 schema 是：

```text
++id, num, company, role, status, score, date, createdAt
```

这些索引用于支撑页面常见查询：

- 按公司和岗位去重或查找。
- 按状态过滤。
- 按日期排序。
- 按分数排序。

投递追踪页没有直接依赖复杂后端查询，因此它打开速度快，离线或弱网络下也能读到本地记录。代价是：多设备同步、多用户服务端一致性、团队级追踪要依赖后续 repository 化迁移。

## 6. 状态流转

纸鸢定义了 8 个标准状态：

| 状态 | 中文展示 | 产品含义 |
|---|---|---|
| `evaluated` | 已评估 | 机会已被评分，但不一定投递 |
| `applied` | 已投递 | 用户已经投递 |
| `responded` | 已回复 | 对方有回复，需要跟进 |
| `interview` | 面试中 | 进入面试流程 |
| `offer` | 已获Offer | 进入 Offer 决策 |
| `rejected` | 已拒绝 | 对方拒绝或流程失败 |
| `discarded` | 已放弃 | 用户主动放弃 |
| `skip` | 跳过 | 不进入正式漏斗 |

在追踪页中，用户可以通过状态标签的下拉菜单更新状态。页面调用：

```text
db.applications.update(app.id, { status, updatedAt: new Date() })
```

当用户把状态改成 `interview`，且该记录还没有面试轮次时，页面不会只改状态，而是打开面试轮次弹窗。这是一个产品细节：进入面试不是一个普通状态，它需要补充轮次和日期，才能被后续提醒和复盘使用。

## 7. 三种视图

投递追踪页提供 list、grouped、kanban 三种视图。

### 7.1 列表视图

列表视图适合快速浏览所有机会。

每条记录展示：

- 选择框
- 分数徽标
- 公司
- 岗位
- 状态标签
- 日期
- 详情按钮

它适合做批量筛选、导出和快速检查。

### 7.2 分组视图

分组视图按 `STATUS_ORDER` 把机会归类。

它回答的是：

```text
我现在有哪些机会卡在已评估？
哪些已经进入面试？
哪些被拒绝或放弃？
```

这对复盘特别重要，因为求职问题往往不在单个岗位，而在某个阶段的转化。

### 7.3 看板视图

看板视图把每个状态变成一列。

用户可以拖拽卡片改变状态。`handleDrop()` 读取拖拽中的 application id，然后调用 `updateStatus(app, status)`。

看板的价值不是视觉效果，而是让用户把求职过程当成一个 pipeline 管理。

## 8. 详情面板

点击详情后，页面打开右侧 slide-over。

详情面板展示：

- 分数和基础信息。
- 当前状态和日期。
- 关联报告链接 `reportPath`。
- 备注。
- 面试轮次记录。
- 添加面试轮次按钮。
- 原始 JD 链接。
- 当状态为 offer 时，预留进入 Offer 对比的动作。

这让投递追踪不只是表格编辑，而是一个机会详情页。用户可以从这里回到评估报告，也可以继续补充面试进展。

## 9. 导出能力

投递追踪页使用 `src/lib/exporters.ts` 中的 `exportApplicationsMD()` 导出 Markdown 表格。

导出格式是：

```text
| # | Date | Company | Role | Score | Status | PDF | Report | Notes |
```

每一行会写入：

- 序号
- 日期
- 公司
- 岗位
- `score.toFixed(1)/5`
- 中文状态
- PDF 是否生成
- 报告链接
- 备注

页面支持“导出全部”和“导出已选”。这说明投递记录既是产品内数据，也可以被带出系统，继续用于外部复盘或备份。

## 10. 与 Analytics 的关系

Analytics 页读取的核心数据也是 `db.applications.toArray()`。

投递追踪系统提供原始状态，Analytics 再计算：

- 漏斗转化。
- 本周新投递、新面试、新 Offer。
- 拒绝模式。
- 跟进提醒。
- Pipeline 健康灯。
- 异常检测。
- Offer 预测。

没有准确的投递状态，Analytics 只能生成漂亮但无意义的图表。

因此投递追踪系统是数据分析系统的前置基础。它解决的是“数据从哪里来”，Analytics 解决的是“这些数据说明什么”。

## 11. 与 JD 评估和岗位发现的关系

投递追踪记录可以从多个地方产生：

| 来源 | 链路 |
|---|---|
| JD 评估报告 | 评估完成后把公司、岗位、分数、报告路径写入 applications |
| 岗位发现 | 发现岗位先保存 JD，再评估，再进入追踪 |
| CLI 导入 | `/api/data/import` 读取 `data/applications.md` |
| 用户本地导入 | 设置页导入 `.md` 文件并写入 Dexie |

这几个来源共同说明：投递追踪不是某一个页面的孤立功能，而是全项目统一的求职进度资产。

## 12. 当前边界

当前投递追踪系统有几个必须清楚的边界：

1. 页面主要使用浏览器本地 Dexie，不是完全服务端 repository。
2. `company + role` 去重主要发生在导入场景，页面内状态更新依赖 `id`。
3. 备注字段展示为只读，没有在详情面板里提供完整编辑器。
4. 面试记录能添加轮次和日期，但还没有和面试教练的训练记录完全联动。
5. “添加到 Offer 对比”按钮位置存在，但具体跳转逻辑仍是预留。
6. 多设备同步依赖后续把页面迁到服务端数据仓储。

这些边界不会削弱系统价值，反而说明当前产品处在 local-first 到 server-backed 的过渡阶段。

## 13. 常见失败模式

| 失败模式 | 影响 | 当前处理 |
|---|---|---|
| IndexedDB 没有数据 | 页面展示空状态 | 提示评估 JD 后加入追踪 |
| 状态改成 interview 但没有面试信息 | 后续提醒缺少日期 | 自动弹出面试轮次弹窗 |
| 用户拖拽数据异常 | 无法解析 application id | catch 后忽略，避免页面崩溃 |
| 导出空筛选结果 | 导出空表格 | 用户可调整筛选 |
| 本地数据和服务端数据不一致 | Analytics 看到的仍是本地数据 | 需要 repository 化迁移解决 |

产品上最重要的是避免“状态看起来变了但数据没有保存”。当前页面每次状态更新都会调用 Dexie update，并重新 `loadData()`。

## 14. 验证依据

与投递追踪相关的项目文件包括：

- `src/app/tracker/page.tsx`
- `src/types/index.ts`
- `src/lib/db.ts`
- `src/lib/exporters.ts`
- `src/lib/analytics.ts`
- `src/app/settings/page.tsx`
- `src/app/api/data/import/route.ts`
- `src/__tests__/data-isolation.test.ts`

验证时应该关注：

- 空数据状态是否正确。
- 搜索、状态筛选、排序是否基于同一批 `applications`。
- 状态标签是否覆盖 8 个标准状态。
- 从 `applied` 到 `interview` 是否能补面试轮次。
- 看板拖拽是否能更新状态。
- 导出内容是否包含公司、岗位、分数、状态、报告和备注。
- Analytics 是否能用这些状态计算漏斗。

## 15. 产品总结

投递追踪系统让纸鸢从“单次评估工具”变成“长期求职助手”。

它把每个机会变成一条可持续推进的记录：评估结果进入追踪，投递状态持续变化，面试轮次被记录，报告可以回看，数据可以导出，Analytics 可以复盘。只要这套状态系统存在，用户的求职过程就不会散落在聊天、浏览器和脑子里。
