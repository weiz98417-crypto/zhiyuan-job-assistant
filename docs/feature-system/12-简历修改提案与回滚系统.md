# 简历修改提案与回滚系统的产品构造

纸鸢求职助手的简历修改提案系统，解决的是 AI 写入简历时最敏感的问题：用户的真实经历不能被模型直接覆盖，任何正式写入都必须有草稿、确认、版本校验、读回证据和回滚路径。

它不是“AI 生成一段新简历，然后点保存”的功能，而是把简历修改变成一条可审阅、可追踪、可撤销的产品链路。

## 1. 产品定位

简历是求职产品里最重要的用户资产之一。纸鸢可以帮用户改写个人概述、工作经历、项目经验、教育背景和技能清单，但它不能把模型生成内容直接写入正式简历。

简历修改提案系统承担四个职责：

```text
读取当前简历板块
  -> 生成待审阅修改提案
  -> 用户确认后应用到正式 CV
  -> 应用后读回校验
  -> 必要时回滚到原内容
```

系统要保护的是两个结果：

- 用户能看到 AI 到底要改什么。
- 系统能证明正式简历真的按用户确认的内容被写入。

## 2. 为什么不能直接保存

如果 Agent 生成内容后直接调用保存工具，产品会出现几个高风险问题：

- 用户只是问“我现在的简历是什么”，系统却误判为要保存或修改。
- AI 生成了一个“修改前 / 修改后 / 原因”的对照表，结果被当成简历正文写入。
- 用户还没确认，模型就把建议内容覆盖掉正式简历。
- 用户在提案生成后又改了简历，旧提案继续应用会覆盖新内容。
- 工具失败但 Agent 回复“已保存”，用户以为简历已经更新。

当前项目里，`src/lib/agent/resume-save-guard.ts` 就是为这些问题存在的。它会识别保存意图、过滤非简历正文、拒绝参考简历保存误判，并在没有真实保存成功时清洗掉“已保存”的自然语言成功提示。

这个功能的产品原则是：AI 可以建议，用户决定写入，系统用读回证明结果。

## 3. 系统入口和关键文件

| 层级 | 文件或接口 | 作用 |
|---|---|---|
| 提案列表/创建 | `src/app/api/cv/edit-proposals/route.ts` | `GET` 查询提案，`POST` 创建待审批提案。 |
| 提案详情 | `src/app/api/cv/edit-proposals/[id]/route.ts` | 读取单个提案，用于创建后读回。 |
| 应用提案 | `src/app/api/cv/edit-proposals/[id]/apply/route.ts` | 用户确认后把提案写入 CV，并返回读回结果。 |
| 丢弃提案 | `src/app/api/cv/edit-proposals/[id]/discard/route.ts` | 用户拒绝或取消提案。 |
| 回滚提案 | `src/app/api/cv/edit-proposals/[id]/rollback/route.ts` | 对已经应用的提案恢复原文。 |
| 提案领域逻辑 | `src/lib/agent/resume-edit-proposals.ts` | 定义提案数据结构、应用校验、回滚校验。 |
| 保存意图防护 | `src/lib/agent/resume-save-guard.ts` | 判断是否允许保存，识别提案操作，阻断伪成功提示。 |
| Agent 创建工具 | `src/lib/agent/tools/action/create-resume-edit-proposal.ts` | 只创建草稿，不写入 CV。 |
| Agent 应用工具 | `src/lib/agent/tools/action/apply-resume-edit-proposal.ts` | 只应用已有 `proposalId`，并做回读校验。 |

这套链路把“生成内容”和“写入正式简历”拆成两个阶段。拆开不是为了复杂，而是为了让用户确认和系统校验有明确位置。

## 4. 提案数据模型

核心数据结构是 `ResumeEditProposalRecord`：

| 字段 | 产品含义 |
|---|---|
| `id` | 提案 ID，格式类似 `rep_xxx`，后续应用、丢弃、回滚都围绕它执行。 |
| `user_id` | 所属用户，防止跨用户访问。 |
| `section_id` | 目标简历板块，只允许 `summary`、`experience`、`projects`、`education`、`skills`。 |
| `base_version` | 生成提案时的 CV 版本。 |
| `base_hash` | 生成提案时 active CV 内容哈希。 |
| `original_content` | 提案生成时该板块的原文。 |
| `proposed_content` | AI 建议写入的新板块正文。 |
| `proposed_hash` | 建议内容的稳定哈希。 |
| `reason` | 为什么建议这样修改，最长保留约 1200 字。 |
| `risk_flags_json` | 风险标记，例如大幅改写、JD 定向、事实需确认。 |
| `status` | `pending`、`applied`、`discarded`、`stale`、`rolled_back`。 |

这里最重要的是 `base_version`、`base_hash` 和 `original_content`。它们一起回答一个问题：用户确认时，当前简历是否还是当初生成提案时那份简历？

如果不是，应用就必须被阻断。

## 5. 创建提案的产品链路

创建提案不是把一段文本插进数据库。`POST /api/cv/edit-proposals` 会先完成这些检查：

1. 用户必须已登录。
2. `sectionId` 必须是合法板块。
3. `proposedContent` 必须通过 `validateResumeSectionContent()`。
4. 当前 CV 必须存在 active version。
5. 目标 section 必须存在。
6. 如果调用方带了 `expectedBaseVersion` 或 `expectedBaseHash`，必须和当前 CV 一致。
7. 记录当前板块原文、CV 版本和 base hash。
8. 写入 `pending` 提案。

如果 CV 在生成方案和创建提案之间变化，接口会返回 409：

```text
简历已经发生变化，已阻止用旧上下文创建修改提案。请重新读取简历后再生成方案。
```

这个错误不是技术异常，而是产品保护：旧上下文下生成的改写不能覆盖新简历。

## 6. 提案内容校验

`validateResumeSectionContent()` 会把很多“看起来像输出，但不能保存”的内容拦下来。

被拒绝的典型内容包括：

- 空内容。
- 内容过短，不像完整板块。
- 只写了“替换为 / 修改为 / 改为”的占位说明。
- “修改前 / 修改后 / 原因”的对照表。
- 工具结果、页面提示、URL、失败提示。
- 对话过程文字，例如“正在分析”“重新提问”“达到处理上限”。

不同板块有不同最低长度：

| 板块 | 最低紧凑长度 | 原因 |
|---|---:|---|
| `summary` | 20 | 个人概述可以短，但不能只是标题或一句提示。 |
| `experience` | 80 | 工作经历需要完整事实、动作和结果。 |
| `projects` | 80 | 项目经验需要背景、动作和成果。 |
| `education` | 10 | 教育背景结构较短。 |
| `skills` | 20 | 技能清单需要有可用能力项。 |

这层校验直接防止“AI 对话文本被写进简历”。

## 7. Agent 创建提案工具

`create_resume_edit_proposal` 的工具描述非常明确：只保存为待审批草稿，不直接写入 CV。

它做三件关键事：

1. 将中文板块名映射为标准 section：个人概述、工作经历、项目经验、教育背景、技能。
2. 对 `proposedContent` 做同样的简历正文校验。
3. 创建成功后立刻通过 `/api/cv/edit-proposals/{id}` 读回，确认提案 ID 和内容匹配。

工具成功时返回的不是“简历已保存”，而是：

```text
已创建简历修改提案 rep_xxx，板块 skills，等待用户审批后才会写入 CV。
```

这个措辞本身就是产品设计的一部分。它让用户知道当前只是草稿态。

## 8. 应用提案的事务校验

`applyResumeEditProposalToCvData()` 在真正写入前会做四层校验：

| 校验 | 失败代码 | 产品意义 |
|---|---|---|
| 提案必须是 `pending` | `proposal_not_pending` | 已应用、丢弃、过期或回滚的提案不能重复应用。 |
| CV active version 必须存在 | `cv_missing` | 没有可写入的正式简历。 |
| `base_version` 和 `base_hash` 必须匹配 | `base_version_conflict` | 简历已经变化，旧提案不能覆盖新内容。 |
| 目标 section 原文必须等于 `original_content` | `base_version_conflict` | 即使版本没变，只要板块内容变了也不能应用。 |

只有全部通过后，系统才会把 `target.content` 替换成 `proposed_content`，并返回：

- `sectionId`
- `baseVersion`
- `baseHash`
- `appliedHash`
- `previousContent`
- `appliedContent`

`apply_resume_edit_proposal` 工具还会用 `validateDocumentFieldContent()` 再做一次读回校验。只有 `readBackVerified` 为真时，Agent 才能说已经应用。

## 9. 丢弃和回滚

丢弃和回滚是两个不同动作：

```text
discard
  -> 用户不接受 pending 提案
  -> 提案状态变成 discarded
  -> 不影响 CV 正文

rollback
  -> 用户撤销已经 applied 的提案
  -> 当前 section 必须仍然等于 proposed_content
  -> 恢复 original_content
  -> 提案状态变成 rolled_back
```

回滚的关键边界是 `rollback_conflict`。如果提案应用后，用户或其他工具又改过同一个板块，当前内容已经不等于 `proposed_content`，系统会拒绝回滚。因为此时回滚会覆盖更新后的简历内容。

这保证了回滚是“撤销这次修改”，不是“粗暴恢复旧版本”。

## 10. 保存意图防护

`resume-save-guard.ts` 负责判断用户当前消息是否真的要保存。

它识别的保存意图包括：

- 应用
- 保存
- 写入
- 确认
- 采用
- 用这个
- 就这个
- 直接改
- 落到简历
- 同步到简历

但它也明确排除“优秀/参考/标杆/样例简历”保存意图。因为保存优秀简历进入的是参考简历库，不是用户自己的正式 CV。

它还能从最近对话里找三类可保存内容：

- 用户直接粘贴的“改为 / 修改后 / 新版 / 优化后”正文。
- 最近一次优化结果里的某个方案。
- 最近一次助手生成的提案正文。

如果用户只是问“有没有保存”“我现在的简历是什么”，系统不应该创建提案，也不应该保存任何内容。这类问题属于读取和解释，不属于写入。

## 11. 提案操作识别

用户不一定会精确说“apply proposal rep_xxx”。`buildResumeEditProposalActionPlan()` 支持自然语言识别：

| 用户说法 | 动作 |
|---|---|
| “应用这个”“确认”“采用”“就这个” | `apply` |
| “不要了”“丢弃”“取消”“算了” | `discard` |
| “撤销”“回滚”“还原”“恢复” | `rollback` |

如果用户消息里没有 `rep_xxx`，系统会从最近 8 条消息里找最近出现的提案 ID。这样用户可以自然回复“应用这个”，但系统仍然有明确目标。

## 12. 伪成功提示清洗

`sanitizeUnsupportedResumeSaveClaim()` 是这个系统里很关键的一层。

如果模型输出里出现“已保存 / 已写入 / 已更新 / 已同步简历”等说法，但工具结果并没有证明保存成功，它会把回复替换成：

```text
我刚才只生成了修改方案，还没有真正写入简历页面。

请回复「应用这个技能清单」或「保存到技能板块」，我会调用保存工具写入当前简历。
```

这解决的是 AI 产品里非常常见的问题：自然语言说成功，但实际数据没有变。

纸鸢要求成功态必须来自工具结果和读回校验，不来自模型措辞。

## 13. 用户链路

完整链路如下：

```text
用户要求优化某个简历板块
  -> Agent 或页面生成改写方案
  -> create_resume_edit_proposal 创建 pending 提案
  -> 前端展示原文、新文、原因、风险标记、提案 ID
  -> 用户应用 / 丢弃
  -> apply_resume_edit_proposal 写入 CV
  -> 系统读回 section 内容并校验 hash
  -> 用户必要时 rollback
```

这条链路里，最重要的产品状态是：

- `pending`：提案存在，但还没有写入正式简历。
- `applied`：提案已经写入，并完成读回。
- `discarded`：用户拒绝，不能再应用。
- `stale`：上下文已过期，不能继续使用。
- `rolled_back`：已应用内容被恢复。

每个状态都要对应明确的用户可见行为。不能让用户看到“已保存”，但后台还是 `pending`。

## 14. 与简历优化 Judge 的关系

简历优化 Judge 引擎负责生成改写方案，提案系统负责保护写入。

两者边界是：

```text
Judge 引擎
  -> 生成一个或多个优化变体
  -> 解释改写策略
  -> 不直接改正式 CV

提案系统
  -> 把被选中的变体转成 pending proposal
  -> 等用户确认
  -> 写入并读回
  -> 支持回滚
```

这个边界让“生成质量”和“写入安全”分别治理。生成不好可以重新生成，写入失败不能假装成功。

## 15. 失败模式

| 失败模式 | 产品处理 |
|---|---|
| 未登录 | 返回 401，不能访问或创建用户提案。 |
| 无效 section | 返回 400，提示“无效的简历板块”。 |
| 提案正文不是简历内容 | 返回 400 或工具失败，要求用户提供完整正文。 |
| CV 数据为空 | 提示先在 CV 页面创建简历。 |
| 提案生成时 CV 已变化 | 返回 409，要求重新读取简历后再生成。 |
| 应用时提案不是 pending | 阻断重复应用或应用已丢弃提案。 |
| 应用时 section 原文变化 | 阻断旧提案覆盖新内容。 |
| 回滚时当前内容已变化 | 返回 rollback conflict，避免覆盖更新后的简历。 |
| 应用后读回失败 | 阻断成功提示。 |

## 16. 测试与验证证据

当前项目里，这套能力主要通过这些测试和工具验证：

- `src/__tests__/resume-save-guard.test.ts`：验证保存意图识别、非简历内容拦截、伪成功提示清洗。
- `src/__tests__/resume-edit-proposals-route.test.ts`：验证提案接口、状态和错误处理。
- `src/lib/agent/tools/action/create-resume-edit-proposal.ts`：创建后读回校验。
- `src/lib/agent/tools/action/apply-resume-edit-proposal.ts`：应用后读回校验。
- `src/lib/agent/resume-edit-proposals.ts`：纯领域逻辑，覆盖 base hash、section、rollback 等约束。

验收时要看五件事：

- 未确认时不会写入正式简历。
- 创建提案后可以读回同一个提案。
- CV 变化后旧提案不能应用。
- 应用后目标 section 内容和预期一致。
- 没有真实保存成功时，Agent 不会说“已保存”。

## 17. 产品总结

简历修改提案与回滚系统，是纸鸢把 AI 改写变成可信求职产品的关键能力。它不追求最快把文本写进去，而是追求每次写入都有依据、确认、版本保护、读回证明和撤销路径。

没有这套系统，AI 简历优化很容易变成一次性文本生成。有了这套系统，简历改写才真正进入可管理、可恢复、可持续迭代的产品流程。
