# 纸鸢求职助手评分系统的产品构造

纸鸢求职助手的评分系统，不是一个“把 JD 丢给大模型，然后返回几分”的小功能。它是用户看到一个岗位之后，判断要不要投、怎么投、怎么改简历、怎么准备面试、这个岗位有没有坑的核心判断层。

在这个项目里，评分系统覆盖的是完整的 JD 评估链路：输入可以是 JD 文本、JD 链接、JD 截图，也可以来自 Agent 对话里刚识别出的岗位内容；系统会先统一得到 JD 正文，再识别岗位类型，读取用户简历和长期记忆，生成 A-G 七个板块，抽取分项分数，计算 A-F 总分，把 G 职位真实性和黑话风险单独展示，最后把报告、JD、投递记录和必要记忆写入数据层。

这个功能的产品目标是：把一份复杂、口径不稳定、经常夹杂招聘黑话的岗位信息，转成用户可以执行的求职判断。

## 1. 产品定位

求职用户看到 JD 时，真正要解决的不是“这份 JD 看起来怎么样”，而是下面这些更具体的问题：

- 这个岗位到底是什么方向，是产品、运营、数据产品、AI 产品、解决方案，还是混合岗位？
- 这份 JD 对用户当前简历来说，是强匹配、弱匹配，还是需要重新包装表达？
- 岗位写的年限、职责和职级是否一致，用户应该按什么职级去谈？
- 薪资、福利、城市、工作强度是否值得投入？
- 简历应该改哪里，哪些项目要前置，哪些经历要弱化？
- 面试时应该讲哪些故事，如何回应短板、转型、行业经验不足等问题？
- JD 里有没有“抗压能力强”“弹性工作制”“培训后上岗”“付费内推”等风险信号？
- 报告是否能保存下来，后续让 Agent 继续改简历、准备面试、追踪投递？

所以评分系统在纸鸢里承担的是“机会判断中枢”角色。它上游接收 JD、截图、URL、简历、画像和记忆，下游连接报告库、JD 库、简历优化、面试准备、PDF 导出和投递追踪。

```text
JD 文本 / URL / 截图
  -> 统一得到 JD 正文
  -> 识别岗位类型和基础信息
  -> 读取简历、画像和长期记忆
  -> 生成 A-G 七个板块
  -> 抽取分项评分
  -> A-F 加权计算总分
  -> G 独立展示职位真实性与风险
  -> 保存报告、JD 和求职记录
  -> 后续简历优化、面试准备、PDF 导出复用
```

这套系统不是为了给用户一个漂亮数字，而是为了让用户能做决策。分数只是入口，真正有价值的是分数背后的板块解释、风险证据和后续动作。

## 2. 为什么不能只做一个总分

如果产品只输出“匹配度 3.8/5，建议投递”，用户仍然不知道该怎么行动。

用户会继续追问：

- 3.8 是因为我简历不匹配，还是岗位本身不清楚？
- 职级到底高了还是低了？
- 如果没有行业经验，还有没有机会靠 AI 产品经验弥补？
- 薪资偏低是否值得换取成长机会？
- 简历应该改什么，而不是笼统说“加强匹配度”？
- 面试该讲哪个项目，而不是泛泛准备 STAR 故事？
- 岗位里面的“弹性工作制”和“年轻团队”到底是不是风险？

因此纸鸢采用“分板块判断 + 总分聚合 + 风险单独展示”的结构。

```text
总分：快速判断机会优先级
分项：解释哪里强、哪里弱、哪里需要补
风险：提醒用户投入时间前要确认什么
报告：把一次判断沉淀成后续行动资产
```

这个设计也避免了 AI 产品里常见的两个错误：

- 把所有判断都混成一个模糊匹配分，用户看不出行动路径。
- 看到风险词就粗暴扣分，导致完整的定制化方案、面试准备、职级策略被误判成低质量内容。

项目里曾经出现过“定制化方案、面试准备、职级与策略、简历匹配都只有 1 分”的问题。后来排查发现，E/F/C 板块内容本身并不差，问题在旧评分规则把“缺口、未明确、红线问题、风险”等词当成低分证据。但在求职报告里，这些词经常恰恰是高质量策略内容的一部分。比如：

- E 板块写“缺少 SQL 表达”，是在告诉用户简历怎么补。
- F 板块写“红线问题”，是在准备面试防守话术。
- C 板块写“JD 未明确职级”，是在做职级推断，不是无法分析。
- G 板块写“未发现培训公司风险”，反而说明岗位可信度更高。

所以当前评分系统的关键原则是：按板块语义评分，而不是按全文风险词扣分。

## 3. 系统入口

评分系统有两个主要入口。

第一个入口是页面评估流程，对应 `src/app/api/evaluate/stream/route.ts`。它直接接收 JD 文本、JD URL、截图、简历文本、目标公司、是否允许联网等参数，并通过 SSE 流式返回阶段、OCR 进度、板块生成、分数和最终报告数据。

第二个入口是 Agent 工具 `evaluate_jd_full`，对应 `src/lib/agent/tools/action/evaluate-jd-full.ts`。用户在 Agent Chat 里说“评估这个 JD”“看看这个职位”“帮我看这张 JD 截图”，Agent 会调用这个工具。工具会处理对话输入、图片识别、最近 JD 回退、长期记忆上下文，然后把任务委托给 `/api/evaluate/stream`。

两个入口不是两套评分系统，而是同一个评分管道的不同入口形态：

| 入口 | 用户场景 | 关键文件 |
|---|---|---|
| 页面评估 | 用户在评估页面粘贴 JD、输入链接、上传截图 | `src/app/api/evaluate/stream/route.ts` |
| Agent 评估 | 用户在聊天里让 Agent 评估 JD 或截图 | `src/lib/agent/tools/action/evaluate-jd-full.ts` |
| URL 获取 | 用户给职位链接，系统抓取正文 | `src/lib/agent/tools/action/fetch-jd-content.ts`、`/api/fetch-jd` |
| 图片识别 | 用户上传 JD 截图，系统先识别再评估 | `/api/agent/image-intake`、`src/lib/agent/image-intake-router.ts` |
| 风险扫描 | G 板块生成前扫描 JD 黑话和风险信号 | `src/app/api/agent/scan-risks/route.ts` |
| 分数计算 | 从 A-G 内容中抽取板块分数并计算总分 | `src/lib/evaluation-scoring.ts` |
| 保存报告 | 把结果写入 applications、reports、jds 并读回校验 | `src/app/api/agent/persist-eval/route.ts` |

这个结构说明，评分系统不是一个页面组件，也不是一个 prompt。它是从输入识别、Agent 路由、流式生成、规则评分、风险扫描、保存读回到报告展示的一整条产品能力。

## 4. 输入层如何统一 JD 正文

评分系统支持三类输入：文本、URL、截图。

### 4.1 文本输入

文本输入是最稳定的路径。只要 `jdText` 长度达到基本要求，系统会直接进入评估流程。

文本输入适合用户从 Boss 直聘、猎聘、LinkedIn、公司官网或飞书文档里复制岗位描述。它的产品价值是快，不需要 OCR，也不会受截图清晰度影响。

### 4.2 URL 输入

URL 输入用于用户只提供职位链接的情况。`/api/evaluate/stream` 会用 `cheerio` 抓取页面文本，移除 `script`、`style`、`nav`、`footer`、`header` 等噪声，再截取正文进入评估。

URL 路径有天然边界：很多招聘网站有登录、反爬、动态渲染或权限限制，所以失败时不能假装评估成功。当前产品要求 URL 抓取失败时提示用户粘贴文本，而不是生成空报告。

### 4.3 截图输入

截图输入是纸鸢很重要的产品入口，因为真实用户经常直接上传手机长截图。

截图路径不是“上传图片后直接让模型评估”，中间要先完成 JD 图片识别：

```text
用户上传截图
  -> 图片 intake 判断 documentType
  -> 如果是 JD，提取 company、role、body、skills
  -> 如果不是 JD，进入澄清、描述图片或重试提示
  -> 有效 JD 正文进入评分管道
```

`evaluate_jd_full` 中的 `extractJDFromImages` 会最多处理 5 张图片。它会调用 `/api/agent/image-intake`，并检查识别出的正文是否可用。可用正文必须满足长度、关键词和内容质量要求，不能把“上传了 JD 截图”“马上帮你评估”“评估过程遇到”这类聊天气泡或系统提示当成 JD 正文。

这也是之前截图识别卡住、最终提示“未能从截图中提取到有效 JD 文本”的原因之一：系统已经能识别图片意图是 JD，但后续 OCR 正文质量校验没有拿到可用于评估的完整 JD 正文。产品上这一步必须严格，否则会把聊天界面、缩略图、失败提示当成岗位正文，生成错误报告。

## 5. A-G 报告结构

纸鸢评分系统把 JD 评估拆成 A-G 七个板块。

| 板块 | 名称 | 解决的问题 | 是否进入总分 |
|---|---|---|---|
| A | 职位概览 | 这个岗位到底是什么，信息是否清楚？ | 是 |
| B | 简历匹配 | 用户简历和 JD 要求是否匹配？ | 是 |
| C | 职级与策略 | 用户应该按什么职级和竞争策略去谈？ | 是 |
| D | 薪资与市场 | 薪资、福利、市场价值是否值得？ | 是 |
| E | 定制化方案 | 简历和投递材料应该怎么改？ | 是 |
| F | 面试准备 | 面试应该讲哪些故事、准备哪些问题？ | 是 |
| G | 职位真实性 | JD 是否真实可靠，有没有黑话和风险？ | 否，单独展示 |

这个结构的核心是：求职判断不是单一匹配问题，而是“岗位质量 + 用户匹配 + 竞争策略 + 行动方案 + 风险判断”的组合。

## 6. A 板块：职位概览

A 板块负责把自然语言 JD 转成岗位画像。

它会提取：

- 公司名称
- 岗位名称
- Archetype
- 领域
- 职能
- 职级倾向
- 工作模式
- 团队规模
- 一句话 TL;DR

在产品上，A 板块解决的是“这份 JD 到底在招什么人”。很多 JD 标题写得很泛，比如“AI 产品经理”“数据产品经理”“增长产品经理”，但正文里可能同时包含需求调研、数据分析、项目管理、客户沟通、售前方案和交付推进。A 板块先把岗位拆清楚，后续 B-F 才知道应该按什么岗位类型去匹配。

A 分数不应该因为用户简历缺失而低。它主要反映 JD 自身信息质量：职责是否明确、岗位方向是否稳定、标题和正文是否一致。

## 7. B 板块：简历匹配

B 板块是 A-F 总分里权重最高的部分，权重是 20。

它的产品任务不是评价用户“强不强”，而是判断用户已有材料能不能证明 JD 要求。

典型结构是：

```text
JD 要求
  -> 简历证据
  -> 匹配状态
  -> 缺口或应对策略
```

B 板块会识别三类信号：

| 信号 | 含义 | 示例 |
|---|---|---|
| 正向匹配 | 简历里有直接证据 | 强匹配、高度匹配、直接证据、可作为证明点 |
| 部分匹配 | 有相邻经验，但表达需要补强 | 部分匹配、可迁移、建议补充、应对策略 |
| 负向缺口 | 缺少关键证据或无法判断 | 不匹配、明显缺口、待提供简历、无法证明 |

如果用户没有提供简历，B 可以低分甚至 0 分，因为系统确实无法判断简历证据。但这个低分只应该影响 B，不应该污染 C、E、F。

这点在 `evaluation-scoring.test.ts` 里有明确回归测试：当 B 板块全是“待提供简历/待评估”时，B 可以是 0；但 C 板块只要给出职级推断和策略，就不应该被拖成低分。

## 8. C 板块：职级与策略

C 板块解决的是“用户应该怎么定位自己”。

真实 JD 很少直接写“P6/P7/P8”，尤其是中小公司、创业公司和外企岗位。系统不能因为 JD 没写职级就判定无法评估。它需要从这些信息推断：

- 年限要求
- 职责复杂度
- 是否需要独立负责模块
- 是否需要跨团队推进
- 是否涉及战略、指标、预算、管理或客户交付
- 是否更像执行岗、专家岗、负责人岗

C 板块输出的不只是职级判断，还要给策略：

- 如果按 senior 候选人去讲，应该强调哪些复杂项目？
- 如果用户是转型候选人，如何用 AI 应用、业务理解、数据能力补位？
- 如果被 downlevel，如何谈薪资、试用期、review 节点和晋升标准？
- 如果岗位明显高于当前经历，是否还值得投，应该如何降低投入成本？

当前评分函数 `scoreStrategyBlock` 会把“方案、策略、话术、应对、review、P6/P7、职级”等具体策略信号识别为有效内容。也就是说，C 的分数看的是策略是否具体，而不是 JD 有没有写出明确职级。

## 9. D 板块：薪资与市场

D 板块判断机会收益是否值得。

它关注：

- 税前月薪或年薪区间
- 年终奖和发薪月数
- 五险一金
- 工作城市和通勤成本
- 加班情况
- 行业薪资水平
- 公司薪资竞争力

如果用户明确允许联网，评估流程可以查公开信息辅助判断。当前 `/api/evaluate/stream` 里 D 板块会在 `allowWebSearch` 为 true 时尝试搜索公司和岗位薪资信息。没有公开数据时，系统会基于行业常识估算，并应该标注估算。

D 的产品价值是避免用户只看岗位名称和技术栈，而忽略收益、成本和机会质量。一个岗位可能和用户经历匹配，但薪资偏低、工作强度高、福利不完整，这种情况 D 分就不应该高。

## 10. E 板块：定制化方案

E 板块是从“评估”走向“行动”的关键。

它回答的是：为了投这个岗位，简历和投递材料具体怎么改。

典型结构是：

```text
修改前
  -> 修改后
  -> 原因
```

比如：

| 修改前 | 修改后 | 原因 |
|---|---|---|
| 原项目经历缺少 SQL 表达 | 增加 SQL 分析、指标体系和 BI 看板建设证据 | 对齐 JD 数据产品要求 |
| 未明确原型评审 | 补充需求评审、验收测试和交付闭环 | 回应岗位职责缺口 |
| 简历摘要偏泛 | 改为 AI 数据产品经理定位 | 强化岗位匹配 |

E 板块有一个非常重要的产品边界：它提到“缺少、补充、未明确、缺口”并不代表质量低。定制化方案本来就应该指出缺口，并给出修改方式。

所以当前评分测试专门覆盖了这个场景：完整的 E 板块即使出现“缺少 SQL 表达”“职责缺口”等词，也不能被打成 1 分。它应该按照方案的具体性、可执行性和 JD 贴合度评分。

## 11. F 板块：面试准备

F 板块帮助用户把经历转成面试表达。

它通常包括：

- 6-10 个 STAR+R 故事
- 每个故事对应的 JD 要求
- 情境、任务、行动、结果、反思
- 红线问题应对话术
- 反问面试官的问题
- 需要重点讲的项目

F 板块的重点不是“列一堆面试题”，而是把 JD 要求、用户经历和面试叙事连接起来。它应该告诉用户：这个岗位最可能追问什么，哪些项目要讲，哪些短板要提前准备，哪些表达不能夸大。

“红线问题”“风险话术”“短板应对”在 F 板块里是正常内容。它们不是低分证据，而是面试准备的核心部分。

## 12. G 板块：职位真实性与黑话风险

G 板块不进入 A-F 总分。它单独回答：这个岗位是否真实可靠，投之前要小心什么。

G 板块会结合两类信息：

- 大模型对 JD 真实性、清晰度、公司岗位匹配度的判断。
- 风险扫描系统产出的 `riskSignals`。

风险扫描系统不是独立于评分系统之外的小工具，而是 G 板块的重要输入来源。它发生在 G 板块生成前，对 JD 正文进行三层扫描：

```text
JD 正文
  -> 正则触发词扫描
  -> 黑话词典扫描
  -> 多信号模式识别
  -> 合并去重
  -> 生成 riskSignals
  -> 注入 G 板块
```

对应代码是 `src/app/api/agent/scan-risks/route.ts`。它读取 `risk-intel-triggers.yml` 和 `modes/zh/risk-intel.md`。

### 12.1 正则触发词

`risk-intel-triggers.yml` 里沉淀了确定性较强的风险表达。例如：

- “先培训后上岗”
- “培训费、服装费、押金、保证金”
- “央国企内推、保录、直签”
- “零基础高薪”
- “刷脸入职”
- “付费内推、买工作”
- “弹性工作制”
- “抗压能力强”
- “扁平化管理”

这些表达会被匹配成带 severity 的风险信号，severity 包括 `critical`、`high`、`medium`、`low`。

### 12.2 黑话词典

`modes/zh/risk-intel.md` 里有招聘黑话词典。它不是只识别诈骗，也识别工作强度、管理方式、薪资表达和 AI 岗位筛选信号。

例如：

| 词 | 产品解释 |
|---|---|
| 抗压能力强 | 可能意味着加班多、背锅多 |
| 弹性工作制 | 可能意味着下班时间不稳定 |
| 扁平化管理 | 可能意味着组织小、老板直接管 |
| 期权激励 | 可能意味着现金薪资低，用期权画饼 |
| Agent 作品 | AI 岗位筛选信号，不一定是风险 |
| 下午茶 | 可能是轻面试邀约，不应直接判定为不正规 |

这里的产品重点是：黑话不是一命中就劝退，而是把模糊表达转成需要确认的问题。

### 12.3 模式识别

有些风险不是一个词决定的，而是多个信号组合后形成的模式。

例如：

```text
零基础
+ 高薪
+ 先培训
+ 包就业
```

这类组合比单个词更危险。扫描系统会在多个 signals 同时出现时生成 `[模式]` 风险提示。

### 12.4 riskSignals 数据结构

风险扫描结果会形成 `riskSignals`：

| 字段 | 含义 |
|---|---|
| signal | 风险解释，例如“弹性工作制可能暗示加班边界不清” |
| excerpt | JD 原文片段，说明证据来自哪里 |
| severity | 风险等级，`low`、`medium`、`high`、`critical` |
| source | 来源，`regex`、`dictionary`、`pattern` |

这个结构很关键，因为它让风险不是大模型凭感觉判断，而是有原文证据、有等级、有来源。

### 12.5 黑话风险为什么不进入 A-F 总分

风险和匹配是两个不同问题。

一个岗位可能与用户高度匹配，但 JD 里有加班黑话。这个时候系统应该说：

```text
匹配度较高，但岗位存在工作强度或用工边界风险，面试时需要确认。
```

而不是把用户简历匹配度也打低。

反过来，一个岗位可能真实可靠，但用户经验差距大。这个时候 G 可以高，B/C/E/F 可能不高。

所以当前评分系统采用：

```text
A-F：匹配、策略、收益、行动方案
G：职位真实性和风险提示
总分：只由 A-F 加权计算
```

这个分离是评分系统能保持产品语义清晰的关键。

## 13. A-F 权重与总分计算

当前代码中，A-F 的权重定义在 `src/lib/evaluation-scoring.ts`：

| 板块 | 权重 | 产品含义 |
|---|---:|---|
| A 职位概览 | 10 | 判断 JD 信息质量和岗位清晰度 |
| B 简历匹配 | 20 | 核心匹配度，权重最高 |
| C 职级与策略 | 15 | 判断用户竞争定位和谈判策略 |
| D 薪资与市场 | 15 | 判断机会收益和市场合理性 |
| E 定制化方案 | 15 | 判断是否能形成可执行投递方案 |
| F 面试准备 | 15 | 判断是否能进入下一步面试竞争 |

总分计算逻辑是：

```text
overallScore = sum(板块分数 * 板块权重) / sum(有效板块权重)
```

分数会被限制在 0-5，并保留 1 位小数。G 不参与总分。

这个权重设计体现了几个产品判断：

- B 权重最高，因为简历证据是投递胜率的核心。
- C/E/F 决定转化能力，不能太低。
- D 影响机会质量，但不能压过匹配和行动方案。
- A 是基础信息判断，重要但不应决定一切。

## 14. 显式评分与兜底评分

模型生成 A-F 板块时，提示词要求最后输出：

```text
**评分：X/5**
```

这是显式评分。

但模型输出不总是稳定，所以 `extractEvaluationBlockScore` 还提供兜底评分规则：

- 先读取显式评分、总分、得分、分数、匹配度、推荐度等表达。
- B 板块用正向、部分、负向匹配信号计算比例分。
- C/E/F 板块识别表格、策略、话术、行动、STAR、职级等具体方案信号。
- G 板块识别“高可信度、谨慎推进、疑似虚假”等定性等级。
- 如果内容短且表达“无法评估、未提供简历、缺少 JD”，才按不可用处理。

兜底评分的产品意义是：模型负责生成分析，但分数落到产品里之前，需要经过代码规则约束。这样系统不会因为模型临场发挥、关键词误伤或缺少显式评分，就给出严重偏离用户感受的结果。

## 15. 报告生成与聊天摘要

完整 A-G 报告不会全部塞进聊天框。

Agent 工具 `evaluate_jd_full` 的 `formatResult` 明确要求：评估完成后，只给用户一个聊天摘要，不输出完整 A-G 报告正文，不输出大表格。完整内容保存到报告库或 JD 管理，用户可以打开详情，也可以下载 PDF。

聊天摘要由 `formatJDEvaluationSummary` 生成，结构包括：

- 结论：建议投递、可以投递但确认风险、谨慎投递、不建议投递。
- 岗位：公司、职位、岗位类型。
- A-G 速览：每个板块一句摘要。
- 行业黑话 / 风险扫描：展示风险信号。
- 报告入口：报告编号、报告库、JD 管理、PDF。

这个设计解决了一个体验问题：完整报告很长，适合详情页和 PDF，不适合聊天流。聊天里只需要告诉用户结论、风险和下一步。

## 16. 报告、JD 和投递记录如何沉淀

评分系统生成报告后，会通过 `src/app/api/agent/persist-eval/route.ts` 保存数据。

持久化不是简单插入一条报告。它会写入三类数据：

| 数据 | 作用 |
|---|---|
| `applications` | 把这个机会进入投递追踪体系，状态为 `Evaluated` |
| `reports` | 保存报告编号、日期、公司、岗位、archetype、总分、legitimacy、A-G blocks、keywords、source_hash |
| `jds` | 保存 JD 正文、来源、关键词和关联报告编号 |

如果使用 PostgreSQL，系统还会把 JD 和报告写入记忆索引，形成后续 Agent 可检索的长期上下文：

- `sourceType: jd`
- `sourceType: jd_report`
- `memoryType: jd_evaluation_observation`

这让一次 JD 评估不是一次性对话，而是后续简历优化、面试准备、岗位对比和投递追踪的上游资产。

## 17. 读回校验为什么重要

纸鸢评分系统有一个很重要的工程产品原则：不能只因为执行了写入代码，就告诉用户“已保存”。

`persist-eval` 保存后会读回校验：

- report 是否按预期写入。
- JD 是否按预期写入。
- JSON 内容是否语义一致。
- PostgreSQL 模式下如果读回失败，要回滚事务。

接口返回里会包含：

```text
reportReadBackVerified
jdReadBackVerified
```

这对应用户之前遇到的“不能把没验证成功的东西说成已保存”的问题。对于求职产品来说，报告和简历修改是用户会依赖的资产。如果写入失败还提示成功，后续所有动作都会建立在错误状态上。

相关测试在 `src/__tests__/persist-eval-jd-verified-write.test.ts`，覆盖了 SQLite 读回、PostgreSQL jsonb 语义读回、JD 读回失败时事务回滚等场景。

## 18. JD 库、报告库和 PDF

评分结果会进入两个用户可见资产库。

JD 库对应 `src/app/evaluate/jds/page.tsx`。它展示所有录入的职位描述，支持按公司、职位、正文、关键词搜索，按来源筛选，包括粘贴、OCR、链接、Agent、职位发现。用户可以查看、编辑、删除 JD，并看到是否已关联报告。

报告库对应 `src/app/evaluate/reports/page.tsx`。它展示所有评估报告，支持按公司、职位、关键词搜索，按评分和时间筛选，按日期或分数排序。打开报告后通过 `ReportBlocks` 展示 A-G 板块和分项分数。

PDF 导出对应 `src/app/api/reports/[reportNum]/pdf/route.ts`。它会把报告 HTML 渲染成 PDF，并校验生成结果非空、文件头是 `%PDF`，再返回下载文件和 `X-Content-SHA256`。

这个设计让评分结果不只是聊天内容，而是可查、可筛、可导出、可复用的求职资产。

## 19. 失败模式

评分系统需要处理的失败不是一种，而是一串。

### 19.1 输入失败

用户没有提供 JD 文本、URL 或截图时，系统返回缺少输入，不进入评估。

如果图片不像 JD，或者 image intake 置信度低，系统不能硬跑评估。`jd-image-routing.test.ts` 覆盖了这些场景：未知截图不进入 JD/Offer/resume 流程，低置信度缩略图提示上传更清晰图片，OCR 超时被当成临时服务失败，而不是直接指责图片不清楚。

### 19.2 OCR 正文失败

截图识别可以判断图片是 JD，但仍可能拿不到有效正文。比如长图分段识别失败、缩略图太小、识别到的是聊天气泡而不是 JD 正文。

这种情况应该提示用户上传更清晰原始 JD 截图，或直接粘贴文本/链接，而不是生成空报告。

### 19.3 URL 抓取失败

招聘网站可能限制访问。URL 抓取失败时，系统提示粘贴文本，不继续生成假报告。

### 19.4 模型生成失败

某个板块生成失败时，该板块内容会标记为生成失败，分数为 0。整体流程仍可以尽量返回，但不应该掩盖板块失败。

### 19.5 风险扫描失败

风险扫描是 G 的增强输入。失败时评估流程可以继续，但 G 的风险证据会变少。产品上不能把“未扫描到风险”说成“没有风险”，只能说没有检测到明显风险信号。

### 19.6 保存失败

保存失败或读回失败时，不能提示报告已保存。PostgreSQL 模式下读回失败会回滚。

## 20. 测试与验收

评分系统相关测试主要覆盖这些产品事实。

| 测试文件 | 证明什么 |
|---|---|
| `src/__tests__/evaluation-scoring.test.ts` | E/F 完整策略内容不会因为提到缺口、红线、风险而被误打 1 分；G 不进入 A-F 总分；缺简历只影响 B |
| `src/__tests__/persist-eval-jd-verified-write.test.ts` | 报告和 JD 写入后必须读回校验；PostgreSQL jsonb 能做语义匹配；读回失败会回滚 |
| `src/__tests__/jd-image-routing.test.ts` | JD 截图必须先识别；未知图片、低质量图片、OCR 超时都有正确路由 |
| `src/__tests__/jd-evaluation-summary.test.ts` | 聊天摘要使用 A-G 板块和风险扫描，不把完整报告或表格塞回聊天框 |
| `src/__tests__/jd-eval-partial-candidate.test.ts` | JD 评估摘要要避免被局部候选内容污染 |

这些测试不是纯技术测试，而是在保护产品语义：

- 评分不能误伤策略内容。
- 风险不能污染匹配分。
- 截图不能绕过识别。
- 保存必须可证明。
- 聊天摘要不能替代报告详情。

## 21. 当前边界

当前评分系统已经能把 JD 评估做成稳定产品链路，但仍有边界。

- B 板块的兜底评分仍依赖关键词信号，未来可以升级成结构化 JSON rubric。
- C/E/F 的策略评分仍是启发式规则，未来可以按“具体性、可执行性、证据贴合、风险覆盖”设计更细分的 rubric。
- D 板块的市场判断依赖公开信息质量，未联网时只能估算。
- G 风险扫描不能替代用户自行核实，只能帮助用户节省筛选时间。
- OCR 对超长图、低清图和聊天截图仍有失败概率，需要用户粘贴文本或上传原始清晰图兜底。
- 旧报告不会自动重算，重新评估后才会使用新的评分逻辑。

## 22. 产品总结

纸鸢评分系统的本质，是把一份 JD 拆成可解释、可行动、可沉淀的求职判断：

```text
岗位是否清楚
简历是否匹配
职级是否合理
薪资是否值得
方案是否可执行
面试是否能准备
岗位是否真实可信
```

它不是一个“AI 打分器”，而是一套求职决策系统。它用 A-G 板块把问题拆清楚，用 A-F 权重把机会优先级算出来，用 G 和黑话扫描把风险独立展示，用报告库和 JD 库把判断沉淀下来，用读回校验证明系统真的完成了保存。

成熟的 AI 求职产品不能只依赖模型自由发挥。它需要稳定的输入识别、清晰的评分维度、板块语义隔离、风险与匹配分离、可复用的报告资产，以及能防止历史问题复发的测试。

这就是纸鸢求职助手评分系统当前的产品构造。
