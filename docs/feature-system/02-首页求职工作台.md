# 首页求职工作台的产品构造

纸鸢求职助手的首页不是营销页，也不是简单导航页。它是用户每天打开产品后看到的求职状态总览：当前评估了多少机会、投了多少、哪些还在面试、有没有 Offer、最近行业和目标公司有什么动态、今天该跟进什么。

这个页面的产品目标是：把分散在 JD 评估、投递追踪、Offer、面试、新闻和设置里的信息，组织成“今天应该做什么”的工作台。

## 1. 产品定位

求职是一个持续数周甚至数月的过程。用户每天打开产品时，最需要的不是重新选择功能，而是快速恢复上下文：

- 最近评估了哪些岗位。
- 哪些岗位已经投递。
- 哪些进入面试。
- 哪些有 Offer。
- 过去一周节奏有没有变化。
- 哪些评估后很久没投。
- 哪些面试后需要跟进。
- 目标行业和目标公司有没有新动态。

首页在纸鸢里的定位是“求职每日工作台”：

```text
服务端求职数据
  -> 机会数量和转化漏斗
  -> 待办提醒
  -> 管线状态
  -> 行业快讯和目标企业动态
  -> 快速进入核心模块
```

它不是替代评估页、简历页、投递追踪页，而是让用户知道下一步应该进入哪个模块。

## 2. 页面入口和关键文件

| 模块 | 文件 | 作用 |
|---|---|---|
| 首页主体 | `src/app/page.tsx` | 加载数据、计算指标、组织首页布局。 |
| 核心指标 | `src/components/home/HeroMetrics.tsx` | 展示已评估、已投递、面试中、Offer、平均匹配分及周趋势。 |
| 转化漏斗 | `src/components/home/PipelineFunnel.tsx` | 展示从发现/评估到投递、面试、Offer 的漏斗。 |
| 待办提醒 | `src/components/home/TodoReminders.tsx` | 基于投递状态和面试日程生成跟进提醒。 |
| 管线总览 | `src/components/home/MiniPipeline.tsx` | 按状态展示管线入口，支持跳转到 Tracker 过滤状态。 |
| 行业快讯 | `src/components/home/IndustryNews.tsx` | 读取行业新闻，支持强制刷新。 |
| 目标企业动态 | `src/components/home/CompanyNews.tsx` | 读取目标公司动态，无目标公司时引导去设置。 |
| 错误态 | `src/components/design/ErrorState.tsx` | 首页数据加载失败时展示重试入口。 |

首页所有功能都围绕同一个目标：让用户不必先想“我要去哪一页”，而是先看到当前求职状态。

## 3. 数据来源

首页加载时会并行读取三个服务端接口：

| 接口 | 用途 |
|---|---|
| `/api/data/applications` | 投递记录、岗位状态、公司和岗位名称、日期、匹配分。 |
| `/api/data/reports` | JD 评估报告数量，用于计算“已评估”。 |
| `/api/offers` | Offer 数量，用于计算收口阶段机会。 |

还有一个本地数据源：

| 数据源 | 用途 |
|---|---|
| Dexie `db.interviews` | 本地面试日程草稿，用于待办提醒。 |

源码里有一句注释说明了首页的数据原则：

```text
Server data is authoritative; local storage is only used for local interview drafts.
```

也就是说，首页不是靠本地假数据展示求职进度。投递、报告、Offer 以服务端为准；只有面试草稿仍保留在本地。

## 4. 首屏结构

首页布局从上到下是：

1. 时间问候和标题。
2. 行业快讯、目标企业动态。
3. 核心求职指标。
4. 转化漏斗和待办提醒。
5. 非空时展示管线总览。
6. 快速操作入口。
7. 每日鼓励语。

这个顺序不是随机的：

- 新闻放在前面，是为了让用户先看到外部机会环境。
- 核心指标紧跟其后，恢复当前求职进度。
- 漏斗和待办把“状态”转成“动作”。
- 快速操作在下面承接下一步路径。

首页不是把所有模块平均铺开，而是先让用户看状态，再引导行动。

## 5. 指标计算口径

首页的核心指标由 `src/app/page.tsx` 计算。

### 5.1 已评估

```text
evaluated = max(reportCount, applications 中 status 为 evaluated 的数量)
```

这个口径很关键。用户可能有报告，但 application 状态没有完全同步；也可能 tracker 里有 evaluated 状态但报告接口数量更少。首页取两者最大值，避免低估评估数量。

### 5.2 已投递

已投递包含所有已经进入投递后阶段的记录：

- `applied`
- `responded`
- `interview`
- `offer`

这说明“已投递”不是只数状态等于 applied，而是包含已经收到回应、面试和 Offer 的机会。

### 5.3 面试中

面试中只统计 `status = interview` 的 applications。

### 5.4 Offer

Offer 优先使用 `/api/offers` 的数量。如果 Offer 接口没有记录，则退回统计 applications 中 `status = offer` 的数量。

```text
offers = offerCount > 0 ? offerCount : application offer status count
```

这个设计避免 Offer 模块和 Tracker 状态同步不完全时首页空缺。

### 5.5 平均匹配分

平均匹配分只统计 `score > 0` 的 applications。没有有效分数时展示 `—`，不显示 0 分。

这避免用户误以为“没有评分数据”就是“平均分为 0”。

## 6. 周趋势

首页会计算最近 7 天和前一个 7 天：

```text
thisWeek = date >= 7 天前
lastWeek = 14 天前 <= date < 7 天前
```

`HeroMetrics` 的 `calcTrend(current, previous)` 会返回当前值和上一周期差值：

- previous 不存在或为 0 时，不显示趋势。
- 正数显示上升。
- 负数显示下降。
- 0 显示持平。

趋势不是绩效评判，而是节奏提醒。比如已评估增加但已投递没有变化，就说明用户可能评估了很多岗位但没有转化成投递。

## 7. 转化漏斗

首页漏斗 stages：

```text
已发现 = evaluated + applied + interviewing + offers
已评估 = evaluated + applied + interviewing + offers
已投递 = applied
面试中 = interviewing
Offer = offers
```

目前“已发现”和“已评估”口径相同，反映的是首页当前还没有把职位发现扫描记录单独纳入漏斗。真正的岗位扫描数据在职位发现系统里维护。

`PipelineFunnel` 会用最大 count 计算条形宽度：

```text
width = max(8, count / max * 100)
```

最低 8% 保证即使数量很小也能看到条形。每一层还会显示和上一层的转化率，上一层为 0 时显示 `—`。

## 8. 待办提醒

`TodoReminders` 当前生成三类待办：

| 类型 | 触发规则 | 跳转 |
|---|---|---|
| `followup` | application 状态为 `interview`，且 updatedAt 距今超过 3 天 | `/tracker` |
| `interview` | 本地面试日程在未来 7 天内 | `/interview` |
| `apply` | application 状态为 `evaluated`，且评估日期距今超过 7 天未投递 | `/tracker` |

首页最多展示 5 条待办。没有待办时显示“暂无待办，一切顺利”。

这个模块把求职系统从“记录型产品”往“行动型产品”推进：它不只是告诉用户有多少机会，而是指出哪些机会需要处理。

## 9. 管线总览

`MiniPipeline` 会按固定状态展示：

- `evaluated`
- `applied`
- `interview`
- `offer`
- `discarded`

如果总数为 0，显示：

```text
暂无投递记录，评估第一份 JD 开始追踪
```

如果有数据，每个状态块都链接到：

```text
/tracker?status=<status>
```

这让首页不仅展示状态，还能直接跳到对应过滤后的追踪页。

## 10. 行业快讯

`IndustryNews` 调用：

```text
/api/news/industry
```

点击刷新时调用：

```text
/api/news/industry?force=1
```

展示逻辑：

- 初次加载显示 skeleton。
- 接口失败显示“快讯暂不可用”。
- 数据为空也显示“快讯暂不可用”。
- 有数据时最多展示 6 条。
- 有 URL 的新闻用新窗口打开，并显示来源和相对时间。

这类动态信息不参与核心求职数据计算，失败时不应该影响首页主数据。

## 11. 目标企业动态

`CompanyNews` 调用：

```text
/api/news/company
```

刷新时调用：

```text
/api/news/company?force=1
```

它有一个特殊空态：如果接口返回 `hasTargets=false`，说明用户还没有设置目标公司，首页会展示“去设置添加”的入口，跳到 `/settings`。

这个设计把空态变成下一步动作，而不是只显示“暂无数据”。

## 12. 快速操作

首页提供四个核心入口：

| 按钮 | 路径 | 用途 |
|---|---|---|
| 评估 JD | `/evaluate` | 粘贴或上传 JD，生成评估报告。 |
| 查看追踪 | `/tracker` | 查看投递管线和状态。 |
| 优化简历 | `/cv` | 进入简历工作台。 |
| AI 顾问 | `/agent` | 进入 Agent Chat。 |

这些入口对应求职日常最频繁的四类动作：判断机会、追踪机会、优化材料、继续对话。

## 13. 空态、加载态和错误态

首页有三类状态处理：

| 状态 | 处理 |
|---|---|
| 加载中 | `mounted=false` 时展示骨架屏，避免闪烁空数据。 |
| 无求职数据 | 标题显示“欢迎打开你的求职手帳”，核心指标显示 `—`，管线总览不展示真实状态块。 |
| 数据加载失败 | 显示 `ErrorState`，点击重试会刷新页面。 |

首页不能在数据为空时展示假数字，也不能在接口失败时把 0 当作真实进度。

## 14. 产品边界

| 边界 | 原因 |
|---|---|
| 首页不直接修改投递状态 | 状态变更应在 Tracker 或具体业务模块完成。 |
| 新闻失败不影响核心指标 | 外部动态是增强信息，不是求职主数据。 |
| 本地面试草稿不能代表所有服务端状态 | 当前只有 interviews 仍从 Dexie 读取。 |
| 无数据时显示 `—` 而不是 0 | 0 分和无数据不是同一件事。 |
| 快速操作只做跳转 | 复杂写入动作必须进入对应页面。 |

## 15. 当前实现的限制

首页当前还有几个明确边界：

- “已发现”和“已评估”漏斗口径相同，还没有独立接入职位发现扫描库。
- 面试日程仍从本地 Dexie 读取，和服务端投递记录没有完全统一。
- 待办只覆盖三类规则，没有覆盖 Offer 截止时间、简历提案待确认、JD 报告待导出等更细动作。
- 周趋势只看数量差，不解释质量变化。

这些限制不是文案问题，而是后续产品演进点。

## 16. 验收口径

首页验收时要看：

- `/api/data/applications`、`/api/data/reports`、`/api/offers` 成功时指标口径正确。
- 服务端接口失败时进入 ErrorState。
- 没有数据时指标显示 `—`，不显示假统计。
- 面试 7 天内、面试后 3 天未跟进、评估后 7 天未投递能生成待办。
- 目标公司未设置时，目标企业动态能引导到 settings。
- 管线状态块能跳到 tracker 对应过滤路径。

## 17. 产品总结

首页求职工作台把纸鸢的多页面能力收束成每日入口。它不负责完成所有求职动作，而是把用户从“我该点哪里”带到“我今天该处理什么”。

它的产品价值来自真实数据口径、空态和错误态、待办规则、趋势提醒和模块跳转，而不是一个漂亮的欢迎页。
