# 个人设置与数据管理系统的产品构造

个人设置与数据管理系统是纸鸢求职助手里的用户基础配置层。它保存用户的基本信息、职业定位、核心优势、薪资预期、目标公司动态偏好，并提供导入、导出、清除数据和退出登录能力。

这个系统的价值不在于“有一个设置页”，而在于让求职助手拥有稳定的用户上下文。没有设置和数据管理，Agent 每次都只能从当前对话猜用户是谁、想找什么、薪资底线是什么、目标公司有哪些。

## 1. 产品定位

纸鸢是长期求职助手，不是一次性问答工具。

长期助手需要稳定记住几类信息：

| 信息类型 | 用途 |
|---|---|
| 基本信息 | 简历导出、个人资料展示、联系信息补全 |
| 职业定位 | JD 评估、简历优化、面试准备时判断用户方向 |
| 核心优势 | 作为用户可复用卖点 |
| 薪资预期 | Offer 评估、薪资判断、岗位筛选 |
| 目标公司 | 首页快讯、机会关注、岗位发现 |
| 数据备份 | 防止本地数据丢失，支持迁移 |
| 登录退出 | 保护用户数据边界 |

因此，个人设置页是整个产品的“用户上下文控制台”。

## 2. 页面入口

设置页是 `src/app/settings/page.tsx`。

页面包含这些模块：

| 模块 | 页面内容 | 数据落点 |
|---|---|---|
| 求职画像卡片 | archetype、推荐方向、优势技能、偏好、硬约束、求职叙事 | `zhiyuan-profile` localStorage |
| 基本信息 | 姓名、邮箱、电话、城市、LinkedIn、GitHub、作品集 | `zhiyuan-profile` localStorage |
| 职业定位 | 职业头衔、职业故事、核心优势 | `zhiyuan-profile` localStorage |
| 薪资 | 最低/最高税前月薪、是否可谈 | `zhiyuan-profile` localStorage |
| 快讯设置 | 目标公司、刷新频次 | `zhiyuan-news-settings` localStorage + `/api/data/profile` |
| 账户 | 退出登录 | `/api/auth/logout` |
| 数据管理 | 导出、导入文件、从 CLI 导入、清除数据 | Dexie、`/api/data/import`、localStorage |

这套页面同时管理本地状态和服务端状态，所以文档必须区分“当前页面真实写在哪里”。

## 3. 用户画像数据

页面使用 `UserProfile` 类型，定义在 `src/types/index.ts`。

核心字段包括：

| 字段 | 含义 |
|---|---|
| `fullName`、`email`、`phone`、`location` | 基础身份和联系方式 |
| `linkedin`、`github`、`portfolioUrl` | 外部履历链接 |
| `targetRoles` | 目标岗位方向 |
| `headline` | 职业头衔 |
| `exitStory` | 职业故事 |
| `superpowers` | 核心优势 |
| `salaryMinK`、`salaryMaxK` | 薪资区间 |
| `salaryFlexibility` | `open` 或 `firm` |
| `narrative` | 求职叙事 |
| `archetype` | 匹配类型 |
| `preferences` | 公司类型、行业、文化、工作方式 |
| `constraints` | 薪资、地点、工时和其他硬约束 |

页面首次加载时读取：

```text
localStorage.getItem("zhiyuan-profile")
```

用户修改字段时调用 `saveProfile()`：

```text
setProfile(p)
localStorage.setItem("zhiyuan-profile", JSON.stringify(p))
```

这说明当前设置页的核心画像数据是 localStorage 持久化。服务端的 `/api/data/profile` 也存在，但页面并没有把所有字段统一写入服务端。

## 4. 求职画像卡片

设置页顶部会根据 profile 中已有字段展示一张求职画像卡。

它展示：

- `archetype`: 匹配类型。
- `targetRoles`: 推荐方向，并区分首选和备选。
- `superpowers`: 优势技能。
- `preferences`: 公司类型、行业、文化、工作方式。
- `constraints`: 薪资、地点、工时和其他硬约束。
- `narrative`: 求职叙事。

这张卡片的产品意义是：让用户看到系统当前理解的“我是谁”和“我想要什么”。如果这里的信息不准，后续 JD 评分、简历优化和 Agent 建议都会偏。

## 5. 基本信息与职业定位

基本信息模块保存：

- 姓名
- 邮箱
- 电话
- 城市
- LinkedIn
- GitHub
- 作品集

职业定位模块保存：

- 职业头衔
- 职业故事
- 核心优势

核心优势使用 `superpowers` 数组，用户可以通过输入框添加，也可以从已有标签中删除。这个字段会被 JD 评估和简历优化用来识别用户的长期卖点。

薪资模块保存：

- `salaryMinK`
- `salaryMaxK`
- `salaryFlexibility`

其中 `salaryFlexibility` 有两个选项：

```text
open: 可谈
firm: 不接受低于区间
```

这对 Offer 评估非常重要。一个 30K 的 Offer 对不同用户含义不同，必须结合用户薪资底线判断。

## 6. 快讯设置

快讯设置保存用户关注的目标公司和刷新频次。

页面本地保存：

```text
localStorage.setItem("zhiyuan-news-settings", JSON.stringify(settings))
```

同时会尝试写入服务端：

```http
PUT /api/data/profile
```

请求体结构是：

```json
{
  "goals": {
    "target_companies": ["字节跳动", "腾讯"],
    "news_refresh_interval": "6h"
  }
}
```

这个设计体现了当前项目的过渡状态：前端先保证本地可用，同时把关键目标公司偏好写入服务端 profile，供其他模块读取。

刷新频次包括：

| 值 | 展示 |
|---|---|
| `6h` | 每 6 小时 |
| `12h` | 每 12 小时 |
| `24h` | 每天 |
| `manual` | 手动 |

## 7. 数据导出

设置页的“导出数据”会读取：

```text
db.applications.toArray()
```

然后调用 `exportApplicationsMD()` 生成 `applications.md`，再通过浏览器下载。

导出字段包括：

- 序号
- 日期
- 公司
- 岗位
- 分数
- 状态
- PDF 标记
- 报告链接
- 备注

这个导出和投递追踪页使用的是同一套 `src/lib/exporters.ts`，说明投递记录有统一带出系统的格式。

## 8. 文件导入

本地文件导入通过隐藏 `<input type="file">` 实现，支持 `.md` 和 `.json`，但当前逻辑只对 `.md` 做了解析。

导入流程：

```text
用户选择文件
  -> file.text()
  -> 如果文件名以 .md 结尾，调用 parseApplicationsMD()
  -> 按 company + role 查重
  -> 不存在则写入 db.applications
  -> 展示成功导入 N 条投递记录
```

去重条件是：

```text
db.applications.where({ company, role }).first()
```

这能避免重复导入同一个公司岗位，但也意味着同公司同岗位的不同批次记录会被视为重复。对于求职产品来说，这是一个合理的保守默认，但未来如果要支持多次投递，需要加入时间或来源维度。

## 9. 从 CLI 导入

“从 CLI 导入”调用的是 `src/app/api/data/import/route.ts`。

这个接口在服务端读取项目里的历史数据：

| 文件或目录 | 读取内容 |
|---|---|
| `data/applications.md` | 申请记录 |
| `reports/*.md` | 历史报告 |
| `config/profile.yml` | 用户配置 |
| `cv.md` | 简历内容 |

接口返回：

```json
{
  "success": true,
  "data": {
    "applications": [],
    "reports": [],
    "profile": {},
    "cv": null,
    "hasData": true,
    "summary": "找到 N 条申请、M 份报告、K 个配置项"
  }
}
```

前端收到后会：

1. 把 `applications` 写入 Dexie `db.applications`。
2. 把 `reports` 写入 Dexie `db.reports`。
3. 如果本地还没有 `zhiyuan-profile`，把 CLI profile 映射为 `UserProfile`。
4. 展示导入结果。

这个能力解决的是项目从 CLI 形态迁移到 Web 产品时的数据延续问题。

## 10. 清除数据

清除数据前会弹出浏览器确认：

```text
确定清除所有数据？建议先导出备份。
```

用户确认后，页面执行：

```text
db.applications.clear()
db.reports.clear()
db.offers.clear()
db.stories.clear()
db.interviews.clear()
localStorage.removeItem("zhiyuan-profile")
setProfile(DEFAULT_PROFILE)
```

这里清除的是本地 Dexie 和 localStorage 数据，不等于清除服务端所有用户数据。这个边界必须写清楚。

## 11. 退出登录

账户模块调用：

```http
POST /api/auth/logout
```

然后跳转：

```text
/login
```

这与认证准入、JWT、个人信息隔离系统相关。设置页只提供入口，真正的登录态清除逻辑在认证 API。

## 12. 当前边界

个人设置与数据管理系统当前有几个重要边界：

1. 核心 profile 字段主要存在 localStorage，不是全部服务端化。
2. 快讯目标公司会尝试写服务端 `/api/data/profile`，但失败被视为 non-critical。
3. `.json` 文件在 input accept 中允许，但当前导入逻辑主要处理 `.md`。
4. 清除数据只清本地 Dexie 和 localStorage，不清服务端 repository。
5. CLI 导入读取的是项目本地文件，不是用户上传文件。
6. CLI profile 只在本地没有 profile 时才导入，避免覆盖用户现有设置。
7. 清除操作使用浏览器 confirm，不是更复杂的二次密码验证。

这些边界说明它是 Web 产品从本地优先到服务端化过程中的配置中心。

## 13. 常见失败模式

| 失败模式 | 当前处理 |
|---|---|
| localStorage 中 profile JSON 损坏 | catch 后忽略，使用默认 profile |
| 快讯设置写服务端失败 | 本地仍保存，`newsSaving` 结束，不阻断 |
| 导入文件格式不符合 | 展示“文件解析失败，请检查格式” |
| CLI API 请求失败 | 展示“CLI 导入失败：...” |
| CLI 没有数据 | 展示“CLI 端暂无数据” |
| 用户取消清除 | 不执行任何清除 |
| 退出登录失败 | 当前页面未显式捕获，仍尝试跳转逻辑需后续增强 |

产品上最重要的是：数据管理操作不能暗中覆盖或删除。导入要查重，清除要确认，CLI profile 不覆盖已有 profile。

## 14. 验证依据

相关项目文件包括：

- `src/app/settings/page.tsx`
- `src/types/index.ts`
- `src/lib/db.ts`
- `src/lib/exporters.ts`
- `src/lib/parsers.ts`
- `src/app/api/data/import/route.ts`
- `src/app/api/data/profile/route.ts`
- `src/app/api/auth/logout/route.ts`

验证重点包括：

- 刷新页面后 profile 是否能从 localStorage 恢复。
- 核心优势添加和删除是否能持久化。
- 薪资区间和可谈/不可低于区间是否能保存。
- 目标公司设置是否同时写本地和尝试写服务端。
- 导出 `applications.md` 是否包含完整投递字段。
- `.md` 导入是否能去重写入投递记录。
- CLI 导入是否能读取 applications、reports 和 profile。
- 清除数据是否需要确认并清空本地表。
- 退出登录是否回到登录页。

## 15. 产品总结

个人设置与数据管理系统让纸鸢有了稳定的用户上下文。

它保存的不只是姓名和邮箱，而是长期求职判断所需的目标、偏好、优势、薪资底线、目标公司和历史数据。只有这些信息稳定存在，JD 评分、简历优化、面试准备、Offer 评估和 Analytics 才能围绕同一个用户连续工作。
