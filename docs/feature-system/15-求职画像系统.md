# 求职画像系统的产品构造

纸鸢求职助手的求职画像系统，不是一个“个人资料表”。它是 Agent 理解用户长期求职目标、能力证据、偏好和约束的记忆层。它决定了系统能不能从通用建议，走向“按这个用户的方向、经历、底线和历史反馈来判断机会”。

这个系统的产品目标是：让用户不必每次重新解释自己是谁、想找什么、不能接受什么，同时防止低质量信号污染长期记忆。

## 1. 产品定位

求职助手如果没有画像，只能做一次性问答：

- 评估 JD 时不知道用户目标方向。
- 改简历时不知道哪些能力应该前置。
- Offer 分析时不知道薪资底线和工作方式偏好。
- 面试准备时不知道用户有哪些真实项目可以讲。
- 用户每次打开 Agent，都要重复介绍背景。

画像系统把这些信息沉淀成长期上下文：

```text
自我定位对话 / 简历 / JD / Offer / 面试回答 / 手动确认
  -> 候选画像信号
  -> 质量门过滤
  -> profile_signals
  -> 用户确认 / 编辑 / 拒绝
  -> confirmed skill 晋升进 profile
  -> Agent、JD 评估、简历优化、面试准备复用
```

它的核心不是“多存点信息”，而是“只把有证据、有归属、有质量的信号沉淀下来”。

## 2. 为什么不能把所有对话都写进画像

如果所有对话都自动写进画像，会带来严重污染：

- JD 里的要求被误当成用户技能。
- 面试题里的假设被误当成用户经历。
- Agent 输出的建议被误当成用户事实。
- 用户随口说的一句偏好被永久当成底线。
- 噪声词、泛词、失败提示进入技能库。

当前项目通过 `src/lib/profile-skill-quality.ts` 做质量门。它会判断信号来源、证据归属、文本是否像 JD 要求、是否是噪声、是否有用户自有证据，再决定能不能入库。

一个关键规则是：`sourceType === "jd"` 的 `skill_claim` 会被拒绝，错误原因是 `jd_requirement_is_not_user_skill`。这条规则直接防止“岗位要求会 SQL”被记成“用户会 SQL”。

## 3. 系统入口和关键文件

| 层级 | 文件或接口 | 作用 |
|---|---|---|
| 服务端画像 API | `src/app/api/data/profile/route.ts` | 读取、更新、重置 profile，处理 goals、history、dealBreakers。 |
| 服务端信号 API | `src/app/api/data/signals/route.ts` | 信号 CRUD、质量门、读回校验、确认后晋升技能。 |
| 画像生成入口 | `src/lib/profile-mining.ts` | 前端调用 `/api/profile/analyze`，失败时用本地统计生成 fallback 画像。 |
| 画像缓存 | `src/lib/profile-storage.ts` | Dexie 本地缓存 `profiles`，固定主记录 `id=1`，保留快照上限。 |
| 缓存同步 | `src/lib/profile-update.ts` | 后台触发服务端分析，并同步到 Dexie 缓存。 |
| 信号质量门 | `src/lib/profile-skill-quality.ts` | 归一化技能、偏好、底线、薪资等信号，过滤污染。 |
| 读回校验 | `src/lib/profile-signal-persistence-verifier.ts` | 校验 signals 写入后内容一致，校验确认技能已进入 profile。 |
| 自我定位状态 | `src/lib/agent/profile-sop.ts` | 管理用户自我定位问答阶段和分支。 |

这套系统同时包含服务端可信数据层和前端缓存层。不能把 localStorage 或 Dexie 当作唯一真实来源。

## 4. Profile 主记录

服务端 profile 由三个 JSON 组成：

| 字段 | 含义 |
|---|---|
| `data_json` | 画像主体数据，例如 skills、preferences、marketFit。 |
| `goals_json` | 求职目标，例如目标岗位、薪资、地点、底线、锁定字段。 |
| `history_json` | 画像演变历史，例如确认技能、重置画像等事件。 |

`GET /api/data/profile` 会读取当前登录用户的 profile。如果不存在，会尝试从 `config/profile.yml` 中读取 `target_roles.primary` 作为初始 goals，再创建空 profile。

返回给前端前，系统会清洗 goals 中的 `dealBreakers`，过滤不合法或噪声底线。

`PUT` 用于合并写入 data、goals、history。`PATCH` 支持局部更新 goals 或 data，并可带上 `source` 和 `_lockedFields`。`DELETE` 会清空 profile，并删除该用户 signals。

## 5. 前端缓存层

`profile-storage.ts` 在 Dexie 中保存前端缓存：

- 主 profile 固定使用 `id=1`。
- 每次保存会更新 `lastUpdated`。
- 快照最多保留 10 个，超过后删除最旧快照。

`profile-update.ts` 的 `triggerProfileUpdate()` 会后台调用 `/api/profile/analyze`，拿到服务端画像后同步到 Dexie。

如果服务端分析失败，`profile-mining.ts` 会用本地统计生成 fallback：

- 从 applications 计算投递数量、面试/offer 通过率、状态分布。
- 从 reports 计算平均评分和行业/岗位 archetype。
- 从 practiceRecords 计算训练记录数量和题型分布。
- 生成一个“统计画像生成（LLM 暂不可用）”历史事件。

这让前端即使在服务端分析不可用时，也能展示最低限度的画像概览；但它不会冒充完整智能画像。

## 6. 自我定位问答状态

`profile-sop.ts` 管理 Agent 的自我定位流程。状态保存在 localStorage，key 是：

```text
zhiyuan-profile-sop-state
```

状态结构包括：

- `stage`：0 到 5。
- `branch`：A / B / C / D。
- `collected`：每一阶段用户回答。
- `startedAt`
- `updatedAt`

状态 24 小时过期。

四个分支对应用户当前求职状态：

| 分支 | 用户状态 | 后续问题方向 |
|---|---|---|
| A | 已经在投简历找工作 | 追问已投方向、回应最多的岗位、理想岗位、竞争力证据。 |
| B | 还没开始找，想搞清方向 | 追问细分方向、相关经历、缺口、岗位名称和工作方式期待。 |
| C | 应届生或完全没方向 | 从不想做什么、时间过得快的事情、别人找他帮忙的能力切入。 |
| D | 几个方向纠结 | 让用户列方向、选择先试方向、比较市场机会、排除方向。 |

这部分的产品作用是收集高质量画像素材，而不是直接把每句话写进 profile。真正写入还要经过 signals 质量门。

## 7. Profile Signal 数据结构

画像信号通过 `/api/data/signals` 管理。一个 signal 至少包含：

- `source`
- `signal_type`
- `content_json`
- `session_id`

支持的信号类型包括：

| signal_type | 产品含义 |
|---|---|
| `skill_claim` | 用户具备某项技能或方法。 |
| `raw_context` | 有自有证据的原始上下文。 |
| `role_preference` | 目标岗位或方向偏好。 |
| `dealbreaker` | 求职底线或明确约束。 |
| `company_pref` | 公司偏好。 |
| `salary_expectation` | 薪资期望。 |

系统会把信号归类为：

- `hard_skill`
- `soft_skill`
- `domain`
- `tool`
- `method`
- `project_experience`
- `preference`
- `goal`
- `constraint`

每个信号还会带状态：

- `candidate`
- `confirmed`
- `rejected`

这个状态设计让“系统识别到一个可能的信号”和“用户确认这是事实”分开。

## 8. 来源权重

不同来源的可信度不同。当前项目写死了来源权重：

| 来源 | 权重 | 产品解释 |
|---|---:|---|
| `resume` | 0.95 | 简历里出现且归属用户，可信度最高。 |
| `manual` | 0.95 | 用户手动确认，可信度最高。 |
| `user_preference` | 0.90 | 用户主动表达偏好。 |
| `interview_answer` | 0.75 | 面试回答里可能包含真实经历。 |
| `offer` | 0.65 | Offer 可用于偏好和约束判断。 |
| `ordinary_chat` | 0.55 | 普通对话需要谨慎。 |
| `agent_output` | 0.35 | Agent 输出不能直接当事实。 |
| `jd` | 0.20 | JD 是岗位要求，不是用户能力。 |
| `unknown` | 0.45 | 来源不明，默认谨慎。 |

这套权重让系统不会把所有输入一视同仁。

## 9. 技能信号质量门

`skill_claim` 的归一化流程很严格。

系统会先把别名归一化，例如：

- `js` -> `JavaScript`
- `nextjs` -> `Next.js`
- `rag` -> `RAG`
- `llm` -> `大模型应用`
- `prompt engineering` -> `提示词工程`
- `bi` -> `BI 分析`
- `数仓` -> `数据仓库`
- `指标体系` -> `指标体系设计`

然后过滤：

- 泛词：业务、技术、能力、经验、项目、系统、平台等。
- 噪声词：面试题、考察点、失败提示、无关聊天片段。
- JD 要求：岗位职责、任职要求、至少、需要具备、N 年以上等。
- 没有自有证据的技能。
- 太短、太长或不像技能的词。

自动技能必须有用户归属证据，例如“我”“本人”“曾”“项目中”“负责”“主导”“参与”“简历”等。手动技能可以更宽松，但仍有长度限制。

这就是为什么画像系统宁可少存，也不能乱存。

## 10. 底线和约束清洗

`dealbreaker` 用于保存用户不能接受的条件，例如：

- 996 / 007
- 大小周
- 外包 / 驻场 / 派遣
- 加班
- 单休
- 社保 / 五险一金 / 公积金
- 远程 / 通勤 / 城市
- 降薪
- 裁员风险
- PUA、拖欠、管理混乱等

但它会过滤按钮文案和动作噪声，例如“拒绝此 Offer”“接受此 Offer”“点击”“重新上传”“截图识别”等。

这避免了 Offer 评估页面的按钮或系统提示被当成用户长期底线。

## 11. 写入和读回校验

`POST /api/data/signals` 的流程：

```text
接收 signal
  -> normalizeProfileSignalForStorage()
  -> 质量门通过
  -> insert
  -> get(id)
  -> profileSignalReadBackMatches()
  -> 返回 readBackVerified
```

读回校验会比较：

- `source`
- `signal_type`
- `content_json` 的 canonical JSON
- `session_id`
- 可选的 ID

如果读回不一致，会返回：

```text
画像信号写入后回读校验失败，已阻止成功提示
```

这和简历保存系统一致：写入类动作必须用读回证明。

## 12. 确认、编辑、拒绝

`PATCH /api/data/signals` 支持三种动作：

| action | 效果 |
|---|---|
| `confirm` | 信号状态变成 `confirmed`，source 变成 `user_confirmed`，confidence 至少 0.9。 |
| `edit` | 合并用户编辑内容，状态保持 confirmed 或 candidate。 |
| `reject` | 信号状态变成 `rejected`，写入 rejectedAt。 |

每次 PATCH 后也会读回校验。

如果确认的是 `skill_claim`，系统还会执行 `upsertConfirmedSkill()`，把该技能晋升进 profile 的 `skills` 数组。

晋升规则：

- 同名技能合并。
- 手动来源优先。
- proficiency 取更高值。
- evidence 去重，最多保留 5 条。
- profile skills 最多保留 20 个。
- history 追加“确认画像技能”事件。
- 再读回 profile，确认 `profileContainsSkill()` 为真。

如果 profile 读回没有包含该技能，也会阻断成功提示。

## 13. 与其他功能的关系

画像系统不是孤立页面，它会影响多个核心功能：

| 下游功能 | 如何使用画像 |
|---|---|
| JD 评分 | 判断用户目标方向、能力证据、偏好和底线。 |
| 简历优化 Judge | 注入 headline、superpowers、targetRoles 和角色写作指南。 |
| Offer 评估 | 结合薪资目标、工作方式偏好和 dealBreakers。 |
| 面试准备 | 从确认技能和项目经验中选择可讲故事。 |
| 岗位发现 | 用目标角色和偏好过滤机会。 |
| Agent Chat | 减少重复询问用户背景。 |

画像越准确，后续功能越个性化；画像越污染，后续功能越容易给错建议。

## 14. 重置和数据隔离

所有服务端 profile 和 signals 操作都会调用 `getCurrentUser()`，按 `userId` 读写。用户 A 不能查询或修改用户 B 的画像信号。

`DELETE /api/data/profile` 会：

- 清空当前用户 profile data。
- 清空 goals。
- 记录“画像已重置”历史。
- 删除当前用户 signals。
- 返回 deletedSignals 数量。

这保证用户可以清空长期记忆，而不是被历史数据永久绑定。

## 15. 失败模式

| 失败模式 | 系统处理 |
|---|---|
| 未登录 | 返回 401。 |
| signal 缺少 `signal_type` | 返回 400。 |
| 信号质量不达标 | 返回 422，并给出 rejectedReason。 |
| JD 要求被当作技能 | 返回 `jd_requirement_is_not_user_skill`。 |
| raw_context 没有用户自有证据 | 返回 `raw_context_not_user_owned`。 |
| dealbreaker 是按钮或动作噪声 | 返回 `invalid_constraint`。 |
| salary_expectation 数值异常 | 返回 `invalid_salary_expectation`。 |
| signal 写入后读回不一致 | 返回 500，阻断成功提示。 |
| confirmed skill 晋升后 profile 读回不包含技能 | 返回 500，阻断成功提示。 |
| `/api/profile/analyze` 不可用 | 前端降级为本地统计 fallback 画像。 |

## 16. 测试与验证证据

当前项目相关测试包括：

- `src/__tests__/profile-skill-quality.test.ts`：验证技能、底线、来源、噪声、JD 要求过滤。
- `src/__tests__/profile-signal-verified-write.test.ts`：验证 signal 写入读回、确认技能晋升 profile。
- `src/lib/profile-signal-persistence-verifier.ts`：验证 canonical JSON 读回和 profile 技能包含关系。
- `src/lib/agent/profile-sop.ts`：定义自我定位问答状态机。
- `src/lib/profile-mining.ts`：定义服务端分析失败后的 fallback 画像。

验收时要看：

- JD 要求不能进入用户技能。
- 没有用户自有证据的普通对话不能进入长期画像。
- 用户确认技能后，profile 里能读回该技能。
- 用户拒绝信号后，它不会继续作为确认事实使用。
- 重置画像会删除 signals。

## 17. 产品总结

求职画像系统让纸鸢从一次性求职问答，变成能持续理解用户的求职助手。它的难点不在于“多记住一点”，而在于严格区分岗位要求、用户事实、模型建议、用户偏好和长期底线。

只有画像信号足够干净，JD 评估、简历优化、Offer 分析和面试准备才会真正变成“为这个用户服务”，而不是通用建议的重新包装。
