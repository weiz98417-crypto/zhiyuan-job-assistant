# 岗位发现扫描系统的产品构造

岗位发现扫描系统处在纸鸢求职助手的机会入口层。JD 评分系统解决的是“用户已经拿到一份 JD 以后如何判断”，岗位发现扫描系统解决的是更前面的事情：用户还没有稳定机会池时，系统如何按目标方向、目标公司、关键词和地点持续发现可评估的岗位。

这个系统不是“搜索框 + 列表页”。它把目标公司配置、扫描任务、外部页面抓取、岗位去重、状态流转、JD 保存和 Agent 评估连接成一条产品链路。它的价值在于让求职机会从零散浏览变成可沉淀、可筛选、可继续加工的数据资产。

## 1. 产品定位

在完整求职链路里，岗位发现扫描系统承担“机会供给”的职责。

用户不是每次都能主动找到高质量 JD。很多时候，用户只知道自己想找“AI 产品经理”“大模型产品经理”“Agent 产品经理”“数据产品经理”等方向，但不知道该去哪些公司官网、哪些招聘平台、哪些关键词组合下搜索。纸鸢把这个问题拆成三个动作：

- 用户配置自己关心的岗位关键词、排除关键词、城市和结果上限。
- 系统按照公司官网优先、招聘平台补扫的顺序发现岗位。
- 用户对发现到的岗位做下一步处理：查看 JD、保存到 JD 库、交给 Agent 评估、跳过。

所以它不是自动投递系统，也不是批量海投系统。它只负责把可能有价值的机会放进用户的工作台，让用户继续判断。

完整产品位置可以表示为：

```text
目标方向 / 关键词 / 城市 / 公司源
  -> 扫描任务 scan_queue
  -> 公司官网适配器 / 平台补扫
  -> 岗位记录 scan_jobs
  -> 查看 JD / 保存 JD / Agent 评估 / 跳过
  -> JD 库、报告库、投递追踪继续使用
```

## 2. 真实用户问题

岗位发现系统解决的不是“能不能搜到岗位”这么简单。

真实求职场景里，用户会遇到几个具体问题：

| 用户问题 | 产品里的处理方式 |
|---|---|
| 每天手动刷很多网站，重复劳动太多 | 扫描任务按配置统一跑，结果集中展示 |
| 同一个岗位被反复看见 | 用 `dedup_key` 对 URL 做去重 |
| 平台推荐里混入实习、销售、客服、外包等不相关岗位 | 支持正向关键词和排除关键词 |
| 用户只想看某个城市 | 支持地点过滤，但保留无法读取地点的岗位，避免误杀 |
| 官网没扫到结果 | 触发猎聘、前程无忧、智联招聘补扫 |
| 外部站点触发验证码或页面结构变化 | 不伪装成功，把失败写入 `error_log` 并在页面提示 |
| 发现岗位后还要手动复制 JD 去评估 | 发现页直接提供“查看 JD”“保存到 JD 库”“让 Agent 评估” |

这些问题决定了系统必须有任务状态、结果状态、失败记录和后续动作，而不能只做一次性搜索结果。

## 3. 页面入口

用户入口是 `src/app/discover/page.tsx`。

页面上有三个主要区域：

| 区域 | 产品作用 | 代码事实 |
|---|---|---|
| 扫描配置区 | 输入岗位关键词、排除关键词、就业地点、最多结果 | `titleKeyword`、`excludeKeyword`、`locationFilter`、`maxResults` |
| 扫描进度区 | 展示 pending/running/done/failed/canceled 和公司进度 | `scanStatus`、`pollStatus`、`checkActiveScan` |
| 岗位结果区 | 展示发现岗位，并支持查看 JD、Agent 评估、跳过、进入 JD 管理 | `visibleJobs`、`openJobDetail`、`saveDiscoveryJD`、`evaluateWithAgent` |

默认关键词不是空的。页面内置：

```text
正向关键词：
AI产品经理, 大模型产品经理, Agent产品经理, 数据产品经理, AI运营

排除关键词：
实习, 销售, 客服, 外包, 劳务, 兼职, 电话销售, 地推
```

这体现了纸鸢项目的真实定位：它服务的是以 AI 产品、数据产品、Agent 产品方向为核心的求职助手，不是泛岗位搜索工具。

## 4. 扫描任务如何创建

扫描入口是 `src/app/api/scan/route.ts`。

用户点击“开始扫描”后，前端向 `/api/scan` 发送：

```json
{
  "titleKeyword": "AI产品经理,大模型产品经理",
  "excludeKeyword": "实习,销售,客服,外包",
  "location": "北京",
  "maxResults": 100
}
```

服务端会做几件事：

1. 调用 `getCurrentUser()`，没有登录则返回 `401 Unauthorized`。
2. 解析岗位关键词、排除关键词、地点、结果上限。
3. 如果没有岗位关键词，返回 `missing_title_keywords`，不创建任务。
4. 读取 `portals.yml` 中的公司源。
5. 调用 `createScanEntryForUser()` 创建 `scan_queue`。
6. 没有冲突时启动 `scripts/scan-worker.mjs --once`。
7. 返回 `scanId` 和 `companiesTotal`。

这里有一个很重要的项目边界：当前当 `DB_DRIVER=postgres` 时，`/api/scan` 会直接返回 `503 scan_worker_postgres_not_ready`。

原因不是系统忘了做 Postgres，而是扫描 worker 仍基于本地 SQLite/`better-sqlite3` 写入。代码选择在 Postgres 模式下阻止启动新扫描，避免任务被创建后卡在 pending。这是一个产品保护：宁可明确告诉用户“暂不启动”，也不让用户看到一个永远跑不完的任务。

## 5. 扫描任务的数据结构

扫描任务通过 `scan_queue` 和 `scan_jobs` 两层数据承载。

### 5.1 `scan_queue`

`scan_queue` 记录一次扫描任务本身。

核心字段包括：

| 字段 | 含义 |
|---|---|
| `id` | 扫描任务 ID，页面轮询和 worker 认领都用它 |
| `user_id` | 用户隔离字段 |
| `status` | `pending`、`running`、`done`、`failed`、`canceled` |
| `title_positive_json` | 正向岗位关键词 |
| `title_negative_json` | 排除关键词 |
| `location_filter` | 城市或地区过滤 |
| `max_results` | 结果上限，代码限制在 1-200 |
| `companies_total` | 本次要扫的公司数 |
| `companies_done` | 已完成公司数 |
| `jobs_found` | 已写入的新岗位数 |
| `jobs_new` | 新增岗位数 |
| `error_log` | 每家公司失败、空结果或告警记录 |

`createScanEntryForUser()` 会先检查当前用户是否已有 `pending` 或 `running` 任务。如果有，返回 `{ conflict: true }`，页面提示“扫描已在运行中”。这样可以避免同一用户重复启动多个扫描 worker。

### 5.2 `scan_jobs`

`scan_jobs` 记录扫描出来的具体岗位。

核心字段包括：

| 字段 | 含义 |
|---|---|
| `scan_id` | 来自哪次扫描 |
| `user_id` | 用户隔离字段 |
| `company` | 公司名 |
| `title` | 岗位标题 |
| `url` | 岗位原始链接 |
| `location` | 地点 |
| `department` | 部门 |
| `jd_snippet` | 抓取到的简短描述或薪资摘要 |
| `status` | `new`、`viewed`、`saved`、`evaluating`、`evaluated`、`dismissed` |
| `dedup_key` | URL 的 SHA-256，用于去重 |
| `jd_id` | 保存到 JD 库后的关联 ID |

这套状态让岗位发现系统不是一次性搜索结果，而是一个可操作的机会池。

## 6. Worker 如何执行扫描

真实执行逻辑在 `scripts/scan-worker.mjs`。

这个 worker 支持两种运行方式：

```text
node scripts/scan-worker.mjs
  daemon mode，每 5 秒轮询 pending 任务

node scripts/scan-worker.mjs --once
  单次执行，API 启动时使用
```

执行过程如下：

```text
pending scan_queue
  -> CAS 更新为 running
  -> 读取 portals.yml
  -> 启动 Playwright Chromium
  -> 每家公司选择适配器扫描
  -> 应用岗位关键词过滤
  -> 应用地点过滤
  -> 用 URL hash 去重写入 scan_jobs
  -> 实时更新 companies_done / jobs_found / error_log
  -> 若公司官网无新岗位，补扫猎聘/51job/智联
  -> 更新为 done
```

worker 中有几个关键保护：

| 保护 | 代码位置 | 产品含义 |
|---|---|---|
| 运行中任务恢复 | `recoverStaleScans()` | 超过 10 分钟的 running 任务会标记为 failed |
| 任务认领 | `UPDATE ... WHERE id = ? AND status = 'pending'` | 防止多个 worker 同时处理同一任务 |
| 单家公司超时 | `SCAN_COMPANY_TIMEOUT_MS`，默认 20 秒 | 外部站点慢不能拖死整个任务 |
| 用户取消 | `isCanceled(scanId)` | 用户取消后 worker 停止继续扫描 |
| Debug HTML | `--save-html` | 外部页面结构变化时可保存页面辅助排查 |
| 结果上限 | `maxResults` | 避免一次扫描写入过多噪声机会 |

这说明扫描系统面对的是不稳定外部世界：公司官网结构会变、平台会拦截、页面会超时、岗位标题会非常杂。产品必须把这些不确定性显性化。

## 7. 公司官网与招聘平台补扫

系统的第一优先级是 `portals.yml` 中配置的目标公司官网。

`lib/scan/orchestrator.mjs` 会读取：

- `tracked_companies`
- 每家公司的 `careers_url`
- `ats_type`
- 自定义 `selectors`
- 默认 `title_filter`

如果公司官网没有写入任何新岗位，worker 会触发 `lib/scan/job-board-fallback.mjs`。

补扫平台包括：

| 平台 | 代码函数 | 处理方式 |
|---|---|---|
| 猎聘 | `searchLiepin()` | 根据城市 code 和关键词构造搜索 URL |
| 前程无忧 | `search51Job()` | 根据城市 code 和关键词构造搜索 URL |
| 智联招聘 | `searchZhaopin()` | 根据关键词和城市构造搜索 URL |

补扫代码会检测验证码、安全验证、行为异常等页面内容。如果触发拦截，错误会被转成：

```text
平台触发安全验证，无法自动抓取
```

并写入 `error_log`，而不是假装没有结果。

## 8. 过滤与去重逻辑

岗位过滤逻辑在 `lib/scan/orchestrator.mjs`。

### 8.1 标题过滤

`applyTitleFilter()` 的逻辑是：

```text
如果岗位标题命中任一排除关键词 -> 丢弃
如果设置了正向关键词 -> 必须命中至少一个正向关键词
如果没有正向关键词 -> 保留
```

这和用户体验直接相关。用户在发现页看到的不是所有岗位，而是已经经过方向过滤的岗位。

### 8.2 地点过滤

`applyLocationFilter()` 的逻辑更保守：

```text
如果用户没有设置地点 -> 保留
如果岗位地点为空 -> 保留
如果岗位地点包含用户设置的地点 -> 保留
否则丢弃
```

这里保留地点为空的岗位，是为了避免误杀。很多公司官网的列表页不会展示城市，如果因为地点为空就丢掉，会损失潜在机会。产品上更合理的做法是保留，再由用户查看 JD 时确认。

### 8.3 去重

`makeDedupKey(url)` 使用 SHA-256 对 URL 做 hash。

写入 `scan_jobs` 时使用 `INSERT OR IGNORE`。这意味着同一个岗位链接不会反复生成新记录。用户看到的是新的机会，而不是重复噪声。

## 9. 页面状态如何呈现

发现页轮询 `/api/scan/status?scanId=...`，并把状态展示成用户能理解的进度。

页面主要展示：

- 正在扫描多少家公司。
- 已发现多少岗位。
- 当前结果上限。
- 每家公司是成功、空结果还是错误。
- 本次扫描的岗位关键词、地点、来源说明。
- 取消扫描按钮。

当扫描完成且发现新岗位时，页面提示：

```text
扫描完成 — 发现 N 个职位，M 个为新
```

当没有匹配岗位时，页面会展示当前过滤条件，并提示用户放宽岗位关键词或地点。

当部分公司失败时，页面会列出失败公司和错误原因。这个设计很重要，因为“没有结果”和“抓取失败”不是同一个问题。

## 10. 岗位卡片如何进入 JD 和 Agent 链路

发现到的岗位不会直接变成投递记录。

岗位卡片有几种动作：

| 动作 | 代码函数 | 状态变化 |
|---|---|---|
| 查看 JD | `openJobDetail(job)` | 调用 `/api/scan/jobs/[id]/jd`，岗位可变为 `viewed` |
| 保存到 JD 库 | `saveDiscoveryJD(false)` | 调用 POST `/api/scan/jobs/[id]/jd`，岗位变为 `saved` |
| 让 Agent 评估 | `evaluateWithAgent()` | 先保存 JD，再跳转 `/agent?jdId=...&intent=evaluate`，岗位变为 `evaluating` |
| 跳过 | `dismissJob(job.id)` | PATCH `/api/scan/jobs/[id]` 为 `dismissed` |
| 去 JD 管理 | `goToJDManagement()` | 跳转 `/evaluate/jds` |

保存 JD 时，页面要求正文长度至少 50 字：

```text
JD 正文太短，请先粘贴完整 JD
```

这个限制防止用户把空抓取结果或极短摘要当成完整 JD 保存。

## 11. Agent 工具入口

Agent 侧有 `scan_portals` 工具，对应 `src/lib/agent/tools/action/scan-portals.ts`。

它声明的参数包括：

- `query`
- `company`
- `days`
- `portal`
- `location`
- `salary_min`

当前 handler 实际调用的是 `/api/scan/status` 的 POST，并返回“扫描完成，找到 N 个新职位”。这说明 Agent 入口仍是较薄的一层，真实的扫描主链路在发现页和 worker。文档里不能把它夸成完整的智能扫描 Agent，它更像是未来 Agent 化扫描能力的工具占位。

## 12. 产品边界

岗位发现扫描系统有几个明确边界：

1. 它不自动投递。发现岗位只是进入机会池，用户仍要查看 JD、保存或评估。
2. 它不绕过招聘平台风控。遇到验证码或安全验证时写入错误。
3. 它不承诺所有岗位都能抓取正文。自动抓取失败时允许用户手动粘贴 JD。
4. 它不把 Postgres 迁移中未完成的 worker 当作可用能力。Postgres 模式下 `/api/scan` 明确阻断。
5. 它不因为单家公司失败就失败整个任务。失败公司进入 `error_log`，其他公司继续。
6. 它不把地点为空的岗位直接丢弃，避免由于官网字段缺失造成误杀。

这些边界让系统更像一个真实产品，而不是演示脚本。

## 13. 常见失败模式

| 失败模式 | 系统表现 | 用户能看到什么 |
|---|---|---|
| 没填岗位关键词 | `/api/scan` 返回 `missing_title_keywords` | 提示先填写岗位名称或关键词 |
| 同一用户已有扫描运行 | 返回 `scan_already_running` | 页面恢复已有 scanId 并继续轮询 |
| Postgres 模式启动扫描 | 返回 `scan_worker_postgres_not_ready` | 明确提示 worker 迁移中，暂不启动 |
| 外部平台验证码 | `error_log` 记录 WARN | 页面显示平台触发安全验证 |
| 公司官网无结果 | `error_log` 记录 INFO | 页面显示空结果，不视为严重错误 |
| 单家公司超时 | 记录 timeout after Ns | 当前公司失败，任务继续 |
| 用户取消扫描 | `scan_queue.status = canceled` | 页面停止轮询并提示已取消 |
| JD 抓取失败 | 侧边栏展示错误 | 用户可以手动粘贴 JD 正文 |

这些失败模式可以直接用于判断系统是否真正可用：可用不是“永远不失败”，而是失败时状态清楚、用户知道下一步做什么。

## 14. 测试与验证依据

当前项目中，岗位发现扫描系统的事实主要来自：

- `src/app/discover/page.tsx`
- `src/app/api/scan/route.ts`
- `src/app/api/scan/status/route.ts`
- `src/app/api/scan/history/route.ts`
- `src/app/api/scan/jobs/route.ts`
- `src/app/api/scan/jobs/[id]/route.ts`
- `src/app/api/scan/jobs/[id]/jd/route.ts`
- `src/lib/scan-data.ts`
- `scripts/scan-worker.mjs`
- `lib/scan/orchestrator.mjs`
- `lib/scan/job-board-fallback.mjs`
- `portals.yml`
- `src/lib/agent/tools/action/scan-portals.ts`

验收重点不是页面是否能打开，而是：

- 未登录用户不能创建扫描任务。
- 空关键词不能创建任务。
- 同一用户不能重复启动 pending/running 扫描。
- worker 可以把任务从 pending 推进到 running/done/canceled/failed。
- 结果用 dedup_key 去重。
- 公司失败、空结果、平台验证码能进入 `error_log`。
- 用户可以从岗位卡片保存 JD 或进入 Agent 评估。
- Postgres 模式下不会创建一个无法执行的扫描任务。

## 15. 产品总结

岗位发现扫描系统把“找机会”从手动浏览变成了一个可管理的产品流程。

它的核心不是抓取技术，而是机会数据的状态化：用户输入目标，系统创建任务，外部岗位被过滤和去重，结果进入机会池，用户再决定保存、评估或跳过。只有当这个状态链路成立时，岗位发现才不是一次性搜索，而是纸鸢求职助手全生命周期的第一环。
