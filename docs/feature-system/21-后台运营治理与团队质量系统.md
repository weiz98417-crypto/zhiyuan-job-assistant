# 后台运营治理与团队质量系统的产品构造

后台运营治理系统不是普通求职用户的主流程，而是纸鸢从单人Demo走向多人产品后必须具备的治理层。它负责四件事：账号准入、团队共享素材治理、Agent运行质量复盘、失败样本沉淀。

## 1. 产品定位

纸鸢的前台功能围绕求职者：JD评估、简历优化、投递追踪、面试准备、Offer判断。后台治理围绕产品团队：谁能进入系统，团队素材能否被共享，Agent是否真的按任务契约执行，失败样本能否进入后续回归。

核心页面和API：

| 能力 | 页面/API | 产品作用 |
|---|---|---|
| 团队洞察 | `src/app/admin/insights/page.tsx`、`/api/admin/insights` | 查看活跃用户、待审批、热门方向、评估趋势 |
| 用户管理 | `src/app/admin/users/page.tsx`、`/api/admin/users`、`/api/admin/users/[id]` | 审批账号、调整角色、重置密码、删除用户 |
| 记忆治理 | `src/app/admin/memory/page.tsx`、`/api/admin/memory` | 审核团队共享优秀简历、处理embedding异常、治理候选记忆 |
| 参考简历治理 | `/api/admin/reference-resumes` | 审核、拒绝、禁用、重建参考简历索引 |
| Agent Run台账 | `src/app/admin/agent-runs/page.tsx`、`/api/admin/agent-runs` | 查看任务、步骤、工具、读回和错误证据 |
| Agent Review | `src/app/admin/agent-reviews/page.tsx`、`/api/admin/agent-reviews` | 复盘失败类型，生成OpenSpec建议和eval候选 |
| Eval候选流转 | `/api/admin/agent-eval-candidates/[id]` | 接受、拒绝、提升失败样本 |

这些能力应当作为一套后台治理闭环，而不是拆成互不关联的小功能。用户准入决定谁能用系统；素材治理决定共享材料是否可信；Agent Run决定执行证据是否完整；Review和eval候选决定失败是否可复现。

## 2. 权限边界

所有后台API都要求当前用户是`admin`，并且会校验`token_version`。非admin访问返回403，未登录、token失效或token被撤销返回401。

真实代码边界：

| API | 权限检查 |
|---|---|
| `/api/admin/insights` | `payload.role !== 'admin'`返回403 |
| `/api/admin/users` | `payload.role !== 'admin'`返回403 |
| `/api/admin/users/[id]` | `ensureAdmin()`，写操作前`verifyTokenVersion(payload)` |
| `/api/admin/memory` | `ensureAdmin()`，校验token版本 |
| `/api/admin/reference-resumes` | `ensureAdmin()`，校验token版本 |
| `/api/admin/agent-runs` | admin检查+token版本 |
| `/api/admin/agent-reviews` | `ensureAdmin()` |
| `/api/admin/agent-eval-candidates/[id]` | `ensureAdmin()` |

`token_version`的意义是让角色变更、禁用、重置密码后旧token失效。后台不是单纯隐藏菜单，而是在API层阻断。

## 3. 团队洞察

`src/lib/team-insights.ts`同时适配SQLite和PostgreSQL。它聚合的不是商业BI大屏，而是后台首页级运营信号：

| 指标 | 来源 | 用途 |
|---|---|---|
| active用户数 | `users.status='active'` | 判断团队有效规模 |
| 本周活跃用户 | 最近7天报告关联用户 | 看系统是否被真实使用 |
| 待审批用户 | `users.status='pending'` | 提醒admin处理准入 |
| 近7天个人活跃榜 | `reports` JOIN `users` | 看谁在高频评估JD |
| 近30天热门方向 | `reports.archetype` | 判断求职方向集中在哪些岗位 |
| 近8周评估趋势 | `reports.created_at` | 看评估使用量变化 |

这些指标直接连接后台动作：待审批上升就去用户管理；热门方向变化就检查优秀简历素材是否覆盖；评估趋势异常就去Agent Run和Review查失败。

## 4. 用户准入与账号治理

用户管理页围绕`users`表工作。用户有`role`和`status`两套状态：

| 字段 | 当前取值 |
|---|---|
| `role` | `admin`、`member` |
| `status` | `pending`、`active`、`rejected` |

`/api/admin/users`支持按status过滤列表，返回id、username、displayName、email、role、status、createdAt、lastLoginAt。

`/api/admin/users/[id]`支持三类管理动作：

| 方法 | 动作 | 数据影响 |
|---|---|---|
| `PUT` | 更新status或role | `updateStatus()`、`updateRole()`，角色变更会推进token版本 |
| `POST` | 重置密码 | `hashPassword()`后写入新密码hash |
| `DELETE` | 删除用户 | 禁止删除自己，随后`deleteCascade()`清理用户相关数据 |

这套准入机制对应纸鸢的隐私属性：注册用户不能默认进入团队环境；被拒绝或权限变更后，旧token不能继续访问受保护数据。

## 5. 记忆治理总览

记忆治理页管理两类长期资产：优秀参考简历和抽象记忆/模式。`src/lib/memory/governance.ts`把治理对象拆成几条队列：

| 队列 | 产品含义 |
|---|---|
| `pendingTeamReferences` | 用户申请团队共享的优秀简历，尚未批准 |
| `embeddingHealth` | 参考简历或记忆切片embedding失败、超时pending |
| `candidatePatterns` | 从使用反馈中沉淀出的候选模式，可能升级为active |
| `riskyReferences` | 低质量、高拒绝、未匿名或索引失败的参考素材 |

后台页面还显示健康统计：团队共享数量、pending数量、disabled数量、reference chunks状态、memory items状态、memory chunks状态。

## 6. 参考简历治理动作

`/api/admin/memory`和`/api/admin/reference-resumes`都能处理参考简历，但前者是综合治理页，后者是参考简历专用接口。

核心动作：

| 动作 | 数据变化 |
|---|---|
| `approve_reference` / `approve` | `visibility='team'`、`status='active'`、`anonymized=true`、写入`approved_by/approved_at` |
| `reject_reference` / `reject` | 回到`visibility='private'`、`status='active'`，清空审批信息 |
| `disable_reference` / `disable` | `visibility='disabled'`、`status='disabled'` |
| `restore_reference` | 回到`private/active` |
| `reindex_reference` | 对最新记录执行`reindexReferenceResumeRecord()` |
| `delete_reference` | 优先禁用，必要时删除 |

批准团队共享时会调用`redactReferenceResumeText()`生成`shared_text_redacted`，并重建索引。这个动作的产品边界很清楚：团队共享不是把原始简历直接公开，而是把脱敏后的高质量材料放入可检索范围。

## 7. 记忆条目治理动作

`applyMemoryItemAction()`处理抽象记忆条目：

| 动作 | 下一状态 |
|---|---|
| `approve_memory` | `active` |
| `reject_memory` | `rejected` |
| `disable_memory` | `archived` |
| `restore_memory` | `candidate` |
| `delete_memory` | 删除条目 |

这用于治理从使用反馈或Agent运行中沉淀的模式记忆。候选记忆不能默认进入Agent检索，必须经过状态流转。

## 8. Agent Run台账

Agent Run台账回答“Agent到底干了什么”。`/api/admin/agent-runs`返回run摘要和最近步骤：

| 字段 | 含义 |
|---|---|
| `taskType` | `jd_evaluation`、`resume_edit`、`offer_evaluation`等 |
| `agentId` | general、evaluate、resume、offer、interview、profile等 |
| `status` | planned、running、waiting_user、verifying、repairing、recovered、succeeded、failed、rolled_back、cancelled等 |
| `contract` | 任务契约、目标、成功标准、验证器、路由信息 |
| `recentSteps` | phase、toolName、status、inputSummary、outputSummary、verifier、error |

API会脱敏`data:image`、邮箱、手机号，并压缩长文本。这让后台可以看失败证据，但不能把用户原文隐私暴露在列表里。

## 9. Agent Review与Eval候选

Agent Review把终态run复盘成可治理的失败类型。`/api/admin/agent-reviews`支持按verdict、failureType、taskType和candidateStatus过滤，并返回：

| 字段 | 作用 |
|---|---|
| `summary` | pass/warning/fail数量、失败类型分布、任务类型分布、待处理候选数 |
| `draftSuggestion` | 根据review生成OpenSpec草案建议 |
| `data` | review列表 |
| `candidates` | eval候选列表 |

`/api/admin/agent-eval-candidates/[id]`支持候选状态流转：

| 输入 | 状态 |
|---|---|
| `accept` | `accepted` |
| `reject` | `rejected` |
| `promote` | `promoted` |
| `candidate` | 回到候选 |

这个流程让“用户遇到的问题”变成可跟踪资产：先复盘，后进入候选，经过admin判断后再沉淀为回归验证。

## 10. 后台数据结构

后台治理依赖的数据表主要包括：

| 表 | 产品资产 |
|---|---|
| `users` | 账号、角色、状态、token_version |
| `reports` | 评估趋势、热门方向、活跃度 |
| `reference_resumes` | 优秀简历素材、可见性、质量分、审批状态 |
| `reference_resume_chunks` | 参考简历向量切片、embedding状态 |
| `memory_items` / `memory_chunks` | 长期记忆和向量切片 |
| `memory_status_transitions` | 记忆状态变化证据 |
| `agent_runs` / `agent_run_steps` | Agent执行证据 |
| `agent_run_reviews` | 运行质量复盘 |
| `agent_eval_candidates` | 可转成回归验证的失败样本 |

如果没有后台治理，这些数据会散落在业务功能里，只能靠临时查库定位问题。后台把它们组织成运营动作。

## 11. 风险边界

后台治理必须遵守以下边界：

1. 非admin不能访问`/api/admin/*`。
2. 团队洞察只能展示聚合信息，不能展示用户简历正文。
3. 团队共享优秀简历批准前不能进入团队检索。
4. 批准团队共享时必须脱敏并记录审批人。
5. Agent Run和Review展示要脱敏邮箱、手机号和图片base64。
6. Eval候选接受或提升只改变候选状态，不等于自动修改代码。
7. 删除用户不能删除当前admin自己，防止后台被误关。

## 12. 验收口径

后台运营治理系统的验收看这些事实：

1. 非admin请求后台API返回403。
2. token失效或被撤销时后台API返回401。
3. 用户审批、拒绝、角色变更、重置密码会真实写回数据层。
4. 团队共享优秀简历必须经过approve后才变成`team/active`。
5. approve会生成脱敏文本并触发索引重建。
6. embedding失败和长期pending能出现在治理队列。
7. Agent Run列表能看到任务、工具、状态和读回证据，同时不泄露敏感文本。
8. Agent Review能把失败沉淀为可接受、拒绝或提升的eval候选。
