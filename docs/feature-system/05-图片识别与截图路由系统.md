# 图片识别与截图路由系统的产品构造

纸鸢求职助手的图片识别系统，不是“上传图片后让大模型看一下”的附属能力。它是求职材料进入产品链路的分流层：用户上传一张 JD 长截图、Offer 截图、简历截图或聊天窗口图片后，系统必须先判断它是什么、文字是否可用、用户想做什么，再决定能不能进入 JD 评估、Offer 评估、简历预览、优秀简历保存或普通图片描述。

这个系统的核心产品目标是：把不稳定的图片输入，变成可解释、可路由、可阻断错误成功态的材料入口。

## 1. 产品定位

真实求职场景里，用户很少先把材料整理成标准文本。更常见的是：

- 从招聘 App 截一张超长 JD 图。
- 从聊天窗口转发一张职位缩略图。
- 把 Offer 邮件或 HR 聊天截图直接上传。
- 拍一张简历或参考简历截图。
- 只上传图片，不说明要评估、保存还是提取。

这些输入的风险在于：图片内容、用户文字意图和后续业务动作经常不一致。用户说“评估 Offer”，图片可能是 JD；用户上传简历截图，系统不能直接写入用户简历；用户上传的是聊天窗口里的小图预览，OCR 即使执行也很可能读不到正文。

所以图片识别系统在纸鸢里承担三个职责：

```text
图片材料输入
  -> 图片预处理和候选图生成
  -> 多模态识别图片类型和正文
  -> 对齐用户文字意图
  -> 选择业务路由或要求重传/澄清
  -> 只有路由可信时才允许调用业务工具
```

它不是为了提高“识别率”一个指标，而是为了让后续评估、保存和记忆动作建立在正确材料上。

## 2. 为什么不能直接把图片送进业务工具

如果上传图片后直接调用 JD 评估或 Offer 评估，会出现几类严重问题：

- 错路由：JD 被当成 Offer，Offer 被当成 JD，报告方向完全错。
- 空文本评估：OCR 没读到正文，后续模型仍然生成一份看似完整的报告。
- 缩略图误判：聊天截图里的小图预览被当成原始 JD，导致长时间识别后失败。
- 简历误写入：用户只是上传简历图片让系统看看，产品却把它当作正式保存请求。
- 错误成功提示：工具失败或读不到正文时，Agent 仍用自然语言说“已处理”。

当前实现里，`src/lib/agent/image-intake.ts` 明确规定：图片轮次不能绕过识别。只要还有 `data:image/` 输入但没有 `ImageIntakeResult`，`buildImageIntakeToolCall()` 会返回 `null`，调用方应展示识别中、澄清或重试状态，而不是把原图直接丢进业务工具。

这个设计让图片入口先成为“材料准入层”，再成为“业务执行入口”。

## 3. 系统入口和关键文件

| 层级 | 文件或接口 | 作用 |
|---|---|---|
| 图片识别 API | `src/app/api/agent/image-intake/route.ts` | 接收 `images`、`userText`、`preferredDocumentType`，返回统一识别结果。 |
| 服务端识别 | `src/lib/server-image-intake.ts` | 校验图片数量和大小，调用多模态模型，合并候选图识别结果。 |
| 图片预处理 | `src/lib/server-image-variants.ts` | 生成长图切片、整图规范化、右侧缩略图裁剪等 OCR 候选图。 |
| 路由决策 | `src/lib/agent/image-intake-router.ts` | 根据图片类型、置信度、质量、用户文字意图决定走哪条业务流。 |
| Agent 工具计划 | `src/lib/agent/image-intake.ts` | 将可信图片识别结果转成 `evaluate_jd_full`、`evaluate_offer`、`save_reference_resume` 工具调用。 |
| 旧 JD OCR 兼容接口 | `src/app/api/ocr/jd-screenshot/route.ts` | 兼容早期只服务 JD 截图 OCR 的路径。 |

这几个文件构成了完整的图片入口，而不是某一个 OCR 函数独立完成。

## 4. 图片预处理层

图片预处理的目标不是美化图片，而是为 OCR 找到最可能读到正文的候选图。

`buildOCRImageCandidates()` 会先做基础校验：

- 只接受 `png`、`jpeg/jpg`、`webp` 的 `data:image/*;base64`。
- 原始图片解析失败时返回空数组，识别层会给出“图片预处理失败”。
- 如果 `@napi-rs/canvas` 不可用，降级只使用原图，不让整个流程崩溃。

然后根据图片形态生成候选：

| 图片形态 | 候选策略 | 产品原因 |
|---|---|---|
| 普通图片 | 生成“整图规范化” | 保留完整上下文，适合 Offer、普通 JD、简历截图。 |
| 超长图 | 生成“长图上半段”“长图中段”“长图下半段”“长图正文中下段” | 手机 JD 长截图常常因为整图缩放导致正文过小，分段能提升可读性。 |
| 宽图或聊天窗口图 | 生成右上/右侧裁剪候选 | 用户经常上传聊天窗口截图，真正的材料可能只是右侧一张嵌套小图。 |

当前候选上限是 6 张。每个候选会被缩放到适合 OCR 的尺寸区间：最大边不超过 2400，过小区域会放大到至少 1600 边长。输出统一转成 JPEG，白底，质量 0.9。

这一步直接对应用户曾遇到的长图问题：长图不能只识别整图，否则正文被压缩后很容易出现“上半段、中段、下半段都未识别到正文”的失败。

## 5. 多模态识别层

`inspectDocumentImages()` 是服务端统一识别入口。它有几个硬边界：

- 每次最多处理 5 张图片。
- 单张图片最大 10MB。
- 只接受 `data:image/` 输入。
- 每个候选图调用视觉模型的超时时间是 45 秒。
- 模型必须返回 JSON，不允许返回散文式解释。

识别字段包括：

| 字段 | 含义 |
|---|---|
| `documentType` | `jd`、`offer`、`resume`、`chat_screenshot`、`unknown`。 |
| `confidence` | 0 到 1 的置信度，后续路由会按阈值判断是否继续。 |
| `quality` | `clear`、`thumbnail`、`blurred`、`unreadable`、`unknown`。 |
| `extractedText` | 尽可能完整的图片原文，不是总结。 |
| `structured` | 按类型提取的结构化字段。JD、Offer、Resume、Chat 截图字段不同。 |
| `errors` | 图片级失败原因，例如格式无效、超过 10MB、OCR 超时。 |
| `perImage` | 每张图片的类型、置信度、提取文本长度、候选图标签。 |

JD 的结构化字段包含 `company`、`role`、`location`、`salary`、`skills`、`body`、`isJD`。Offer 的字段更细，包括月薪、年薪月数、奖金、社保、公积金、试用期、通勤、股权、合同期限等。简历字段包括概述、经历、项目、技能、教育和原文。

这里的产品重点是：识别结果必须保留“为什么这么判断”和“哪里失败了”。如果只返回一个文本字符串，后续就无法区分低清晰度、OCR 超时、图片不是材料、用户意图冲突这些不同问题。

## 6. 候选图合并与长图处理

长图识别不是取第一张候选图的结果。`inspectImage()` 会对候选图逐个识别，然后做三件事：

1. 对每个候选图计算分数，分数来自置信度、文本长度、图片质量和是否识别出文档类型。
2. 如果多个长图切片都识别为同一文档类型，且置信度达到 0.72、正文长度不低于 40，会合并这些切片。
3. 合并时保留各段原文，用 `---` 分隔，并合并结构化字段，数组字段会去重。

早停条件也带着产品约束：当候选图清晰、置信度不低于 0.78、正文长度不低于 80 时可以停止；但如果存在长图切片，不能只凭一个切片就结束，需要至少多个成功切片支撑，避免只读到一小段就进入完整评估。

这就是为什么长图失败信息会显示“长图上半段 / 中段 / 下半段”各自识别情况。它不是随机报错，而是在告诉用户到底是整张图质量不够、切片也失败，还是服务超时。

## 7. 用户意图和图片内容的对齐

`routeImageIntake()` 不只看图片，也看用户输入的文字。它会从用户话里识别三类强意图：

- JD 意图：`JD`、`职位`、`岗位`、`招聘`、`任职要求` 等。
- Offer 意图：`offer`、`录用`、`薪资`、`待遇`、`谈判` 等。
- 简历意图：`简历`、`履历`、`CV`、`resume` 等。

路由阈值有两个：

- `LOW_CONFIDENCE_THRESHOLD = 0.62`：低于这个范围通常要求重传。
- `CLEAR_CONFIDENCE_THRESHOLD = 0.8`：低于这个范围且图片质量差时不继续业务流。

最终路由只有六种：

| 路由 | 触发条件 | 用户会看到的产品行为 |
|---|---|---|
| `evaluate_jd` | 图片是 JD，用户意图是 JD 或泛化分析，正文可用 | 进入 JD 评估流程。 |
| `evaluate_offer` | 图片是 Offer，用户意图是 Offer 或泛化分析，正文可用 | 进入 Offer 评估流程。 |
| `resume_preview` | 图片是简历，识别稳定 | 只展示提取预览，等待用户确认，不直接保存。 |
| `describe_image` | 图片是聊天截图或非求职材料 | 只描述图片，不进入求职业务流。 |
| `clarify_intent` | 用户只上传图片，或文字意图和图片内容冲突 | 先问用户要按 JD、Offer 还是简历处理。 |
| `retry_image` | OCR 超时、缩略图、质量差、正文不足 | 给出重传建议或稍后重试建议。 |

这个决策层解决的是“图片是什么”和“用户要做什么”之间的差异。比如用户说“分析 Offer”，但图片识别成 JD，系统会问“这张图看起来更像 JD，不像 Offer。你要我按 JD 评估，还是重新上传 Offer 截图？”

## 8. OCR 超时和图片不清晰要分开处理

当前实现专门区分了两类失败：

```text
OCR 服务超时
  -> route=retry_image
  -> 原因：服务处理超时，不代表图片不清晰
  -> 建议：稍后重试，系统会优先尝试长截图分段识别

图片质量不可用
  -> route=retry_image
  -> 原因：缩略图、模糊、不可读、正文太少
  -> 建议：上传原始截图或粘贴文本
```

这个区别很重要。服务超时是外部能力或长图处理时长问题，用户不一定需要重新截图；图片本身不可读才需要换原图。把两者混成“请换清晰图片”会让用户误以为自己上传错了。

## 9. 缩略图和聊天截图防护

`hasNestedThumbnailSignal()` 会识别聊天窗口、对话截图、小图预览、右上缩略图、读不清、thumbnail、preview 等信号。

当图片被判定为聊天窗口里的嵌套缩略图时，系统不会继续 JD 或 Offer 评估，而是提示用户：

```text
请在 DingTalk/微信/招聘 App 里先点开图片大图，再保存或复制原图上传。
聊天窗口缩略图即使放大，也无法恢复完整 JD/Offer 文字。
```

这是产品边界，不是技术失败。缩略图里缺失的像素无法靠模型补回来，如果继续评估，只会制造幻觉报告。

## 10. 从识别结果到工具调用

识别和路由完成后，`buildImageIntakeToolCall()` 才会生成业务工具计划。

| 工具 | 调用条件 | 关键参数 |
|---|---|---|
| `evaluate_jd_full` | 路由是 `evaluate_jd`，工具白名单允许 | `jd_text` 长度至少 40，或在文本不足时传 images。 |
| `evaluate_offer` | 路由是 `evaluate_offer`，工具白名单允许 | `offerText` 长度至少 10，并补充结构化薪资、公司、岗位等字段。 |
| `save_reference_resume` | 路由是 `resume_preview`，用户明确要保存优秀/参考简历，并且能确认岗位方向 | `resume_text`、`role_category`、`visibility`。 |

有两个非常关键的限制：

- 简历截图默认只能预览，不能自动保存到用户简历。
- 保存优秀简历前必须确认岗位方向，例如 AI 产品经理、AI 运营、AI 售前、数据产品经理。

这保证了图片入口不会把“看看这张图”误解成“写入我的长期数据”。

## 11. 前端状态应该展示什么

图片识别结果不应该只展示“完成”。对用户最有用的是这几个状态：

- 图片类型：JD / Offer / 简历 / 聊天截图 / 未知。
- 置信度：例如 97%。
- 路由：例如 `evaluate_jd`。
- 原因：例如“JD 文本意图与 JD 图片一致，进入评估流程”。
- 每张图或每个切片的识别结果。
- 如果失败，是超时、缩略图、低清晰度、正文不足，还是用户意图冲突。

用户曾遇到“识别卡住 100 多秒，最后长图三段都未识别到正文”的情况。这个场景暴露的是：长图分段、超时、OCR 结果和前端等待状态必须协同设计。否则用户看到的只是长时间等待，无法知道是服务还在跑、图片不可读，还是系统卡死。

## 12. 产品边界

这个系统的边界可以概括为六条：

- 没有识别结果的图片轮次不能绕过识别直接进业务工具。
- 图片和用户文字意图冲突时，必须先澄清。
- 只上传图片但没有说明意图时，JD 和 Offer 也要先确认。
- 简历图片只能先预览，写入类动作必须有明确用户确认。
- OCR 超时不能说成图片不清晰。
- 缩略图不能通过放大补救，必须要求原图。

这些边界决定了它不是一个“识别增强”模块，而是求职产品的材料安全闸门。

## 13. 失败模式

| 失败模式 | 系统处理 | 不能做什么 |
|---|---|---|
| 未上传图片 | `/api/agent/image-intake` 返回 400 `images required` | 不能生成空识别结果。 |
| 图片格式不是 `data:image/` | 过滤后没有有效图片，返回 missing images | 不能把 URL 或普通文本当图片。 |
| 单张图片超过 10MB | 写入 `errors`，跳过该图 | 不能压缩后假装原图已识别。 |
| `@napi-rs/canvas` 不可用 | 降级使用原图 | 不能让预处理依赖导致全流程不可用。 |
| Zhipu API 未配置 | 返回 `ZHIPU_API_KEY not configured` | 不能伪造识别结果。 |
| OCR API 超时 | `retry_image`，提示稍后重试 | 不能要求用户一定换图。 |
| 图片是聊天缩略图 | `retry_image`，要求打开原图上传 | 不能评估缩略图里的不完整文本。 |
| 模型返回非 JSON | 返回“格式解析失败” | 不能从散文里猜结构化字段。 |

## 14. 测试与验证证据

当前项目里，这个系统有多组测试覆盖：

- `src/__tests__/jd-image-routing.test.ts`：验证 JD 图片和用户意图一致时进入评估，冲突时澄清。
- `src/__tests__/server-image-intake.test.ts`：验证服务端识别结果、错误和超时处理。
- `src/__tests__/server-image-variants.test.ts`：验证长图、整图和裁剪候选生成。
- `src/__tests__/image-thumbnail-guard.test.ts`：验证聊天缩略图不会进入业务评估。
- `src/__tests__/evaluate-jd-full-image-priority.test.ts`：验证 JD 评估工具优先使用图片识别出的正文。
- `src/__tests__/agent-image-loop.test.ts`：验证 Agent 图片轮次不会绕过识别直接执行业务工具。

验收这套系统时，不能只看“图片能不能识别出文字”。更重要的是看：

- 路由是否正确。
- 错误路由是否被澄清。
- 低质量图片是否被阻断。
- 工具调用是否只在可信路由后发生。
- 失败时是否没有伪装成功。

## 15. 产品总结

图片识别与截图路由系统解决的是求职产品里的材料入口问题。它让用户可以用最自然的方式上传截图，同时让系统在进入高风险业务动作前完成识别、分流、澄清和阻断。

在纸鸢里，JD 评估、Offer 评估、简历预览、优秀简历保存都依赖这个入口的判断质量。它越稳，后面的评分、简历优化、面试准备和记忆沉淀就越可信。
