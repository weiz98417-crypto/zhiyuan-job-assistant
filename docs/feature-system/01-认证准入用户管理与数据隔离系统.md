# 纸鸢求职助手认证、准入、用户管理与数据隔离系统的产品构造

纸鸢求职助手不是一个单用户本地 demo。它已经有登录、注册、管理员审批、用户状态、角色管理、JWT、cookie 安全、token_version 失效机制，以及按 `user_id` 隔离的业务数据。这个系统的产品目标不是“能登录”，而是保证每个用户只能看到自己的简历、JD、会话、Offer、画像和记忆资产。

因此，`用户认证与审批`、`Admin用户管理`、`登录安全与个人信息隔离` 不应该拆成三篇重复文档。它们是同一条安全链路的三个层面：谁能进入系统、管理员如何控制准入、进入后数据如何隔离。

## 1. 产品定位

求职助手处理的是高敏感个人信息：

- 简历内容。
- 手机号、邮箱、教育背景、工作经历。
- 投递记录。
- JD 评估报告。
- Offer 待遇。
- 面试回答。
- 求职画像和长期偏好。

所以登录系统不是外围能力，而是整个产品的数据边界。它要解决：

- 新用户注册后不能直接访问全部功能，需要审批。
- 管理员可以批准、拒绝、调整角色、重置密码、删除用户。
- 非管理员不能访问 Admin API。
- 用户数据必须按 `user_id` 查询和写入。
- 角色或密码变化后，旧 token 应失效。
- cookie 在 HTTPS 下应启用 Secure，但本地/LAN HTTP 不能因此无法登录。

完整链路是：

```text
注册
  -> pending / active / rejected
  -> 登录
  -> JWT + auth_token cookie
  -> getCurrentUser
  -> user_id scoped repositories
  -> Admin 审批与角色管理
  -> token_version 使旧会话失效
```

## 2. 为什么不能只做一个登录页

如果只做用户名密码登录，会出现几个风险。

第一，任何注册用户都能立即进入系统。对于一个包含简历、Offer、投递数据的产品，这会让内部团队工具、演示环境或多人试用缺少准入控制。

第二，登录成功不等于有权限访问 Admin。所有 Admin API 都必须服务端校验 `role === 'admin'`，不能靠前端隐藏入口。

第三，多用户数据不能只靠前端过滤。简历、会话、投递、Offer、画像、故事库都必须在仓储层按 `user_id` 查询。

第四，角色或密码变更后，旧 JWT 如果继续有效，就会产生权限残留。`token_version` 是解决这个问题的关键。

所以当前系统是“认证 + 审批 + Admin 用户管理 + 数据隔离”的组合。

## 3. 核心代码边界

| 能力 | 项目文件 | 产品含义 |
|---|---|---|
| JWT 签发与验证 | `src/lib/auth.ts` | signToken、verifyToken、getCurrentUser、verifyTokenVersion |
| cookie 安全 | `src/lib/auth-cookie.ts` | 判断是否给 auth cookie 设置 Secure |
| 路由中间件 | `src/middleware.ts` | 控制登录态访问 |
| 注册接口 | `src/app/api/auth/register/route.ts` | 创建用户，决定首个 admin 或 pending member |
| 登录接口 | `src/app/api/auth/login/route.ts` | 校验密码、状态，写入 cookie |
| 当前用户 | `src/app/api/users/me/route.ts` | 返回当前登录用户信息 |
| Admin 用户列表 | `src/app/api/admin/users/route.ts` | 管理员查看用户列表 |
| Admin 用户操作 | `src/app/api/admin/users/[id]/route.ts` | 审批、改角色、重置密码、删除 |
| 数据仓储 | `src/lib/data-repositories.ts` | 业务表按 `user_id` 查询和写入 |

这些文件组成的是产品级安全边界，不是单独页面功能。

## 4. 用户状态

用户表里有 `status` 字段，核心状态包括：

| status | 产品含义 |
|---|---|
| `pending` | 已注册，等待管理员审批 |
| `active` | 已通过，可以登录使用 |
| `rejected` | 已拒绝，不允许登录 |

注册测试里验证了新用户默认是 `pending`、角色是 `member`。登录测试验证了 pending 和 rejected 用户会被阻止登录。

这个机制对应真实产品里的“准入审批”：团队内部工具或多人试用环境不是谁注册都能立即进入。

## 5. 角色体系

当前角色主要有：

| role | 产品权限 |
|---|---|
| `admin` | 访问 Admin 用户管理、运行审计、记忆治理等后台能力 |
| `member` | 使用求职助手个人功能 |

Admin API 的服务端逻辑会通过 `getCurrentUser()` 读取 JWT payload，并检查：

```text
payload.role === 'admin'
```

这意味着角色校验发生在服务端，不依赖前端是否展示按钮。

## 6. 注册链路

注册接口负责：

- 接收用户名、密码、显示名。
- hash 密码。
- 写入 users 表。
- 判断用户状态和角色。

项目事实里有一个重要设计：首个用户可以成为 active admin，后续用户进入 pending 审批流。这个设计适合内部部署，因为系统需要有人能进入后台批准其他用户。

产品上，这解决了“系统刚部署时谁来审批管理员”的问题。

## 7. 登录链路

登录接口会做几步：

```text
查找用户
  -> 校验密码 hash
  -> 检查 status 是否 active
  -> 签发 JWT
  -> 写入 auth_token cookie
```

`auth.ts` 里的 JWT payload 包含：

- `userId`
- `username`
- `role`
- `tokenVersion`

token 不是只标识身份，还携带角色和 token_version，用于后续写操作校验。

## 8. Cookie 安全

`auth-cookie.ts` 根据请求环境判断是否设置 Secure。

测试覆盖了两个边界：

- LAN HTTP 请求不设置 Secure，避免本地或局域网部署时 cookie 无法保存。
- HTTPS 请求设置 Secure，提升线上安全性。

这不是理论安全项，而是项目里真实需要平衡的产品部署问题：本地演示、内网运行、线上 HTTPS 都要能工作。

## 9. token_version

`verifyTokenVersion()` 会在写操作前校验当前 token 的版本是否仍然有效。

当管理员修改用户角色或重置密码时，系统会递增 `token_version`。这样旧 token 即使没有过期，也会因为版本不匹配而失效。

Admin 用户测试验证了：

- 角色提升会递增 `token_version`。
- 角色降级会递增 `token_version`。
- 重置密码会递增 `token_version`。

产品意义是：权限变化必须尽快生效，不能等 JWT 自然过期。

## 10. Admin 用户管理

Admin 用户管理不是独立产品，它是认证准入系统的后台操作面。

管理员可以：

- 查看用户。
- 批准 pending 用户。
- 拒绝 pending 用户。
- 把 member 提升为 admin。
- 把 admin 降级为 member。
- 重置用户密码。
- 删除用户。

当前代码里明确禁止删除自己的账户，但没有看到“唯一 admin 不可降级”的保护，所以文档不能写成系统已经完全防止最后一个管理员被降级。这个边界需要如实记录：项目实现了主要管理动作，但仍有可继续加固点。

## 11. 数据隔离

数据隔离是这套系统最重要的产品价值。

`data-repositories.ts` 里大量仓储方法都按 `userId` 查询，例如：

- `sessions.list(userId)`
- `sessions.get(id, userId)`
- `stories.list(userId)`
- `agentPreferences.list(userId)`
- `offers.list(userId)`
- `offers.get(id, userId)`
- `offerReports.list(userId)`
- `offerReports.get(id, userId)`

测试 `data-isolation.test.ts` 覆盖了多类表：

- `applications`
- `sessions`
- `profiles`
- `stories`
- `cv_data`
- `agent_preferences`
- `session_memory`
- `optimization_preferences`
- `profile_signals`
- `offers`
- `offer_reports`

测试会为两个用户写入数据，再验证 A 用户只能读到 A 的数据，B 用户只能读到 B 的数据。

## 12. 隔离扫描

`check-isolation.test.ts` 不是普通接口测试，它像一条安全扫描规则：私有表查询如果没有 `user_id`、`getCurrentUser` 或 `scopedDb` 这类上下文，就会被认为有风险。

它覆盖的产品原则是：

```text
任何用户私有数据表，读写时都必须有用户上下文。
```

这让“个人信息隔离”从口号变成代码检查。

## 13. 用户链路

完整用户链路如下：

```text
用户注册
  -> 系统创建 pending member
  -> 管理员在 Admin 后台审批
  -> 用户登录
  -> 系统检查账号 active、密码正确
  -> 写入 JWT cookie
  -> 用户访问个人功能
  -> 所有业务数据按 user_id 读写
  -> 管理员变更角色或密码
  -> token_version 递增，旧 token 失效
```

## 14. 失败模式

| 失败点 | 典型表现 | 正确处理 |
|---|---|---|
| 未登录访问 API | 没有 auth_token 或 token 无效 | 返回 401 |
| pending 用户登录 | 账号未审批 | 阻止登录 |
| rejected 用户登录 | 账号被拒绝 | 阻止登录 |
| 非管理员访问 Admin | role 不是 admin | 返回 403 |
| token_version 失效 | 角色或密码已变更 | 写操作前拒绝 |
| 查询未带 user_id | 可能读到他人数据 | 测试和仓储层阻断 |
| HTTPS cookie 未 Secure | 线上 cookie 风险 | HTTPS 下启用 Secure |
| LAN HTTP cookie 误 Secure | 本地无法登录 | HTTP 下不强制 Secure |

## 15. 测试与证据

相关测试包括：

- `src/__tests__/auth.test.ts`：注册、登录、密码校验、pending/rejected 阻断、token_version。
- `src/__tests__/auth-cookie.test.ts`：HTTP/HTTPS 下 cookie Secure 判断。
- `src/__tests__/admin-users.test.ts`：审批、拒绝、角色变更、重置密码、删除用户。
- `src/__tests__/data-isolation.test.ts`：业务数据按用户隔离。
- `src/__tests__/check-isolation.test.ts`：扫描私有表访问是否具备用户上下文。

这些测试共同证明：纸鸢的登录系统不是孤立入口，而是覆盖准入、权限和数据隔离的安全底座。

## 16. 产品总结

这套系统可以分成五层：

```text
身份层：用户名、密码、JWT
准入层：pending / active / rejected
权限层：admin / member
会话层：auth_token cookie、token_version
隔离层：user_id scoped repositories
```

它的产品价值是保护用户的求职隐私和系统后台边界。对纸鸢这种处理简历、Offer、面试和画像的产品来说，认证系统不是附属功能，而是所有个人数据可信运行的前提。
