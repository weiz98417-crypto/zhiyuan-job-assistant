# 优秀简历记忆系统的产品构造

纸鸢求职助手的优秀简历记忆系统，不是一个“范文收藏夹”。它把高质量简历转成两类长期资产：一类是可检索的参考片段，用于简历优化时提供同岗位、同板块的表达参照；另一类是抽象写作模式，用于迁移优秀简历的结构、指标意识和故事组织方式。

这个系统的产品目标是：让用户和团队沉淀优秀简历的判断力，而不是复制优秀简历的原文。

## 1. 产品定位

用户在改简历时，常见痛点不是“不知道要不要改”，而是不知道“好简历具体好在哪里”：

- 项目经历应该展开到什么颗粒度。
- 产品经理经历应该写需求、决策、协作还是结果。
- AI 产品经历应该怎么体现 Agent、RAG、评测和闭环。
- 数据产品经历应该怎么从看板写到指标体系和决策价值。
- 技能清单是堆工具名，还是按岗位能力簇组织。

优秀简历记忆系统让这些判断不只停留在一次对话里，而是沉淀成后续优化可以检索和复用的材料。

```text
用户上传 / 粘贴 / 图片识别参考简历
  -> 确认岗位方向和可见性
  -> 解析成标准 sections
  -> 质量评分、脱敏、去重
  -> 保存 reference_resumes
  -> PostgreSQL/pgvector 索引片段
  -> 抽取优秀写作模式
  -> 简历优化 Judge 检索并注入
  -> 用户反馈反哺排序
```

## 2. 为什么不能只存原文

如果系统只是保存一份参考简历原文，会有三个问题：

- 版权和真实性风险：用户可能照抄别人经历。
- 检索颗粒度太粗：优化技能区时不应该读完整简历所有内容。
- 复用能力弱：真正有价值的是“写法”和“结构”，不是某个候选人的事实。

因此当前项目把优秀简历拆成三层：

| 层级 | 保存内容 | 用途 |
|---|---|---|
| 原始参考简历 | 标准 sections、原文、标签、岗位方向、质量分 | 作为参考资产和追溯来源。 |
| 向量片段 | 按 section 切分后的 chunk、embedding、质量分、可见性 | 优化时按角色、板块和相似度检索。 |
| 抽象模式记忆 | “AI 产品经历要写成业务目标 -> 技术链路 -> 评测/反馈 -> 产品结果”这类模式 | 给 Judge 引擎提供可迁移写作规律。 |

这就是它和普通文件库的区别。

## 3. 系统入口和关键文件

| 层级 | 文件或接口 | 作用 |
|---|---|---|
| 导入参考简历 | `src/app/api/cv/import-reference/route.ts` | 支持文本、文件、图片导入，解析 sections、保存记录、索引、抽取模式。 |
| Agent 保存工具 | `src/lib/agent/tools/action/save-reference-resume.ts` | 将对话或图片中识别出的优秀简历保存到参考库，并做读回校验。 |
| 保存会话状态 | `src/lib/agent/reference-resume-save-flow.ts` | 判断是否保存优秀简历、缺少岗位方向时追问、处理确认/取消。 |
| 向量索引与检索 | `src/lib/reference-resume-vector.ts` | 质量评分、脱敏、chunk、pgvector 索引、检索排序、usage 记录。 |
| 抽象模式记忆 | `src/lib/excellent-resume-patterns.ts` | 从优秀简历中抽取可迁移写作模式，保存到 `memory_items`。 |
| Judge 注入 | `src/lib/judge-engine.ts` | 把参考片段和抽象模式注入简历优化 prompt。 |

## 4. 导入来源和解析方式

`/api/cv/import-reference` 支持两类请求。

第一类是 JSON 文本导入：

- `text`
- `name`
- `roleCategory`
- `visibility`
- `tags`
- `notes`
- `saveAsExcellent`

第二类是 `multipart/form-data` 文件导入。当前支持：

| 格式 | 解析方式 |
|---|---|
| `.txt` / `.md` | 直接解码文本。 |
| `.docx` | 使用 `mammoth.extractRawText()`，如果乱码则尝试 Qwen-Long。 |
| `.doc` | 通过 Qwen-Long 文件解析。 |
| `.pdf` | 通过 Qwen-Long 文件解析。 |
| `.png` / `.jpg` / `.jpeg` / `.webp` | 通过 Zhipu Vision OCR 提取简历文本。 |

文件大小上限是 10MB。不支持的格式会返回明确错误，而不是尝试让模型乱读。

解析成正文后，系统会调用 DeepSeek 把简历拆成标准 sections：

- `summary`，中文标题“个人概述”。
- `experience`，中文标题“工作经历”。
- `projects`，中文标题“项目经历”。
- `skills`，中文标题“技能”。
- `education`，中文标题“教育背景”。

解析 prompt 特别要求：工作经历中嵌套的项目描述要抽到 `projects`，不能丢段落，量化数据、专业术语和项目名必须原样保留。

## 5. 保存前的意图和岗位方向确认

Agent 场景下，不是所有简历图片或文本都会保存成优秀简历。`reference-resume-save-flow.ts` 要同时满足：

- 用户明确表达保存优秀 / 参考 / 标杆 / 样例简历的意图。
- 提取出的内容看起来像一份完整简历。
- 有明确岗位方向，或者能从内容里推断出建议方向并等待用户确认。

支持的岗位方向会归一化为：

- `ai_product_manager`
- `ai_operations`
- `ai_presales`
- `data_product_manager`
- `product_manager`
- `general`

如果用户没有明确岗位方向，系统会问：

```text
这份优秀简历要保存到哪个岗位方向？
可选方向：AI产品经理 / AI运营 / AI售前 / 数据产品经理 / 产品经理。
```

这个追问不是形式要求。岗位方向会影响后续检索过滤和 Judge 引擎注入，缺少方向会让参考记忆变得不准。

## 6. 可见性和团队共享

参考简历有四种可见性：

- `private`：仅本人可用。
- `team_pending`：申请团队共享，但未审核。
- `team`：团队可用。
- `disabled`：禁用。

导入时，如果用户请求团队共享：

- 管理员且质量分不低于 0.45，可以直接进入 `team`。
- 非管理员或质量分不足，进入 `team_pending`。

检索时，用户能看到自己的 `private`、`team_pending`、`team`，以及全局 `team`。也就是说，`team_pending` 不会扩散给其他人，但保存者自己仍可使用。

这让团队共享有审核缓冲，不会把低质量或未脱敏材料直接放进公共记忆。

## 7. 脱敏和匿名化

当参考简历不是私有可见性时，系统会对共享文本做脱敏。

`redactReferenceResumeText()` 会替换：

- 邮箱：`[REDACTED_EMAIL]`
- 手机号：`[REDACTED_PHONE]`
- 身份证号：`[REDACTED_ID]`
- 微信 / WeChat / QQ：`[REDACTED_CONTACT]`
- 现居 / 地址 / 住址：`[REDACTED_ADDRESS]`

保存记录里会标记：

- `anonymized`
- `shared_text_redacted`

私有参考简历可以保留原文用于个人检索；团队共享必须使用脱敏文本做索引和模式抽取。

## 8. 质量评分

`scoreReferenceResumeQuality()` 会给参考简历打 0 到 1 的质量分。规则不是模型自由判断，而是可解释的加分项：

| 加分项 | 产品含义 |
|---|---|
| 文本长度超过 800 | 内容比较完整。 |
| 文本长度超过 1800 | 内容更充分。 |
| sections 数量不少于 4 | 结构完整。 |
| 包含工作 / 实习经历 | 有职业经历证明。 |
| 包含项目经历 | 有可迁移项目表达。 |
| 包含技能区 | 能服务技能和关键词优化。 |
| 包含数字、提升、增长、转化、准确率等信号 | 有结果意识和量化表达。 |
| 看起来像完整简历 | 不是普通段落或 JD。 |

这个质量分会进入向量检索排序，也会影响团队共享的审核状态。

## 9. 去重和保存记录

保存前系统会把标准 sections 重新拼成 raw text，然后计算 `sourceHash`。如果同一个用户已经保存过相同来源，会直接返回已有记录，并标记：

```json
{
  "duplicate": true,
  "indexing": {
    "status": "skipped",
    "reason": "Duplicate source hash"
  }
}
```

这避免同一份优秀简历反复进入向量库，污染检索排序和模式抽取。

保存主记录包含：

- `name`
- `source`
- `sections_json`
- `raw_text`
- `tags`
- `notes`
- `role_category`
- `visibility`
- `status`
- `quality_score`
- `anonymized`
- `shared_text_redacted`
- `source_hash`
- `metadata_json`
- `approved_by`
- `approved_at`

## 10. 向量索引

向量索引只在 PostgreSQL 配置可用时执行。如果当前数据库不是 Postgres，或没有配置 pgvector，索引结果会是：

```text
status=skipped
reason=PostgreSQL is not configured
```

这不是失败，而是本地 SQLite 模式下的明确边界。

索引流程：

```text
reference_resumes
  -> parse sections
  -> 每个 section 按最大约 1200 字切 chunk
  -> chunk 文本包含参考简历名称和 section 标题
  -> embedding
  -> 写入 reference_resume_chunks
```

每个 chunk 记录：

- `reference_resume_id`
- `owner_user_id`
- `visibility`
- `status`
- `role_category`
- `section_type`
- `chunk_index`
- `chunk_text`
- `content_hash`
- `embedding_model`
- `embedding_dimension`
- `embedding`
- `embedding_status`
- `quality_score`
- `metadata_json`

索引前会删除该 reference resume 的旧 chunks，保证重建索引不会产生重复片段。

## 11. 检索排序

`retrieveReferenceResumeSnippets()` 根据当前优化任务构造 query：

- 用户意图。
- 角色方向。
- JD 岗位和公司。
- JD 关键词。
- 当前 section 内容。

检索过滤条件包括：

- chunk 必须已 embedded。
- chunk 状态必须 active。
- 用户能访问该可见性。
- 如果有 roleCategory，优先同岗位、general 或空角色。
- 如果有 sectionType，优先同板块。

最终分数由四部分组成：

```text
score =
  similarity * 0.68
  + quality * 0.18
  + roleScore * 0.10
  + feedbackTrustScore * 0.04
```

其中 feedbackTrustScore 来自用户后续接受或拒绝该参考片段的反馈。这个设计让参考简历不是一次性静态库，而是会随使用效果调整排序。

## 12. 抽象模式记忆

优秀简历系统还会提取“写作模式”，保存到 `memory_items`，类型是：

```text
excellent_resume_pattern
```

当前规则能识别的模式包括：

| pattern key | 抽象模式 |
|---|---|
| `ai_product_technical_loop` | AI 产品经历写成业务目标、技术链路、评测反馈、产品结果闭环。 |
| `metric_result_framing` | 每段经历用可验证指标收束结果。 |
| `zero_to_one_delivery` | 从 0 到 1 或上线落地经历要写出阶段推进。 |
| `cross_functional_delivery` | 跨团队项目要写清协作对象、交付物和推进机制。 |
| `data_product_framing` | 数据产品经历要把数据源、指标体系、分析场景和决策价值连起来。 |
| `project_story_structure` | 项目经历用背景/目标、关键动作、难点取舍、结果指标组织。 |
| `summary_positioning` | 个人概述用目标岗位定位开头，压缩呈现能力栈和成果证据。 |
| `skills_grouping` | 技能区按岗位能力簇分组。 |

模式抽取有质量门：

- 模式文本不能太短。
- 证据 quote 不能太短。
- 不能是“业务”“技术”“能力”等泛词。
- 模式文本必须有基本句式标点。

保存时会同时写入 memory evidence，保留来自哪份参考简历、哪段 quote 和抽取方法。

## 13. 模式记忆如何进入简历优化

`retrieveExcellentResumePatternMemory()` 只返回满足条件的模式：

- PostgreSQL 可用。
- `memory_type = excellent_resume_pattern`。
- `status = active`。
- 属于当前用户或团队可见。
- roleCategory 匹配、general 或空角色。
- `confidence >= 0.65`。
- `importance >= 0.55`。

返回后按 importance、confidence、feedbackTrustScore 综合排序，最多注入 6 条。

Judge 引擎收到这些模式后，会明确告诉模型：

- 这些是抽象写作模式，不是当前用户事实。
- 只能改善结构、具体性、指标框架和故事逻辑。
- 不能复制来源措辞，不能编造事实。
- 如果和当前 CV 或 JD 冲突，以用户 CV 和 JD 为准。

## 14. 保存工具的读回校验

Agent 工具 `save_reference_resume` 保存成功后，不会只看接口返回。它会再读：

```text
/api/cv/references/{referenceId}
```

读回校验包括：

- 保存接口必须返回 reference resume ID。
- 读回 ID 必须和保存 ID 一致。
- 读回 roleCategory 必须和请求 roleCategory 一致。

只有这些通过，工具才返回成功，并在摘要里展示：

- 简历名称。
- 岗位方向。
- 可见性。
- 质量分。
- 索引状态。
- 模式记忆状态。

如果读回失败，工具会返回“保存优秀简历后读回校验失败”，并阻止成功提示。

## 15. 产品边界

| 边界 | 原因 |
|---|---|
| 未确认岗位方向不能保存优秀简历 | 后续检索和排序依赖 roleCategory。 |
| 内容不像完整简历不能保存为优秀简历 | 防止把 JD、聊天或短段落塞进参考库。 |
| 团队共享必须脱敏 | 避免个人隐私进入公共记忆。 |
| SQLite 模式跳过向量索引 | pgvector 能力只在 Postgres 下存在。 |
| 参考简历不能原文复制进用户简历 | 只迁移结构和表达模式，保护真实性。 |
| team_pending 不扩散给其他用户 | 共享前需要审核。 |
| 重复来源跳过索引 | 防止相同材料污染检索。 |

## 16. 测试与验证证据

当前项目里相关验证包括：

- `src/__tests__/reference-resume-save-flow.test.ts`：验证保存优秀简历的意图识别、岗位方向追问、确认和取消。
- `src/__tests__/reference-resume-vector.test.ts`：验证质量评分、脱敏、索引、检索查询和排序。
- `src/__tests__/excellent-resume-patterns.test.ts`：验证抽象模式提取和质量门。
- `src/__tests__/excellent-resume-memory-evolution.eval.test.ts`：验证优秀简历记忆在优化链路里的演进。
- `src/lib/agent/tools/action/save-reference-resume.ts`：验证保存后的读回动作和成功提示边界。

验收这个系统时，要看：

- 保存前是否确认岗位方向。
- 团队共享是否进入正确可见性。
- 质量分和 tags 是否符合内容。
- PostgreSQL 环境下是否生成 chunks 和模式记忆。
- SQLite 环境下是否明确 skipped，而不是假装 indexed。
- Judge 引擎是否只使用参考模式，不复制参考原文。

## 17. 产品总结

优秀简历记忆系统把“看一份好简历”变成了“沉淀一套可复用写法”。它用参考简历主记录保留来源，用 pgvector 片段支持精准检索，用抽象模式把优秀结构迁移到用户自己的经历里，用反馈机制持续调整排序。

它真正服务的不是收藏，而是让纸鸢在每次简历优化时更懂什么叫“好”，同时不牺牲用户经历的真实性。
