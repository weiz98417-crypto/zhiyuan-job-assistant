# 纸鸢求职助手简历工作台与版本管理系统的产品构造

纸鸢求职助手里的简历工作台，不是一个“粘贴简历文本”的输入框，也不是单纯的富文本编辑器。它是用户求职材料的资产中心：用户把简历导入、拆分、编辑、保存、对比、分析、导出之后，后续 JD 评估、简历优化、面试准备、求职画像、Agent 工具调用都会读取这份简历资产。

因此，简历版本对比不应该单独写成一个独立系统。它是简历工作台里的审阅能力，用来回答“这次修改到底动了哪里、右侧版本是否可以设为当前版本”。完整的产品边界应该是：简历内容如何进入系统、如何被拆成结构化板块、如何形成版本、如何同步到服务端、如何被 Agent 安全读取和修改、如何导出成可投递材料。

## 1. 产品定位

用户在求职过程中会反复修改简历：同一份经历要面向 AI 产品、海外社交、增长、数据产品等不同岗位表达不同重点。纸鸢的简历工作台承接的是这个反复变化的材料资产，而不是一次性的文本。

它要解决的核心问题包括：

- 用户可以从 PDF、图片、Word、纯文本等材料中导入简历。
- 简历进入系统后要拆成固定板块，便于 JD 评估和 Agent 调用。
- 用户可以手动编辑，也可以让 AI 生成优化版本。
- 每次形成新版本后，用户能看到与旧版本的差异。
- 简历既要保存在浏览器本地，也要同步到当前登录用户的服务端数据。
- PDF 导出必须能生成真实文件，而不是只显示“导出成功”。
- Agent 不能在用户不确认的情况下直接覆盖正式简历。

这使得简历工作台成为纸鸢求职助手的材料底座：

```text
简历导入 / 手动编辑
  -> 结构化板块
  -> 本地版本与服务端同步
  -> AI 分析 / 优化 / 提案
  -> 版本对比
  -> PDF 导出
  -> JD 评估、面试、画像等模块复用
```

## 2. 为什么不能只做一个简历输入框

如果简历只是一个普通输入框，产品会很快遇到几个真实问题。

第一，简历不是临时上下文。用户可能今天评估一个 JD，明天准备面试，后天再定制另一份简历。如果简历只存在一次对话里，用户每次都要重新粘贴，Agent 也无法知道当前材料是否是最新版本。

第二，简历不是一整块文本就够了。JD 评估需要读取整体经历，简历优化需要定位到某个板块，面试准备需要抽取项目故事，PDF 导出需要把个人概述、工作经历、项目经验、教育背景、技能放进对应版式。没有结构化板块，这些动作都会变得不稳定。

第三，AI 修改简历是高风险动作。简历包含用户真实履历，不能因为模型说“已保存”就直接覆盖。系统必须让修改先变成提案或新版本，再由用户确认。

第四，用户需要审阅变化。简历优化不是只看“新版本更好不好”，还要知道哪些量化表达被新增、哪些内容被删掉、有没有误改真实经历。

所以纸鸢把简历工作台做成“资产管理 + 版本管理 + 分析导出 + 安全写入”的组合，而不是一个简单输入框。

## 3. 页面入口与代码边界

当前简历工作台的主入口是 `/cv` 页面，对应文件是 `src/app/cv/page.tsx`。

围绕这个页面，系统连接了以下项目事实：

| 能力 | 项目文件或接口 | 产品含义 |
|---|---|---|
| 简历主页面 | `src/app/cv/page.tsx` | 承载导入、编辑、分析、版本、导出等主操作 |
| 本地版本存储 | `src/lib/cv-storage.ts` | 维护 `activeVersion`、`versions`、默认板块和本地缓存 |
| 服务端简历数据 | `src/app/api/cv/data/route.ts` | 当前登录用户的 `cv_data` 读写接口 |
| 简历导入 | `src/app/api/cv/import/route.ts` | PDF、图片、Word、文本进入结构化板块 |
| 简历分析 | `src/app/api/cv/analyze/route.ts` | 根据简历、JD、岗位和 archetype 生成匹配反馈 |
| PDF 导出 | `src/app/api/generate-cv-pdf/route.ts` | 用 Playwright 渲染简历 PDF |
| 版本对比 | `src/app/cv/version-diff.tsx`、`src/lib/version-diff.ts` | 按板块展示两个版本的增删改 |
| 简历优化入口 | `src/app/cv/optimize-panel.tsx` | 针对单个板块生成多种优化结果 |
| 写入安全 | `src/lib/agent/resume-save-guard.ts`、`src/lib/agent/resume-edit-proposals.ts` | 防止 Agent 未确认覆盖简历 |

这些文件说明了一个事实：简历工作台不是单页面 UI，它是一个材料生命周期系统。页面负责承载动作，`cv-storage.ts` 负责版本状态，服务端 API 负责按用户保存，导入和导出接口负责文件边界，Agent 写入安全层负责保护正式简历。

## 4. 简历数据模型

`src/lib/cv-storage.ts` 定义了当前简历数据的核心形态。它不是单个字符串，而是：

```text
CVData
  activeVersion: 当前生效版本 id
  versions:
    v1 / v2 / v3 ...
      id
      label
      createdAt
      source
      sections
```

每个版本里都有一组 `sections`，默认包括：

| section id | 中文含义 | 产品用途 |
|---|---|---|
| `summary` | 个人概述 | 职业定位、求职方向、个人亮点 |
| `experience` | 工作经历 | 公司、岗位、职责、业务成果 |
| `projects` | 项目经验 | 可复用的项目案例和结果证明 |
| `education` | 教育背景 | 学历、学校、专业等信息 |
| `skills` | 技能 | 工具、方法、平台、语言、领域能力 |

这个结构对产品很重要：纸鸢不是让 Agent 自由理解一份长文本，而是先把简历变成可定位、可修改、可对比、可导出的材料结构。

## 5. 本地存储与服务端同步

简历数据有两层保存。

第一层是浏览器本地 `localStorage`，key 是 `zhiyuan-cv`。这让页面刷新后仍能保留当前简历状态，也能支持一些即时编辑体验。

第二层是服务端 `/api/cv/data`。这个接口通过 `getCurrentUser()` 拿到当前登录用户，再用 `getDataRepositories().cv` 读取或写入该用户的 `cv_data`。

当前读写逻辑是：

```text
GET /api/cv/data
  -> 获取当前用户
  -> 查询该用户 cv_data
  -> 返回 data_json

PUT /api/cv/data
  -> 获取当前用户
  -> 接收 CVData
  -> upsert 到当前用户的 cv_data
```

`loadCVDataFromServer()` 会把服务端数据拉回本地缓存；`saveCVData()` 会先写本地，再 fire-and-forget 同步服务端。

这说明当前简历工作台既有本地优先体验，也有登录用户隔离。它不是完整的实时协同编辑系统，服务端同步失败时本地仍可能先成功，所以文档不能把它写成“强一致简历云文档”。

## 6. 旧数据迁移

`cv-storage.ts` 里保留了旧格式迁移逻辑。早期简历数据可能只是 `CVSection[]` 数组，系统会把它迁移成：

```text
activeVersion = "v1"
versions.v1 = {
  label: "初始版本",
  source: "manual",
  sections: legacySections
}
```

这个设计说明项目不是一开始就有完整版本体系，而是在已有简历编辑能力上逐步演进出版本管理。版本能力不是凭空设计出来的，而是当 AI 改写和多岗位定制出现后，才变成必要能力。

## 7. 简历导入链路

`/api/cv/import` 支持多种材料入口。

| 输入类型 | 处理方式 | 关键事实 |
|---|---|---|
| PDF / `.doc` | DashScope Qwen-Long 文件通道 | 用 `===个人信息===` 等分隔标记抽取栏目 |
| 图片 | 智谱视觉模型 | 读取图片后直接归类到 JSON |
| `.docx` | `mammoth` 抽取文本，再交给 DeepSeek 归类 | 适合 Word 简历 |
| `.txt` / `.md` | 文本直接交给 DeepSeek 归类 | 适合粘贴式材料 |
| JSON 文本请求 | `text` 字段进入 DeepSeek | 支持纯文本导入 |

导入输出统一成：

```text
summary
experience
projects
skills
education
```

系统还做了两类后处理：

- 如果工作经历里混入“项目名称：”块，会尝试拆出项目经验。
- 如果个人信息或概述里混入教育背景，会把学校、学历、专业等内容挪到教育背景。

这不是泛泛的文件上传功能，而是为求职产品定制的简历结构化入口。

## 8. 简历分析链路

`/api/cv/analyze` 接收：

- `sections`
- `jdText`
- `keywords`
- `role`
- `archetype`

它会把简历各板块拼成全文，并读取 `modes/zh/jianzhi.md` 里的 B 板块简历匹配规则，再调用 DeepSeek 生成结构化 JSON。

返回结果包括：

- `overallScore`
- `atsScore`
- `matchedKeywords`
- `missingKeywords`
- `strengths`
- `weaknesses`
- `suggestions`
- `sectionFeedback`

产品上，这个分析不是给用户一个漂亮分数，而是告诉用户：当前简历和目标 JD 的差距在哪里，哪个板块强，哪个板块需要补证据。

## 9. 版本创建与切换

版本管理由 `cv-storage.ts` 承担。

| 操作 | 代码行为 | 产品含义 |
|---|---|---|
| 创建版本 | 复制当前 active version 的 sections，生成下一个 `vN` | 用户可以基于当前简历另开一个岗位版本 |
| 删除版本 | 至少保留一个版本；删除当前版本后切到剩余版本 | 避免用户删空全部简历 |
| 切换版本 | 检查目标版本存在后设置 `activeVersion` | 当前简历上下文随版本改变 |
| 重命名版本 | 修改版本 label | 用岗位、公司或用途标记版本 |
| 获取全文 | 当前 active version 的 sections 拼接 | Agent、分析、面试等模块读取当前材料 |

这就是为什么“版本对比”不应单独成为一个系统。它依赖这些版本状态，只是工作台审阅版本差异的一个视图。

## 10. 版本对比视图

`src/app/cv/version-diff.tsx` 接收两个版本：

```text
oldVersion
newVersion
versionIds
versionLabels
```

它调用 `diffVersions(oldVersion.sections, newVersion.sections)`，按板块计算差异，并展示：

- 修改了多少个板块。
- 新增了多少行。
- 删除了多少行。
- 量化表述增加或减少了多少。
- 左侧旧版本和右侧新版本的逐行差异。
- 用户可以把右侧版本设为当前版本。

这个视图的产品价值是让用户在接受 AI 改写或多岗位版本前能看见证据。尤其是量化表述统计，它对应求职简历里非常关键的“成果是否变得可证明”。

## 11. PDF 导出链路

`/api/generate-cv-pdf` 用 Playwright 打开 HTML 简历版式并生成 PDF。

它会读取：

- `sections`
- `profile`
- `targetCompany`
- `template`

再把板块填进 HTML：

- `summary`
- `skills`
- `experience`
- `projects`
- `education`

导出前还会做 ATS 文本归一化，避免某些特殊字符影响简历可读性。导出文件名包含目标公司和日期，例如：

```text
cv-{company}-{YYYY-MM-DD}.pdf
```

这说明 PDF 导出是正式投递链路的一部分，不是附属按钮。导出失败、空文件、hash 不匹配都不能被产品说成成功。

## 12. Agent 写入边界

简历工作台最敏感的边界是 Agent 写入。

项目里有两层保护。

第一层是 `resume-save-guard.ts`。它会判断用户是否真的表达了保存意图，例如“应用这个”“保存到技能板块”“写入简历”。同时它会过滤参考简历、优秀简历、失败提示、修改说明表格等不应该写入正式简历的内容。

第二层是 `resume-edit-proposals.ts`。它把修改变成提案：

```text
pending proposal
  -> 用户确认
  -> apply
  -> read-back hash
  -> applied / stale / rolled_back / discarded
```

提案里包含：

- `section_id`
- `base_version`
- `base_hash`
- `original_content`
- `proposed_content`
- `proposed_hash`
- `risk_flags_json`
- `status`

系统应用提案前会检查当前 active version、base hash 和原始板块内容是否仍匹配。如果用户中途改过简历，提案会变成冲突，而不是强行覆盖。

## 13. 用户链路

完整用户链路可以这样理解：

```text
用户进入 /cv
  -> 系统从服务端和本地恢复简历
  -> 用户导入或编辑简历
  -> 系统保存为当前 active version
  -> 用户为不同岗位创建版本
  -> 用户通过分析或 Agent 获得优化建议
  -> 修改先进入提案或新版本
  -> 用户在版本对比里审阅差异
  -> 用户把确认后的版本设为当前
  -> 系统导出 PDF 或供 JD/面试/画像模块读取
```

这条链路的核心不是“编辑简历”，而是“把简历变成可复用、可审阅、可安全修改的求职资产”。

## 14. 失败模式

简历工作台常见失败不能只显示一个泛化错误。

| 失败点 | 典型表现 | 正确处理 |
|---|---|---|
| 文件格式不支持 | 上传非支持格式 | 明确提示支持 PDF、图片、doc、docx、txt、md |
| 文件过大 | 超过 10MB | 阻止导入并提示限制 |
| 视觉识别失败 | 图片简历没有抽出正文 | 要求上传更清晰材料或改用文本 |
| LLM 返回无法解析 | JSON 不完整或无栏目 | 返回导入失败，不覆盖当前简历 |
| 服务端未登录 | `/api/cv/data` 返回 401 | 提示未登录，本地数据仍可保留 |
| 版本切换有未保存内容 | 用户可能丢失编辑 | 弹出确认，不静默切换 |
| 提案 base hash 不匹配 | 简历在提案生成后被改动 | 标记 stale，阻止覆盖 |
| PDF 生成失败 | Playwright 或版式渲染失败 | 不提示导出成功 |

## 15. 测试与证据

当前项目里与该系统相关的测试和证据包括：

- `src/__tests__/cv-optimize-postgres-boundary.test.ts`：验证简历优化和数据仓储边界，防止把 Postgres/SQLite 切换写混。
- `src/__tests__/file-export-verified-write.test.ts`：验证文件导出必须返回 size、sha256、read-back 证据。
- `src/__tests__/resume-save-guard.test.ts`：验证 Agent 不能把失败提示、修改说明或未确认内容当作正式简历保存。
- `src/__tests__/resume-edit-proposals-route.test.ts`：验证简历修改提案的创建、应用、废弃和回滚。

这些测试背后的产品目标是一致的：简历是用户的核心求职资产，系统可以帮忙生成和分析，但不能伪造保存、不能静默覆盖、不能把临时对话当成正式履历。

## 16. 产品总结

纸鸢的简历工作台实际由四层组成：

```text
材料入口层：导入 PDF、图片、Word、文本
结构化资产层：summary / experience / projects / education / skills
版本审阅层：activeVersion、versions、diff、右侧设为当前
安全写入层：保存意图识别、提案、hash、read-back、回滚
```

它的产品价值不是让用户“把简历放进系统”，而是让简历在整个求职周期里成为可信材料：能被分析、能被定制、能被对比、能被导出，也能在 Agent 参与时被安全保护。
